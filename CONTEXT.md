# Glossary

This file defines the domain terms the DocChat design documents use: the product's own concepts (projects, indexes, documents, chunks, sessions, turns, memory), the parts of the chat and ingestion pipelines, the stores and their states, the identities and environments, and the delivery and operations vocabulary. Each definition is a summary; the file and section named beside it hold the rule, and where the two read differently the named section governs. A term whose owning file is named without a section number is specified in that file as a whole.

## 1. Reading the glossary

1. Terms are in alphabetical order word by word, ignoring case, reading a hyphen as a space and ignoring other punctuation, with one table per initial letter in section 2.
2. The column "Specified in" names the `docs/spec/` file and section that specify the term, the owning file first. Other files use the term with this meaning and refer to that section.
3. Text in `code` is an exact name used in code, data, configuration or the API: a module, a field, a setting, a resource or a value.
4. An entry that says "See" names the term under which a synonym is defined.
5. Section numbers of this file are stable: other files cite a letter's table as, for example, `CONTEXT.md` section 2.3.

## 2. Terms

### 2.1 A

| Term | Definition | Specified in |
|---|---|---|
| Abandoned turn | A turn still `streaming` after its `deadlineAt`, because its process died or its finalisation failed every attempt. Session reads show it as `failed` with `errorCode` `turn_abandoned`; the next start in its session or a duplicate of its request stores that status, and it is never used as history. | `13-conversations-and-memory.md` section 2.8; `12-chat-pipeline.md` section 12.6 |
| Access functions | The functions of `docchat_core.access` that answer every access question of every route: `require_admin`, `authorize_project_for_chat`, `resolve_chat_index`, `list_reachable_project_ids` and `list_my_projects`. Each returns a positive result or raises, and none accepts a user identifier other than the validated principal. | `11-api.md` sections 1.4.2 and 1.4.3 |
| Access gate | The approval step of the load-test workflow, GitHub environment `load-access`, at which a tenant administrator consents to and assigns each run's new app registrations, excludes them in Conditional Access and confirms the test passwords stay valid for the run. | `84-testing.md`; `83-infrastructure.md` sections 7.5 and 10.4 |
| Access level | The class of caller an operation admits, published in the OpenAPI document as `x-docchat-access`: `public` (only `getHealth`), `user` (a token holding `User` or `Admin`) or `admin` (a token holding `Admin`). | `11-api.md` section 1.4.1 |
| Access state | A state the web client shows instead of, or above, the app when sign-in or the first calls don't lead to a usable session: Unsupported browser, Configuration error, Signed out, Not assigned, Consent missing, Sign-in failed, Couldn't load your account, No projects, Admin only and the Session expired bar, besides Starting and Redirecting. Each comes from the signals of MSAL, the API's answers and the sign-out flag. | `10-web-client.md` sections 4.8 and 4.9 |
| Action group | An Azure Monitor notification target: `ag-docchat-<env>-ops` receives the budget and application alerts of an environment, and `ag-docchat-security` receives every security alert. Both send e-mail only, to shared mailboxes. | `83-infrastructure.md` section 12.8 |
| Active physical index | The one physical index in state `active` that serves a logical index's readers, named by `search_indexes.active_physical_index_id`. Only the creation of the first physical index and the repoint change it. | `14-ingestion.md` sections 8.2 and 8.9; `80-data-model.md` section 8.3 |
| Active turn | The one turn of a session allowed to run at a time, recorded on the session as `activeTurn` `{turnId, deadlineAt}`. A new turn starts only when it is null or its deadline has passed. | `13-conversations-and-memory.md` section 2.3 |
| Activity | One checkpointed step of a Durable Functions orchestration in the ingestion app, run inside the failure boundary with its own deadline, retries and fenced lease update, and returning a typed `ActivityResult`. | `14-ingestion.md` sections 4.4 to 4.8 |
| Actor column | A SQL column that holds the object ID of the person or identity that made a change (`created_by`, `updated_by`, `archived_by`, `set_by` and others), declared with `info={"actor": True}` so that a user's export and deletion find every one. | `80-data-model.md` section 2.23 |
| Admin | The app role `Admin`: chats in every active project without membership rows, manages projects, members, index mappings, indexes and documents, and sees ingestion runs. It is granted in Microsoft Entra ID through groups, never in the app, and gives no access to another user's sessions or memory. | `11-api.md` section 1.4.1; `83-infrastructure.md` section 7.3 |
| Admin consent | The tenant-wide delegated grant (`consentType: 'AllPrincipals'`) from the web client, and in `dev` and `load` the test client, to Microsoft Graph's sign-in scopes, created by the post-provision identity steps. The API's own scope `access_as_user` needs no consent, because the API pre-authorises both clients; a missing grant shows the Consent missing access state. | `83-infrastructure.md` sections 7.3 and 7.5; `10-web-client.md` sections 4.8 and 4.9 |
| Admin route | Every operation under `/v1/admin`. `require_admin` refuses a caller without `Admin` with `403 admin_required` before any validation or lookup, so a non-admin learns nothing about the route. | `11-api.md` sections 1.3 and 1.4.2 |
| After-response trigger | The turn finaliser's call of `schedule_post_turn_work(oid, session_id, turn_id)` for a turn that ended `completed`, which registers the after-response work and returns at once. | `12-chat-pipeline.md` section 12.7 |
| After-response work | The tracked in-process task that, after a completed turn, extracts memory from pending turns and rebuilds the rolling summary when it is due. All its state lives in Cosmos DB, so any instance finishes work another started; it never raises and no user request waits for it. | `13-conversations-and-memory.md` section 6.4 |
| Alert | A rule that evaluates telemetry or the Activity Log on a schedule and notifies an action group with a severity and the name of its runbook. | `85-observability.md`; `83-infrastructure.md` sections 12.5 and 12.6 |
| Allowed client set | The client applications whose tokens the API accepts in the `azp` claim: the web client, plus the test client only when its setting is present and the environment is `dev`, `load` or `local`. | `11-api.md` section 1.2 |
| Allowed link | An `https:` URL of at most 2,048 characters that appears verbatim in a source block actually sent to the answer call. The turn's `allowedLinks` lists at most 50, and they are the only URLs the web client renders as links: the first 10 in an answer, each followed by its host (link policy). | `12-chat-pipeline.md` section 11.5; `10-web-client.md` section 9.3 |
| Answer call | The streamed chat completion on the chat deployment that writes the answer from the assembled prompt; its `max_completion_tokens` is the completion reserve and its markers become citation tokens. | `12-chat-pipeline.md` sections 10 and 17.4 |
| Answer cap | The limit of 100,000 code points on a released answer, the conversation store's limit for a stored answer; reaching it closes the model stream, which counts as a `length` finish with visible text. | `12-chat-pipeline.md` section 10.3 |
| API web app | `app-docchat-api-<env>-<token>`, the Linux App Service site that runs the API container behind platform authentication; with the static site it is the only endpoint reachable from the internet. | `83-infrastructure.md` sections 2.4 and 4.5 |
| App role | `Admin` or `User`, defined on the API's app registration and assigned to groups in Entra ID. A token without either is refused with `403 role_not_assigned`. | `83-infrastructure.md` section 7.3; `11-api.md` section 1.2 |
| App setting | An environment variable of a site, named `DOCCHAT_<AREA>_<NAME>` unless the platform names it, composed in Bicep from `infra/config/app-settings.json`, the environment file and resource outputs, and read once at process start. | `81-config.md` sections 2.1 and 2.2; `83-infrastructure.md` section 8.9 |
| App shell | The frame of the signed-in web client around every screen: the skip link, the top bar with the theme toggle and the account menu, the navigation drawer and the main content. | `10-web-client.md` section 6.3 |
| Approver | A named person who owns an environment's just-in-time groups and grants their temporary membership; at least two per environment, holding no SQL or Cosmos DB right, never listed in `operators`, and a member of `sg-docchat-operators` for its Azure reads only. | `13-conversations-and-memory.md` section 10.1; `83-infrastructure.md` section 6.13 |
| Archived project | A project with `status` `archived`. It is unreachable on every user path for everyone, administrators included, can't be a default project, and is listed, read and restored only through administrator routes. | `11-api.md` section 1.4.2; `80-data-model.md` section 2.3 |
| Atomic claim | The one SQL transaction `claim_ingestion_items` in which the dispatcher counts running items and moves queued items to `running`, by priority and then first in, first out across every run, up to `ingestion.max_parallel_items`. | `14-ingestion.md` section 5.6 |
| Audit event | An append-only row of `app.audit_events` recording an admin, operator, system or security action from the closed catalogue of 43 actions on 18 target types, with its actor, subject, target and metadata, never content. | `80-data-model.md` sections 2.8 and 2.21 |
| Authorisation matrix | The generated test that proves every operation's `401`, `403` and `404` behaviour from the exported OpenAPI document and its access metadata (`x-docchat-access`, `x-docchat-scoped-params`). | `84-testing.md`; `11-api.md` section 1.13 |
| azd environment | `.azure/<env>/.env`, the gitignored file of `main.bicep` outputs and of values the deploy job and its hooks set, read by the web configuration generator, `docchat-ops`, the hooks and the deployed tests. It holds no secret. | `81-config.md` section 4.9; `83-infrastructure.md` section 8.8 |
| Azure Verified Modules | Microsoft's published Bicep modules, referenced as `br/public:avm/res/<path>:<version>` with telemetry off. A local module takes a resource's place where the published module would deploy a preview API. | `83-infrastructure.md` section 8.6 |

| Term | Definition | Specified in |
|---|---|---|

| Broadened search | The second retrieval pass run once when confidence is low and the first response wasn't partial: a search passage is written and embedded, and a search with both vectors replaces the kept set. | Browser storage | The web origin's `localStorage` keys `docchat.theme` and `docchat.nav.open` and the `sessionStorage` flag `docchat.signedOut`, read and written only through `src/platform/storage.ts` with every access guarded, so a failure means the default. | Build stage | One numbered step of the build order, from stage 0 (the scaffold, the first `dev` provision and the stage-0 spikes and platform checks) onward, each with its acceptance gate. | `90-build-order.md` |
| Building physical index | The at most one physical index in state `building` per logical index: a rebuild's target, filled by its rebuild run until the repoint makes it active. | `14-ingestion.md` sections 8.7 and 8.8; `80-data-model.md` section 2.11 |
| Burst limit | The per-user, per-worker-process token bucket of 40 tokens refilled at 10 per second that every `/v1` request except a chat turn passes before any store is touched; an empty bucket answers `429 too_many_requests`. | `11-api.md` section 1.11 |
