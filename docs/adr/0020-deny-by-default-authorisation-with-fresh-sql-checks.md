# ADR 0020: Deny-by-default authorisation with fresh SQL checks

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 11-api.md, 12-chat-pipeline.md, 13-conversations-and-memory.md, 80-data-model.md, 82-security.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0012, 0017, 0021, 0022, 0024, 0026, 0028, 0030, 0045, 0058, 0069, 0078, 0133, 0134, 0139, 0143

## Context

One DocChat deployment serves many projects, and each project's documents, sessions and answers must stay with the people allowed to use that project. Every request is therefore authorised on the server, from the validated token and from SQL, never from anything the browser asserts. A `User` chats in, and opens citations from, the projects they belong to, and manages their own sessions, feedback and memory; an `Admin` does everything a user can on every project without membership rows, and manages projects, members, indexes, mappings and documents; operators act outside the app through audited scripts. Admin status comes from the token's app role; project access is product data, a many-to-many mapping in SQL. No admin can read another user's conversations or memory through the app.

Every identifier a request names (project, index, document, session, turn) is looked up and checked. A resource the caller can't reach answers `404`, so the existence of another project's data never leaks, and an admin route called by a non-admin answers `403`. The API alone chooses the index: the project's default, or, for live testing, a per-user override that an operator sets for a limited time and that always names an index mapped to the same project. Callers never name an index, key or prompt. A revoked membership, an archived project or a removed mapping must take effect on the very next request, so access data is read from SQL on every request with one index-backed query; only slow-changing configuration may be cached, for at most 60 seconds. Every endpoint and data path needs cross-project tests, so one module must answer every access question in one way.

Vendor facts (Microsoft Learn, confirmed 2026-10-14):

- `READ_COMMITTED_SNAPSHOT` is on by default in Azure SQL Database: statements read a snapshot and take no shared locks, so access reads never wait on admin writes.
- A filtered index is nonclustered, takes only simple comparisons in its predicate, and a `UNIQUE` filtered index constrains only the rows its predicate selects; ODBC defaults satisfy the `SET` options it needs.
- Error 1785: one `DELETE` or `UPDATE` may not reach a table through two cascading paths from the same table.
- Cosmos DB hierarchical keys: a full key routes to one partition and point reads need it; a leading prefix is a targeted query that reaches only the partitions holding that prefix.
- `oid` is an immutable GUID; access tokens live a random 60 to 90 minutes; JWT group claims overflow at 200 groups.

## Decision

1. **One module, deny by default.** `docchat_core.access` is used by every route and data path. Each function returns a positive result or raises; none returns a boolean a caller could ignore; none accepts a user identifier other than the validated `Principal` (ADR 0017).

   | Function | Reads | Result | Refusal |
   |---|---|---|---|
   | `require_admin(principal)` | nothing | `None` | `AdminRequired` → `403 admin_required` |
   | `await authorize_project_for_chat(principal, project_id)` | Q1 | `AccessibleProject` | `ProjectNotFound` → `404 project_not_found`; session, turn and citation paths translate it to their own `404` code |
   | `await resolve_chat_index(principal, project)` | Q2, then the index-record cache (Q3 on a miss) | `ResolvedIndex` | `ProjectIndexUnavailable` → `409 project_index_unavailable` |
   | `await list_reachable_project_ids(principal)` | Q4 | `frozenset[UUID]`, possibly empty | none |
   | `await list_my_projects(principal, after, limit)` | Q5 | rows for `listMyProjects` | none |

   `AccessibleProject`: `id`, `name`, `description`, `instructions`, `example_questions` (tuple of strings), `access` (`admin` or `member`; `admin` when both apply). `ResolvedIndex`: `search_index_id`, `source` (`user_override` or `project_default`, the values the stored turn trace and the dashboards use), `override_expires_at` (datetime or `None`), `physical_index` (`id`, `name`, `schema_version`, `embedding_model`, `embedding_dimensions`, `query_embedding_deployment`). Admin routes call `require_admin` through one router-level dependency on `/v1/admin`.
2. **Project reachability.** A project is reachable when its row exists, its `status` is `active`, and the caller is `Admin` or has an `app.project_members` row for it. On every user path (chat, citations, session reads and lists, feedback, the project picker) an unreachable project behaves exactly as an absent one. Archived projects are unreachable for everyone on those paths, admins included, so archiving hides a project's chat at once; admin routes see and restore them (ADR 0022). Admins reach every active project without membership rows.
3. **Index resolution for chat.** Precedence: (1) the caller's `app.user_index_overrides` row for the project whose `expires_at` is later than `SYSUTCDATETIME()`; (2) the project's `app.project_indexes` row with `is_default = 1`. The logical index then resolves to its active physical index (the `app.search_indexes` row joined with the `app.physical_indexes` row it names in `active_physical_index_id`, in state `active`). No override and no default, or no active physical index, gives `409 project_index_unavailable` before streaming starts; a logical index in `reingest_required`, `reingesting` or `rebuilding` still serves from its active physical index. An override's index is always mapped to its project, through the composite foreign key `FK_user_index_overrides_mapping (project_id, search_index_id)` → `app.project_indexes` with `ON DELETE CASCADE`, so unmapping removes the overrides that point at it. Expired overrides are ignored and never deleted automatically. Operators set and clear overrides only with `docchat-ops override set` and `clear` under just-in-time `config` membership, each with `--ticket` and `--reason` (ADR 0139), for longer than 0 and at most 30 days (default 7; `CK_user_index_overrides_expiry`: `expires_at > set_at AND expires_at <= DATEADD(DAY, 30, set_at)`); no API operation or screen changes them. When an override is used, the span attribute `docchat.access.index_source` is `user_override` and the custom event `index_override_used` fires.
4. **Ownership through partition keys.** Every Cosmos DB read, write and query in `conversations`, `memories` and `usage` uses `str(principal.oid)` (lowercase hyphenated) as the user-level partition key value; no request field, path segment, header or cursor ever supplies it (ADR 0030). No app operation takes another user's ID for these containers, admins included, and session and turn IDs from a request only address documents inside the caller's own partition, where a guessed ID simply doesn't exist.
5. **Sessions and citations follow project reachability.** `getSession`, `listSessionTurns`, `putTurnFeedback`, `getCitation`, `getCitationContent` and `getCitationDocument` call `authorize_project_for_chat` with the session's stored `projectId` and turn a refusal into their own `404` code (`session_not_found`, `turn_not_found`, `citation_not_found`); `listSessions` filters by `list_reachable_project_ids` at query time, so pages stay full and hidden sessions never appear. A citation also needs its document's logical index to be mapped to the turn's project at that moment, which the citation query checks (ADR 0069). Revoking a membership, archiving a project or unmapping an index hides the affected sessions or citations from the next request; nothing is changed or deleted, and restoring access shows them again.
6. **`403` versus `404`, and the order of checks.** `403` is used only for `role_not_assigned` (any route) and `admin_required` (any `/v1/admin` route); every missing or unreachable resource is `404` with its resource's code, and that body is byte-identical, apart from `correlationId`, to the one for a random ID. Every route except `createChatTurn` runs this order; the first failure wins:

   | Step | Check | Failure |
   |---|---|---|
   | 1 | Platform authentication (deployed environments) | platform `401` or `403` |
   | 2 | In-app token validation | `401`, `503` |
   | 3 | `User` or `Admin` role | `403 role_not_assigned` |
   | 3a | Per-user burst limit (every `/v1` route except `createChatTurn`; touches no store) | `429 too_many_requests` |
   | 4 | `Admin` role on `/v1/admin/*`, before any validation or lookup | `403 admin_required` |
   | 4a | Per-user write limit (writes except `createChatTurn` and the four upload operations) | `429 write_rate_limited`, `503 dependency_unavailable` |
   | 5 | First-sign-in provisioning (ADR 0021) | `503 dependency_unavailable` |
   | 6 | Body size and media type, checked when the body is first read | `413 request_too_large`, `415 unsupported_media_type` |
   | 7 | Path, query, header and body validation | `422 validation_failed` |
   | 8 | Lookup and reachability of every identifier | `404 <resource>_not_found` |
   | 9 | Preconditions | `428 precondition_required`, then `412 precondition_failed` |
   | 10 | State rules | `409 <conflict code>` |

   `createChatTurn` skips steps 3a and 4a, which its own limits replace (ADR 0058), and follows the chat pipeline's order after step 5. An unknown path answers `404 route_not_found` from routing (a deployed environment answers the platform's `401` first). A non-admin therefore learns nothing about admin resources or their schemas, and a `404` never depends on whether a resource exists in a project the caller can't reach.
7. **One query per check.** Each check is one parameterised, index-backed statement, run on every request. Q1 reads the project row `LEFT JOIN` the caller's membership row (seeks on `PK_projects` and `PK_project_members`) and decides in code: no row, `status <> 'active'`, or neither admin nor member → `ProjectNotFound`. Q2 starts from a one-row anchor and `LEFT JOIN`s the caller's unexpired override (seek on `PK_user_index_overrides`) and the project's default mapping (seek on the filtered unique index `UX_project_indexes_default (project_id) WHERE is_default = 1`). Q3, on a cache miss only, makes primary-key seeks on `app.search_indexes` and `app.physical_indexes`. Q4 reads active projects through `IX_projects_status_name` for an admin, and the caller's `app.project_members` rows joined to active projects for anyone else. Q5 is Q4's reachability with the default mapping, its logical index and its active physical index joined, ordered by `name` with a keyset cursor, so `hasDefaultIndex` is true exactly when Q2's default branch and Q3 would resolve the project to an active physical index. Each statement shape is one constant text per case (with or without a cursor), never an `:x IS NULL OR …` predicate, so every plan stays a seek. Every value is a bound parameter (SQLAlchemy Core; Ruff S608 forbids string-built SQL); the literal `1` in `is_default = 1` stays in the statement text so the optimizer can match the filtered index, and the plan test of item 11 proves every seek.
8. **What is never cached, and what is.** Memberships, overrides, mappings and project status are never cached, so a revoked membership, an archive or an unmapping takes effect on the next request. Projects aren't cached either: Q1 returns the project with the membership in the same round trip. Cached in process for at most 60 seconds: the ops-config snapshot (ADR 0028) and the index-record cache of `resolve_chat_index` (a logical index's status plus its active physical index, keyed by `search_index_id`, at most 256 entries, 60-second lifetime). Only a record that has an active physical index is cached, so chat works from the first request after an index's first physical index becomes active, the moment `listMyProjects` starts reporting `hasDefaultIndex: true`; ingestion deletes a retired physical index no sooner than 10 minutes after the repoint (ADR 0045), so a cached record never names a deleted index. Three in-process structures hold no access data and decide no access: the signing-key set (24 hours, ADR 0017), the last-seen throttle map (ADR 0021) and the burst limiter's buckets (ADR 0143); losing one costs one more key fetch or last-seen write, or briefly loosens the burst limit, never correctness.
9. **Revocation latency.** Removing a membership, archiving a project or removing a mapping takes effect on the caller's next request. Removing an app-role assignment or the app assignment takes effect when the caller's access token expires, 60 to 90 minutes after issue, because roles come only from the token; disabling the account and revoking its sign-in sessions stops new tokens. The urgent-removal runbook gives the order: memberships in the admin UI first, then the groups and direct assignments in Entra ID, then, for an incident, disabling the account and revoking its sessions, then reviewing the person's recent admin changes in `app.audit_events`.
10. **Telemetry.** Spans `docchat.access.authorize_project` (`docchat.project_id`; `docchat.access.outcome` `allowed` or `not_found`; `docchat.access.via` `admin` or `member`), `docchat.access.resolve_index` (`docchat.project_id`, `docchat.index_id`, `docchat.access.index_source` `user_override` or `project_default`, `docchat.access.outcome` `ok` or `unavailable`, `docchat.access.index_cache` `hit` or `miss`) and `docchat.access.reachable_projects` (`docchat.access.project_count`); metrics `docchat.access.denials` (`kind` `role_not_assigned`, `admin_required` or `not_found`; `operation`) and `docchat.access.index_overrides_used`; custom event `index_override_used` (`oid`, `projectId`, `indexId`, `expiresAt`). Alert A40 `index-override-used` (`prod` only, severity 3, a daily summary of uses and distinct users per project and index; runbook R04, which reviews each override's ticket).
11. **Tests.** Unit: `authorize_project_for_chat` over {admin, member, non-member} × {active, archived, missing} allows only (admin, active) and (member, active), and every refusal raises the same `ProjectNotFound`; `resolve_chat_index` uses an unexpired override, ignores an expired one, falls back to the default and raises `project_index_unavailable` with neither or with no active physical index, and on a fake clock a record without an active physical index isn't cached while one with it is served from the cache for 60 s. Integration (SQL Server container): after `adminRemoveProjectMember`, the very next `authorize_project_for_chat` for that user and project refuses; an archived project is refused on every chat-path check for admins and members alike, and a restore brings reachability back; an override for an unmapped project and index fails on the composite foreign key; every Q1 to Q5 statement under `SET SHOWPLAN_XML ON`, with 10,000 users, 2,000 projects and 100,000 memberships loaded, uses only seeks; `hasDefaultIndex` and `resolve_chat_index` agree in every index state. Authorisation matrix generated from the OpenAPI access metadata (ADR 0133): no token → `401`; no role → `403 role_not_assigned`; a `User` on every admin operation → `403 admin_required` with real IDs, random IDs and an invalid body, never `404` or `422`; for every scoped parameter, an unreachable ID and a random ID give the operation's `404` code with byte-identical bodies apart from `correlationId`. Isolation registry entries for projects, members, mappings, overrides and admin routes, each with its negative case. Deployed: removing a test user's membership makes their next `createChatTurn` in that project `404 project_not_found`.

## Alternatives considered

- **Caching memberships, overrides or access decisions for some seconds, in process or in a shared cache.** A revoked membership or an archive would keep working on every instance for the cache lifetime, while revocation must act on the next request; each check is one or two index seeks, and the load test holds the cheap authenticated endpoint at or under 200 ms p95 (ADR 0134).
- **Caching projects for up to 60 seconds.** Archiving would leave chat open for up to a minute, and Q1 already returns the project with the membership, so a cache saves no round trip.
- **Project access as token claims (groups or per-project app roles).** Project access is product data that admins change in the app; revocation would wait 60 to 90 minutes for the token to expire, group claims overflow at 200 groups, and the client and the API would read access from two places.
- **`403` for an existing resource the caller can't reach.** It tells the caller that a project, session or document exists elsewhere, which cross-project isolation forbids.
- **Checks written in each route or repository.** One forgotten check opens a data path; one module that returns positive results makes a missing call fail the matrix and isolation tests.
- **SQL row-level security.** It covers SQL only, while sessions, memory and usage live in Cosmos DB, files in Blob Storage and chunks in AI Search, and it needs session context set on every pooled connection from the SQL thread pool; one module decides access for every store.
- **An admin view of other users' sessions.** Conversations are per-user and no app operation exposes another user's conversations, admins included; operators read conversation data only through just-in-time access outside the app (ADR 0024).
- **Deleting expired overrides automatically.** A sweep would add a writer to a table only operators change, for rows Q2's predicate already ignores; `docchat-ops override list` shows them with an `expired` flag until `set` or `clear`.

## Consequences

- Every authenticated request on a project path costs one or two index seeks, plus Q3 on a cache miss. SQL is a dependency of every such request: while it is unreachable the request fails closed with `503 dependency_unavailable`, never with a guess.
- Revoked memberships, archives and unmappings act on the next request; role removal waits for the access token to expire (item 9).
- A new route can't ship without its access metadata and scoped parameters in the OpenAPI document, because the matrix generates its cases from them.
- An archived project disappears from chat for admins too, until an admin restores it.
- Forgotten overrides surface daily in `prod` (A40) and on the access dashboard.
- Risk: a defect in Q1 to Q5 affects every route at once; the unit matrix and the isolation registry exercise each function, and the plan test keeps each a seek.
