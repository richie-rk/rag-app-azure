# ADR 0137: Telemetry configuration and end-to-end traces

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Product owner and architect
- **Specified in:** 85-observability.md, 81-config.md, 14-ingestion.md, 83-infrastructure.md, 84-testing.md
- **Related ADRs:** 0009, 0012, 0014, 0037, 0081, 0088, 0113, 0138, 0139

## Context

Both Python apps send OpenTelemetry through the Azure Monitor OpenTelemetry distro into one workspace-based Application Insights resource per environment, and every user action is one trace: browser, API, queue message, orchestration and activities. The queue message carries the run ID and the W3C trace context, and the dispatcher passes that context on to each document's activities (ADR 0037), so an error a user reports can be matched to its server trace through the reference ID the client shows.

Under load the telemetry must keep the record of every failure: a sampler that drops traces at random can drop the only record of a failed ingestion activity. Telemetry must also carry metadata only (ADR 0014): every exporter must pass through the scrubbing processors, so nothing may configure an exporter on its own.

Vendor facts: azure-monitor-opentelemetry 1.8.11 is GA and depends on the pre-release exporter 1.0.0b58 (ADR 0009); the distro's default sampler is rate-limited at 5 traces per second; since exporter 1.0.0b36 the Entra credential is built from `APPLICATIONINSIGHTS_AUTHENTICATION_STRING` (`Authorization=AAD;ClientId=<client ID>` for a user-assigned identity) when none is passed, which needs Monitoring Metrics Publisher on the component; `OTEL_TRACES_SAMPLER=microsoft.fixed_percentage` selects the distro's percentage sampler; the Functions host's OpenTelemetry mode is preview; the Python worker's own Azure Monitor auto-configuration (`PYTHON_APPLICATIONINSIGHTS_ENABLE_TELEMETRY`) bypasses first-party processors; Azure Monitor stores histograms as sum, count, minimum and maximum.

## Decision

1. **One configuration function.** `docchat_core.telemetry.configure_telemetry(service, settings, exporters=None)` is the only place telemetry is configured; `service` is `docchat-api` or `docchat-ingestion`. The API calls it once per Gunicorn worker at the start of the FastAPI lifespan, after the fork and before any client is created; the ingestion app calls it once per Functions worker process when the root `function_app.py` shim imports `docchat_ingestion.function_app`. It sets `OTEL_TRACES_SAMPLER=microsoft.fixed_percentage`, `OTEL_TRACES_SAMPLER_ARG=<DOCCHAT_TELEMETRY_SAMPLING_RATIO>` and `OTEL_PROPAGATORS=tracecontext` in the process environment, then calls `configure_azure_monitor(connection_string=<APPLICATIONINSIGHTS_CONNECTION_STRING>, logger_name="docchat", resource=<item 3>, span_processors=[ScrubbingSpanProcessor()], log_record_processors=[ScrubbingLogRecordProcessor()], views=[<the millisecond histogram view>], instrumentation_options={"azure_sdk": {"enabled": True}, "httpx": {"enabled": True}, "fastapi": {"enabled": <service is docchat-api>}, "django": {"enabled": False}, "flask": {"enabled": False}, "psycopg2": {"enabled": False}, "requests": {"enabled": False}, "urllib": {"enabled": False}, "urllib3": {"enabled": False}}, enable_live_metrics=False, enable_performance_counters=True)`. For `docchat-ingestion` it then emits the custom event `ingestion_worker_started` (no properties) once per process, which the deploy's `postdeploy` hook waits for. The test-only `exporters` argument swaps in in-memory exporters; without a connection string (local runs) nothing is exported.
2. **Entra-authenticated export.** No credential is passed in code: the exporter builds it from `APPLICATIONINSIGHTS_AUTHENTICATION_STRING` (`Authorization=AAD;ClientId=<workload identity client ID>`), so no synchronous identity class enters first-party code. The component has `disableLocalAuth: true` and no ingestion sampling, sits on the environment's Log Analytics workspace, and each app identity holds Monitoring Metrics Publisher (`3913510d-42f4-4e42-8a64-420c390055eb`) on it.
3. **Resource attributes.** `service.name` (`docchat-api` or `docchat-ingestion`, which becomes `AppRoleName`), `service.version` = `DOCCHAT_BUILD_COMMIT` (the 40-hex commit baked into the image) and `deployment.environment.name` = `DOCCHAT_CORE_ENVIRONMENT` (`dev`, `prod`, `load`); no `service.namespace`, because the exporter would prefix the role name with it and every query filters on `AppRoleName`. The distro's Azure resource detectors add `service.instance.id` (`AppRoleInstance`), `cloud.provider`, `cloud.platform`, `cloud.region`, `cloud.resource_id` and `host.id`. Service names are constants in code.
4. **Sampling.** Traces are sampled by the distro's percentage sampler `microsoft.fixed_percentage` at `DOCCHAT_TELEMETRY_SAMPLING_RATIO`, the one app setting for it, set on both apps from the environment-file field `telemetrySamplingRatio` (number, default 1.0, allowed 0.1 to 1.0); no `OTEL_*` app setting exists, so two settings can't disagree. The sampler decides from the trace ID, so a trace is kept or dropped whole across both apps, and it ignores the caller's sampled flag, so the browser's constant flag `01` never forces sampling. A unit test measures this: at ratio 0.5 a request carrying flag `01` must be exported only when its trace ID falls inside the ratio, and one carrying `00` must be exported when it does. If the distro's sampler honours the parent flag, `configure_telemetry` wraps it in a sampler that ignores the parent and applies the same trace-ID rule, and this ADR gains a note saying so. The Functions host's sampling is off in `host.json`. Metrics are never sampled; rate alerts use metrics or `ItemCount`-weighted request counts.
5. **Logging and host settings.** Logger `docchat` at `DOCCHAT_TELEMETRY_LOG_LEVEL` with `propagate = False` and a stderr handler at `WARNING` carrying the scrubbing filter; loggers `azure`, `azure.core.pipeline.policies.http_logging_policy`, `httpx`, `httpcore`, `httpx2`, `openai`, `opentelemetry` and `uvicorn.error` at `WARNING`; `uvicorn.access` disabled; `apps/api/gunicorn.conf.py` sets `accesslog = None`, `errorlog = "-"`, `loglevel = "warning"`, `capture_output = False`. The ingestion `host.json` sets `logging.logLevel` (`default` `Warning`, `Host.Results` and `Host.Aggregator` `Information`, `Function`, `DurableTask.AzureStorage` and `DurableTask.Core` `Warning`), `logging.applicationInsights` `{"samplingSettings": {"isEnabled": false}, "enableDependencyTracking": false}` and `extensions.durableTask.tracing` `{"distributedTracingEnabled": false, "traceInputsAndOutputs": false, "traceReplayEvents": false}`. `PYTHON_APPLICATIONINSIGHTS_ENABLE_TELEMETRY` stays unset and the preview host `telemetryMode: OpenTelemetry` isn't used.
6. **One trace per user action.** (1) The web client sends `traceparent` with a fresh trace ID on every API call (ADR 0088). (2) The API propagates `tracecontext` only (no baggage, so client-supplied baggage never reaches telemetry), the FastAPI instrumentation continues the incoming trace, and the problem body's `correlationId` is its trace ID; after-response work (follow-ups, summaries, memory) runs in tasks created inside the request's context, so its spans join the request's trace. (3) Every operation that enqueues ingestion work injects the current context into the message fields `traceparent` and `tracestate` and stores `traceparent` on the `ingestion_runs` row (ADR 0037). (4) The queue-triggered starter extracts it with `TraceContextTextMapPropagator().extract(...)` and runs inside `docchat.ingestion.queue_message` (kind `CONSUMER`). (5) The dispatcher's activities open root spans `docchat.ingestion.dispatcher.sweep` and `docchat.ingestion.dispatcher.claim`, with one span link per run they touch; orchestrator functions never create spans, because they replay. (6) Each document sub-orchestration's input carries its run's `traceparent`, and every activity runs inside `docchat.ingestion.activity` (kind `INTERNAL`, attribute `docchat.activity_name`) parented on that remote context, with Azure SDK and `httpx` spans nested below. (7) `docchat-ops` creates one trace ID per run and writes it as `audit_events.correlation_id`; its spans aren't exported.

## Alternatives considered

- **The distro's default rate-limited sampler (5 traces per second).** Rejected: under load it drops failures at random, and the only record of a failed ingestion activity can be the dropped trace.
- **Honouring the caller's sampled flag (parent-based sampling).** Rejected: every browser call sends `01`, so the client would decide what the server keeps.
- **`OTEL_TRACES_SAMPLER` and its argument as app settings.** Rejected: two settings could disagree with the ratio; one setting is read and the variables are derived in-process.
- **The Functions host's OpenTelemetry mode, or the worker's automatic Azure Monitor export.** Rejected: the first is preview, and the second bypasses the scrubbing processors.
- **Durable Functions' own distributed tracing.** Rejected: the host writes that telemetry outside the scrubbing processors and roots it at the long-lived dispatcher, not at the request (ADR 0037).
- **An instrumentation key or connection-string-only export.** Rejected: local authentication is off on the component, and Entra-authenticated export needs no secret.
- **Configuring telemetry in each app separately.** Rejected: two configurations drift, and scrubbing and sampling have to be proven in one place.

## Consequences

- A user's reference ID is the trace ID, and it leads to the browser call, the API request, the starter and every activity of every document of the run in one Application Insights operation; the dispatcher's work is found through its span links.
- At the default ratio of 1.0 every trace is kept; an operator who lowers `telemetrySamplingRatio` loses whole traces, never parts of one, and alerts keep working because they read metrics or weighted counts.
- The exporter is a pre-release package pinned exactly in `uv.lock` and changed only through a Dependabot pull request that passes the telemetry and scrubbing unit tests (ADR 0009).
- Entra-authenticated export doesn't work in local development, so local runs export nothing; tests use the in-memory exporters.
- Tests (84-testing.md): sampler, ratio, propagators and resource attributes; no export without a connection string and scrubbed stderr; trace-ID sampling that ignores the parent flag; an upload's trace holding the starter span and every activity span, with dispatcher spans as linked roots; `correlationId` equal to the request's trace ID, in-process and deployed; `ingestion_worker_started` once per ingestion process and never in the API.
