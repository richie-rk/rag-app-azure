# ADR 0106: Hardening defaults checked by PSRule

- **Status:** Accepted
- **Date:** 2026-10-21; amended 2026-11-07 (`Azure.SQL.Auditing` replaced by the custom rule `DocChat.SQL.Auditing` and suppressed on the same servers, the product owner's decision; and the configuration's first full run: the binding and `rule.includeLocal` that let the custom rules and suppression groups match, `DocChat.OpenAI.DeploymentRules` reading the deployments PSRule nests under their account, `main.bicep` and `shared.bicep` expanded only through their parameter files, the suppressions of item 5's last eight rows, and synopses kept to one line)
- **Decided by:** Architect
- **Specified in:** 83-infrastructure.md, 82-security.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0009, 0026, 0044, 0097, 0102, 0105, 0107, 0108, 0112, 0115, 0116, 0117, 0136, 0141, 0142

## Context

Every Azure resource of this product is a Bicep declaration, and no service may authenticate with a key or a password. The security settings of each resource must hold in every environment, and a regression must be caught before it deploys, not reported after it is live. PSRule for Azure expands the templates with each environment's real parameter files, so it can fail the pull request that weakens a setting. A waiver is allowed only as a named suppression with a reason and an expiry.

Vendor facts:

- PSRule for Azure expands Bicep and `.bicepparam` files (v1.34.0 and later with Bicep 0.18.4 and later); modules with required parameters can't be expanded on their own, so they are expanded through the files that use them and excluded with `input.pathIgnore`.
- PSRule for Azure v1.47.0 (8 January 2026) is the latest stable release and added the `Azure.GA_2025_12` baseline (516 rules); the documentation site, built from the v1.48.0 pre-releases, marks that baseline obsolete and lists `Azure.GA_2026_03`. The `microsoft/ps-rule` action installs the latest stable version of each module unless told otherwise, and PSRule's `requires` option makes a run fail when a module version doesn't satisfy its constraint.
- Built-in rules cover HTTPS, minimum TLS, FTP, client affinity, remote debugging, storage local auth, public blob access and firewall, Cosmos DB local auth and metadata writes, SQL Entra-only and auditing, AI services local auth and private endpoints, Key Vault RBAC, soft delete and purge protection, registry admin user and anonymous pull, and Application Insights local auth; none covers App Service basic publishing credentials, AI Search local auth, Cognitive Services custom subdomains, Log Analytics local auth or TLS 1.3.
- The `Azure.GA_2025_12` baseline also holds rules the settings below don't satisfy: `Azure.Search.ManagedIdentity` (`identity.type` set), `Azure.SQL.DefenderCloud` (a `securityAlertPolicies` child enabled), `Azure.SQL.VAScan` (a `sqlVulnerabilityAssessments` child enabled), `Azure.SQL.MaintenanceWindow` (a non-default `maintenanceConfigurationId`), `Azure.AppService.AvailabilityZone` (`zoneRedundant: true` on PremiumV2, PremiumV3 and ElasticPremium plans) and `Azure.AppService.PlanInstanceCount` (`sku.capacity` of at least 2, not applied to elastic plans). `Azure.Storage.DefenderCloud` runs only when `AZURE_STORAGE_DEFENDER_PER_ACCOUNT` is `true` (default `false`); `Azure.Storage.Defender.MalwareScan` runs by default.

## Decision

1. **Settings, each with its check** (built-in or custom rule in brackets):

   | Resource | Settings |

   | Ingestion function app | the same, plus `publicNetworkAccess: 'Disabled'` [DocChat.Functions.PublicAccessDisabled] |
   | Storage, data and Functions host | `allowSharedKeyAccess: false` [Azure.Storage.LocalAuth] and `allowBlobPublicAccess: false` [Azure.Storage.BlobPublicAccess], both also denied by Azure Policy (ADR 0116); `supportsHttpsTrafficOnly: true` [Azure.Storage.SecureTransfer]; `minimumTlsVersion: 'TLS1_2'` [Azure.Storage.MinTLS]; `defaultToOAuthAuthentication: true`; `networkAcls.defaultAction: 'Deny'` [Azure.Storage.Firewall]; trusted-service bypass `None` [DocChat.Network.NoTrustedServiceBypass]; `requireInfrastructureEncryption: true`; blob and container soft delete [Azure.Storage.SoftDelete, Azure.Storage.ContainerSoftDelete] |

2. **Custom rules** in `.ps-rule/docchat.Rule.yaml` (YAML rules), for the settings no built-in rule checks: `DocChat.AppService.MinTLS13` (every `Microsoft.Web/sites`: `siteConfig.minTlsVersion` and `siteConfig.scmMinTlsVersion` equal `'1.3'`); `DocChat.AppService.NoBasicPublishing` (every site has `basicPublishingCredentialsPolicies` `ftp` and `scm` with `allow: false`); `DocChat.AppService.ScmDenied` (every site: `siteConfig.scmIpSecurityRestrictionsDefaultAction: 'Deny'`, no SCM rule, `scmIpSecurityRestrictionsUseMain` not `true`); `DocChat.Functions.PublicAccessDisabled` (every site whose `kind` contains `functionapp`: `publicNetworkAccess: 'Disabled'`); `DocChat.SQL.MinTLS13` (`minimalTlsVersion: '1.3'`); `DocChat.SQL.Auditing` (every SQL server named `sql-docchat-*` has exactly one `extendedAuditingSettings` named `default`, enabled, sent to Azure Monitor and with a non-empty `predicateExpression`); `DocChat.Search.LocalAuthDisabled` (`disableLocalAuth: true`); `DocChat.AI.CustomSubdomain` (every `Microsoft.CognitiveServices/accounts` has a `customSubDomainName` that isn't empty); `DocChat.AI.RestrictOutbound` (`restrictOutboundNetworkAccess: true` and an empty `allowedFqdnList`); `DocChat.LogAnalytics.LocalAuthDisabled` (`features.disableLocalAuth: true`); `DocChat.Network.NoTrustedServiceBypass` (storage `networkAcls.bypass`, Key Vault `networkAcls.bypass`, AI Search and Cognitive Services `bypass`, Cosmos DB `networkAclBypass` and the registry's `networkRuleBypassOptions` all `None`); `DocChat.OpenAI.DeploymentRules` (every deployment whose model name doesn't start with `text-embedding` names a `raiPolicyName`; every embedding deployment has `versionUpgradeOption: 'NoAutoUpgrade'` and no `raiPolicyName`).
3. **Configuration.** `ps-rule.yaml` at the repository root: `requires: {PSRule: '>=2.9.0 <3.0.0', PSRule.Rules.Azure: '>=1.47.0 <1.48.0'}`; `include.module: [PSRule.Rules.Azure]`; `binding: {preferTargetInfo: true, targetName: [ResourceName, name], targetType: [ResourceType, type]}`, because PSRule for Azure's own binding applies only to its rules, and the custom rules, their selector and the suppression groups match a resource's `type` and `name` only through this one; `rule.includeLocal: true`, because the baseline selects rules by tag and would leave the custom rules out; `configuration: {AZURE_BICEP_FILE_EXPANSION: true, AZURE_BICEP_PARAMS_FILE_EXPANSION: true, AZURE_BICEP_FILE_EXPANSION_TIMEOUT: 60, AZURE_RESOURCE_GROUP: {name: 'rg-docchat-prod', location: 'eastus2'}}`; `input.pathIgnore: ['infra/main.bicep', 'infra/shared.bicep', '!infra/*.bicepparam', 'infra/modules/**', 'infra/bootstrap/modules/**', 'infra/teardown/**', 'apps/**', 'tests/**']`, so the two templates with required parameters expand only through their parameter files (a path pattern also matches longer names, so the negation puts the parameter files back); `execution: {suppressionGroupExpired: Error, ruleSuppressed: Warn}`; `output.culture: ['en-US']`.
4. **The CI job.** The `infra-validate` job runs `microsoft/ps-rule` v2.9.0 (pinned to its commit SHA) with `modules: PSRule.Rules.Azure`, `baseline: Azure.GA_2025_12`, `inputType: repository`, `outputFormat: Sarif` and `outputPath: reports/ps-rule-<env>.sarif`, three times, with `AZURE_ENV_NAME` set to `dev`, `prod` and `load` and representative image references, so `infra/main.bicepparam`, `infra/shared.bicepparam` and the bootstrap parameter files expand for every environment. Any failure that no suppression group covers fails the job, and the SARIF goes to code scanning.

   | `Azure.AppService.MinPlan`, `Azure.AppService.PlanInstanceCount` | `dev`'s B1 API plan | development SKU |
   | `Azure.AppService.PlanInstanceCount` | `load`'s API plan; the `load` model stub plan | the single-instance load scenario needs one instance at start; the stub runs one instance (ADR 0112) |

   | `Azure.Search.QuerySLA`, `Azure.Search.IndexSLA` | the `dev` search service | Basic with 1 replica and no zone redundancy (ADR 0102) |
   | `Azure.Cosmos.AvailabilityZone` | the `dev` Cosmos DB account | serverless and single-zone; `dev` holds test data (ADR 0102) |

6. **Built-in failures found later.** Stage 0 of the build order runs this configuration against all three environments, and every PSRule module update reruns it. Each built-in rule that fails is resolved in the same pull request by one of two actions: the template change, when the required setting adds no identity, network path, role, preview API or monthly cost and contradicts no ADR; otherwise a suppression group naming that rule and those resources, with the same `expiresOn` and a `# Synopsis:` naming the ADR whose decision the rule conflicts with. No suppression may cover a resource for which item 1 requires that rule's setting; the one case where item 1 names a custom rule in place of the built-in one that reads another resource type (`Azure.SQL.Auditing`, item 5) is suppressed only together with that custom rule on the same resources.
7. **Versions.** PSRule 2.9.0 with PSRule for Azure 1.47.0 and the baseline `Azure.GA_2025_12`, the newest GA baseline of the latest stable release (confirmed 2026-10-14). Dependabot has no ecosystem for these modules, so the quarterly dependency review (runbook R17) moves the `requires` range and the baseline together, in one pull request that passes this gate, when a stable release ships.
8. **Diagnostic settings coverage.** No PSRule rule checks that every resource has its diagnostic setting, so a deployed `dev` test lists every resource in `rg-docchat-dev` whose type appears in ADR 0107's table (`az monitor diagnostic-settings list --resource <ID>`, and the sub-resource IDs for the storage services and the SQL databases) and fails unless each has `to-log-analytics` (the `master` database: `sql-audit`) with exactly that type's categories.

## Alternatives considered

- **Azure Policy audit or deny as the only check.** Rejected: it reports drift after deployment; PSRule fails the pull request before anything deploys. Deny policies still guard the settings whose reversal would open data (ADR 0116).
- **The preview baseline `Azure.Preview_2025_12`.** Rejected: GA over preview; preview rules change without notice.
- **No `requires` constraint, so the module floats.** Rejected: a new release would add or change rules and fail or pass pull requests with no repository change.
- **Suppressions without expiry.** Rejected: a waiver nobody reviews outlives its reason; `suppressionGroupExpired: Error` forces a review by 31 October 2027.
- **A system-assigned identity on AI Search to satisfy `Azure.Search.ManagedIdentity`.** Rejected: a principal with no use is one more identity to watch.
- **Enabling Microsoft Defender for SQL to satisfy its two rules.** Not adopted for the first version (reason in item 5); an organisation that uses Defender for Cloud adds the `securityAlertPolicies` and `sqlVulnerabilityAssessments` children and removes the suppression.

## Consequences

- A pull request that weakens any setting of item 1 in any environment fails before deployment, including a change that arrives through an Azure Verified Module update.
- Publication of PSRule for Azure 1.48.0 fails every PSRule run until the pull request of item 7 lands, because the action installs the newest stable module and `requires` refuses it; the gate fails closed.
- On 31 October 2027 every suppression expires and fails the job until each is reviewed and renewed or removed.
- Deployed `dev` tests (84-testing.md): the API's SCM host refuses every request; FTP and basic-auth publishing are rejected; the ingestion app's default host name refuses every request; each data and AI resource rejects key or shared-key authentication with `401` or `403`; without a firewall rule, Cosmos DB, both storage accounts, AI Search, the AI services and the environment Key Vault refuse the runner; the coverage test of item 8.
