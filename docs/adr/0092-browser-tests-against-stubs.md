# ADR 0092: Browser tests against stubs

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Architect
- **Specified in:** 84-testing.md, 10-web-client.md, 01-repository.md, 90-build-order.md
- **Related ADRs:** 0018, 0019, 0083, 0084, 0085, 0086, 0087, 0090, 0091, 0093, 0131, 0152

## Context

The web client's defences live in code that only a real browser runs: the Content Security Policy (ADR 0083), MSAL's redirect flow with its cache in session storage (ADR 0018), sanitised rendering with a link allowlist (ADR 0084), the byte-buffered NDJSON reader (ADR 0085) and the upload client (ADR 0093). The product needs an exfiltration test (rendering an answer that holds an image or a URL that isn't in its sources makes no network request) and streaming tests, and every release needs the access states of ADR 0091 proven. Many of the states to prove can't be produced on demand from real services: an `AADSTS50105` redirect, a bare `403`, a `412` race, `429` waits, `503 malware_scanning_not_ready`, a stream split at every byte, a stall, a missing terminal event.

Signing in to Entra ID through the web client needs a person: the sign-in page, MFA and Conditional Access run there. The only documented non-interactive user sign-in for tests is ROPC, which is incompatible with MFA and needs public client flows; the web client registration keeps them off (`isFallbackPublicClient: false`). Deployed and load tests get user tokens by ROPC through a test client that exists only in `dev` and `load`, with a Conditional Access MFA exclusion scoped to cloud-only test users and that test client (Entra ID P1, ADR 0019). Widening the exclusion to the web client would let a test user's password alone open the real web client in those environments.

Vendor facts:

- The Static Web Apps CLI (2.0.10, released 2026-07-20) runs a local static server on port 4280 that enforces the routes and configuration of `staticwebapp.config.json`, and handles `/.auth/*` itself with a mock identity, so only the deployed service proves how those routes are blocked. A pre-configured provider is blocked with a route rule such as `{"route": "/.auth/login/aad", "statusCode": 404}`.
- Playwright's `browserContext.route()` sees every request a page makes, XHR and fetch included, and `route.fulfill()` answers it with a chosen status, headers and body without touching the network.

## Decision

1. **Levels for the web client.** Unit and component tests: Vitest 5.0.4 with jsdom 30.1.2, Testing Library and MSW 3.0.3 (`onUnhandledRequest: "error"`). Browser integration tests: Playwright against the stubs below, on every pull request. Deployed smoke tests: Playwright, unauthenticated, after every web deploy to `dev` and `prod`. Manual: the release sign-in check (item 8) and the release accessibility check (ADR 0090).
2. **Package and configuration.** `tests/e2e` is the private npm package `@docchat/e2e` with `@playwright/test` 1.64.1, `@axe-core/playwright` 4.13.0 and `@azure/static-web-apps-cli` 2.0.10, all exact. `playwright.config.ts`: projects `chromium`, `firefox`, `webkit` and `msedge` (`channel: "msedge"`, for the PDF viewer, which needs `navigator.pdfViewerEnabled`) run `specs/web/`; `chromium` alone runs `specs/web-deployed/`; `retries` 0 locally and 1 in CI; `trace: "retain-on-failure"`; `forbidOnly: true` in CI. The stubs live in `tests/e2e/fixtures/web/`.
3. **The site under test is the shipped build.** The unconfigured `dist` artifact that every environment deploys (ADR 0086) is configured by `write-env-config.mjs --allow-loopback` with API origin `http://127.0.0.1:4010` and served on `http://127.0.0.1:4280` by `swa start <dir> --port 4280`, which applies the generated `staticwebapp.config.json` (global headers, route rules, navigation fallback, 404 override). The bundle has no test mode, flag or alternative code path: MSAL, the CSP and every module run unchanged.
4. **Stub identity provider.** `context.route('https://login.microsoftonline.com/**')` answers the OpenID metadata and instance-discovery calls; `/authorize` with a `302` to the redirect URI carrying `code` and `state`, or carrying an error such as `AADSTS50105`; `/token` with an ID token that carries the authorize request's `nonce`, an access token, a refresh token and `client_info`, and, as a per-case option, no `refresh_token`, so no test edits MSAL's storage entries; and `/logout` with a `302` to the post-logout URI.
5. **Stub API.** `tests/e2e/fixtures/web/stub-api/`, built on Node's `http` module with no dependencies, listening on `127.0.0.1:4010`. It implements every operation the client calls with fixture data and scripted NDJSON streams (normal; split at every byte; slow with heartbeats; broadened search; error event; missing terminal event; stalled; oversized line; invalid event; unknown event type); answers CORS preflights the way App Service platform CORS does (origin `http://127.0.0.1:4280`, any method and header); records every request; and fails any request without a valid `traceparent` or bearer token. A spec can script: a bare `403` from `getCurrentUser`; `503 malware_scanning_not_ready` with `retryAfterSeconds` from `adminPreflightUploads` and `adminUploadContent`; `412 precondition_failed` and `428 precondition_required` on the four membership and mapping operations, and their success bodies carrying `projectRowVersion`; `429 too_many_requests`, `429 write_rate_limited`, `429 rate_limited` and `429 too_many_downloads`, each with `retryAfterSeconds`; a `getCitationContent` or `getCitationDocument` `200` whose body ends before its `Content-Length`; `409 document_pdf_unavailable` from `getCitationDocument`; and stored up-rating feedback with a comment returned by `getSession`.
6. **Gates in every browser test.** A shared fixture registers a `securitypolicyviolation` collector with `page.addInitScript` and collects console messages; any CSP violation, console error or Permissions-Policy warning fails the test. After each screen state a test reaches, an `AxeBuilder` scan with the tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` applies ADR 0090's pass rule. `specs/web/identity.spec.ts` holds the sign-in, storage, sign-out and renewal cases (with ADR 0091's access states); `specs/web/exfiltration.spec.ts` renders an answer holding images, raw HTML and unlisted URLs and passes only when no request goes to any origin other than the site, the stub API and the stub Entra ID, and clicking the plain-text URL navigates nowhere.
7. **Deployed smoke tests.** `tests/e2e/specs/web-deployed/`, unauthenticated, against each environment's web origin after each web deploy: every response header equals ADR 0083's policy with that environment's API origin in the CSP; `/chat/<random UUID>` returns `200` with the app shell; `/.auth/login/aad`, `/.auth/login/github` and `/.auth/me` return `404` with no `Location` and no `Set-Cookie`; `/assets/missing.js` returns `404`; `/config.json` returns `200` with exactly four members equal to the environment's Bicep outputs; loading `/` navigates to `https://login.microsoftonline.com/<tenantId>/oauth2/v2.0/authorize` with the environment's `client_id`, `redirect_uri` `<origin>/`, a `scope` containing the API scope and `code_challenge_method=S256`, with no CSP violation and no request to another origin before that navigation. They run in the `web-deployed` job, which has no GitHub environment and no `id-token`, because it runs `npm ci` and needs no Azure sign-in; a failure fails the deploy job.
8. **No MFA exclusion and no ROPC for the web client.** The web client registration keeps public client flows off, and the Conditional Access exclusion covers only the test users and the test client. Signed-in behaviour in deployed environments is covered by the API's deployed tests through the test client (ADR 0019) and by the manual release sign-in check: in `dev`, then in `prod` after the deploy, sign in with a real account, send one question, open one PDF citation, open one DOCX citation's page and download its full document, sign out and confirm the Signed out screen, then sign in again and confirm that Entra ID asks for an account rather than signing in silently.

## Alternatives considered

- **Signing in to the real Entra ID in browser tests.** Rejected: it needs the MFA exclusion widened to the web client or scripts that drive Entra ID's own pages, which change without notice; either way a password alone would open the web client in `dev` and `load`.
- **Writing tokens into MSAL's session-storage cache.** Rejected: MSAL's storage format is internal and changes between versions, and the tests would skip the redirect flow they exist to prove.
- **A test-only sign-in bypass in the bundle.** Rejected: the shipped bundle would carry a bypass, and the tested bundle would differ from the one users load.
- **Browser tests against the deployed `dev` API.** Rejected: they need user tokens (above), can't produce rare states on demand and would tie every pull request to a shared environment.
- **Mock Service Worker in the page.** Rejected: its worker script must be served from the site's own origin, which the shipped build doesn't contain, and requests would never cross origins, so CORS preflights would go unexercised.
- **`vite preview` or another plain static server.** Rejected: it ignores `staticwebapp.config.json`, so headers, the navigation fallback and the 404 override would first meet a test after deployment.

## Consequences

- Every pull request proves the shipped bundle under its real CSP in four browser engines with no Azure resource, no token and no secret; a failed run keeps its Playwright trace.
- Every client state is reachable and repeatable through scripted stub answers, so a defect report becomes a stub script and a test.
- The stub identity provider proves MSAL's use of the protocol, not Entra ID's behaviour. The emulator handles `/.auth/*` itself, so only the deployed smoke tests prove those routes are blocked; Conditional Access differs per tenant, so a real sign-in is checked by hand at each release.
- Maintenance: updates to MSAL, Fluent UI, React Router, DOMPurify, Zod or the `unified` family merge only after the full browser suite passes, stub identity provider tests included; when a browser reports a Permissions-Policy feature as unrecognised, the header template drops it in the next release.
- Build order (90-build-order.md): stage 5's acceptance requires Playwright to pass in CI on the four browser projects and the deployed smoke tests to pass against the `dev` site with zero CSP violations.
