# ADR 0072: Turn statuses and single-batch finalisation

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 13-conversations-and-memory.md, 12-chat-pipeline.md, 80-data-model.md, 11-api.md, 10-web-client.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0007, 0055, 0056, 0057, 0060, 0070, 0071, 0073, 0074, 0075, 0078, 0080, 0081

## Context

The product owner requires NDJSON streaming with an explicit end marker. Every stream ends with exactly one `done` or `error`; when the client disconnects, the API cancels the model call and saves the turn as cancelled with the partial answer; citations are sent as soon as the answer ends, and the client re-enables input when they arrive; the API, never the browser, persists the turn. A retry sends a new `clientTurnId`, and failed and cancelled turns are never sent to the model as history, because the model must only ever see earlier answers that finished, in order, as earlier conversation.

A disconnect can happen while the answer streams or after it has ended, and the two need different outcomes: a user who closes the tab after reading a complete answer must keep that answer in history. Persistence must also survive the cancellation of the request that carried the stream, and a finalisation whose response is lost must not be reported as superseded when it did commit.

Further forces: an instance can stop (the shutdown drain of ADR 0007) or die mid-turn; the end of a turn must release the session's one-active-turn guard (ADR 0056) and add to the summary counters (ADR 0074) in the same write that stores the answer. Cosmos DB facts: a transactional batch over one full partition key commits only if every operation succeeds in the order given, and otherwise rolls back; the failed operation returns its own status and every other operation returns `424`, so a batch reports a single failing operation; a create of an existing item answers `409`; each operation accepts its own `if_match_etag`, and an `_etag` mismatch answers `412`; a batch holds at most 100 operations, 2 MB and 5 s.

## Decision

1. **Status machine.** `begin_turn` creates every turn as `streaming` (ADR 0056). It moves to exactly one of `completed`, `failed` or `cancelled`, and a terminal status never changes.
   - `completed`: answer generation finished with visible text and finish reason `stop` or `length` (`length` sets `answerTruncated: true`), including when the client disconnected after generation finished.
   - `cancelled`: the client disconnected before generation finished. The text released so far is stored with its citation tokens, together with the citations of the markers already converted and `finishReason: "cancelled"`; usage is recorded, estimated when the usage chunk hadn't arrived (ADR 0060).
   - `failed`: an error ended the turn. `error` is `{code, retryable}` with the code and retryable flag of the stream's `error` event (the stream codes of 12-chat-pipeline.md, `turn_timeout` and `service_restarting` included), or `{code: "turn_abandoned", retryable: true}` when a later start or a duplicate found the turn still `streaming` after its `deadlineAt`. Text released before the failure stays in `answer` and is never used.
2. **What may change after finalisation.** On a `completed` turn only `followups`, `followupsAt`, `feedback`, `usage` (the follow-ups record), `memoryExtraction` and `updatedAt`; on a `cancelled` turn only `feedback` and `updatedAt` (feedback needs a non-empty answer, ADR 0080); a `failed` turn never changes again.
3. **One finalisation batch.** In the partition `[oid, sessionId]`, `finalize_turn` executes `[replace turn (if_match = the turn ETag from begin_turn), create turn_trace, replace session (if_match = the latest session ETag)]`. The turn replacement writes `status`, `answer`, `answerTruncated`, `finishReason`, `error`, `citations`, `allowedLinks`, `usage` (the calls so far, without follow-ups), `endedAt` and `updatedAt`; for a `completed` turn also `historyTokens` (tokens of the question plus the answer without citation tokens, chat encoding, counted in a worker thread when the two texts exceed 20,000 characters together, inline otherwise). It sets `memoryExtraction` in the same write (ADR 0075): `{state: pending}` for a `completed` turn with `memory.enabled` true and a question that wasn't a suggestion, `{state: not_applicable, reason: suggested_question}` for a suggestion, `{state: not_applicable}` for every other turn. The session replacement sets `activeTurn` to null when it still names this turn and, for a `completed` turn, adds `historyTokens` to `history.unsummarisedTokens` and 1 to `history.unsummarisedTurns`.
4. **Retry budget**, inside the chat pipeline's finaliser, which runs under `asyncio.shield` with a 15-second budget (ADR 0057): at most 5 attempts with waits of 25, 50, 100, 200 and 400 ms, and retries stop when either the attempts or that budget run out.
   - `412` on the session: re-read it, reapply the session changes and resubmit.
   - `412` on the turn, or `409` on the trace create: re-read the turn and point-read its trace (the trace ID derives from the turn ID). A trace that exists proves an earlier attempt of this batch committed and only its response was lost (a timeout, for one): return `saved: true`, with no second increment. No trace and a turn in a terminal status means a takeover or a duplicate marked it `turn_abandoned`: stop with `saved: false` and increment `docchat.conversations.finalize_superseded`, because a terminal status never changes. No trace and a turn still `streaming`: resubmit with the turn's fresh ETag.
   - Throttling (`429`, `449`), `408`, timeouts and `5xx`: resubmit within the same attempts.
   - Every attempt failed: raise `ConversationError(turn_save_failed)`. The stream ends with the `error` event `turn_save_failed` (retryable) and no `citations` event; the turn stays `streaming` until its `deadlineAt` and reads as `failed` / `turn_abandoned` after it.
5. **Order on the wire.** A completed answer is finalised as soon as the model stream ends, before the `citations` event, so the session is free when the client re-enables input; follow-ups are attached only after `saved: true`, and the `followups` event is written only after `attach_followups` returns `True`; `done` comes last. `failed` and `cancelled` turns are finalised by the finaliser, and a disconnect after finalisation never changes a `completed` turn. Only a `completed` turn triggers the after-response work (`schedule_post_turn_work`, ADR 0081).
6. **Abandoned turns.** A turn still `streaming` after `deadlineAt` (receipt + `chat.max_turn_seconds` + 30 s, 210 s by default) belongs to a process that died. The next start in its session replaces it with `failed` / `turn_abandoned` inside its own start batch, a duplicate submit does the same, and session reads show it as `failed` with `errorCode` `turn_abandoned` before anything writes it. The chat pipeline never writes `turn_abandoned` on a stream; a turn its own process ends at shutdown is stored with `service_restarting`. `turn_abandoned` is registered in `docchat_core.errors.CODES` with no HTTP status, because it only ever appears as a stored code.
7. **History rule.** Only `completed` turns are ever used as history, as input to the standalone-query step, as summary input or as memory-extraction input. `failed` and `cancelled` turns stay in session reads with their `status` and `errorCode` and never reach a model again.

## Alternatives considered

- **The client reports or saves the outcome.** Lost: the client may be gone, can't be trusted, and can't tell from the end of a response body whether the answer is complete.
- **Any disconnect before `done` cancels the turn.** Lost: a user who closes the tab after the answer finished would lose a complete answer from history and from the summary.
- **Finalise after `citations` or at `done`.** Lost: a question sent as soon as `citations` arrives would meet `409 turn_in_progress`, and a disconnect between `citations` and the write would lose the answer.
- **Separate writes for turn, trace and session.** Lost: a crash between them leaves a finished turn with its session still blocked, history counters out of step or a turn without its trace.
- **Letting a late finaliser overwrite `turn_abandoned`.** Lost: the user and the takeover have already seen the turn as interrupted; changing it would make duplicate handling, replays and the order of history disagree.
- **Judging a `412` on the turn by the turn's status alone, with a `409` on the trace create as the sign of a lost response.** Lost: a batch reports a single failing operation and the turn replace runs first, so after a lost response the turn replace answers `412` and the trace create's `409` is never seen; the turn then already holds this finalisation's own terminal status, which can't be told from a takeover's. Only a finalisation batch creates a trace, so the trace's existence settles it.

## Consequences

- Easier: input is re-enabled on `citations` with the session already free; a duplicate submit meets a stored, final state; history and summaries read only answers that finished.
- Harder: an answer the user saw can still end `turn_save_failed` when Cosmos DB stays unavailable for the whole 15-second budget; the user asks again to have it stored, and the turn reads as abandoned after `deadlineAt`. When the last attempt timed out after committing, the turn is stored even though the stream said otherwise, and the next session read shows it.
- A crash between the end of generation and the commit loses that answer, and the session stays blocked until `deadlineAt` (210 s by default).
- Obligations: tests that a summary lease written between start and finalisation forces a session `412` and that finalisation retries and adds `historyTokens` once; that a batch whose response is lost after the commit returns `saved: true` on the retry, with one increment; that finalisation after a takeover returns `saved: false` and leaves `turn_abandoned`; that a disconnect after `citations` leaves the turn `completed` and in the next turn's history, while a disconnect during generation stores `cancelled` with the partial answer and keeps it out of history, standalone-query input and summary input; that 20 turns get contiguous `seq` 1 to 20 with failed and cancelled turns keeping their numbers; that a turn past its deadline is taken over and reads as `failed` / `turn_abandoned`; that an instance stopped mid-load leaves its sessions usable by `deadlineAt`; and that counting tokens for a 4,000-code-point question with a 100,000-code-point answer never blocks the loop for more than 100 ms.
- Monitoring: `docchat.conversations.turns_finalized` (`status`, `error_code`), `docchat.conversations.abandoned` (`source`: `takeover`, `duplicate`) with an alert at more than 5% of finalised turns over 1 hour (severity 2), `docchat.conversations.finalize_superseded` and `docchat.conversations.store_conflicts`; the runbook for "an answer is still being written" waits for `deadlineAt`, then checks Cosmos DB availability and the conflict counter.
- The web client renders `failed` turns from `errorCode` with a retry that resends the question under a new `clientTurnId`, `cancelled` turns as a stopped partial answer, and feedback controls only on `completed` turns and on `cancelled` turns with an answer.
