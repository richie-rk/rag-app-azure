# ADR 0017: Two-layer API authentication

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 11-api.md, 81-config.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0004, 0006, 0009, 0012, 0014, 0016, 0018, 0019, 0020, 0023, 0091, 0130, 0150

## Context

The API is DocChat's only public entry point and serves every browser-facing operation, so every request must come from a verified Microsoft Entra ID user holding a DocChat role. The product owner chose two layers. Platform authentication (Easy Auth) on the API's App Service rejects anonymous and foreign traffic before it reaches the container: it uses the Entra provider with the tenant's v2 issuer, answers `401` and never a redirect, accepts the API as audience and the web client (plus the test client in `dev` and `load`, ADR 0019) as client applications, accepts only the tenant listed in `WEBSITE_AUTH_AAD_ALLOWED_TENANTS`, and excludes no path, because App Service health checks work through it. The API then validates every token again itself, so it never depends on a header it can't verify and behaves the same locally, in tests and in Azure.

The in-app check covers the signature against the tenant's signing keys, the issuer, the audience, expiry and not-before within 60 seconds of clock skew, the tenant, the authorised party, the `access_as_user` scope, and a `roles` claim holding `User` or `Admin`. A valid token with neither role gets `403`, so the web client can tell a person without access from an expired session. Identity comes only from the validated claims, never from `X-MS-*` headers or request fields. The signing keys are fetched asynchronously and cached, because no blocking call may run on the event loop, and refreshed when a token names an unknown key. `GET /healthz` is the only route exempt from in-app validation (ADR 0023).

Vendor facts that bound the choice (Microsoft Learn and PyPI, confirmed 2026-10-14, unless dated otherwise):

- v2 access tokens: `aud` is the API's client ID; `iss` is `https://login.microsoftonline.com/{tid}/v2.0` and must match exactly for a single tenant; `azp` is the client's `appId`; `scp` is a space-separated string; `roles` is an array; `oid` is an immutable GUID; `tid` and `oid` need the `profile` scope; `ver` is `2.0`; the header carries `kid` only. The single-tenant key set is `https://login.microsoftonline.com/{tenantId}/discovery/v2.0/keys`.
- Signing keys: cache by `kid` for 24 hours, refresh at startup, hourly and on an unknown `kid`, but fetch on demand at most every 5 minutes; keys can roll at once in an emergency. Access tokens live a random 60 to 90 minutes.
- Easy Auth (`Microsoft.Web/sites/config` `authsettingsV2`, latest GA API 2025-03-01): `Return401` is Microsoft's recommended action for APIs; `allowedApplications` checks `appid` or `azp`; `WEBSITE_AUTH_AAD_ALLOWED_TENANTS` checks `tid` (up to 10 tenants); failed built-in checks answer `403`; on Linux the module is a separate container that every request passes through; health checks work through it with no setting; a bearer-only API with `Return401` needs no client secret, and without web redirect URIs or implicit grant `/.auth/login/aad` can't complete; `runtimeVersion '~1'` always runs the latest middleware.
- Global Administrators bypass "assignment required", so only the in-app `roles` check stops one who holds no role.
- PyJWT's `PyJWKClient` offers only synchronous methods (`fetch_data`, `get_jwk_set`, `get_signing_key`, `get_signing_key_from_jwt`) and keeps a key set for `lifespan` 300 seconds by default (PyJWT documentation, checked 2026-10-18).

## Decision

1. **Layer 1: platform authentication.** `Microsoft.Web/sites/config@2025-03-01`, name `authsettingsV2`, on the API's App Service: `platform.enabled: true`, `platform.runtimeVersion: '~1'`, no `configFilePath`; `globalValidation.requireAuthentication: true`, `unauthenticatedClientAction: 'Return401'`, no `redirectToProvider`, `excludedPaths: []`; `identityProviders.azureActiveDirectory.enabled: true` with `registration.openIdIssuer: 'https://login.microsoftonline.com/<tenantId>/v2.0'`, `registration.clientId` = the API's `appId` and no client-secret or certificate setting, `login.disableWWWAuthenticate: false`, `login.loginParameters: []`, `validation.allowedAudiences: ['<API appId>']`, `validation.defaultAuthorizationPolicy.allowedApplications: ['<web appId>']` in `prod` and `['<web appId>', '<test appId>']` in `dev` and `load`, no `allowedPrincipals` or `jwtClaimChecks`, and `isAutoProvisioned` never read or written; no other identity provider is declared; `login.tokenStore.enabled: false`, `login.preserveUrlFragmentsForLogins: false`, `login.allowedExternalRedirectUrls: []`, no `routes`, `cookieExpiration` or `nonce`; `httpSettings.requireHttps: true`, `httpSettings.routes.apiPrefix: '/.auth'`, `httpSettings.forwardProxy.convention: 'NoProxy'`. App setting `WEBSITE_AUTH_AAD_ALLOWED_TENANTS` = the tenant ID (one lowercase GUID). The platform answers `401` with `WWW-Authenticate: Bearer` when a token is missing or invalid and `403` when the `azp` or tenant check fails; neither response carries a problem body.
2. **Layer 2: in-app validation.** `docchat_core.auth.TokenValidator.validate(authorization_header) -> Principal` runs on every request except `GET /healthz`, in this order; the first failure wins:

   | Step | Check | Failure |
   |---|---|---|
   | 1 | Exactly one `Authorization` header, scheme `Bearer` (case-insensitive), one token of 1 to 16,384 characters with three dot-separated parts | `401 authentication_required` when the header is absent or the scheme isn't `Bearer`; otherwise `401 invalid_token` |
   | 2 | Unverified JOSE header: `alg` exactly `RS256`, `kid` of 1 to 128 characters, `typ` absent or `JWT` | `401 invalid_token` (`none`, `HS*`, `PS*` and `ES*` stop here, before any key lookup) |
   | 3 | The key for `kid` from the signing-key cache (item 3) | `401 invalid_token`; `503 authentication_unavailable` when no valid key set exists |
   | 4 | `jwt.decode` with `algorithms=['RS256']`, `audience=<API appId>`, `issuer='https://login.microsoftonline.com/<tenantId>/v2.0'`, `leeway=60` (seconds), `options={'require': ['exp', 'nbf', 'iat', 'iss', 'aud', 'sub', 'oid', 'tid', 'azp', 'scp', 'ver'], 'strict_aud': True}` and every `verify_*` option true | `401 invalid_token` |
   | 5 | `ver` is `2.0` | `401 invalid_token` |
   | 6 | `tid` equals `DOCCHAT_AUTH_TENANT_ID` | `401 invalid_token` |
   | 7 | `azp` is in the allowed client set (item 5) | `401 invalid_token` |
   | 8 | `scp` is a string whose space-separated values include `access_as_user` | `401 invalid_token` |
   | 9 | `oid` parses as a UUID | `401 invalid_token` |
   | 10 | `roles`, when present, is an array of strings, and it contains `User` or `Admin` | `401 invalid_token` when malformed; `403 role_not_assigned` when neither role is present or the claim is absent |

   Decoding is CPU work of well under 1 ms and runs on the event loop. Each failure records one `reason` from a closed set (`missing_header`, `bad_scheme`, `duplicate_header`, `token_too_long`, `malformed`, `bad_alg`, `missing_kid`, `unknown_kid`, `keys_unavailable`, `bad_signature`, `expired`, `not_yet_valid`, `bad_iat`, `bad_issuer`, `bad_audience`, `missing_claim`, `bad_version`, `bad_tenant`, `bad_client`, `missing_scope`, `bad_oid`, `bad_roles`, `no_role`); nothing else from a failed token (claims, header, the token itself) is logged except the `azp` once step 4 has passed.
3. **Signing-key cache.** `EntraSigningKeyProvider` fetches `https://login.microsoftonline.com/<tenantId>/discovery/v2.0/keys`, the URL built only from `DOCCHAT_AUTH_TENANT_ID`, with one `httpx.AsyncClient` created at startup and closed at shutdown (`timeout=httpx.Timeout(8.0, connect=4.0)`, `follow_redirects=False`, `limits=httpx.Limits(max_connections=4)`, TLS verification on); each fetch, body included, runs under `asyncio.timeout(8.0)`, so no fetch holds the single-flight lock for more than 8 s. A response is used only when it is `200`, at most 1 MiB and JSON with a `keys` array; each key with `kty` `RSA`, a `kid` and `use` absent or `sig` becomes a public key through `jwt.PyJWK(key, algorithm='RS256')`, keys that fail to parse are skipped, at most 100 are kept, and a response with no usable key counts as a failed fetch. A key set is valid for 24 hours after the fetch that produced it. A background task started at startup (not awaited) fetches at once and then every 3,600 seconds; a failed refresh keeps the current set until it is 24 hours old. An unknown `kid` triggers one on-demand fetch when the last on-demand fetch started at least 300 seconds ago (30 seconds while no valid set exists); concurrent requests await the same fetch under one `asyncio.Lock`; a `kid` still unknown fails with `401 invalid_token`. With no valid set and a failed fetch, requests get `503 authentication_unavailable` with `retryAfterSeconds: 30` and the same `Retry-After`. Tests inject any `SigningKeyProvider` through a seam; no setting changes the key source.
4. **Status mapping.** `401 authentication_required`: no `Authorization` header, or a scheme other than `Bearer`. `401 invalid_token`: any other failure of steps 1 to 9, an unknown `kid` after refresh, a malformed `roles` claim. `403 role_not_assigned`: a valid token whose `roles` holds neither `User` nor `Admin`, or no `roles` claim. `503 authentication_unavailable`: no valid key set and the fetch failed. Every in-app `401` carries `WWW-Authenticate: Bearer realm="docchat"`, plus `error="invalid_token"` for `invalid_token`. A token for another tenant, client or scope is `401` in the app, because the API can't accept it as a DocChat user token at all; `403` is kept for authenticated callers without permission (ADR 0020).
5. **Allowed clients and startup checks.** The allowed `azp` set is `{DOCCHAT_AUTH_WEB_CLIENT_ID}`, plus `DOCCHAT_AUTH_TEST_CLIENT_ID` only when that setting is not empty and `DOCCHAT_CORE_ENVIRONMENT` is `dev`, `load` or `local` (`local` is a developer machine and follows `dev`'s non-production identity rules). Settings validation stops the process before it serves when `DOCCHAT_CORE_ENVIRONMENT` is `prod` and `DOCCHAT_AUTH_TEST_CLIENT_ID` is not empty, when the API, web and test client IDs aren't distinct, or when `DOCCHAT_CORE_ENVIRONMENT` is `local` and `WEBSITE_SITE_NAME` or `WEBSITE_INSTANCE_ID` is set, so local mode can never run in Azure (ADR 0019).
6. **The `Principal`.** A frozen Pydantic model that only `TokenValidator` builds: `oid` (UUID; its lowercase hyphenated text is every Cosmos DB partition key value), `tid` and `azp` (UUIDs), `client` (`web` or `test`, from `azp`), `roles` (frozen set of `Admin` and `User`; other values dropped), `is_admin` (`Admin` in `roles`), `display_name` (from `name`: Unicode NFC, every code point of category Cc, Cf, Cs, Co or Cn removed, trimmed, cut to 256 characters, `''` when absent) and `email` (the `email` claim, else a `preferred_username` with exactly one `@`, no whitespace and no `#`; trimmed, at most 320 characters; else `''`). `display_name` and `email` are display data for the user's row only; no decision and no log uses them, and the raw token is never kept.
7. **Identity only from validated claims.** The API never reads `X-MS-CLIENT-PRINCIPAL`, `X-MS-CLIENT-PRINCIPAL-ID`, `X-MS-CLIENT-PRINCIPAL-NAME`, `X-MS-CLIENT-PRINCIPAL-IDP`, `X-MS-TOKEN-*` or any other `X-MS-*` header, nor any user identifier from a path, query, body or cursor, to decide who the caller is. A unit test fails when `x-ms-client-principal` or `x-ms-token` (case-insensitive) appears in `apps/api` or `packages/core` outside tests.
8. **Position in the request.** Platform authentication, token validation and the role check are steps 1 to 3 of every route's check order (ADR 0020). The `/v1` route class `DocChatRoute` runs steps 2 and 3 before FastAPI reads the body (ADR 0012), so a request without a token gets `401`, never `413`, `415` or `422`. An unknown path answers `404 route_not_found` from routing; a deployed environment answers it with the platform's `401` first.
9. **Settings and libraries.** `DOCCHAT_AUTH_TENANT_ID`, `DOCCHAT_AUTH_API_CLIENT_ID`, `DOCCHAT_AUTH_WEB_CLIENT_ID`, `DOCCHAT_AUTH_TEST_CLIENT_ID` (empty in `prod`) and `DOCCHAT_CORE_ENVIRONMENT` are read once at startup by `AuthSettings` and `CoreSettings`; an invalid value stops the process before it serves. None is a secret. Libraries, pinned exactly in `uv.lock`: PyJWT 2.15.1 installed as `pyjwt[crypto]`, cryptography 50.0.2, httpx 0.28.1 (confirmed on PyPI 2026-10-14; httpx's Beta classifier is recorded in ADR 0009).
10. **Telemetry and alerts.** Spans `docchat.auth.validate_token` (`docchat.auth.outcome` `ok`, `invalid`, `no_role` or `unavailable`; `docchat.auth.reason`; `docchat.auth.client` `web`, `test` or `unknown`) and `docchat.auth.fetch_signing_keys` (`docchat.auth.trigger` `startup`, `scheduled` or `unknown_kid`; outcome; key count; HTTP status); metrics `docchat.auth.validations` (`outcome`, `reason`, `client`), `docchat.auth.signing_key_fetches` (`trigger`, `outcome`) and the gauge `docchat.auth.signing_key_age` (seconds since the last successful fetch); custom event `signing_keys_refresh_failed` and the warning log record `signing_keys_fetch_failed` (status code, error type). Alerts: A35 `signing-key-fetch-failures` (severity 2), at least 3 failed key fetches in 60 minutes; A36 `signing-key-age` (severity 2), key age above 14,400 seconds (4 hours) on any instance; A37 `role-not-assigned` (severity 3), more than 30 `role_not_assigned` refusals in 15 minutes; A38 `invalid-token-share` (severity 3), `invalid` above 5% of at least 100 validations in 15 minutes. A35, A36 and A38 follow the incident runbook (R07), A37 the first-admins runbook (R13).

## Alternatives considered

- **Platform authentication alone, trusting the `X-MS-CLIENT-PRINCIPAL*` headers it injects.** The API would trust headers it can't verify, behave differently locally and in tests, and one platform misconfiguration (an excluded path, `AllowAnonymous`) would open every route.
- **In-app validation alone.** Anonymous traffic would reach the API's code and CPU, and a request must be refused as early as possible.
- **PyJWT's `PyJWKClient` for the keys.** Its methods are synchronous, so a fetch inside a request would block the event loop, and its 300-second default set lifetime would refetch keys about 288 times a day per process; an async fetch with Microsoft's 24-hour lifetime and a single-flight lock meets both needs.
- **Discovering `jwks_uri` from the OpenID metadata document on each refresh.** One more round trip and one more failure point; the single-tenant v2 key-set URL is documented.
- **Accepting every algorithm the key allows.** Only RSA keys are taken from the key set, so anything but `RS256` adds algorithm-confusion risk (`none`, or `HS256` signed with the public key) and no capability.
- **`401` for a valid token without a role.** The web client must tell a person without access from an expired session, to show Not assigned without signing the user in again.
- **Accepting v1 tokens as well.** The API requests v2 tokens (ADR 0016); v1 would add a second issuer and other claim names to validate.

## Consequences

- Every token is checked twice: the platform drops anonymous and foreign traffic before the container, and the app's own check keeps the API safe if platform authentication is ever misconfigured, with identical behaviour locally, in tests and in Azure.
- Each request pays one RS256 verification (well under 1 ms); each process fetches the key set at startup and every 60 minutes.
- A held key set survives a key-endpoint outage of up to 24 hours. A process that starts during an outage answers `503 authentication_unavailable` (retry after 30 s) until its first fetch succeeds. After an emergency key roll, tokens signed with the new key work within 300 seconds per instance without action.
- Platform `401` and `403` carry no problem body: the web client treats a bare `401` as an expired token and retries once (ADR 0018), and a bare `403` as an HTTP failure shown with the request's trace ID, never as Not assigned (ADR 0091). A deployed foreign-tenant token gets the platform's `403`, so deployed tests expect `403` while in-app tests assert the app's `401`; an anonymous deployed `/healthz` gets the platform's `401`.
- Removing a user's app role takes effect when their access token expires, 60 to 90 minutes after issue; the urgent access-removal runbook in 86-operations.md gives the order: memberships first, then groups and assignments, then disabling the account and revoking its sessions.
- `runtimeVersion '~1'` follows the platform's latest middleware, so a platform change could alter behaviour; the deployed smoke suite after every `dev` deploy (anonymous `401`, a disallowed `azp` answered `403`, an ROPC token answered `200`) detects it.
- Obligations: the unit tests of every step and reason (algorithms, ±60-second skew, each required claim, `aud` arrays, the test client per environment, the single-flight fetch on a fake clock, 1 MiB and failed-fetch handling, a forged `X-MS-CLIENT-PRINCIPAL-ID`); the deployed checks of both layers; alerts A35 to A38; the signing-key runbook (confirm the API reaches `login.microsoftonline.com` over its default outbound path, where route-all is off; a restart forces a fetch).
