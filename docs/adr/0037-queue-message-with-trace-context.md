# ADR 0037: Queue message with trace context

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 14-ingestion.md, 80-data-model.md, 84-testing.md, 85-observability.md
- **Related ADRs:** 0012, 0014, 0034, 0036, 0088, 0137, 0144

## Context

Every user action is one trace, end to end: the browser call, the API request, the queue message, the orchestration and every activity, with W3C trace context carried inside the queue message, so an error a user reports can be matched to every step that served it. The API starts ingestion only through a queue, and the queue message identifies the run; everything else about the run lives in the SQL ledger (ADR 0034). The long-lived singleton dispatcher, not the starter that received the message, starts each document's sub-orchestration, so the context reaches document activities only if the design passes it on explicitly.

The vendor facts bound the choice. A W3C `traceparent` of version `00` is 55 characters (2 hex version, 32 hex trace ID, 16 hex parent ID and 2 hex flags, joined by `-`); the Recommendation asks participants to propagate at least 512 characters of `tracestate`, at most 32 list-members, and to truncate only whole entries, those longer than 128 characters first and then from the end. A Storage queue message holds up to 64 KiB and lives 7 days by default; the Functions queue trigger expects base64 by default and moves a message to `<queue>-poison` after 5 dequeues. Durable Functions' own distributed tracing (`distributedTracingEnabled` with version V2) needs the DurableTask extension 3.2.0 or later for non-.NET apps, writes its telemetry from the host, outside the app's scrubbing processors (ADR 0014), and correlates along the orchestration tree, whose root is the dispatcher. The Python worker exports to Azure Monitor itself only when `PYTHON_APPLICATIONINSIGHTS_ENABLE_TELEMETRY` is set, and its auto-configuration bypasses the scrubbing processors, so ADR 0137 keeps it unset. Orchestrator code replays from the start on every new event, so it must not create spans.

## Decision

1. **Message.** Queue `ingestion-requests` on the data storage account, poison queue `ingestion-requests-poison` (both declared in Bicep). The only message is `IngestionQueueMessage` (Pydantic, `extra="forbid"`): `runId` (UUID, required); `traceparent` (string, required, matching `^00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}$`); `tracestate` (string, at most 512 characters, omitted when empty). It never carries a name, path, index name, content or credential: the SQL ledger holds everything else.
2. **Encoding and lifetime.** The JSON object as UTF-8, then base64: the API's `QueueClient` uses `TextBase64EncodePolicy`, and `host.json` sets the trigger's `messageEncoding` to `base64`. Sent with `time_to_live` 86,400 seconds and no visibility delay; after a day a message is worthless, because the sweep finds every queued item anyway.
3. **Sender.** Every API operation that creates a run (`adminSubmitUploads`, `adminReingestDocument`, `adminDeleteDocument`, `adminCreateIndex`, `adminStartReingest`, `adminDeleteIndex`) injects the current context with `TraceContextTextMapPropagator().inject`, so the message's parent is a span of the request's trace, which continues the browser's `traceparent` (ADR 0088). It writes the same values to the new run's `ingestion_runs.traceparent` (`VARCHAR(55)`, `CHECK (traceparent IS NULL OR LEN(traceparent) = 55)`) and `tracestate` (`VARCHAR(512)`) in the run-creating transaction, and after commit sends one message with the same values. A `tracestate` longer than 512 characters is cut by the W3C rule before it is stored: whole list-members are removed, every member longer than 128 characters first, then members from the end, until the header is at most 512 characters. A failed send, after the client's 3 retries, emits `ingestion_queue_send_failed` (`runId` only) and the operation still answers `202`: the next wake finds the queued items (ADR 0036).
4. **Starter.** `ingestion_queue_starter` decodes `msg.get_body()` as UTF-8 JSON into `IngestionQueueMessage`; an invalid message emits `ingestion_message_invalid` (`messageId`) and returns normally, so the message is deleted. Otherwise it extracts the context with `TraceContextTextMapPropagator().extract(...)` and runs inside span `docchat.ingestion.queue_message` (kind `CONSUMER`, child of the extracted context) with attributes `docchat.run_id`, `docchat.ingestion.dequeue_count` and `docchat.ingestion.dispatcher_started`, then calls `ensure_dispatcher` and raises `run_queued` with `{"runId": ...}`, ignoring not-found (404) and completed (410) answers. A Durable client failure is logged once (`job_failed`) and re-raised as `DispatcherUnavailableError` with no cause attached; the message reappears after about 10 minutes and moves to the poison queue after 5 dequeues, and nothing is lost, because the sweep covers the run.
5. **Dispatcher.** Orchestrator functions create no spans. The dispatcher's activities `sweep_ingestion_state` and `claim_ingestion_items` start root spans `docchat.ingestion.dispatcher.sweep` and `docchat.ingestion.dispatcher.claim`, each with one span link per run it touches, built from the run's stored `traceparent`. The claim reads each claimed run's `traceparent` and `tracestate`, and the dispatcher copies them into the sub-orchestration's `ItemInput` (`{itemId, claimNumber, operation, runId, traceparent, tracestate, retry, settings}`).
6. **Activities.** Every activity of an item runs inside span `docchat.ingestion.activity` (kind `INTERNAL`, attribute `docchat.activity_name`, plus the run, item, document, version, chunk-set and physical-index IDs, attempts, outcome and error code) whose parent is the remote context extracted from `ItemInput`, so the request, the message and every activity of every document of the run share one trace, with Azure SDK and `httpx` spans nested below. Index-lifecycle runs follow the same rule. Runs created without a request (the sweep's `maintenance` runs and runs created by `docchat-ops`) store null, and each of their items starts a new trace.
7. **Host settings.** `host.json` sets `extensions.durableTask.tracing` to `{"distributedTracingEnabled": false, "traceInputsAndOutputs": false, "traceReplayEvents": false}` and `logging.applicationInsights` to `{"samplingSettings": {"isEnabled": false}, "enableDependencyTracking": false}`; `PYTHON_APPLICATIONINSIGHTS_ENABLE_TELEMETRY` stays unset; `configure_telemetry` sets `OTEL_PROPAGATORS=tracecontext` in both apps, so baggage is never read.
8. **Sampling.** Both apps use the distro's percentage sampler `microsoft.fixed_percentage` at `DOCCHAT_TELEMETRY_SAMPLING_RATIO` (from the environment-file field `telemetrySamplingRatio`, 0.1 to 1.0, default 1.0), which decides from the trace ID and ignores the parent's sampled flag, so a trace is kept or dropped whole across the API and ingestion.

## Alternatives considered

- **The run ID only, with the starter reading the context from the run row.** The starter would open a SQL connection for every message, which it otherwise never needs, and the trace context belongs inside the message.
- **The context only in the message.** The dispatcher, not the starter, starts the document work, and a lost or duplicated message would lose or repeat the link; storing the context on the run makes it available to every claim of every item, whichever message or wake triggered it.
- **Durable Functions distributed tracing V2.** Host-written telemetry outside the scrubbing processors, a correlation rooted at the long-lived dispatcher rather than the request, and an extension-version requirement; the app's own spans already give the one trace the product needs.
- **Parenting the dispatcher's sweep and claim spans under a run's trace.** One sweep or claim serves many runs and a span has one parent; links connect it to each run without merging unrelated traces.
- **The Functions worker's automatic export (`PYTHON_APPLICATIONINSIGHTS_ENABLE_TELEMETRY=true`).** Its auto-configuration bypasses the scrubbing processors (ADR 0137).
- **Rejecting or dropping an oversized `tracestate`.** Rejecting would fail an upload over a header the product never reads; dropping it whole discards entries the standard asks a participant to keep. Whole-entry truncation is the standard's own rule and keeps the 512-character column and model limit.

## Consequences

- An admin's reference ID (the problem's `correlationId`, which is the trace ID, ADR 0012) leads to the browser call, the API request, the starter and every activity of every document of the run in one Application Insights operation.
- One run is one trace, so a 200-document run produces a trace of thousands of spans; sampling by trace ID keeps or drops it whole. Dispatcher spans live in their own traces and reach a run only through links, so a query for what the dispatcher did for one run follows links.
- The message is about 120 bytes of JSON (160 after base64), and at most about 650 bytes (about 870 after base64) with a full `tracestate`, far below the 64 KiB limit.
- `tracestate` is opaque client-supplied text of at most 512 characters, stored in SQL and forwarded to ingestion; it is never added as a span or log attribute and never shown. The browser never sends one (ADR 0088), so only a non-browser caller can supply it.
- Obligations: the message model with `extra="forbid"`, the two run columns, the truncation helper, the propagator calls in the API, the starter, the claim and the activity wrapper, and the `host.json` tracing block. Tests: a message survives the round trip through `TextBase64EncodePolicy` and the trigger's base64 decoding, and a malformed message is dropped and logged; an invalid message is dropped with `ingestion_message_invalid`, and a Durable client failure is logged once and raised with no cause; a `tracestate` longer than 512 characters that holds one member over 128 characters is cut to whole members within 512 characters, that long member first; an upload request's trace contains the starter span and every activity span of its run, the message carries `traceparent` and `tracestate`, and dispatcher spans are roots linked to the run; sampling keeps or drops by trace ID whatever the parent's flag; the stage-1 acceptance shows starter and activity spans under the run's trace ID.
