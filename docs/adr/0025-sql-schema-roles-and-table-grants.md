# ADR 0025: SQL schema, roles and table grants

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 80-data-model.md, 82-security.md, 83-infrastructure.md, 84-testing.md
- **Related ADRs:** 0020, 0021, 0024, 0026, 0027, 0028, 0029, 0033, 0054, 0108, 0113, 0115, 0116, 0125, 0129

## Context

One Azure SQL database holds configuration, access and the ingestion ledger. App identities read and write data but never change the schema; Alembic migrations run under the pipeline's deploy identity. Each app's contained user has a bounded scope: the API reads and writes application tables only, and the ingestion app reads and writes the document, index and ingestion tables and reads `ops_config` and `ingestion_methods`. Operators reach SQL only through just-in-time group membership (ADR 0024), and SQL runs with Microsoft Entra-only authentication. The tables have two owners, the access and configuration tables and the ingestion ledger, and four writers besides the migrations: the two apps and the operators' `config` and `user_data` access levels, each needing a narrow set of rights.

Three needs bound the design:

- A statement an attacker manages to shape must reach as little as possible, so each principal holds exactly the verbs its code uses on the tables it uses. Every value is a bound parameter, and the grants are the second line behind that rule.
- No SQL password may exist anywhere, in an image, a data-source file, a settings file or an app setting, because whoever reads it holds the login's rights.
- Every caller must be its own database principal, so the database and its audit can tell callers apart.

Facts that bound the design:

- Microsoft Entra-only authentication disables SQL authentication, the server admin's included. Entra authentication for Azure SQL doesn't use Azure RBAC, so every identity needs a database principal.
- `CREATE USER [name] WITH SID = <binary(16)>, TYPE = E` (a user, service principal or managed identity) or `TYPE = X` (a group) creates a contained user in Azure SQL Database without a directory lookup, so the server needs no Microsoft Graph permission; the ID isn't validated in Entra ID. Microsoft's pages disagree on whether a managed identity's SID is its client ID or its object ID, which a stage-0 test settles (ADR 0125).
- The server's Microsoft Entra administrator, which may be a group whose members inherit it, has every permission in the database without membership of any role.
- The built-in database roles are database-wide: `db_datareader` reads every user table and view, `db_datawriter` inserts, updates and deletes in every user table, `db_ddladmin` runs any DDL and `db_owner` holds `CONTROL DATABASE`. Microsoft advises against making user-defined roles members of built-in roles.
- A schema permission implies the same permission on every object in the schema, tables created later included. Every database user is a member of `public` and inherits what is granted to it on an object where the user has no grant or deny of its own. A table-level `DENY` doesn't take precedence over a column-level `GRANT`.

## Decision

1. **One database, one schema.** Database `docchat` on the environment's Azure SQL server (collation `SQL_Latin1_General_CP1_CI_AS`), every application table in schema `app`: the seven access and configuration tables (`users`, `projects`, `project_members`, `project_indexes`, `user_index_overrides`, `ops_config`, `audit_events`) and the eleven ingestion tables (`ingestion_methods`, `search_indexes`, `physical_indexes`, `documents`, `document_versions`, `chunk_sets`, `served_chunk_sets`, `ingestion_runs`, `ingestion_run_items`, `ingestion_dispatcher_state`, `scan_canaries`). Alembic revisions in `db/migrations/versions/` create every table, constraint, index, database role and grant, and run only under the deploy identity (ADR 0027). No app identity and no operator group can change the schema.
2. **Principals.** No SQL login exists: the server runs Microsoft Entra-only authentication (`azureADOnlyAuthentication: true`, and the Deny policy of ADR 0116 stops anyone re-enabling SQL authentication). The server's Entra administrator is the group `sg-docchat-<env>-sql-admins`, whose only member is the environment's deploy identity; it runs the migrations and the grants step as `dbo` and is no contained user. The grants step, `scripts/deploy/sql_principals.py` (the azd `postprovision` hook, right after the migrations, connection `APP=docchat-grants`), creates exactly five contained users, idempotently, and puts each in its role:

   | Contained user | Created as | Role |
   |---|---|---|
   | `id-docchat-api-<env>` | `CREATE USER [id-docchat-api-<env>] WITH SID = 0x<32 hex>, TYPE = E` (SID source per ADR 0125) | `docchat_api` |
   | `id-docchat-ingest-<env>` | the same form | `docchat_ingestion` |
   | `sg-docchat-<env>-config-operators` | `CREATE USER [sg-docchat-<env>-config-operators] WITH SID = 0x<group object ID bytes>, TYPE = X` | `docchat_config_operator` |
   | `sg-docchat-<env>-conversation-readers` | the same form | `docchat_conversation_reader` |
   | `sg-docchat-<env>-user-data-operators` | the same form | `docchat_user_data_operator` |

   It adds members with `ALTER ROLE <role> ADD MEMBER [<user>]`, removes every member of the five roles that isn't in this set, and re-creates a user whose SID differs from its identity's current ID (an identity re-created under the same name). DDL can't bind parameters, so the script validates each ID as a UUID before any SQL runs, builds the SID literal as `uuid.UUID(<id>).bytes_le.hex()` (equal to SQL Server's `CONVERT(VARBINARY(16), <uniqueidentifier>)`), and takes its statement text from `docchat_core.sql.statements`.
3. **Rights belong to roles, never to users.** The migrations create the five roles with `CREATE ROLE` and grant table-level rights on `app` tables to them and to nothing else: no grant to a contained user or to `public`, none on the schema or the database, no column-level grant other than the two `UPDATE` grants on `document_versions` of rule 4a, and no role holds `ALTER`, `CONTROL`, `REFERENCES`, `EXECUTE` or any DDL right. No contained user and no role is a member of any built-in database role (`db_owner`, `db_ddladmin`, `db_datareader`, `db_datawriter` or any other).
4. **Each table's owner grants on its own tables.** The access area's migrations grant every role's rights on the seven access tables; the ingestion area's migrations grant every role's rights on the eleven ingestion tables, `docchat_config_operator`'s and `docchat_user_data_operator`'s included; the conversations area owns `docchat_conversation_reader` and `docchat_user_data_operator` and no table. The compiled matrix below is the cross-check that the deployed grants test compares with the database (`S` SELECT, `I` INSERT, `U` UPDATE, `U(cols)` UPDATE on the columns of rule 4a only, `D` DELETE, `–` none):

   | Table (owner) | `docchat_api` | `docchat_ingestion` | `docchat_config_operator` | `docchat_conversation_reader` | `docchat_user_data_operator` |
   |---|---|---|---|---|---|
   | `users` (access) | S I U | – | S | – | S D |
   | `projects` (access) | S I U | – | S | – | S |
   | `project_members` (access) | S I D | – | – | – | S D |
   | `project_indexes` (access) | S I U D | – | S | – | S |
   | `user_index_overrides` (access) | S | – | S I U D | – | S D |
   | `ops_config` (access) | S | S | S U | – | S |
   | `audit_events` (access) | I | I | I | I | S I |
   | `ingestion_methods` (ingestion) | S | S | S | – | – |
   | `search_indexes` (ingestion) | S I U | S U | S U | – | S |
   | `physical_indexes` (ingestion) | S I U | S U | S I U | – | – |
   | `documents` (ingestion) | S I U | S U D | S | – | S |
   | `document_versions` (ingestion) | S I U(cols) | S U D | S U(cols) | – | S |
   | `chunk_sets` (ingestion) | S U | S I U | S U | – | – |
   | `served_chunk_sets` (ingestion) | S D | S I U D | S | – | – |
   | `ingestion_runs` (ingestion) | S I | S I U D | S I U | – | S |
   | `ingestion_run_items` (ingestion) | S I U | S I U D | S I U | – | – |
   | `ingestion_dispatcher_state` (ingestion) | – | S U | S | – | – |
   | `scan_canaries` (ingestion) | S | S I U D | S | – | – |

4a. **Column grants on `document_versions`.** A version's scan result decides whether its bytes may be ingested and served, so only `docchat_ingestion` holds table-level `UPDATE` there. `docchat_api` holds `UPDATE (state, reserved_at, uploaded_by, uploaded_via_project_id, committed_at, blob_last_modified, failure_code, failed_at, superseded_at)`, the columns of the reservation's reuse, the commit, the duplicate refusal and the document delete, and sets `scan_required` and `scan_status` only in the reservation's `INSERT`; `docchat_config_operator` holds `UPDATE (state, failure_code, failed_at)`, the columns of `fail-item`'s failure side effect. Neither names a scan column, so an `UPDATE` of `scan_status`, `scan_required`, `scan_time` or `scan_raw_result` by either fails with SQL error 230. SQL Server has no column-level `INSERT` permission, so the `AFTER INSERT` trigger `app.trg_document_versions_scan_insert` fails an insert with error 51010 unless every inserted row has `scan_status` `awaiting` with `scan_required = 1`, or `not_required` with `scan_required = 0`, and a null `scan_time`, `scan_raw_result`, `converter_version`, `converted_sha256` and `document_pdf_status`. Only `docchat_ingestion` therefore sets a scan result or a rendition column (ADR 0152), and neither column grant names a rendition column. The API's insert still chooses `scan_required`, a residual risk bounded by the API's own write right on every stored source in `documents`.
5. **Every narrow or unusual right has one named use.**
   - `docchat_api`: `INSERT` alone on `audit_events`, which no app operation reads; `SELECT` alone on `ops_config` and `user_index_overrides`, which only operators change; `U` on `physical_indexes` retires a `failed` index's leftover building index (`adminStartReingest`); `U` on `chunk_sets` and `D` on `served_chunk_sets` serve the delete flows; no right on `ingestion_dispatcher_state`, which nothing in the API reads; `SELECT` on `projects`, `project_indexes` and `users` also serves the upload and delete checks and the uploader names of the admin document views.
   - `docchat_ingestion`: among the access tables only `SELECT` on `ops_config` and `INSERT` on `audit_events`; `D` on `documents` and `document_versions` removes the orphan rows of stale uploads; `D` on `ingestion_runs` and `ingestion_run_items` is the 180-day retention; `D` on `scan_canaries` deletes canary rows 90 days after `written_at`.
   - `docchat_config_operator`: `S U` on `ops_config` (`docchat-ops config set` and `reset`), `S I U D` on `user_index_overrides` (`docchat-ops override`), reads of `users`, `projects` and `project_indexes` to validate overrides; its `I` and `U` rights on the ingestion tables serve only `docchat-ops reindex` and `docchat-ops ingestion` (`requeue-item`, `fail-item`, `cancel-run`, `abandon-rebuild`, `set-deployments`), `fail-item` needing `U` on `chunk_sets` and the column `UPDATE` of rule 4a on `document_versions` for its failure side effects; it reads `scan_canaries` for `docchat-ops ingestion status`; it holds `DELETE` on no ingestion table.
   - `docchat_conversation_reader`: `INSERT` on `audit_events` alone, for the `conversation.read` row; its reads are Cosmos DB reads (ADR 0024).
   - `docchat_user_data_operator`: `SELECT` on all seven access tables and on the four ingestion tables that hold actor columns (`search_indexes`, `documents`, `document_versions`, `ingestion_runs`), for the export; `DELETE` on `users`, `project_members` and `user_index_overrides`, for the deletion; `INSERT` on `audit_events`, for `user_data.exported`, `user_data.deleted` and `document.traces_redacted` (ADR 0033).
6. **Cascades and references.** The API deletes a mapping whose overrides cascade (`FK_user_index_overrides_mapping`, `ON DELETE CASCADE`) without holding `DELETE` on `user_index_overrides`. The integration test "cascade under the API role" proves that SQL Server needs no right on the referencing table for the cascading action; if that test ever fails, the migration grants `DELETE` on `app.user_index_overrides` to `docchat_api` and nothing else changes. Foreign-key checks need no right on the referenced table, so the ingestion identity writes rows that reference `app.projects`.
7. **Actor columns.** The actor columns (`created_by`, `updated_by`, `archived_by`, `granted_by`, `set_by` on the access tables; `created_by`, `updated_by`, `deleted_by`, `uploaded_by`, `requested_by` on the ingestion tables) hold Entra object IDs with no foreign key to `app.users`, so they outlive a deleted user, and each carries `info={"actor": True}` in the SQLAlchemy metadata, from which the export finds every actor reference to a user. `audit_events.actor_object_id` and `subject_object_id` aren't marked; the export reads them directly.
8. **Statements.** Every statement binds its values as parameters (SQLAlchemy 2.1 Core; Ruff S608 fails the build on string-built SQL; ADR 0026 and ADR 0129). The literal `1` in `is_default = 1` predicates stays in the statement text, because SQL Server can't match a filtered index to a parameter.
9. **Checks.** The matrix is checked at three levels. Integration tests run in the SQL Server container with one test-only SQL login mapped to each role and prove the denials and the named uses of rule 5 and the cascade of rule 6. A unit test proves the SID conversion for five known UUID and SID pairs and the rejection of a non-UUID before any SQL runs. A deployed test in `dev` reads `sys.database_permissions` and `sys.database_role_members` and fails on any difference from the matrix and the principal table: a missing or extra right of a role (a column grant included, compared by column name), a right on an `app` object held by any other principal, or a member of a built-in database role.

## Alternatives considered

- **The built-in roles `db_datareader` and `db_datawriter` for the app identities.** They grant reads and writes on every user table, present and future: the API could update and delete audit rows, change ops config and overrides and read the dispatcher's state, so one injected statement would reach every table. Table-level grants give each identity the verbs its code uses.
- **Schema-level grants on `app` (`GRANT SELECT, INSERT, UPDATE ON SCHEMA::app`).** A schema permission covers every table, including tables added later, so a new table would open to every role without review, and append-only `audit_events` would need a `DENY` exception. Per-table grants make each new right a reviewed line in its owner's migration.
- **Rights granted to each contained user directly.** Re-creating a user, which a re-created identity requires because its SID changes, would drop its rights, and the grants would name environment-specific users. With roles the grants step re-creates the user and adds it to its role, and the matrix never mentions a user.
- **One schema per owning area with schema-level grants.** The API still needs different verbs on different ingestion tables (`INSERT` on `documents`, no right on `ingestion_dispatcher_state`), so per-table grants would remain, and one schema `app` for every application table keeps one namespace for the migrations, the grants and their checks.
- **Column-level grants on every table.** They would narrow `UPDATE` further, but every column added in an expand revision would become a permission change, and a table-level `DENY` doesn't override a column-level `GRANT`, which makes the effective rights hard to read. The statements in `docchat_core.sql.statements` already determine which columns each operation writes. `document_versions` is the one exception (rule 4a), because a forged scan result would let unscanned bytes reach every reader, and there the statement catalogue alone wouldn't stop an operator's own SQL session.
- **A `DENY UPDATE` on the scan columns with table-level `UPDATE` kept.** A table-level `GRANT` with a column `DENY` gives the same effective rights, but the precedence rules between table and column permissions make it easy to misread, and a later table-level `GRANT` in a revision would be reviewed as harmless; a column `GRANT` lists exactly what each role may change.
- **Moving `scan_required` and `scan_status` to a table of their own.** It would isolate the scan result without column grants, but every scan-gate and sweep query would join on it, and a version's state would be split across two rows.
- **Stored procedures with `EXECUTE` only.** The data-access layer is SQLAlchemy Core with bound parameters (ADR 0026); procedures would put access logic in a second language with its own versioning and test path, while the table-level matrix already confines each identity.
- **Migrations run by each app at start-up.** The app identities would need DDL rights, which this design denies them, and two instances starting together would race on the same revision.
- **Standing operator access through the admin group or SQL logins.** People reach SQL only through just-in-time group membership (ADR 0024), and Entra-only authentication leaves no SQL login to give them.

## Consequences

- A statement running as `docchat_api`, an injected one included, can't change the schema, can't update or delete an audit row, can't write ops config or overrides, can't set or change a version's scan result, and can't read the dispatcher's state; a config operator's own SQL session can't change a scan result either; one running as `docchat_ingestion` can't read or write users, projects, memberships, mappings or overrides.
- No SQL password exists anywhere: the apps' tokens come from their managed identities and operators' tokens from their own sign-in.
- Re-creating an identity changes its SID; the next grants step re-creates the user with the new SID, and the role keeps its rights.
- Operators hold no SQL right outside a just-in-time window, and a conversation reader can only insert its own `conversation.read` row in SQL (ADR 0024).
- The deploy identity holds every right through the admin group; ADR 0115 bounds it and the privileged SQL audit records its statements (ADR 0108).
- Every new table or right needs its owner's migration and a matching matrix row: the deployed grants test fails until both agree, and a role that lacks a right its code needs fails the integration tests that log in as that role.
- Risk: a revision that revokes a right breaks a running release that still uses it, and `scripts/ci/check_migrations.py` doesn't parse `REVOKE`, so the review of a revision that narrows a role confirms that no deployed release still needs the right (the expand and contract rule of ADR 0027 applied to grants).
- Obligations: the access-table integration tests (`docchat_api` denied `SELECT`, `UPDATE` and `DELETE` on `audit_events` and `INSERT` or `UPDATE` on `ops_config` and `user_index_overrides`; `docchat_ingestion` limited to `SELECT` on `ops_config` and `INSERT` on `audit_events` among the access tables; `docchat_config_operator` denied `INSERT` and `DELETE` on `ops_config` and `DELETE` on `users`, allowed `UPDATE` on `ops_config`; `docchat_user_data_operator` allowed `SELECT` and denied `UPDATE` on `project_indexes` and `ops_config`, and able to read every marked actor column; the cascade under the API role; no app identity or operator group in `db_datareader`, `db_datawriter` or `db_owner`); the ingestion-table integration test (every `docchat-ops reindex` and `docchat-ops ingestion` command succeeds as `docchat_config_operator` while `DELETE` on every ingestion table is denied; `docchat_user_data_operator` reads only `search_indexes`, `documents`, `document_versions` and `ingestion_runs` among the ingestion tables; `docchat_api` updates `physical_indexes` and can't read `ingestion_dispatcher_state`; `docchat_api` and `docchat_config_operator` update each column of their rule 4a grant on `document_versions` and get error 230 on `scan_status`, `scan_required` and `scan_time`); the scan-insert trigger integration test (an insert carrying a scan result fails with error 51010 and leaves no row); the unit test of `sql_principals.py`; the deployed grants test; the deployed test that a SQL user-name-and-password login fails while the deploy identity's token login succeeds.
