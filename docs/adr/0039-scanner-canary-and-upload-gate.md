# ADR 0039: Scanner canary and upload gate

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 10-web-client.md, 11-api.md, 14-ingestion.md, 80-data-model.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, 86-operations.md, 90-build-order.md, CONTEXT.md
- **Related ADRs:** 0012, 0032, 0038, 0093, 0117, 0138, 0142

## Context

While Defender for Storage malware scanning is on, every uploaded version waits until its scan is clean and fails as `scan_unavailable` when no usable result arrives within `ingestion.scan_wait_minutes` (240), as ADR 0038 decides. Defender protection can take up to 24 hours to start on a new account, so an environment opens uploads only after a check confirms that a test file gets a scan result.

A check made once at first provision would leave a silent failure mode. Microsoft documents that on-upload scanning halts when the account's monthly cap is reached (it resets monthly at midnight UTC, and a cap change takes up to an hour), that removing the Event Grid system topic Defender creates stops scanning, and that a deleted `StorageDataScanner` resource needs scanning disabled and re-enabled. After any of these, every new version would wait 240 minutes and fail `scan_unavailable`, while uploads kept being accepted with no clear signal to the admin. Defender documents that a test file gets both the result and the scan-time tags, and that an EICAR test file yields `Malicious` and the alert "Malicious file uploaded to storage account". The ingestion app already writes to `documents` (Storage Blob Data Contributor) and reads tags there (the "DocChat Blob Tag Reader" role), and the API reads SQL on every request. Defender's own result table in Log Analytics is available only through a query right and arrives with ingestion delay.

## Decision

1. **Scope.** Everything below applies only while `DOCCHAT_STORAGE_MALWARE_SCANNING_ENABLED` is `true` (`storage.malwareScanning`: `true` in `prod`, `false` in `dev` and `load`, `dev` switched on by pull request only while the end-to-end scan test runs). With it `false` the gate is open and no canary is written.
2. **Table `app.scan_canaries`** (owned by ingestion): `id` `UNIQUEIDENTIFIER` not null, primary key `PK_scan_canaries`, a random UUID from the ingestion app; `blob_path` `NVARCHAR(256)` not null, `_scanner-canary/{id}.pdf` in container `documents`; `written_at` `DATETIME2(3)` not null, default `SYSUTCDATETIME()`, inserted before the blob is uploaded; `result` `NVARCHAR(32)` null while open, `CK_scan_canaries_result`: `CHECK (result IN ('clean','malicious','failed','unavailable'))`; `scanned_at` `DATETIME2(3)` null, the scan-time tag (null for `unavailable`); `minutes_to_result` `INT` null, `CHECK (minutes_to_result IS NULL OR minutes_to_result >= 0)`. Index `IX_scan_canaries_written_at` (`written_at`) `INCLUDE (result)` serves the gate, the sweep and the retention delete. Grants: `docchat_api` S; `docchat_ingestion` S, I, U, D; `docchat_config_operator` S.
3. **Write.** `ingestion_maintenance` (timer `0 40 2 * * *`, 02:40 UTC daily), step 3: draw a new random UUID; `INSERT app.scan_canaries (id, blob_path) VALUES (@id, @blobPath)`; then `upload_blob(<bytes>, overwrite=False, content_settings=ContentSettings(content_type="application/pdf"))` of a one-page PDF built in a worker thread by `pikepdf` (`Pdf.new()`, one 612 × 792-point page, the canary ID as the document ID and as `/Info /Subject`, so every canary's bytes are new). The row comes first, so a scan time can never precede `written_at`, and an upload that fails leaves a row that the sweep resolves as `unavailable`. The first sweep that finds scanning enabled and no `scan_canaries` row at all writes the first canary the same way (sweep duty 11), so a new environment doesn't wait for 02:40 UTC. The canary lives in `documents` because it must travel the path an upload travels: the same container, the same exclusion filters and the same tag writes.
4. **Resolve.** Sweep duty 11, at every wake while scanning is enabled: `SELECT TOP (10) id, blob_path, written_at FROM app.scan_canaries WHERE result IS NULL ORDER BY written_at`; for each, `get_blob_tags()` (a failed read counts as no result for this wake), then ADR 0038's mapper with `written_at` in place of the commit time: `No threats found` with a scan time at or after `written_at` gives `clean`; `Malicious` gives `malicious`; no result tag, `SAM259213` or `SAM259215` keep waiting until `written_at` + `ingestion.scan_wait_minutes`, then `unavailable`; any other value gives `failed`. On a result: `UPDATE app.scan_canaries SET result = @result, scanned_at = @scanTime, minutes_to_result = @minutes WHERE id = @id AND result IS NULL` (whole minutes from `written_at` to `scanned_at`, or to now for `unavailable`), then `delete_blob()` (absent counts as deleted) and event `scanner_canary_result` (`result`, `minutes`).
5. **Gate.** `adminPreflightUploads`, `adminReserveUpload`, `adminUploadContent` and `adminSubmitUploads`, after authorisation and the index lookup and before every other check: while scanning is enabled and `SELECT TOP (1) 1 FROM app.scan_canaries WHERE result = 'clean' AND written_at > DATEADD(hour, -48, SYSUTCDATETIME())` returns no row (one seek on `IX_scan_canaries_written_at` per request), answer `503 malware_scanning_not_ready` (title "Uploads paused", detail "Uploads are paused until malware scanning confirms it's working. Try again later.", `retryAfterSeconds` 3,600, retryable after that time) and write nothing. Forty-eight hours tolerates one missed or failed daily canary. The web client shows the problem's `detail` with the time from `retryAfterSeconds`, marks the current and remaining files paused, sends no further request and enables Upload and Try again at that time.
6. **Retention.** `ingestion_maintenance` step 4, whatever the scanning setting: `SELECT blob_path FROM app.scan_canaries WHERE result IS NULL AND written_at < DATEADD(day, -90, SYSUTCDATETIME())` and `delete_blob()` each one, then repeat `DELETE TOP (500) FROM app.scan_canaries WHERE written_at < DATEADD(day, -90, SYSUTCDATETIME())` until no row is affected. A failed blob delete ends the step before any row is deleted, so the next day retries with every blob path still recorded. With scanning off for more than 90 days the table empties, so the first sweep after scanning is switched on again writes a canary at once.
7. **Operations.** Alert A15 `uploads-scan-gate-closed` (deployed where scanning is enabled; log alert over `P2D` evaluated every `PT1H`, severity 2): no `scanner_canary_result` event with `result` `clean` in the last 48 hours. Runbook R12 confirms the first canary after an environment's first provision (and after any re-creation of the data storage account) and records the acceptance in `docs/runbooks/rehearsals.md`; its steps 7 to 9 handle a closed gate. `docchat-ops ingestion status` lists the last 5 canaries (IDs, states and times only).

## Alternatives considered

- **A one-time acceptance check by an operator.** It meets the first-provision need but misses a scanner that stops later; versions would then wait 240 minutes and fail with no clear signal while uploads stayed open.
- **Judging scanning from recent versions' results.** An environment with no uploads has no evidence, so the first uploads would prove scanning by failing; a canary needs no user action.
- **A canary in its own container.** It wouldn't prove that `documents` is scanned, because Defender's exclusion filters work per prefix; a canary in `documents` crosses the same filters and tag writes as an upload.
- **An EICAR canary.** It would raise Defender's "Malicious file uploaded" alert and the product's malware alert every day; a clean result proves that the scanner runs and writes results, which is what the gate needs, and detection itself is proven by the deployed end-to-end scan test.
- **A 24-hour window.** One missed or failed daily canary would close uploads; 48 hours tolerates one.
- **Reading Defender's Log Analytics table or the Defender settings resource at request time.** The API would need a query or ARM right on every upload request and would wait for log ingestion, and a configured setting doesn't prove that scanning happens.
- **Accepting uploads and letting versions fail later.** Admins would learn of a stopped scanner only from `scan_unavailable` four hours after each upload; refusing at upload time gives a clear answer at once.

## Consequences

- A new environment with scanning on refuses uploads until its first canary is clean (Defender can take up to 24 hours on a new account); the first sweep after the deploy writes that canary when the table is empty, and uploads open by themselves once it is clean. In `dev`, while the end-to-end scan test switches scanning on, the deploy's smoke upload answers `503 malware_scanning_not_ready` until the first clean canary, as expected.
- When scanning stops, the gate closes 48 hours after the last clean canary; versions committed in between fail `scan_unavailable`, and runbook R12 has admins re-upload them once the cause (a reached cap, a removed setting) is resolved.
- Each request to the four upload operations adds one index seek in SQL while scanning is enabled; one small PDF a day is scanned, negligible against the 1,000 GB monthly cap.
- A canary blob is deleted once its result is recorded; the row stays 90 days, about one a day, for incident review, and no canary blob outlives its row.
- Tests: maintenance writes the row and then `documents/_scanner-canary/{id}.pdf`, the first sweep with no row writes one, and the sweep maps `clean`, `unavailable`, `malicious` and `failed`, records `minutes_to_result`, deletes the blob and emits `scanner_canary_result` once; the gate is open with a clean canary written 47 hours ago; with the newest clean canary 49 hours old each of the four operations answers `503 malware_scanning_not_ready` with `retryAfterSeconds` 3,600 and writes nothing; with scanning disabled the gate is open and no canary is written; retention deletes a row written 91 days ago, keeps one written 89 days ago, deletes an open row's blob before its row, and deletes no row when that blob delete fails; the web client's upload tests cover the paused state from any of the four operations.
