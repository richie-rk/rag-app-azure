# ADR 0016: Entra app registrations through Graph Bicep

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 83-infrastructure.md, 81-config.md, 82-security.md, 84-testing.md, 86-operations.md, 01-repository.md
- **Related ADRs:** 0002, 0017, 0018, 0019, 0020, 0021, 0086, 0091, 0114, 0115, 0120, 0126

## Context

DocChat accepts Microsoft Entra ID sign-in only. Each environment needs its own identity objects, so that a token, role or assignment issued in one environment is useless in every other: a public single-page-app web client that redirects only to its own environment's web origin (and to localhost in `dev` only); an API that exposes one delegated scope `access_as_user`, issues v2 access tokens and defines the app roles `Admin` and `User`; and, in the non-production environments `dev` and `load` only, a test client through which automated tests get tokens (ADR 0019). Only assigned users and groups may sign in, the same users or groups are assigned to the web client (default access) and to an API role, and admin status lives in Entra ID as an app role, so no write through the app can make anyone an administrator.

The identity objects must be declared, reviewed and deployed with the rest of each environment's infrastructure, so no environment depends on hand-made settings and no client ever redirects to another environment's origin. The pipeline that deploys them must not hold the right to grant tenant-wide consent or to assign app roles, because with those rights a compromised pipeline could make anyone an administrator. A `load` environment is short-lived, and deleting its resource group doesn't remove identity objects, so its teardown must delete them itself, permanently, before the next run reuses the names.

Vendor facts that bound the choice (Microsoft Learn, confirmed 2026-10-14):

- The Microsoft Graph Bicep extension is GA (types `microsoftgraph/v1.0:1.0.0`, Bicep 0.36.1 or later). `Application.ReadWrite.OwnedBy` creates, updates and permanently deletes only the applications and service principals its holder owns; `appRoleAssignedTo` needs `AppRoleAssignment.ReadWrite.All`, and `oauth2PermissionGrants` needs `DelegatedPermissionGrant.ReadWrite.All`. Only a Privileged Role Administrator can grant a Graph application permission.
- What-if doesn't evaluate extensible resources; `passwordCredentials` aren't supported; the extension fails with `401 AuthenticationFailed` inside a template spec or a hand-authored `templateLink`; resource-group deletion doesn't delete Graph objects.
- An application can't set `identifierUris` from its own `appId` in one declaration (BCP079); `api://<tenantId>/<string>` is a secure identifier-URI format.
- `uniqueName` is the immutable alternate key that makes every deployment an upsert; a soft-deleted object keeps it until it is permanently deleted.
- With assignment required, unassigned users get no token (`AADSTS50105`), Global Administrators bypass the requirement, and the application can't receive user consent, so it needs tenant-wide admin consent. Group assignment needs Entra ID P1 or P2 and ignores nested groups. Pre-authorized clients get the listed API scopes without a prompt, but `openid`, `profile` and `offline_access` are Microsoft Graph scopes that pre-authorization doesn't cover.

## Decision

1. **Registrations per environment.** All single tenant (`signInAudience: 'AzureADMyOrg'`). `dev` and `load` have three applications (web client, API, test client); `prod` has two (web client, API). The test client exists only under the Bicep condition `environmentName != 'prod'`.
2. **Declared with the Graph Bicep extension.** `infra/bicepconfig.json` declares `"extensions": {"graphV1": "br:mcr.microsoft.com/bicep/extensions/microsoftgraph/v1.0:1.0.0"}`; `infra/main.bicep` and its local module `infra/modules/identity/entra-apps.bicep` both declare `extension graphV1`, with resource types `Microsoft.Graph/applications@v1.0` and `Microsoft.Graph/servicePrincipals@v1.0`. The module is compiled inline, never published as a template spec or registry module. Inputs: `environmentName`, `resourceToken`, the tenant ID, the Static Web Apps default host name and `webCustomDomains` (string array, default `[]`); the scope and role GUIDs below are constants in the module. Declaration order: test client, web client, API, so the API's `preAuthorizedApplications` reference earlier `appId` values and nothing references itself. Module outputs `webAppId`, `apiAppId`, `testAppId` (empty string in `prod`) and `apiScope` feed the app settings `DOCCHAT_AUTH_WEB_CLIENT_ID`, `DOCCHAT_AUTH_API_CLIENT_ID` and `DOCCHAT_AUTH_TEST_CLIENT_ID`, platform authentication (ADR 0017), the azd outputs `WEB_CLIENT_ID`, `API_CLIENT_ID`, `TEST_CLIENT_ID` and `API_SCOPE`, and the web client's `config.json` (`clientId`, `apiScope`; ADR 0086).
3. **The deploy identity owns them.** Each environment's deploy identity holds the Graph application permission `Application.ReadWrite.OwnedBy` (`18a4783c-866b-4cc7-a460-3d5e5662c884`), granted to its service principal by the bootstrap's `graph-permission` step, run by a tenant administrator holding Privileged Role Administrator; it creates the objects and so becomes their only owner (`owners` isn't declared). No password or key credential is ever added to any registration.
4. **Names.** `<tenantId>` is lowercase.

   | Property | Web client | API | Test client (`dev`, `load`) |
   |---|---|---|---|
   | `uniqueName` | `docchat-<environmentName>-<resourceToken>-web` | `docchat-<environmentName>-<resourceToken>-api` | `docchat-<environmentName>-<resourceToken>-test` |
   | `displayName` in `prod` | `DocChat` | `DocChat API` | not created |
   | `displayName` elsewhere | `DocChat (<environmentName>)` | `DocChat API (<environmentName>)` | `DocChat test client (<environmentName>)` |
   | `identifierUris` | `[]` | `['api://<tenantId>/docchat-<environmentName>-<resourceToken>-api']` | `[]` |

   The scope string clients request is `api://<tenantId>/docchat-<environmentName>-<resourceToken>-api/access_as_user` (about 90 characters, under the 255-character limit by construction). Every application and service principal carries `notes`: "Managed by the DocChat infrastructure templates. Declared properties are reset on every deployment."
5. **API registration.** `api.requestedAccessTokenVersion: 2`; one delegated scope: `id` `772eca72-e66c-46c6-b40d-60f539a5f867`, `value` `access_as_user`, `type` `User`, `isEnabled` `true`, `adminConsentDisplayName` "Use DocChat as the signed-in user", `adminConsentDescription` "Lets the DocChat web client call the DocChat API for the signed-in user, with only that user's access.", `userConsentDisplayName` "Use DocChat as you", `userConsentDescription` "Lets the DocChat web client call the DocChat API for you, with only your access."; app roles `Admin` (`47dc73a8-b97e-4be8-9481-614f6b17a11f`, display name "DocChat administrator", description "Manages every project, its members, index mappings, indexes and documents, and sees ingestion runs.") and `User` (`6f46cf45-f1e3-4812-8003-c51ae0f5f98d`, "DocChat user", "Chats in the projects they belong to and manages their own conversations, feedback and memory."), both `allowedMemberTypes: ['User']` (users and groups) and enabled; `api.preAuthorizedApplications`: the web client and, in `dev` and `load`, the test client, each with `delegatedPermissionIds: ['772eca72-e66c-46c6-b40d-60f539a5f867']`; optional claim `email` (`essential: false`) in access tokens; no redirect URI of any platform; implicit grant off; `requiredResourceAccess: []`; `isFallbackPublicClient: false`. The GUIDs are the same in every environment, because they are unique per application, not per tenant. Scope type `User` is safe because pre-authorization removes the prompt for the listed clients, and both authentication layers reject any other client on `azp` (ADR 0017).
6. **Web client registration.** `spa.redirectUris`: `https://<Static Web Apps default host name>/`, plus `https://<host>/` for each `webCustomDomains` entry, plus `http://localhost:5173/` in `dev` only (Entra ignores the port for localhost; 5173 is the web client's Vite dev-server port); `web.homePageUrl`: `https://<first custom domain, else the default host name>/`; `web.redirectUris: []`; `web.implicitGrantSettings` with `enableIdTokenIssuance` and `enableAccessTokenIssuance` both `false`; `publicClient.redirectUris: []`; `isFallbackPublicClient: false`; `api.requestedAccessTokenVersion: 2`; no identifier URI, scope, app role or optional claim; `requiredResourceAccess`: Microsoft Graph (`00000003-0000-0000-c000-000000000000`) delegated `openid` (`37f7f235-527c-4136-accd-4a02d197296e`), `profile` (`14dad69e-099b-42c9-810b-d002981feec1`) and `offline_access` (`7427e0e9-2fba-42fe-b0c0-848c9e6a8182`), each `type: 'Scope'`, and nothing else, not even `User.Read`. Redirects return to the app shell at the origin root (ADR 0018), and `offline_access` gives the 24-hour refresh token that silent renewal redeems.
7. **Test client registration.** `isFallbackPublicClient: true` (public client flows on, for ROPC without a redirect URI); `spa`, `web` and `publicClient` redirect URIs all `[]`; implicit grant off; `api.requestedAccessTokenVersion: 2`; `requiredResourceAccess`: Microsoft Graph delegated `openid` and `profile` only (`profile` puts `oid` and `tid` in the token).
8. **Service principals.** One `Microsoft.Graph/servicePrincipals@v1.0` per application (`appId`), each with `appRoleAssignmentRequired: true`, `accountEnabled: true` and the application's `notes`; `tags`: web client `['WindowsAzureActiveDirectoryIntegratedApp']`, API and test client `['WindowsAzureActiveDirectoryIntegratedApp', 'HideApp']`, so administrators find all three under Enterprise applications and My Apps shows only the web client. A Global Administrator who bypasses assignment still gets no role, and the in-app role check refuses the token (ADR 0017).
9. **Consent and first admins after provisioning.** A Cloud Application Administrator or Application Administrator runs `az login --tenant <tenantId>`, then `uv run python scripts/identity_post_provision.py --environment <env> --resource-token <token> --users-group <objectId> --admins-group <objectId> [--admin <objectId> …] [--test-users-group <objectId> --test-admins-group <objectId>] [--test-norole-group <objectId>]`: after the first provision of `dev` and `prod`, at every `load` run's access gate (GitHub environment `load-access`, whose required reviewers are the team `docchat-tenant-admins`, members holding Cloud Application Administrator; runbook R11 step 4) and after any re-creation of a registration. The two test-group flags are required in `dev` and `load` and refused in `prod`; `--test-norole-group` is required in `dev` and refused elsewhere. With a Graph token for `https://graph.microsoft.com/.default` from `AzureCliCredential` and Graph REST v1.0 over `httpx`, it: (a) finds the applications by `uniqueName`, their service principals by `appId` and Microsoft Graph's service principal by appId `00000003-0000-0000-c000-000000000000`; (b) creates, or patches to exactly this scope, one tenant-wide grant (`oauth2PermissionGrant`, `consentType: 'AllPrincipals'`) from the web client's service principal to Microsoft Graph's with `scope: 'openid profile offline_access'`, and in `dev` and `load` one from the test client's with `scope: 'openid profile'`, leaving other grants untouched; (c) assigns `--users-group` to the API's `User` role, and `--admins-group` plus every `--admin` (user or group object ID) to the API's `Admin` role, each also to the web client's default access (`00000000-0000-0000-0000-000000000000`); (d) assigns the test groups of ADR 0019: users group to API `User`, admins group to API `Admin`, the `dev` no-role group to the API with default access and no app role, and every test group to the web client and the test client with default access. Assignments that exist are skipped and a grant whose scope is already exact is left as it is, so a second run changes nothing. If Graph refuses the default-access assignment on the API (HTTP 400, because the API declares app roles), the script finishes every other step and exits 2 naming that step (ADR 0019 records the skip). It prints a summary and the run's correlation ID; the check is a first admin's `getCurrentUser` showing `isAdmin: true`.
10. **Access through groups.** The bootstrap's `groups` step creates the security groups `sg-docchat-<env>-users` and `sg-docchat-<env>-admins` for each environment; item 9 assigns each to the web client's default access and to its API role, and group owners then manage membership in Entra ID, with nothing to change in the app. Group assignment needs Entra ID P1. Admin status exists only as the `Admin` app role.
11. **`load` teardown.** Under the `load` deploy identity, which owns them, `scripts/deploy/teardown_load.py` finds the run's three applications by `uniqueName`, deletes each (`DELETE https://graph.microsoft.com/v1.0/applications/{id}`, which also removes its service principal) and then deletes each permanently (`DELETE https://graph.microsoft.com/v1.0/directory/deletedItems/{id}`), before it removes the run's AcrPull assignments and empties `rg-docchat-load` (ADR 0126). A failure exits 2 with `graph_delete_failed`, and runbook R11 step 13 finishes the deletion by hand.
12. **Review, detection and verification.** `.github/CODEOWNERS` names `docchat-platform` and `docchat-security` for `/infra/modules/identity/`, and the `main` ruleset requires a code owner's approval, so no change to the registrations merges without their review. The bootstrap deploys the log search alert `docchat-alert-app-registrations` (severity 1, every 15 minutes over 30 minutes, to `ag-docchat-security`) over Entra `AuditLogs` in `log-docchat-security`, through the tenant diagnostic setting: it fires when an application or service principal whose `displayName` starts with `DocChat` gets a new credential (`Update application – Certificates and secrets management`, `Add service principal credentials`) or a changed `AppAddress` or `KeyDescription`. The next deployment resets every declared property. A deployed test compares each registration with this ADR property by property, including the absence of a test client in `prod`, and a second deployed test adds a redirect URI to the `dev` web client, expects the alert, and expects the next `dev` deploy to remove the URI.
13. **Stage-0 contingency.** If `az deployment group what-if --validation-level ProviderNoRbac` or PSRule's expansion of `main.bicepparam` fails on the extension, the registrations move to `infra/identity.bicep`, deployed by azd's `preprovision` hook with its outputs written to the azd environment and passed to `main.bicep` as parameters; every value above stays the same, and the stage-0 result is recorded in this ADR.

## Alternatives considered

- **Registrations made by hand or by an `az ad app` script outside the templates.** They drift from the templates, escape review with the rest of a change, and leave an environment depending on settings nobody can reproduce.
- **One pair of registrations shared by every environment.** A `dev` token, role or assignment would then work in `prod`, which environment isolation forbids.
- **A deploy identity with `Application.ReadWrite.All`, `AppRoleAssignment.ReadWrite.All` and `DelegatedPermissionGrant.ReadWrite.All`, so the templates also grant consent and assign admins.** A pipeline could then change every application in the tenant, grant any delegated permission tenant-wide and make anyone an admin. A tenant administrator's step per environment costs minutes and keeps those rights out of CI.
- **Identifier URI `api://<appId>`.** BCP079 makes it a second deployment step; `api://<tenantId>/<uniqueName>` is a secure format known before deployment.
- **The API scope in each client's `requiredResourceAccess`, with a tenant-wide grant.** It adds a grant per client that the pipeline can't create, and together with pre-authorization the API and its clients would reference each other, a cycle Bicep can't deploy. Pre-authorization alone gives the listed clients the scope without a prompt and keeps references one-way.
- **The registrations in their own template from the start.** One more deployment and a hand-off of four outputs through the azd environment on every provision; kept only as the stage-0 contingency for tooling that can't expand the extension in `main.bicep`.
- **Admin status as a flag in the app's database.** An app write would become an escalation path; an app role granted in Entra ID keeps administration outside anything the API can change.
- **Assignment not required.** Every user in the tenant would get API tokens, and the web client couldn't use Entra's `AADSTS50105` to show an unassigned user a clear state.

## Consequences

- Every environment's identity objects are reviewed and deployed with the rest of its infrastructure; a redeployment is an idempotent upsert by `uniqueName`, `resourceToken` keeps two deployments of the template in one tenant apart, and no client secret or certificate exists to rotate or leak.
- What-if shows nothing for Graph resources, so the code-owner review is the gate. A new environment can't be signed in to until item 9 has run (the web client shows Consent missing on `AADSTS65001` or `AADSTS90094`, ADR 0091), and every `load` run waits for a tenant administrator at its access gate.
- Removing a scope or an app role takes two deployments: `isEnabled: false` first, then removal, because Graph refuses to delete an enabled one.
- Removing a user's role or app assignment takes effect when their current access token expires, 60 to 90 minutes after issue, because roles come only from the token (ADR 0020); membership changes take effect on the next request.
- `Application.ReadWrite.OwnedBy` lets each deploy identity create applications and change the ones it owns, never anyone else's. A compromised pipeline that adds a credential or redirect URI to a DocChat registration raises the severity-1 alert; the next deployment removes a redirect URI, and a credential is removed by hand under the incident runbook (R07).
- Obligations: the code-owner entry; the alert and its deployed test; the deployed property test; runbooks R13 (first admins and test identities) part (b) and R11 (run the load test); the teardown script; every registration's `displayName` keeps the `DocChat` prefix the alert selects on. A new custom domain changes the redirect URIs, platform CORS and the web client's CSP together through `webCustomDomains`.
