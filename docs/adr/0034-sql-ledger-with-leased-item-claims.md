# ADR 0034: SQL ledger with leased item claims

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** CONTEXT.md, 14-ingestion.md, 80-data-model.md, 81-config.md, 84-testing.md, 85-observability.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0003, 0006, 0025, 0026, 0028, 0035, 0036, 0037, 0040, 0042, 0050, 0053, 0054, 0144

## Context

Ingestion is billed per document it processes (model calls, layout analysis, indexing), so each document version must be built once per target index: never once per message, once per run that happens to list it, or again because a file name repeats. Admins must see each document's true outcome, and an operator must be able to bound how much runs at once.

The product decisions set the shape: ingestion runs on Durable Functions with one activity per unit of work, checkpoints and per-activity retries; a SQL ledger is the source of truth; a version's identity is the SHA-256 of its bytes, so the same bytes are skipped and constraints stop concurrent duplicates; parallelism defaults to 1 and is an operator setting in the database. Items are handed out by priority (uploads before bulk re-ingests), then first in, first out, across all runs; one dispatcher hands out every slot, so the limit holds across runs; a lost message or event only delays work; and one failed document never fails its run, which ends `completed`, `completed_with_errors` or `failed`.

Vendor facts that bound the choice:

- Durable Functions' concurrency settings apply per worker and don't limit total throughput, so a global limit must come from one place that counts work.
- Terminating or failing an orchestration doesn't stop its sub-orchestrations or activities; they run to completion. A fresh dispatcher that counted only its own children could exceed the limit, and an orphan would keep writing.
- Two clients running the singleton check-and-start at once can both report success; an event raised to a missing instance is discarded; external events are delivered at least once, and the Azure Storage provider can deliver duplicates.
- Child instance IDs should be deterministic, so a replay never starts a duplicate.
- Azure SQL Database runs READ COMMITTED with row versioning (`READ_COMMITTED_SNAPSHOT` on), so a plain read neither blocks nor sees uncommitted writes; a decision that must serialise needs locking hints or a locking write. Filtered unique indexes are nonclustered and single-table, and their uniqueness covers only the filtered rows.

## Decision

**1. The ledger.** SQL (schema `app`, ADR 0025) holds every run, item, version and chunk set. The ingestion app acts on a queue message or a `run_queued` event only by re-reading SQL: a lost, duplicated or replayed message or event can delay work but never creates, skips or repeats it. Runs are created only by the API's admin operations (uploads, re-ingests, deletes, index operations), by the sweep and by operators' `docchat-ops` commands; the ingestion app has no HTTP endpoint (ADR 0003). Each run-creating API operation commits the run and its items in one transaction, then sends one `IngestionQueueMessage` `{runId, traceparent, tracestate}` (ADR 0037); a send that still fails after the client's 3 retries is logged as `ingestion_queue_send_failed` and the request still answers `202`, because the sweep finds every queued item at the dispatcher's next wake. Runs that operators create get no message (operators hold no queue-send right) and start the same way.

**2. Content identity.** `document_versions.sha256` (`BINARY(32)`) is the SHA-256 of the bytes: computed by the browser, recomputed by the API while streaming and compared before the blob is committed (ADR 0042). Three filtered unique indexes make the rules database invariants: `UX_document_versions_document_sha` on (`document_id`, `sha256`) and `UX_document_versions_index_sha` on (`search_index_id`, `sha256`), both `WHERE state IN ('pending','ingesting','ingested')`, and `UX_document_versions_one_ingested` on (`document_id`) `WHERE state = 'ingested'`. A violation at commit deletes the blob, fails the version and answers `409 content_unchanged` or `409 duplicate_content`. `search_index_id` is stored on the version because a filtered index can't reach the `documents` table. Failed, superseded and uploading versions never block the same bytes. Of several pending versions of one document, Validate ingests only the one committed last (later `committed_at`, then higher `version_number`) and supersedes the others with `superseded_by_newer`; the guarded Flip is ADR 0040.

**3. Runs and items.** `ingestion_runs.kind` is one of `upload`, `document_reingest`, `document_delete`, `index_create`, `index_reingest`, `index_rebuild`, `index_delete` and `maintenance`; `priority` is 0 (interactive) for `upload`, `document_reingest`, `document_delete`, `index_create` and `maintenance`, and 1 (bulk) for the other three and for the `maintenance` runs of the sweep's stale-renditions duty, which hold only `rerender` items (ADR 0145 decision 10); each item copies its run's priority. `ingestion_run_items.operation` is one of `ingest`, `cleanup_document`, `rerender`, `create_physical_index`, `delete_physical_index` and `purge_index_blobs`. `queue_seq` (`BIGINT IDENTITY(1,1)`, unique) orders items first in, first out across all runs. `UX_run_items_run_version`, unique on (`run_id`, `document_version_id`) `WHERE document_version_id IS NOT NULL`, keeps one item per document version per run. One submission is one run.

**4. One dispatcher.** The singleton orchestration `ingestion_dispatcher` (instance ID `docchat-ingestion-dispatcher`) is the only claimer. `ensure_dispatcher` starts it when no instance exists or the instance is `Completed`, `Failed`, `Terminated` or `Canceled`, and treats `Running` or `Pending` after a failed `start_new` as success; `host.json` sets `overridableExistingInstanceStates` to `NonRunningStates`. Its continue-as-new is ADR 0035; its wake cadence, keep-alive and watchdog are ADR 0036.

**5. The claim.** `claim_ingestion_items` runs one transaction:

1. Free slots = `ingestion.max_parallel_items` minus the number of items in state `running`, counted `WITH (UPDLOCK, HOLDLOCK)`; no free slot means no claim.
2. Candidates are `queued` items whose `not_before` is null or past; for `ingest`, whose target physical index is provisioned (or `retiring` or `deleted`, so Validate can re-target or skip the item) and whose version passes the scan gate (`scan_required = 0`, `scan_status = 'clean'`, or the version has left `pending`); and whose document (for index operations, whose physical index) has no `running` item; a `purge_index_blobs` item, which has neither, is a candidate only while no other purge item and no item of its logical index (`search_index_id`) is `running`, so no upload under the index's prefixes overlaps the purge (ADR 0052 decision 4).
3. Candidates are ranked by `priority`, then `queue_seq`, at most one per document (or physical index). The first free-slot count become `running` with `claim_count = claim_count + 1`, `instance_id` = `docchat-item-{itemId}-{claimCount}`, `started_at` kept from the first claim, `lease_expires_at` = now + 30 minutes and `not_before` null; their runs become `running`, and the heartbeat row's `last_claim_at` is set.
4. `UX_run_items_running_target`, unique on (`document_id`, `physical_index_id`) `WHERE state = 'running'`, is the hard guard: a violation rolls the claim back and the next wake tries again.

Slots are counted from SQL, never from the dispatcher's memory, so sub-orchestrations that outlive a restarted or terminated dispatcher keep their slots and the limit holds. `ingestion.max_parallel_items` is an `ops_config` integer, default 1, range 1 to 16, changed only through `docchat-ops config set` after the quota and instance check of the parallelism runbook (ADR 0053 sizes the plan for it). The dispatcher reads its settings once per wake and passes each item the values it needs, so one item runs with one consistent set (ADR 0028).

**6. Leases and fencing.** Each claimed item runs as one sub-orchestration whose instance ID carries the claim number, so a re-claim never collides with an orphan of an earlier claim. Every activity of the item starts with the fenced update `UPDATE app.ingestion_run_items SET stage = @stage, lease_expires_at = <now + the activity's deadline + 10 minutes> WHERE id = @item AND claim_count = @claim AND state = 'running'`; zero rows means the claim was lost (`lease_lost`, never stored), and the sub-orchestration stops without another write. Every later write about the item (the chunk-set link, a re-target, the Flip's item update, the outcome) carries the same `claim_count` and `state` predicate. The 30-minute claim lease covers the gap between the claim and the first activity's own update; from then on each activity keeps the lease 10 minutes beyond its deadline (the item activities' deadlines run from 120 to 2,700 seconds, ADR 0144).

**7. Expiry.** The sweep handles every `running` item whose `lease_expires_at` has passed: while `claim_count` is below `ingestion.max_item_claims` (`ops_config`, default 3, range 1 to 10) the item returns to `queued` with `not_before` = now and no lease; otherwise it fails with `processing_interrupted`, with the failure side effects of `record_item_outcome`. The dispatcher drops requeued and failed items from its running set. A sub-orchestration that never started, or that failed with an unhandled error, holds its slot until its lease expires, and an item never runs twice at once.

**8. Outcomes.** Item states are `queued`, `running`, `succeeded`, `skipped` (codes `already_served`, `superseded_by_newer`, `version_not_ready`, `document_deleted`, `target_retired`, `target_repointed`, `renditions_current`), `failed` and `cancelled` (removed before it ran by a document or index delete, a run cancellation or a duplicate found at repoint). `record_item_outcome`, fenced like every write, stores `state`, `outcome_code`, `outcome_message` (the code's catalogue text), the last `stage`, `warnings` (a JSON array of at most 50 `{code, page}` entries), the token and page counts and `completed_at`, always on the item being processed. For `failed` it also retires the item's chunk set and, when the item targets the logical index's active physical index (or its building one when none is active) and the version is `pending` or `ingesting`, fails the version with the same `failure_code`; a failed rebuild or re-ingest of a current version changes only the item and its chunk set.

**9. Run end states.** The sweep finalises a run with no `queued` or `running` item (an `index_rebuild` run only once no `building` physical index names it as `build_run_id`): `failed` when at least one item failed and none succeeded or was skipped; `completed_with_errors` when at least one failed and at least one succeeded or was skipped; `completed` otherwise, cancelled items counting with skipped ones. It stores the five totals and `completed_at` with `WHERE id = @run AND state IN ('queued','running')`, emits `ingestion_run_finished` and recomputes the index status. A failed document never fails its run.

**10. Recovery reads the ledger.** The sweep gives every version left `pending` for `ingestion.orphan_pending_minutes` (`ops_config`, default 15, range 5 to 1,440) with no queued or running item a `maintenance` run with an `ingest` item, up to 100 versions a wake. The heartbeat row `app.ingestion_dispatcher_state` (one row, written by every sweep and claim) is read only by the sweep and `docchat-ops ingestion status`. Because every fact lives in SQL, the last-resort task-hub reset (ADR 0054) loses no work: running items' leases expire and the items are requeued.

## Alternatives considered

- **The queue as the work list** (one message per document, the trigger doing the work): no global slot count across instances, priority only through separate queues, a duplicate or replayed message repeating billed work, and a lost message losing the document.
- **Durable entities or the dispatcher's memory as the ledger:** state hidden in the task hub, lost by a task-hub reset and not queryable by the admin screens; a restarted dispatcher wouldn't see its predecessor's orphans.
- **Durable Functions' concurrency settings as the limit:** they cap one worker, not the system, so with several instances the total would exceed the operator's value.
- **Leases without fencing:** an orphan of a terminated dispatcher, or an activity that ran past its lease, could overwrite the result of the item's next claim.
- **No leases, trusting sub-orchestration completion:** an unhandled failure or a lost dispatcher would leave items `running` for ever and their slots taken.
- **Identity by file name or blob path:** changed bytes under the same name would never re-index, and the same bytes under another name would be processed twice.
- **A run per file, or a run that rescans its batch:** the same file would be processed and billed once per run.
- **A run state with no counting rule:** a run whose every item failed would look successful.
- **A shorter claim lease (5 minutes):** a sub-orchestration slow to start would lose its claim and use up one of its claims; **a longer one (2 hours):** a slot held by a sub-orchestration that never started would stay blocked for hours.

## Consequences

- At most `ingestion.max_parallel_items` items run at once across all runs, instances and dispatcher restarts, and never two for one document and physical index.
- Interactive work overtakes bulk re-ingests, and within a priority work is first in, first out across runs; a large re-ingest waits behind every queued upload.
- A lost message delays work until the next wake (ADR 0036), never loses it; duplicate messages and events are harmless.
- An item that keeps crashing is claimed at most `ingestion.max_item_claims` times, then fails with `processing_interrupted`, so a poison document can't hold a slot for ever; the admin re-ingests it once the cause is removed.
- A crashed sub-orchestration holds its slot until its lease expires, at most 55 minutes (Extract's 2,700-second deadline plus 10 minutes); at the default parallelism of 1 that pauses ingestion for that time, and alert A17 (oldest queued item older than 1,800 seconds) surfaces it.
- Every write on the item path is a fenced, row-counted statement, so activities are idempotent and the data-access layer's whole-unit retries are safe (ADR 0026).
- The admin screens show each item's state, stage, attempts (`claim_count`) and safe message from SQL, and each run's state follows the counting rule.
- Raising parallelism is an operator change with a quota check (Azure OpenAI and Document Intelligence) and enough always-ready instances (ADR 0053).
- Tests: integration against SQL Server from `compose.yaml` proves that the three version indexes reject active duplicates and allow failed, superseded and uploading ones; that a second running item for one document and physical index is rejected; that the claim honours priority, first in, first out across runs, one item per document, the slot count and the scan gate; that an expired lease requeues the item with `claim_count + 1`, that writes fenced by the old claim change nothing, and that the third expiry fails it `processing_interrupted`; the finalisation states and totals; and one item per version per run. The orchestration harness proves that claims never exceed the slots, that a duplicate queue message processes each item once, that a crash between activities resumes from the last checkpoint, and that a dispatcher crash with a running item keeps the limit while the item completes or is requeued. The load test runs 200 documents at parallelism 1 and 4. The stage-1 acceptance includes a failed document leaving its run `completed_with_errors`.
- Monitoring: `docchat.ingestion.items.completed` (`operation`, `state`, `outcome_code`), the event `ingestion_item_failed` with the item's `operation` (alert A16 at more than 5 in 15 minutes; alert A58 on any `rerender` failure with `render_failed` or `render_too_large`), `ingestion_run_finished`, and the queue-age and dispatcher gauges from the keep-alive (alerts A17 and A18), all routed to runbook R18.
- Risk: the claim and sweep statements run on every wake, so they must stay index-backed (`IX_run_items_claim`, `IX_run_items_running`, `IX_ingestion_runs_open`); a test checks their plans against the integration database.
