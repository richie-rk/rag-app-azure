# ADR 0041: New versions during a rebuild

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 14-ingestion.md, 80-data-model.md, 11-api.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0034, 0040, 0045, 0054, 0061

## Context

A change of embedding model, dimensions, language analyzer or schema version builds a new physical index in state `building` while the active physical index keeps serving readers (ADR 0045). Admins keep uploading during that time, so every new version must reach both physical indexes, and the repoint may run only once every live document's current version is served in the building index. Three other rules of the ingestion ledger meet that one:

- A run holds one item per document version, enforced by the filtered unique index `UX_run_items_run_version` on (`run_id`, `document_version_id`).
- Each document sub-orchestration builds one chunk set for one physical index, and the chunk-set build key includes the physical index (`UX_chunk_sets_build_key`).
- The Flip of a new version makes it the document's current version and marks the version it replaces `superseded`. With two physical indexes a new version has two Flips, so exactly one of them must do that.

If either Flip could make a version current, commit order would decide what readers see. A building-index Flip committing first would make version V2 current while the active index still serves V1's chunks: chat would cite V1, now `superseded`, and those citations would answer `410` until V2's active-index Flip committed. In the other order, a rebuild item still building V1 could flip into the building index after V2 became current and leave it serving V1. Readers must always see the version that is current, and a rebuild must never serve an older one.

Vendor facts: Azure SQL Database runs with READ_COMMITTED_SNAPSHOT on, so a plain read sees a snapshot and takes no lock that protects the row from other writers; every guard below is therefore a locking write or an `UPDLOCK` read. A filtered unique index enforces uniqueness only over the rows its filter selects.

## Decision

1. **Only an active-index Flip makes a version current.** `flip_chunk_set` runs one transaction. Its first statement, `SELECT active_physical_index_id FROM app.search_indexes WITH (UPDLOCK, ROWLOCK) WHERE id = @index`, serialises every Flip, repoint and re-ingest start of the logical index. Then: the fenced lease update (`UPDATE app.ingestion_run_items SET stage = 'flip', lease_expires_at = <now + 12 minutes> WHERE id = @item AND claim_count = @claim AND state = 'running'`; zero rows ends the attempt with `lease_lost`); the retry check (a `served_chunk_sets` row for this document and physical index that already names this chunk set means an earlier attempt committed: commit and return `flipped` with empty clean-up lists); the target's state and `build_run_id` read with `UPDLOCK`; the version row read with `UPDLOCK`; then one guarded update of `app.documents`, with its row count checked:
   - (a) target is the active physical index and the version isn't current: `UPDATE app.documents SET current_version_id = @version, updated_at = SYSUTCDATETIME() OUTPUT deleted.current_version_id ... WHERE id = @document AND is_deleted = 0 AND (current_version_id IS NULL OR current_version_id <> @version) AND NOT EXISTS (<another version of the document in 'pending', 'ingesting' or 'ingested' with a later committed_at, or the same committed_at and a higher version_number>)` (the guard of ADR 0040);
   - (b) every other Flip (into the building physical index, or a re-ingest or rebuild of the current version in either index): `UPDATE app.documents SET updated_at = SYSUTCDATETIME() WHERE id = @document AND is_deleted = 0 AND current_version_id = @version`.
   - One row: this version becomes `ingested`; in case (a) only, the version it replaces becomes `superseded`; the chunk set served for (document, this physical index) becomes `retired`, the pair's `served_chunk_sets` row points at the new chunk set, and that set becomes `served`. In case (b) `current_version_id` doesn't change, so a building-index Flip changes only the building index's served row.
   - Zero rows: the chunk set becomes `retired`, a version still `ingesting` becomes `superseded`, and the item is skipped with `document_deleted` (the document is deleted) or `superseded_by_newer`.
2. **The building-index build is an item of the open rebuild run.** When case (a) commits one row and the logical index has a physical index `@b` in state `building`, the same transaction runs `INSERT app.ingestion_run_items (id, run_id, operation, search_index_id, physical_index_id, document_id, document_version_id, priority) SELECT NEWID(), <@b's build_run_id>, 'ingest', @index, @b, @document, @version, 1 WHERE NOT EXISTS (<an item of any run for this version and @b in 'queued', 'running' or 'succeeded'>) AND NOT EXISTS (<an item of @b's build run for this version>)`, and the Flip's output reports `buildingItemQueued`. The upload run keeps its one item for the version, the `index_rebuild` run gains at most one, and the new item runs at bulk priority (1), like the rest of the rebuild.
3. **No version is current without an item that builds it into the building index**, because making it current and queuing that item are one transaction. The repoint condition (ADR 0045: no live document lacks a `served_chunk_sets` row in the building index for its current version) is counted by the dispatcher's sweep and counted again inside the repoint transaction under the same `UPDLOCK` on the logical index row, so a Flip and a repoint never interleave.
4. **Stale builds lose.** A rebuild item still building a version that stopped being current fails guard (b) at its Flip: its chunk set is `retired` and the item is skipped `superseded_by_newer`, while the item rule 2 queued fills the building index with the newer version. A rebuild item that flipped V1 into the building index before V2 became current leaves V1 served there only until V2's building-index item flips; until then the repoint condition is false.
5. **A target that changed while the item ran.** Validate, finding its target `retiring` or `deleted` while the logical index has an active physical index, re-targets the item in place (`UPDATE app.ingestion_run_items SET physical_index_id = @active WHERE id = @item AND claim_count = @claim AND state = 'running'`) and continues, unless an item of any run already covers the version there (`queued`, `running` or `succeeded`: skipped `target_repointed`); with no active physical index the item is skipped `target_retired`. The Flip, finding its target in neither the active nor the building state (repointed or abandoned after Validate), retires the chunk set and, when an active physical index exists that no item covers for this version, re-targets the item to it and returns it to `queued` with `not_before` = now (outcome `requeued`, no outcome code; the next claim starts again at Validate); otherwise it skips `target_repointed` or `target_retired`. Validate never inserts an item; rule 2 is the only insertion a Flip makes.
6. **A logical index without an active physical index** (its first creation, or a rebuild of a `failed` index) takes uploads into its building physical index; `create_search_index` makes that index `active` in the transaction that records it provisioned, and the claim gives an `ingest` item a slot only once its target is provisioned, so every Flip into it is an active-index Flip.
7. **A failed building-index item changes only itself.** `record_item_outcome` with `failed` retires the item's chunk set, and fails the version only when the item targets the active physical index (or, with none, the building one) and the version is `pending` or `ingesting`. A failed rebuild item of a current version leaves that version `ingested` and served by the active index.
8. **Deletes during a rebuild.** `adminDeleteDocument` (ADR 0040) deletes the document's `served_chunk_sets` rows in every physical index and cancels its queued items in the same transaction, so a deleted document leaves the repoint condition at once.
9. **Run accounting.** The `index_rebuild` run finalises only when it has no `queued` or `running` item and no physical index in state `building` names it as `build_run_id`; items added by rule 2 count in its totals, and its finalisation alone ends the logical index's `rebuilding` status.

## Alternatives considered

- **Build both physical indexes inside the upload item.** Rejected: one sub-orchestration would build two chunk sets and record one outcome for two targets, so a building-index failure would fail an upload whose version already serves readers, and every retry would repeat both builds.
- **A second item for the version in the upload run.** Rejected: it breaks one item per document version per run (`UX_run_items_run_version`), and the upload run's totals would count one file twice.
- **A new run per version for the building index**, created by the Flip. Rejected: the item that holds back the repoint would sit outside the `index_rebuild` run that admins follow on the Indexes and Ingestion runs screens, and the rebuild run's finalisation rule couldn't see it.
- **Whichever Flip commits first makes the version current.** Rejected: when the building-index Flip wins, chat cites a superseded version (`410` on open) until the active-index Flip commits, and the result depends on commit order, which nothing controls.
- **Refuse uploads while an index rebuilds** (`409 index_busy`). Rejected: a large rebuild runs for hours at bulk priority, and admins must be able to update documents during it.
- **One catch-up pass at repoint time.** Rejected: the repoint would wait for a batch that starts only at the end, and a version changing during the pass needs another pass; queuing at the Flip keeps the building index current one version at a time.

## Consequences

- The building index only ever converges on current versions, the repoint condition stays one count query, and every run keeps one item per version, so run totals and the run screens stay exact. A rebuild never serves an older version, and readers never see a gap.
- A version uploaded during a rebuild is extracted, enriched, chunked, embedded and indexed twice, so its Document Intelligence pages and its summary and embedding tokens are billed twice; its building-index item waits at bulk priority behind interactive items.
- Each update during a rebuild adds one bulk item to the rebuild run and postpones the repoint until that item flips. A failed rebuild item holds the repoint back until an admin re-ingests the document (`adminReingestDocument`, which targets the building physical index while one exists, in a `document_reingest` run of one item) or an operator abandons the rebuild (`docchat-ops ingestion abandon-rebuild`, ADR 0054). `adminGetIndex` shows `rebuildProgress` (`servedCurrent`, `liveDocuments`), and the run lists the failed item with its code.
- The `index.reingest_started` audit row's `itemCount` counts the items created when the rebuild starts; the run's totals at finalisation also count the items Flips added.
- The guarantee holds only while every write of `documents.current_version_id` goes through the Flip's guarded update or the delete flow: the database role `docchat_config_operator` holds only `SELECT` on `app.documents`, and no migration may set the column.
- Tests (84-testing.md): an update while a rebuild runs, with the building-index Flip forced to commit before the active-index one, after which the repoint serves the update; one item per version per run, `adminReingestDocument` during a rebuild creating one item into the building index, and no building-index item added when the rebuild run already holds one for the version; a retried Flip after a committed attempt changing nothing, and a Flip whose target was repointed after Validate returning the item to `queued` against the new active index; Validate re-targeting in place and never inserting; an older version's Flip after a newer one committed ending `superseded`; the repoint itself.
- Runbook (86-operations.md, stuck runs): open the rebuild run, find the failed item and its code, then re-ingest the document or abandon the rebuild.
