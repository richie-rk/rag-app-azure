# ADR 0071: Conversation documents and a write-once turn trace

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 80-data-model.md, 13-conversations-and-memory.md, 12-chat-pipeline.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, CONTEXT.md
- **Related ADRs:** 0014, 0015, 0024, 0030, 0032, 0033, 0056, 0059, 0072, 0073, 0074, 0078, 0079, 0149

## Context

The product owner requires conversations to live in Cosmos DB, partitioned by user, kept indefinitely, encrypted at rest and readable for debugging only through privileged, audited access. Every turn must keep a complete record of how its answer was produced: the question, the standalone query, the answer, citations, retrieved chunk IDs with their scores, the exact text sent to the model, whether search was broadened, the deployments used, token usage per call and timings. Logs and traces carry only metadata and pointers, so an investigation follows a session and turn ID from telemetry into this store, and the store is the one place that holds prompt text. Every Cosmos DB query on the chat path must be single-partition, and the integration emulator must support hierarchical partition keys.

Three isolation needs shape the store. A user is identified only by the validated token's Entra object ID, never by an email address or part of one, so two people can never share data. Every query is a constant text with parameters, scoped to the caller's own partition, so no request value can widen it. A session belongs to one project, so history never crosses projects, and a session in a project the user can't reach now stays hidden.

The access pattern decides the layout. The session document is read at every turn start and replaced when a turn starts, when it ends and when a summary rebuild runs. The turn document is read by every session read and changed after finalisation by three kinds of patch (follow-ups, feedback, memory-extraction state). The diagnostic record is written once and read only by operators; its exact model input reaches about 800 KB at the largest context budget (200,000 tokens).

Cosmos DB facts that bound the choice: an item holds at most 2 MB of UTF-8 JSON and an `id` of at most 1,023 bytes; a transactional batch commits all-or-nothing only for point operations with the same full partition key, with at most 100 operations, 2 MB and 5 s; a hierarchical key has up to 3 levels and is set only when the container is created, point reads need the full key, and a leading-prefix query is a targeted cross-partition query; each full key is a logical partition of at most 20 GB, while a prefix may exceed 20 GB. The request-unit charge of reading or writing an item grows with its size, and a partial update (patch) is billed like any other write, with no significant reduction. Fewer indexed paths lower the charge of every write; partition-key paths aren't indexed unless included, and each level of a hierarchical key should be; an `ORDER BY` over two or more properties needs a composite index, which also serves the opposite order on all its paths.

## Decision

1. **One logical partition per session.** Container `conversations` in database `docchat` (ADR 0030) has partition key paths `/userId` then `/sessionId` (`kind: MultiHash`, `version: 2`) and no unique keys, because every ID is derived and unique within its logical partition. Every document of a session lives in the logical partition `[userId, sessionId]`. The `userId` of every read, write and query is the validated token's `oid`, lower-case hyphenated; no request field, header, path segment or cursor supplies it, and a `sessionId` from a path or body is only ever combined with the caller's own `oid`, so a guessed session ID resolves inside the guesser's own partition. Every query is a constant text with `@` parameters, the `type`, `status` and state literals included. `defaultTtl` follows `conversationRetentionDays` (`-1` when 0, ADR 0032), and no document carries its own `ttl`.
2. **Three document types, told apart by `type`.** Every document carries `id`, `userId`, `sessionId`, `type` and `schemaVersion`.
   - `session`, one per session, `id` = session ID: `projectId` (never changes), `title` (1 to 80 code points, never changes, ADR 0079), `createdAt`, `updatedAt`, `lastTurnAt`, `turnCount`, `activeTurn` (`{turnId, deadlineAt}` or null, ADR 0056), `history.unsummarisedTokens`, `history.unsummarisedTurns`, `summary` (`text`, `tokens`, `coversThroughSeq`, `version`, `updatedAt`, `deployment`, `lastUsage`; ADR 0074) and `summaryJob` (`leaseExpiresAt`, `consecutiveFailures`, `notBefore`, `lastErrorCode`, `lastAttemptAt`, `lastSucceededAt`).
   - `turn`, one per turn, `id` = turn ID (ADR 0056): what the user sees and every field that changes after finalisation: `seq`, `clientTurnId`, `projectId`, `status`, `question`, `answer`, `answerTruncated`, `finishReason`, `error`, `citations` (`StoredCitation`), `allowedLinks`, `followups`, `followupsAt`, `feedback`, `historyTokens`, `usage` (`TurnUsage`: per-call `ModelCallUsage` records, `totals` and `billable` counts), `memoryExtraction`, `traceId`, `deadlineAt`, `createdAt`, `endedAt`, `updatedAt`.
   - `turn_trace`, one per finalised turn, `id` = UUIDv5 over namespace `fc6c167c-bdc0-407d-9fcb-0bb4c6a2c701` and the name `"{turnId}:trace"`: `turnId`; `rewriteOutcome` (`skipped`, `rewritten`, `fallback`); `standaloneQuery`; `searchQuery`; `retrieval` (null when the turn ended before retrieval; otherwise `searchIndexId`, `physicalIndexId`, `physicalIndexName`, `indexSource`, `queryEmbeddingDeployment`, `embeddingModel`, `embeddingDimensions`, `candidateCount`, `keepCount`, `rerankerThreshold`, `minConfidentResults`, `rerankPartial`, `broadenAttempted`, `broadened`, `broadenOutcome`, `searchPassage`, `firstPass` and `broadenedPass` with at most 50 results each as `{chunkKey, documentId, chunkSetId, searchScore, rerankerScore, served}`, at most 16 `kept` sources, and `screening`); `modelInput` (null when generation wasn't reached; otherwise the answer call exactly as sent: `rulesVersion`, `marker`, `deployment`, `model`, `maxCompletionTokens`, `reasoningEffort`, `messages`, `promptTokens`, `droppedTurns`, `droppedSourceIds`); `promptBudget` (`budgetTokens`, `completionReserveTokens`, `memoryFactsIncluded`, `summaryIncluded`); `deployments` (`chat`, `small`, `queryEmbedding`); `timings` (integers in ms, from `rewriteMs` to `totalMs`); `contentFilterDegraded`; `createdAt`; `redactedAt`.
   The conversation store owns these field names and limits; the chat pipeline supplies the values under those names.
3. **The trace is write-once.** It is created in the finalisation batch together with the turn and session replacements (ADR 0072) and never changed, with one exception: the legal-removal redaction of ADR 0149 replaces the bodies of a withdrawn document's `SOURCE` blocks with `[removed]` and sets `redactedAt`, under an ETag condition. No app operation returns a trace or any of its fields; operators read it only through just-in-time access (ADR 0024), and it is exported and deleted with the user's data (ADR 0033).
4. **Size limits**, validated by the document models before every write: a `turn` at most 350,000 bytes of UTF-8 JSON, a `turn_trace` at most 1,300,000 bytes and a `session` at most 64,000 bytes, so a finalisation batch carries at most 1,714,000 bytes, below the 2 MB limit of a batch and of an item. Inside them: question 1 to 4,000 code points, answer at most 100,000 code points, title 1 to 80 code points, at most 16 citations, at most 50 allowed links of at most 2,048 characters each, at most 3 follow-ups of 1 to 200 characters, a feedback comment of at most 2,000 code points, at most 10 usage records, summary text at most 6,000 code points and `summary.max_summary_tokens` tokens. A trace above its limit is written with `modelInput` set to `{"omitted": "size_limit"}` and increments `docchat.conversations.trace_truncated`. Every other breach is a programming defect: `500 internal_error` before streaming, the `error` event `internal_error` after; nothing is truncated silently.
5. **Indexing only what queries use.** `indexingMode: consistent`, `automatic: true`; included paths `/userId/?`, `/sessionId/?`, `/type/?`, `/projectId/?`, `/lastTurnAt/?`, `/seq/?`, `/status/?`, `/endedAt/?`, `/memoryExtraction/state/?` and `/retrieval/kept/[]/documentId/?` (the redaction query of ADR 0149); excluded paths `/*` and `/"_etag"/?`; one composite index `[(lastTurnAt ascending), (sessionId ascending)]`, which serves the session list's `lastTurnAt` descending, `sessionId` descending order (ADR 0078). Questions, answers and model input add no index cost.
6. **Versioned, typed documents.** Every document carries `schemaVersion: 1`. The Pydantic models in `docchat_core.cosmos` (module `conversations`, beside its repositories) ignore unknown fields when reading and forbid them when building a write, so during a rolling deployment the release being replaced reads documents the next one wrote; a change an older reader can't handle needs a new `schemaVersion` and two releases (expand, then contract). The conversation store of ADR 0073 makes every app read and write; the operator commands that export, delete or redact (ADR 0033, ADR 0149) use the same repositories and models.

## Alternatives considered

- **Turns as an array inside the session document.** Lost: every turn would replace one growing item; the 500 turns a session may hold (up to 350,000 bytes each) can't fit in one 2 MB item; every session read would pay for every turn; concurrent writes would contend on one ETag.
- **Diagnostic fields on the turn document.** Lost: every follow-up, feedback and memory-state patch and every session read would pay request units for up to about 800 KB of model input, because a patch is billed like a full write, and a large prompt would push the turn towards the 2 MB item limit. The turn stays the one record of each turn that users and session reads see; the trace is its companion in the same partition.
- **The trace in its own container, in Blob Storage or in Log Analytics.** Lost: a batch can't span containers or services, so a turn could exist without its trace or the reverse; Log Analytics would put prompts and retrieved text into logs, which must carry metadata only; a blob store adds a second data path, identity and access-review scope for the same content.
- **A trace that later steps may update.** Lost: a record that never changes is evidence an investigator can trust, and it keeps the redaction as the one deliberate, audited change.
- **A single-level key `/userId`.** Lost: a user's whole history would share one logical partition capped at 20 GB, while each session needs only its own partition for its batches.

## Consequences

- Easier: follow-up, feedback and memory-state patches touch a small item; session reads are cheap; one batch makes a turn, its trace and its session agree; an investigation reads one logical partition by session and turn ID.
- Harder: each finalised turn writes two documents; reading a trace needs just-in-time access; export, deletion and redaction cover traces explicitly (ADR 0033, ADR 0149).
- With retention on (ADR 0032), each item expires from its own last change, so a trace can expire before its turn when later feedback or memory-state patches keep the turn alive, and a turn before its session.
- Obligations: tests that a turn above 350,000 bytes is refused and a trace above 1,300,000 bytes is stored with `modelInput` omitted and the metric incremented; that the session and turn views carry no trace field; that every call between `begin_turn` and the terminal event names the full `[oid, sessionId]` key and that prefix queries happen only in the session list and the post-turn work; that the first turn creates session and turn in one batch and a failed turn create leaves no session; that cross-user and cross-project reads answer `404`; and that redaction changes only `SOURCE` bodies and `redactedAt`. The integration emulator is pinned by digest at a tag with hierarchical keys (`vnext-EN20260907` or a later evaluated tag).
- Throughput is sized from about 300 RU per completed turn including post-turn work (begin 25, history query 5, finalisation 90 with a 100 KB trace, follow-ups 15, memory work 50, amortised summary 40, reads 75) until the load test measures it; the load test's pass mark is a p95 of at most 400 RU per completed turn. Monitoring: `docchat.conversations.trace_truncated` and the `docchat.conversations.request_charge` histogram by operation.
- Risk: the Linux emulator lists composite and range indexes as not yet available, so the indexing policy is proven only against the real service: by the deployed tests and by the load test's session list for a user with 500 sessions at a p95 of at most 200 ms.
- Risk: traces keep the source text sent to the model for as long as conversations are kept (indefinitely by default), so a withdrawn document's text stays in them until the redaction of ADR 0149 runs.
