# ADR 0046: Method interface, catalogue and versions

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 14-ingestion.md, 80-data-model.md, 11-api.md, 10-web-client.md, 86-operations.md, 84-testing.md, 01-repository.md, CONTEXT.md
- **Related ADRs:** 0002, 0027, 0034, 0037, 0044, 0045, 0047, 0048, 0050

## Context

The product owner decided that each index's ingestion method comes from a catalogue that grows over time, that an index's method can be swapped, and that the product supports the re-ingest a swap needs. Every method implements one interface in `packages/core` (extract, enrich, chunk), declares a typed parameter schema and registers by key and version, and adding a method must cost code plus one migration row and nothing else. Sources left for later (audio and video transcripts, source-code repositories, images) must arrive as a new method plus a new allowed file type, with no redesign.

A chunk set is unique on (document version, physical index, method version, parameter hash), and a re-ingest whose key matches the served chunk set does nothing. A served chunk set therefore has to be an exact record of the code and parameters that built it.

The two halves of a method run in different processes. The API validates parameters when an admin creates or edits an index and serves each method's schema to the admin form, but it never parses a document. Only the ingestion image carries the parsing stack: `unstructured` with torch, OpenCV and Tesseract for the page-wise method (ADR 0047), and the Document Intelligence client for the recursive method (ADR 0048).

Two further needs shape the design. A request, run or queue message must never be able to ask for a processing mode that no code implements, because such a request is accepted and then fails out of sight. And every change to how chunks are produced must travel through a version and a migration, so an index can always be rebuilt to match the code.

Constraints: the admin form renders a subset of JSON Schema; the draft 2020-12 validation vocabulary defines `minimum`, `maximum`, `multipleOf`, `minLength`, `maxLength`, `minItems`, `maxItems`, `uniqueItems`, `required`, `enum`, `const`, `title`, `description` and `default`. Schema changes run through Alembic (1.20.0) migrations that the deploy identity applies before the apps deploy, expand then contract (ADR 0027).

## Decision

1. **Interface in core.** `docchat_core.ingestion.methods` holds:
   - `MethodDescriptor`: `key` (1 to 64 characters of `a` to `z`, `0` to `9` and `_`), `version` (integer, at least 1), `display_name`, `description`, `parameters_model` (a Pydantic v2 model with `extra="forbid"`), `parameter_schema` (the hand-written JSON Schema constant of item 4) and `supported_content_types`;
   - the protocol `IngestionMethod`: `extract_plan(source) -> ExtractPlan` (the whole document, or page ranges), `async extract(ctx, params, part) -> ExtractResult`, `async enrich(ctx, params) -> EnrichResult` and `async chunk(ctx, params) -> ChunkResult`, where every context object carries only blob paths, IDs and settings, never document content;
   - `MethodRegistry.register(descriptor, implementation)`, keyed by (`key`, `version`), raising on a duplicate key and version;
   - the parameter models `PagewiseParametersV1` and `RecursiveParametersV1` (ADRs 0047 and 0048) and `parameter_hash()`.
2. **Implementations in the ingestion app.** `docchat_ingestion.methods.pagewise` and `docchat_ingestion.methods.recursive` register against the core descriptors when `docchat_ingestion.function_app` is imported. Import contracts checked in CI keep `docchat_core` free of both apps and keep `docchat_api` and `docchat_ingestion` independent, so the API loads descriptors and parameter models and never a parsing library.
3. **Catalogue table.** `app.ingestion_methods`: `method_key NVARCHAR(64)` (`CHECK (method_key COLLATE Latin1_General_BIN2 NOT LIKE '%[^a-z0-9_]%')`), `method_version INT` (`CHECK (method_version >= 1)`), `display_name NVARCHAR(100)`, `description NVARCHAR(500)`, `parameter_schema NVARCHAR(MAX)` (`ISJSON`, the descriptor's constant), `default_parameters NVARCHAR(MAX)` (`ISJSON`), `supported_content_types NVARCHAR(400)` (a JSON array of media types, `ISJSON`), `is_active BIT NOT NULL DEFAULT 1` and `created_at DATETIME2(3) NOT NULL DEFAULT SYSUTCDATETIME()`; primary key `PK_ingestion_methods` (`method_key`, `method_version`), referenced by `search_indexes` and `chunk_sets` through (`method_key`, `method_version`). The first migration seeds two active rows, both for PDF, DOCX and PPTX: (`pagewise`, 1, "Page by page", "One passage per page, with tables summarised and kept as structured tables. Uses the built-in parser.", defaults `{"summarizeTables":true,"ocrLanguages":["eng"]}`) and (`recursive`, 1, "By headings and paragraphs", "Splits by headings, then paragraphs and sentences, into passages of a target size. Uses Azure AI Document Intelligence.", defaults `{"targetTokens":512,"overlapPercent":25,"tableMaxTokens":1600}`). `docchat_api`, `docchat_ingestion` and `docchat_config_operator` hold SELECT only; rows change only through migrations.
4. **Parameter schemas.** Each descriptor's schema is a hand-written JSON Schema (draft 2020-12) constant inside the admin form's subset: a root with only `type: object`, `properties`, `required` and `additionalProperties: false`; properties of type `integer` or `number` (`minimum`, `maximum`, `multipleOf`), `boolean`, `string` with `enum` or with `oneOf` of `{const, title}`, `string` with `minLength` and `maxLength`, or `array` of such enumerated strings (`minItems`, `maxItems`, `uniqueItems: true`); and per property `title`, `description` and `default`. The migration stores the same text in `parameter_schema`.
5. **Choosing a method through the API.** `adminGetIndexOptions` returns the active rows ordered by key, then version descending (`key`, `version`, `displayName`, `description`, `parameterSchema`, `defaultParameters`, `supportedContentTypes`), with `defaults.methodKey` `recursive` and `defaults.methodVersion` 1. `adminCreateIndex` takes `methodKey` (required), `methodVersion` (optional: the key's highest active version) and `methodParameters` (optional: the method's defaults) and checks, in this order, `422 method_not_found` (`body.methodKey`, reason `not_found`), `422 method_inactive` (`body.methodKey`, `not_allowed`) and `422 invalid_method_parameters` (one `errors[]` entry per failing field at `body.methodParameters.<name>`, reason `required`, `unknown_field`, `invalid_type`, `out_of_range`, `too_many_items`, `duplicate` or `not_allowed`). The index stores `method_key`, `method_version`, `method_parameters` (validated, defaults filled) and `method_parameter_hash`. `adminUpdateIndex` takes the same fields: a new key without parameters takes that method's defaults, and parameters alone are validated against the method the index will have; method fields change only while the status is `ready`, `reingest_required` or `failed` (`409 index_busy`), after which the status becomes `compute_index_status(index_id)`.
6. **Parameter hash.** `parameter_hash()` is the SHA-256 of the UTF-8 bytes of `json.dumps({"key": method_key, "version": method_version, "parameters": params}, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`, where `params` is the validated model's `model_dump(mode="json", by_alias=True)` with defaults filled. It is stored as `BINARY(32)` on the index and on every chunk set.
7. **Every build records its method.** Validate reads the index's method key, version, parameters and hash inside its transaction. It skips with `already_served` when the target's served chunk set is for this version with the same key, version and hash; otherwise it reuses or inserts the chunk set under `UX_chunk_sets_build_key` (`document_version_id`, `physical_index_id`, `method_key`, `method_version`, `parameter_hash`, filtered to `building`, `ready` and `served`) and stores the parameters in `chunk_sets.method_parameters`. The item's plan carries `method: {key, version, parameters, parameterHash}`, and every later activity runs the implementation and parameters the plan names, so an edit to the index during a run never changes a build in progress.
8. **Re-ingest marking.** `compute_index_status(index_id)` returns `reingest_required` when any live document's served chunk set in the active physical index has a method key, version or parameter hash other than the index's, or when the active physical index's model, dimensions, analyzer or schema version differ from the index's settings (ADR 0045); otherwise `ready`. The admin screen shows its Re-ingest needed banner for that status, and `adminStartReingest` queues every current version at bulk priority.
9. **Consistency checks.** Unit tests fail when a migration row differs from its descriptor (key, version, display name, description, schema text, defaults, content types), when a schema uses a keyword or type outside the subset of item 4, and when a schema and its Pydantic model disagree on any boundary or default value (the schema side checked with `jsonschema`, a test-only dependency). `docchat_ingestion.function_app` raises at import when an active row has no registered implementation, so the host loads no function and ingestion fails closed.
10. **Any behaviour change is a new version.** A change to a method's code, or to `apps/ingestion/models.lock.json`, that changes the chunker's output on the four fixture documents (`tables.pdf`, `scanned.pdf`, `headings.docx`, `slides.pptx`) ships as (`key`, `version + 1`). The code registers the new version with its own parameter model and schema. One migration adds its row, sets the prior row's `is_active` to 0, moves every index on the prior version to the new one, validating its stored parameters with the new model (defaults fill added fields) and writing the recomputed `method_parameter_hash`, and sets each moved index in `ready` or `reingest_required` to `reingest_required`; indexes in `deleting` or `deleted` aren't moved, a moved index in `provisioning` needs no re-ingest, one in `reingesting` or `rebuilding` reaches its status through `compute_index_status` when its run ends, and a `failed` one keeps `failed` (80-data-model.md section 2.24). The prior implementation stays registered in that release, so items planned on it before the deploy finish, and is deleted in the next release; its row stays, inactive, because chunk sets and run history reference it. A version is never changed in place, and version numbers are never reused.
11. **No request chooses a mode.** The queue message carries only the run ID and trace context (ADR 0037); an item's operation is a closed set stored in SQL (`ingest`, `cleanup_document`, `create_physical_index`, `delete_physical_index`, `purge_index_blobs`); the method comes only from the index's row, which the API accepts only for an active catalogue row.

## Alternatives considered

- **Implementations in `packages/core`.** Rejected: the API image would carry `unstructured`, torch, OpenCV and Tesseract bindings, with their size and their vulnerability surface, for code the API must never run, because documents are parsed only in the ingestion app.
- **A catalogue in code only, with no table.** Rejected: the foreign keys from `search_indexes` and `chunk_sets` need a row per version, migrations must record when a method ships, and retired versions must stay visible to run history after their code is deleted.
- **A catalogue in SQL only, with schemas edited as data.** Rejected: the schema must agree with the Pydantic model that validates parameters, so the descriptor in code is the source and the row its tested copy.
- **Schemas generated from the Pydantic models at run time.** Rejected: a generated schema follows the generator's conventions (titles derived from field names, no per-value titles for the language list), which can move with a library upgrade and would leave the form's subset; a constant compared with the model by test stays stable.
- **Changing a method's behaviour under its current version number.** Rejected: the build key would then claim that chunks built by different code are current, a re-ingest would skip them as `already_served`, and no banner would tell admins.
- **Plug-in discovery through package entry points.** Rejected: an installed package could add a method with no migration row, schema review or start-up check; explicit registration keeps every method visible in code review.
- **A mode or parser named in the request or queue message.** Rejected: a caller could then ask for work no code performs, and the method belongs to the index, not to the request.

## Consequences

- A new method is one parameter model, descriptor and schema constant in core, one implementation in the ingestion app and one migration row; a new file type also needs its extension and signature check in the upload flow, which keeps the later sources possible without a redesign.
- Every behaviour change re-ingests every index on that method, paying again for Document Intelligence pages, table summaries and embeddings; a model pin change that alters chunker output counts as a behaviour change.
- The pull request that regenerates a fixture expectation file must also register a new version; code review checks it, because no test can tell an intended output change from an accidental one.
- Deploy window: migrations run before the new image starts (ADR 0027). An item whose plan names the new version while the prior image still runs gets retryable `internal_error` at its next activity and succeeds on a later attempt once the new image runs (the retry schedule of ADR 0050 spans about 16 minutes).
- Inactive rows accumulate, one per retired version; each is a few hundred bytes and keeps foreign keys and history intact.
- Obligations: the tests of item 9, the parameter-hash test (equal for any key order, different for another key or version, computed after defaults), the `compute_index_status` test after a method change, and the runbook for shipping a new method version (86-operations.md), which also covers updating model pins with `apps/ingestion/image/fetch_models.py --update <repository> <revision>`.
