# ADR 0133: Generated authorisation matrix and isolation registry

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Product owner and architect
- **Specified in:** 84-testing.md, 11-api.md, 82-security.md, 01-repository.md
- **Related ADRs:** 0012, 0013, 0017, 0019, 0020, 0023, 0030, 0131, 0143

## Context

Every browser-facing operation sits behind two authentication layers, and the API decides access from validated token claims and fresh SQL checks (ADR 0017, ADR 0020). An unreachable project, index, document, session or turn answers `404`, never `403`, so a caller can't learn that a resource exists; admin routes need the `Admin` app role; only `GET /healthz` is public (ADR 0023). The product requires cross-project access tests for every endpoint: an authorisation matrix that enumerates every route in the OpenAPI document (`401` for an unauthenticated call, `403` for a non-admin on admin routes, `404` for a signed-in user without access), and isolation tests on chat, retrieval, sessions, memory, feedback, citations, documents and ingestion status.

A hand-written list of authorisation tests drifts from the routes it guards: a new route ships with no case, and an operation that acts on whatever user, session or project the request names goes unnoticed. Revoked access must take effect on the next request, and a session must never be read through another project. Several operations also name resources inside the request body (`createChatTurn` names `projectId` and `sessionId`), which a generator reading only path and query parameters can't see.

Vendor facts: OpenAPI 3.1 allows specification extensions whose field names begin with `x-`; FastAPI writes them into the operation object of the generated document; HTTPX's `ASGITransport` sends requests to an ASGI app in-process; RFC 9457 lets a problem type add extension members.

## Decision

1. **Access metadata is the input (ADR 0013).** Every operation carries `x-docchat-access` (`public`, `user`, `admin`), `x-docchat-scoped-params` (each parameter that identifies a resource subject to a reachability or existence check: a path or query parameter name, or `body:<JSON pointer>` for a body field, such as `body:/projectId` and `body:/sessionId` on `createChatTurn`, `body:/projectId` on `adminReserveUpload`, `body:/initialMemberIds` on `adminCreateProject` and `body:/versionIds` on `adminSubmitUploads`; an empty list when none) and `x-docchat-error-codes`. An operation whose valid body can't be generated from its schema alone carries an OpenAPI request example that the API accepts: `adminCreateProject` (a constant name, no initial members), `adminUpdateProject` (one field, no `status`), `adminMapProjectIndex` (`isDefault: true`), `adminCreateIndex`, `adminUpdateIndex`, the upload operations and `createChatTurn`. A contract test sends each example to an in-process app with seeded data and expects success.
2. **The matrix test.** `apps/api/tests/integration/test_authorization_matrix.py`, on the harness `docchat_testing.authz_matrix`, runs in CI job `python-tests` on every pull request. It builds the document from the app under test (`app.openapi()` through the API's exporter, never the committed `apps/api/openapi.json`, so a route left out of the export can't hide) and emits one parametrised pytest case per operation and check. The app under test receives `fakes.PermissiveBurstLimiter` and `fakes.PermissiveWriteRateLimiter`, so the hundreds of requests each principal sends never meet a `429`; the limiters' own answers are tested elsewhere with the real implementations (ADR 0143).
3. **Seeded world and principals.** Tokens are RS256 v2 access tokens minted with a per-session 2,048-bit key pair that the API's injectable signing-key provider serves. Principals: `alice` (`User`, member of project A), `bob` (`User`, member of project B), `carol` (`Admin`, no memberships), `dave` (`User`, no projects), `erin` (a valid token with no `roles` claim). Projects A and B each hold mapped indexes, documents, versions, runs, sessions, turns, citations and memory facts. Each request comes from the operation's OpenAPI example when it has one, otherwise from its request schema through `schema_fill`, and every ID is resolved by one name-to-kind map: `projectId` → project, `indexId` → index, `documentId` → document, `versionId` → document version, `runId` → ingestion run, `sessionId` → session, `turnId` → turn, `citationNumber` → citation, `factId` → memory fact, `userId` → user. A scoped name outside the map fails the suite; an ID the world can't resolve fails the case `unresolved_example`.
4. **The checks.** (1) Every operation has all three extensions; a missing one emits the failing case `missing_access_metadata`. (2) The `public` set is exactly `GET /healthz`, which answers an anonymous call `200` with an empty body. (3) Every other operation answers `401` with no `Authorization` header, with `Bearer not-a-token`, and with no header and a 33 KiB body (never `413`, so authentication runs before the body is read). (4) Every non-public operation answers `erin` `403 role_not_assigned`. (5) Every `admin` operation answers `alice` `403 admin_required` with real IDs, with random IDs and with an invalid body, never `404`, `412`, `422` or `428`. (6) For each scoped parameter of a `user` operation, `alice` gets the operation's not-found answer both when the ID belongs to project B and when it is a random UUID, and the two problem bodies are byte-identical once `correlationId` is removed; for `admin` operations, `carol` gets the not-found answer for a random UUID. The not-found answer is the operation's `404` code from `x-docchat-error-codes`, except at `body:/initialMemberIds`, where it is `422 validation_failed` with reason `not_found` at `body.initialMemberIds.<i>` for both IDs; at an array pointer the harness substitutes into every element. (7) The unmodified request with the right caller (`alice` for `user`, `carol` for `admin`) answers `2xx`, which proves the refusals are real.
5. **Fail rules.** An operation that yields fewer than three cases fails the suite. A meta-test runs the generator against a small app and proves it fails a route without an extension, two `404` bodies that differ, and an operation with fewer than three cases.
6. **One isolation registry.** `docchat_testing.isolation.DATA_PATHS` holds every cross-project and cross-user case of every component, and `tests/integration/isolation/` runs them all against the emulators through the API. An entry has a dotted name (`chat.other_project`, `conv.sessions.revoked_and_restored`), and names its owning component, its data path, its actor (one of the five principals, with its fixture role), its setup as builder calls (memberships, mappings, sessions and facts are created here), its action and its expected result; an entry whose expected result is a refusal or an absence is a negative case. Required assertions: **chat**, `alice` in project B → `404 project_not_found`, a session from B → `404`, and every chunk retrieved for A comes from an index mapped to A (read from the turn's stored retrieval record); **retrieval with a shared index**, an index mapped to A and B serves both (positive control), and an override for `alice` in A to an index not mapped to A is refused by the composite foreign key; **sessions**, the list holds only `alice`'s sessions in reachable projects, `bob`'s session → `404`, removing `alice` from A hides A's sessions and restoring the membership shows them again; **memory**, any operation on `bob`'s fact ID → `404`, and the Cosmos DB audit wrapper records only `alice`'s partition key; **feedback**, on `bob`'s turn → `404`, on her own turn in a revoked project → `404`; **citations**, `bob`'s turn → `404`, her own turn after revocation → `404`, a superseded version → `410`; **documents, uploads and ingestion status**, a non-admin → `403 admin_required`, and an admin's document list, document reads and upload calls for index X never return or touch index Y's documents or versions; **overrides**, an expired override is ignored.
7. **Who writes entries.** Identity and access supplies projects, members, mappings, overrides and admin routes; ingestion supplies documents, uploads and ingestion status; the chat pipeline supplies chat, retrieval with a shared index and citations; conversations and memory supplies sessions, memory and feedback, each with revoke and restore. The isolation suite runs every entry and fails unless each data path (chat, retrieval, sessions, memory, feedback, citations, documents, ingestion status) has at least one negative entry.

## Alternatives considered

- **Hand-written authorisation tests per route.** Rejected: nothing forces a new route to get them; generation makes a missing case a build failure.
- **Generating from the committed `openapi.json`.** Rejected: a route registered on the app but left out of the export would escape the matrix; `app.openapi()` of the app under test lists what actually serves requests.
- **Inferring scoped parameters from names ending in `Id`.** Rejected: body fields and arrays need explicit JSON pointers, an inference rule can't tell a reference from a payload value, and explicit metadata is reviewed with the route.
- **`403` for a resource in another project.** Rejected: a `403` confirms that the resource exists, so the matrix asserts byte-identical bodies for a foreign ID and a random one.
- **Running the matrix against the deployed `dev` API.** Rejected: thousands of cases would need many test users, take minutes per run and meet the request limits; the in-process run takes seconds on every pull request, and deployed smoke tests cover platform authentication separately.
- **The real limiters in the matrix.** Rejected: one principal's burst of more than 40 requests gets `429 too_many_requests`, which would mask the answer under test.
- **One isolation test module per component.** Rejected: no single check could prove that every data path has a negative case; one registry gives one runner and one meta-check across components.

## Consequences

- A route can't merge without its three extensions and, when its body needs one, a working request example; adding a scoped parameter of a new kind means adding it to the name-to-kind map and the seeded world.
- Every refusal path must build its problem body from the code alone (one title and one safe `detail` per code, ADR 0012), because a foreign ID and a random ID must yield identical bytes apart from `correlationId`.
- Each owning component maintains its `DATA_PATHS` entries as its data paths change; an entry states its own memberships in setup, so components can use different project layouts without changing the shared principals.
- The matrix proves the in-app layer only. Platform authentication is proven by the deployed tests: an anonymous `GET /healthz` gets `401`, and the deployed test users `outsider`, `norole`, `member` and `admin` get `404`, `403 role_not_assigned`, `403 admin_required` and `isAdmin: true`.
- Tests (84-testing.md): the matrix over every operation, the isolation suite with its negative-case meta-check, the generator's own meta-test and the request-example contract test; all run on every pull request.
- Risk: a resource referenced in a way the metadata doesn't name escapes check (6). Review of `x-docchat-scoped-params` belongs to the route's owning component, and the isolation entries test each data path end to end as a second line.
