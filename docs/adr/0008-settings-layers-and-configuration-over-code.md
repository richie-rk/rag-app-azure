# ADR 0008: Settings layers and configuration over code

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 01-repository.md, 10-web-client.md, 80-data-model.md, 81-config.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0007, 0020, 0024, 0028, 0046, 0086, 0096, 0099, 0100, 0103, 0113, 0122, 0139

## Context

DocChat is a template that many organisations deploy, each in at least two environments, so everything that differs between deployments must be data or a setting, and nothing specific to a domain may sit in code. Values change on different lifecycles: infrastructure values change with a reviewed deploy, process values when an app restarts, operational limits while the system runs, and product data (projects, indexes, mappings, memberships) whenever an admin edits it. Ingestion parallelism, by the product owner's decision, is an operator setting in the database, never in the admin UI. Model deployment names, models and versions are deployment parameters, never constants in code. The web client is one build that serves every environment, configured by four public values written at deploy time. No secret may sit in code, configuration files, images, the browser bundle or CI. Every setting is a typed model, because a setting read as an untyped string turns `'false'` into true, and a setting evaluated as code executes whatever it contains. A client that falls back to a built-in endpoint when its configuration is missing can send users to the wrong environment.

Platform facts (checked 2026-10-14): app settings whose names contain a period aren't supported on Linux Elastic Premium or Dedicated plans; a configuration change restarts an App Service app; Key Vault references are refetched every 24 hours, and on Linux a reference to a vault behind a private endpoint needs all outbound traffic routed through the network.

## Decision

1. **Each value lives in exactly one layer.**

| Layer | Holds | Changed by | Read |
|---|---|---|---|
| Environment file `infra/env/<env>.json`, typed by the Bicep type `environmentConfig` (ADR 0096) | subscription, tenant and region, address space, SKUs and instance bounds, zone-redundancy switches, model deployments and embedding models with their deployment types, retention days, sampling ratio, alert thresholds, budget amount, group object IDs; never an IP address or a personal email | a reviewed pull request, then the pipeline | at provisioning |
| Runtime parameters of `infra/main.bicepparam`, read from environment variables | `environmentName` (`AZURE_ENV_NAME`), the three running image references, `operatorIpAllowlist` (at most 20 public IPv4 addresses), `resourceTokenSalt`, `releaseSha`, `opsAlertEmails`, `budgetStartDate` | the pipeline and its `preprovision` hook (environment name, images, release, budget start), the load workflow (token salt), operators through GitHub environment variables (allowlist, mailboxes) | at provisioning |
| `infra/shared.bicepparam` and `scripts/bootstrap/bootstrap.config.json` | the shared registry's and CI network's locations, the shared operator allowlist, approvers, operators and allowed role assignees | the bootstrap operator | by the bootstrap |
| GitHub variables (environments and repository) | client, tenant and subscription IDs, resource group, region, operator allowlist, alert mailboxes, the test vault's URI; the repository holds no Actions secrets | operators | by the workflows |
| App settings | endpoints, deployment names, models, versions and encodings, identity client IDs, timeouts, upload and process limits | a pull request and a deploy (the app restarts) | once, at process start |
| Image environment (`ENV`) | values bound to the image's own contents: `HF_HUB_OFFLINE`, `DO_NOT_TRACK`, `SCARF_NO_ANALYTICS`, `TIKTOKEN_CACHE_DIR`, `DOCCHAT_BUILD_COMMIT` | the image build | at process start |
| Key Vault references | third-party secrets; none exist in the first version | the pipeline | not used |
| `app.ops_config` | runtime operational values: ingestion parallelism, rate limits, quotas, retrieval and fallback thresholds, summary and memory caps, switches of built features | operators, `docchat-ops config set` or `reset` | one snapshot per request, refreshed after 60 s |
| SQL product tables | projects (description, instructions, example questions, default flag), logical and physical indexes with their method parameters, mappings, memberships | admins, through the admin API | on every request, except index records, cached at most 60 s (ADR 0020); memberships, mappings, overrides and project status are never cached |
| `app.user_index_overrides` | per-user index overrides for live testing | operators, `docchat-ops override` | on every request |
| `app.ingestion_methods` | the method catalogue | an Alembic migration when a method ships (ADR 0046) | with the index record |
| Web `config.json` | exactly `tenantId`, `clientId`, `apiBaseUrl`, `apiScope` | the deploy-time generator `apps/web/scripts/write-env-config.mjs` (ADR 0086) | at browser start-up |
| Local `.env` (gitignored) | `DOCCHAT_LOCAL_EMULATORS`, `DOCCHAT_LOCAL_SQL_SA_PASSWORD` | the developer | at process start; refused inside Azure |

2. **Names, and one source per value.** App settings are `DOCCHAT_<AREA>_<NAME>` in upper snake case; ops-config keys are dotted lower case `<area>.<name>`; platform-defined names keep their own (`APPLICATIONINSIGHTS_*`, `AzureWebJobsStorage__*`, `AzureFunctionsJobHost__*`, `FUNCTIONS_*`, `WEBSITE_*`, `WEBSITES_*`). No app-setting name contains a period, so host overrides use `__` and work on Linux Elastic Premium. A value that two places could hold is given one: the trace sampler variables `OTEL_TRACES_SAMPLER` and `OTEL_TRACES_SAMPLER_ARG` are set inside each process from `DOCCHAT_TELEMETRY_SAMPLING_RATIO`, never as app settings, and the Durable task hub name comes only from `AzureFunctionsJobHost__extensions__durableTask__hubName`, never from `host.json`.
3. **App settings are typed, read once and exact.** Pydantic Settings classes derived from `docchat_core.settings.DocChatSettings` (prefix `DOCCHAT_`, `extra="forbid"`, frozen) read them once at process start: `CoreSettings` and `AuthSettings` in `docchat_core`, `ApiSettings` in the API, and each component's own classes. An invalid or missing value stops the process before it serves; the start-up refusals `local_emulators_in_azure` (emulator mode with `WEBSITE_SITE_NAME` or `WEBSITE_INSTANCE_ID` set) and `insecure_endpoint` (an `http://` or loopback endpoint outside emulator mode) exit with code 78 and one log record; `DOCCHAT_CORE_ENVIRONMENT` `prod` with a non-empty `DOCCHAT_AUTH_TEST_CLIENT_ID`, client IDs that aren't distinct, and `local` inside Azure also stop the process. `infra/modules/compute/app-settings.bicep` composes each site's settings only from resource outputs, Graph outputs, environment-file fields, SKU maps and the owners' defaults in `infra/config/app-settings.json` (keys `api`, `ingestion`, `modelStub`); each site gets exactly the settings 81-config.md lists for it, none is set by hand, in the portal or by a script, and a deployed test reads both sites' settings and fails on any difference in either direction. Derived values are computed in `main.bicep`, never parameters: worker counts from the SKU maps, the prod zone-redundancy values and `DOCCHAT_SEARCH_MAX_INDEXES` from `{basic: 15, standard: 50}`.
4. **Ops config is typed, seeded and changed only by an audited command** (ADR 0028). One row per key; `docchat_core.opsconfig.OpsConfig` holds one Pydantic sub-model per area (`extra="forbid"`, every field aliased to its dotted key, every range declared, cross-field rules included) and no code default, because the database is the source. The Alembic revision that ships a key inserts it with `value_json` = `default_json` = `{"value": <default>}`; a contract revision deletes a retired key. A missing key or an invalid value in an area the process registered fails start-up; rows of unregistered areas are ignored, because an expand migration runs before the code that reads them. Callers take one immutable snapshot per request (per turn on the chat path, per wake in the dispatcher); the snapshot refreshes on the first access after it is 60 s old, single flight and never on a timer, so a paused `dev` database stays paused. A refresh in which an area fails validation keeps that area's last valid snapshot, logs `ops_config_invalid` and increments `docchat.config.invalid` (alert A39); a refresh that can't reach SQL keeps the snapshot and retries on an access at least 15 s later. Values change only through `docchat-ops config set` or `reset` under just-in-time membership of `sg-docchat-<env>-config-operators`, validated by the same models, with `--ticket` and `--reason`, in one transaction with its audit row (ADR 0139).
5. **The web client has no endpoint of its own.** It fetches `/config.json` with `cache: 'no-store'`, `credentials: 'same-origin'` and `redirect: 'error'` and parses it with a strict schema that rejects unknown members; it reads no build-time environment value except Vite's `DEV` flag, has no feature flags and names no endpoint in code. A missing or invalid file shows the configuration error screen and stops; no fallback endpoint exists.
6. **Constants have reasons.** A value is a code constant only when it belongs to the API contract, the stream protocol, stored identity or a vendor limit: the 15-second heartbeat, the 90-second drain point (ADR 0007), the UUIDv5 namespaces, the signing-key lifetime. Each owning component file lists its constants with their reasons. A value an operator could need to tune per deployment is a setting.
7. **Nothing domain-specific is in code.** No organisation, client, industry, person, contact, project, index or tag name appears in code, Bicep, images or the web bundle. The product's own names (the containers `documents`, `renditions` and `ingestion-work`, the queue `ingestion-requests`, the database `docchat`, the service names `docchat-api` and `docchat-ingestion`) are product constants, and the platform rules of the prompt are product text with no domain content. Everything about a customer's domain (project instructions, example questions, documents, an index's method parameters and language analyzer) is data that admins enter.
8. **No layer an app reads holds a secret.** Every service call uses a managed identity (ADR 0113), so no app setting, image variable, ops-config row or `config.json` member is a secret, and no setting is a Key Vault reference in the first version. The only secrets anywhere are the test users' passwords in the shared non-production test vault, which only the CI test identity reads (ADR 0122), and the local SQL `sa` password in a developer's gitignored `.env`; content-share fallback 1 is the only design path that would add one, a host-key connection string behind a Key Vault reference (ADR 0103).

## Alternatives considered

- **App settings for everything, runtime values included.** Lost: changing a rate limit, a quota or ingestion parallelism would need a pull request, a deploy and a restart of every instance, and ingestion parallelism belongs in the database by the product owner's decision.
- **Ops values editable in the admin UI.** Lost: operational limits protect the service and its cost, so they belong to operators under an audited, just-in-time command, separate from the admins who manage projects.
- **Code defaults for ops-config keys.** Lost: two sources of truth, and a missing row would silently run with a value nobody chose. The migration seeds the default, and a missing key fails start-up.
- **Untyped `os.environ` reads, or settings evaluated as code.** Lost: no validation, string truthiness and code execution from configuration.
- **Azure App Configuration as a central store.** Lost: another resource with its own private endpoint, role assignments and a start-up dependency, for values the two existing lifecycles (deploy-time parameters and run-time SQL rows) already cover.
- **A web build per environment with endpoints compiled in.** Lost: a build made for one environment could be deployed to another and call the wrong API; one build configured at deploy time can't.
- **Per-environment values in workflow variables or on the command line.** Lost: not reviewable as a diff; the environment files are committed and changed only by pull request, and workflow variables hold only identifiers, the allowlist and mailboxes.

## Consequences

- Easier: an operator changes a runtime limit within 60 s without a deploy; a reviewer sees every infrastructure difference between environments in three committed files; an invalid value fails loudly at start-up rather than misbehaving later.
- Harder: a new runtime key needs a migration that seeds it and a field in its area model; a renamed key needs an expand and a contract migration; an app-setting change needs a pull request and a deploy.
- Obligations: 81-config.md lists every setting once with its layer, type, default, allowed range, secret flag, who changes it and who reads it; a unit test in each app fails when a settings, queue-message, Cosmos DB document or request model lacks `extra="forbid"`; the deployed app-settings comparison test; ops-config tests (a missing key fails start-up, an invalid refresh keeps the last valid snapshot, the dispatcher never uses a default in place of a stored value); alert A39 on `ops_config_invalid`; runbooks R03 (change an ops-config value) and R04 (per-user index override) in 86-operations.md.
- Risk: different workers can run different ops-config snapshots for up to 60 s after a change. Every value is safe to apply per request, so the window only delays a change.
- Risk: an operator needs just-in-time membership to change a value during an incident, which takes a second person; that delay is the price of the audit trail.
