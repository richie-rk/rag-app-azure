# ADR 0141: Build order and spike register

- **Status:** Accepted
- **Date:** 2026-10-21; amended 2026-10-30 (SC-1 withdrawn, ADR 0122)
- **Decided by:** Architect
- **Specified in:** 90-build-order.md, 84-testing.md, 83-infrastructure.md, 86-operations.md
- **Related ADRs:** 0001, 0004, 0010, 0016, 0024, 0042, 0047, 0049, 0062, 0068, 0075, 0101, 0103, 0106, 0108, 0117, 0122, 0123, 0125, 0128, 0134, 0136, 0140, 0142, 0151, 0152

## Context

The builder compiles the target spec in an order that proves each layer before the next depends on it, and the riskiest platform behaviour must surface first, while changing course is still cheap: stage 0 scaffolds the repository, shared package, SQL schema, local environment and CI and runs the content-share spike; stage 1 is ingestion; then come the API platform, the chat pipeline, conversations and memory, the web client and hardening. Several platform behaviours can't be settled on paper, because the vendor documentation is silent or contradicts itself: whether an Elastic Premium Linux container app runs and scales with no Azure Files content share; whether `acrUserManagedIdentityID` takes a client ID or a resource ID; whether a Cosmos DB data-plane role assignment accepts an Entra group; whether a contained user's SID comes from the client ID or the object ID; whether every parsing model is baked into the image; whether `azd deploy` places a container on a function app with public access off; whether bound parameter values reach the SQL audit log; whether what-if and PSRule expand the Microsoft Graph Bicep extension; whether an unprivileged child process in the Elastic Premium Linux custom container can install a seccomp filter; whether LibreOffice converts DOCX and PPTX to PDF under that filter and within the converting child's limits (ADR 0152); and whether platform authentication buffers request bodies or streamed responses. Each of these, if decided wrong in the design, fails late and expensively.

## Decision

1. **Seven stages, in order**, each starting only when the previous stage is accepted: every acceptance criterion of its section in `90-build-order.md` passes, every test its acceptance record names is green, every spike of the stage has its outcome line in its ADR, and no stop condition of item 3 is open. A pull request appends `Outcome (YYYY-MM-DD): stage <n> accepted at commit <40-hex SHA>; record <ticket link>` to this ADR's Consequences, and its merge accepts the stage (ADR 0001). Every stage's code arrives with its tests, telemetry, settings, runbook text and catalogue rows, and nothing is stubbed for a later stage. Each stage adds the infrastructure it needs to `infra/main.bicep`, `infra/shared.bicep` or the bootstrap template and deploys it to `dev` through the pipeline; `prod` is first provisioned in stage 6.

2. **The spike register.** Each spike has a stated test, a time box (each wait its test states; a criterion not met within its wait counts as failed) and a rule that turns its result into a decision recorded in an ADR. It runs in the stage named beside it, before any later work depends on its result, and the owning component's specification holds the test. An outcome the rule sends to the product owner is a stop condition of item 3; every other outcome applies at once, through the pull request that records it.

   Work on the stopped stage halts at the failing criterion: its pull requests that don't touch the question's subject still merge, and no later stage starts. The build resumes when the product owner's choice makes that ADR `Accepted` and the criterion runs once more under it. Everything else is decided by a rule above.
4. **Other deciding checks.** These checks change a setting, a constant or a list by rule and are no stop condition: the deployed model check (T-250), the tokenizer check (T-251) and the Prompt Shields request check (T-332), operator checks run in `dev` at stage 3 through `docchat-ops --env dev chat model-check` by a member of `sg-docchat-dev-config-operators` and recorded by the stage's performer (ADR 0068; ADR 0075; ADR 0062); the `import-untyped` run of `uv run mypy` at stage 0 (ADR 0128); and the Document Intelligence region list at stage 0 (ADR 0101).

## Alternatives considered

- **Building by layer across all components (all data, then all APIs, then all UI).** Rejected: nothing would run end to end until late, and the uncertain hosting behaviour would surface last.
- **Running the spikes when their component is built.** Rejected for the stage-0 spikes: the content share, the SID source, the pull identity, the azd deployment, the audit action groups, the registrations' template and the PSRule results shape the infrastructure every later stage depends on; SP-6, SP-8, SP-9, SP-10, SP-14 and SP-15 run when their component exists, because their tests need it.
- **Choosing fallback 2 for any SP-1 failure.** Rejected: it changes the hosting resource, the Durable storage provider and the scaling model, while fallback 1 confines the change to one storage account, one secret and the ingestion subnet's outbound path (ADR 0103).
- **Deciding the open behaviours from documentation alone.** Rejected: the pages disagree or are silent, and a wrong guess fails in production; a short test settles each.

## Consequences

- Every stage ends with something deployed to `dev` and proven by named tests, and a later stage never starts on an unproven layer.
- Each spike's result is an ADR the builder writes at the time, so the decision and its evidence stay together; the rule that picks the outcome is set now, so no spike result opens a new design discussion except at the stop conditions.
- Stage 0 is long: it carries the whole repository scaffold, CI, the bootstrap, the first `dev` provision and nine spikes, and SP-1 alone takes at least 26 hours: the fan-out, the 70-minute scale-in window and the 24-hour watch of criterion (6).
- Obligations: `90-build-order.md` lists every acceptance criterion with its proving tests; `docs/runbooks/rehearsals.md` logs the stage rehearsals.
