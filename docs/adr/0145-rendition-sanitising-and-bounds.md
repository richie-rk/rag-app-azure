# ADR 0145: Rendition sanitising and bounds

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Architect
- **Specified in:** 14-ingestion.md, 80-data-model.md, 82-security.md, 84-testing.md, 85-observability.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0031, 0034, 0043, 0049, 0069, 0087, 0138, 0144, 0148, 0152

## Context

A citation opens one page, and a reader can save the whole document as one PDF. Every version, of every format, has a PDF: the source of a PDF version, or the PDF the converter made from a DOCX or PPTX (ADR 0152). Render writes every page of that PDF as its own file to `renditions/{indexId}/{documentId}/{v}/pages/{n}.pdf` and joins the verified pages into `renditions/{indexId}/{documentId}/{v}/document.pdf`; the citation operations stream those files through the API (ADR 0069), and the web client shows a page from an object URL in an iframe without a `sandbox` attribute, because a sandboxed iframe shows no PDF viewer (ADR 0087). Whatever a rendition holds therefore reaches the browser's built-in PDF viewer. The version's PDF was written by someone else, or converted from a file someone else wrote, and a PDF can carry active content: document-level `/OpenAction` and additional actions (`/AA`) on the catalogue, its pages and its annotations; the `/Names` trees (JavaScript, embedded files, named destinations); interactive forms (`/AcroForm`, drawn by `Widget` annotations); annotations that embed files or media (`FileAttachment`, `RichMedia`, `Screen`, `Sound`, `Movie`, `3D`); and actions that run scripts, submit or import form data, launch files, open URLs or other documents (`JavaScript`, `SubmitForm`, `ImportData`, `ResetForm`, `Launch`, `URI`, `GoToR`, `GoToE`, `Rendition`, `Sound`, `Movie`, `Hide`, `Named`, `RichMediaExecute`). Document content is untrusted, and nothing a document carries may make the browser send data anywhere.

A rule set that deletes the constructs it recognises from a copied page leaves every construct it doesn't recognise: an action under a page key the rules don't name, a file specification whose optional `/Type` is left out, or an object reached through a resource key no rule visits passes as it is. A page built anew from a list of what draws a page fails closed instead: whatever the list doesn't name is never written.

Splitting also multiplies shared resources. A page copied into a file of its own takes every object it references with it, so a 2,000-page document whose pages share one 5 MB image becomes 2,000 page files of about 5 MB each, about 10 GB on the instance's disk and in the `renditions` container.

Vendor facts:

- `pikepdf` 10.17.0 (2026-10-11): Production/Stable, MPL-2.0, CPython 3.13 manylinux wheels (PyPI, checked 2026-10-14). Its documentation's split example "will transfer data associated with each page, so that every page stands on its own", and splitting does not carry document-wide data such as bookmarks (checked 2026-10-21).

- ISO 32000-1:2008: the page dictionary (Table 30), resources (Table 33), stream keys (Table 5), the standard filters and their parameters (Tables 6, 8, 11, 12 and 13), the graphics state (Table 58), colour spaces (Tables 62 to 66 and 71), functions (Tables 38 to 41), patterns and shadings (Tables 75, 76 and 78 to 84), images (Tables 89 and 146), forms and groups (Tables 95, 96 and 147), soft masks (Table 144), fonts (Tables 111, 112, 114, 116, 117, 120, 121, 122, 124 and 127), optional content (Tables 98 and 99) and the 18 action types (Table 198). Section 8.4.1 calls the black-generation, undercolour-removal, transfer and halftone parameters device-dependent, which a device-independent page shouldn't set; under section 8.11.4.2 a conforming reader ignores every optional-content structure of a document whose catalogue has no `/OCProperties`.
- The HTML Standard gives a PDF shown by the browser's viewer its own opaque origin and policy container, and sandboxing disables plugins, so a sandboxed iframe shows no viewer (checked 2026-10-14).

## Decision

1. **Scope and runtime.** Renditions exist for every version, of every format. `render_pages` (deadline 2,400 seconds, ADR 0144) runs the parsing child's `render` command (ADR 0049: a parse user of the pool, UIDs 10002 to 10017, the system-call filter, no identity variables, the memory limit, files of at most 2 GiB, wall clock min(`DOCCHAT_INGESTION_PARSE_TIMEOUT_SECONDS`, 1,200 seconds)), which builds every page file anew from the version's PDF with `pikepdf` 10.17.0, and a `verify-render` child under the activity's second parse user checks each batch before upload (decision 8); an `assemble` child and a `verify-render` child in document mode then build the whole-document rendition (decision 9). Readers receive only renditions: no uploaded file and no converted PDF is ever served (ADR 0069). The product owner chose renditions that keep selectable text, so pages aren't rasterised.
2. **Build each page; never strip one.** The child opens the PDF with `inherit_page_attributes=True`, so each page's own dictionary holds its boxes, rotation and resources, and calls `pdf.flatten_annotations(mode="screen")`, which burns the normal appearance of every annotation a viewer shows on screen into its page's content as a form XObject. For each page it makes `out = pikepdf.Pdf.new()` and `page = out.add_blank_page()`, keeps only the blank page's `/Type` and `/Parent`, and sets exactly the keys of the page allowlist, each value built anew by the copier of decision 3: `/MediaBox` (the page's size), `/CropBox` (the region shown), `/Rotate` (the orientation shown), `/UserUnit` (the unit of every coordinate), `/Resources` (what the content names), `/Contents` (what draws the page) and `/Group` (the colour space transparent objects blend in) (ISO 32000-1 Table 30). Every other page key is left out, `/Annots`, `/AA`, `/B`, `/AF`, `/PresSteps`, `/Thumb`, `/Trans`, `/Metadata` and `/StructParents` among them. The child never appends a source page and never calls `Pdf.copy_foreign` or any copy that follows every reference. `out`'s catalogue holds exactly `/Type` and `/Pages`, its page tree root exactly `/Type`, `/Kids` and `/Count`, and its trailer exactly `/Size`, `/Root` and `/ID`. The child saves each page with the `pdf.save` options of decision 8, reopens it with recovery off and runs the checker of decision 8 on it before it renames it; a refusal is `render_failed`.
3. **The rendition object schema.** One module, `docchat_ingestion.isolation.pdf_schema`, holds the schema, the copier `copy_page`, the checker `check_file` and the constant `RENDITION_RULES_VERSION`, and `render`, `assemble` and `verify-render` import it, each in its own process (`14-ingestion.md` section 14.8 states it in full):
   - *Kinds by position.* Every object has a kind given by the position it was reached from (the key and the kind of the object holding it), starting at the page; a key that ISO 32000-1 requires of each candidate kind chooses among the kinds of one position (`/Subtype` for XObjects and fonts, `/FunctionType`, `/PatternType`, `/ShadingType`, a colour space array's family name, and `/Type` only for `/Properties` entries and `/Kids` elements); an optional `/Type` decides nothing anywhere else.
   - *The kinds.* Resources (Table 33), content streams, the graphics state (Table 58) without the device-dependent `/BG`, `/BG2`, `/UCR`, `/UCR2`, `/TR`, `/TR2` and `/HT`, soft masks and groups, colour spaces (the device spaces, CalGray, CalRGB, Lab, ICCBased, Indexed, Pattern, Separation and DeviceN with its attributes but no `/MixingHints`), functions of types 0, 2, 3 and 4, tiling and shading patterns, shadings of types 1 to 7, images (Table 89) without `/Alternates`, `/OPI`, `/OC`, `/Metadata`, `/StructParent`, `/ID`, `/Name`, `/Measure`, `/PtData` or `/AF`, forms (Table 95) without `/Ref`, `/OPI`, `/OC`, `/Metadata`, `/PieceInfo`, `/LastModified`, `/StructParent`, `/StructParents`, `/Name`, `/Measure` or `/AF`, the font kinds Type0, Type1, MMType1, TrueType, Type3 (with `/CharProcs` and `/Resources`), CIDFontType0 and CIDFontType2 with their descriptors, embedded font files, encodings, `/ToUnicode` and CMap streams, `/W`, `/W2` and `/CIDSystemInfo`, and the optional-content groups and membership dictionaries of `/Properties` with the keys that only drive visibility.
   - *Streams.* Every stream keeps only `/Length`, `/Filter` and `/DecodeParms` beside its kind's keys, with the nine standard filters other than `/Crypt` and their parameters; `/F`, `/FFilter`, `/FDecodeParms` and `/DL` are on no list. A stream is copied as `pikepdf.Stream(out, read_raw_bytes(), <its copied keys>)`, so its data keeps the encoding it has.
   - *Copying.* Only listed keys are copied, so an object reached through any other key is never written; an indirect object is copied once per kind through a memo, which also ends reference cycles; a null counts as an absent key. The memo lives for one `copy_page` call, one source page of one source file, so `assemble` starts a new memo for each page file it copies, and two page files that number their objects alike never share a copied font or image.
   - *What fails.* Left out, never a failure: an unlisted key, a `/Type` of another value, a `/Properties` entry that is neither an optional-content group nor a membership dictionary, an unknown entry of `/Resources`. `render_failed`: a listed key whose value has the wrong form, an object of a kind the schema doesn't define in a position whose objects draw (an XObject subtype other than `/Image` and `/Form`, a font, function, pattern or shading type or colour space family outside the lists, a filter outside the list), and a path deeper than the limit; so every entry of a resource sub-dictionary that draws is copied or fails the page, and no page loses what its content names.
   - *Limits.* A depth of 64 containers below the page, keys in sorted order, which leaves room for about 20 levels of nested forms; at most 100,000 distinct containers per page file (`render_too_large` in `render`) and 1,000,000 per whole-document rendition (`too_large` in `assemble`); `verify-render` refuses a file past either limit with `render_failed`.
4. **One page at a time.** The child writes `{n}.pdf.part`, renames it to `{n}.pdf` when complete, and waits while 4 finished page files are on local disk. The parent lists the scratch directory's entry names every 100 ms (`os.scandir` in a worker thread, by name only) and handles finished pages in batches of at most 4: it opens each `{n}.pdf` without following links and accepts only a regular file owned by the child's UID with one link and within the page cap (ADR 0049 decision 6), reads it into memory and deletes it; it hands the batch to a `verify-render` child (decision 8); and only when that child passes the batch does it upload each page that child wrote, `{n}.verified.pdf`, to `renditions/{indexId}/{documentId}/{v}/pages/{n}.pdf` with content type `application/pdf` (overwriting, at most 4 uploads in flight).
5. **Size caps.** A page file above 20 MiB (20,971,520 bytes), a page above 100,000 containers, or a running total above max(10 × the size of the version's PDF, 500 MiB) (at least 524,288,000 bytes), stops Render with the non-retryable item code `render_too_large`: the child checks each page before renaming it and stops; the parent checks again before uploading, deletes every page already uploaded under the version's `pages/` prefix (`delete_blobs`, at most 256 per call), and the item fails. The whole-document rendition has its own cap of 104,857,600 bytes (100 MiB) on the running total of verified page bytes and on the assembled and verified files; above it the whole-document rendition is skipped, never failed (decision 9). The request file carries the caps as `renderMaxPageBytes` (20971520), `renderMaxTotalBytes` (`max(10 × PDF size, 524288000)`), `renderMaxPagesOnDisk` (4) and `renderMaxDocumentBytes` (104857600); they are constants in code, not settings.
6. **Completion and idempotency.** Before the first page or `document.pdf` is written, Render and `rerender_pages` delete `renditions/{indexId}/{documentId}/{v}/complete.json` (an absent blob counts as deleted; a storage error is the retryable `storage_unavailable` with no page written), so no marker stands beside pages that are changing. After the `render` child exits cleanly, every page has been verified and uploaded, and the whole-document rendition has been uploaded or recorded as too large, the parent writes `renditions/{indexId}/{documentId}/{v}/complete.json` = `{"pageCount": <n>, "pdfSha256": "<hex of the version's PDF>", "renditionRulesVersion": <RENDITION_RULES_VERSION>, "documentPdf": "built" | "too_large"}`, last, and then records the version's `document_pdf_status` and `chunk_sets.rendition_rules_version` on every live chunk set of that PDF. When that file exists with the chunk set's `pdf_sha256` and the deployed `RENDITION_RULES_VERSION`, Render records the marker's values and returns `skipped: true`; otherwise a run overwrites every page and the whole-document rendition, so a retry after a crash completes the set. The marker's presence therefore means that the set at its path is complete under the PDF and the rules version it names, and a run that fails part-way leaves none, so the next run renders every page. No reader path reads the marker.
7. **Failures.** Storage errors give retryable `storage_unavailable`; any other `render`, `assemble` or `verify-render` error gives non-retryable `render_failed` ("Page previews couldn't be created for this document."); the `render` child's own limits give `parse_timeout` or `parse_memory_exceeded` (non-retryable); the page caps give `render_too_large` ("Page previews for this document are too large to create."). Render runs before the Flip, so a version is never served without a page file for every page it can cite and a recorded `document_pdf_status` (ADR 0069).
8. **A second check before upload.** For each batch, the parent writes the pages it read, owned by root with mode 0644, into a fresh scratch directory of the activity's second parse user and starts `verify-render` there (ADR 0049 decision 17): a fresh child under another UID than the `render` child, under the same filter and protocol, with 120 seconds per batch and 256 MB of memory. It opens each `{n}.pdf` with `pikepdf.open(path, attempt_recovery=False, inherit_page_attributes=False)`, so qpdf rebuilds no damaged cross-reference table and pushes nothing down the page tree, and refuses the page on any warning from `pdf.get_warnings()`, on a trailer `/Prev` (an incremental update, whose superseded objects stay in the file), on a trailer `/XRefStm` (a hybrid-reference file, which two readers can resolve to different objects), and on bytes after the last `%%EOF` beyond one line ending. It then runs `check_file`, walking the file from the trailer with the schema of decision 3, against one list of invariants for both modes (`14-ingestion.md` section 15.6 item 14.2 states it): the page count; a trailer of exactly `/Size`, `/Root` and `/ID`, a catalogue of exactly `/Type` and `/Pages`, and page tree nodes of exactly `/Type`, `/Kids`, `/Count` and, below the root, `/Parent`, at most 16 nodes deep; every object reached from a page conforming to the schema, every key allowed in its position and every value of its kind, within the depth limit and the container cap; every indirect object of the file reached by that walk; as a second net independent of the schema, no dictionary key and no name of the 25 names `/JS`, `/JavaScript`, `/URI`, `/Launch`, `/GoToR`, `/GoToE`, `/EmbeddedFile`, `/EmbeddedFiles`, `/AF`, `/EF`, `/RF`, `/FS`, `/Filespec`, `/RichMedia`, `/XFA`, `/PresSteps`, `/NA`, `/PA`, `/AA`, `/OpenAction`, `/Outlines`, `/Ref`, `/OPI`, `/URL` and `/Annots` in any object of the file, nor at any depth of a dictionary that a content stream writes inline: `check_file` parses every content stream it reaches once (a page's `/Contents` as one stream through the page; each form, tiling pattern and Type 3 glyph procedure on its own) with `pikepdf.parse_content_stream(<page or stream>, "BDC DP BI ID EI")` and refuses a `BDC` or `DP` property list or an inline image dictionary (`iimage.obj`) that holds one of the 25, a parse that raises or leaves a warning, and an inline dictionary nested past the depth limit, in which it counts one container below its stream, all inside the child's existing time and memory limits; and no dictionary whose `/S` is one of the 18 action types of ISO 32000-1 Table 198, whatever key holds it and with or without `/Type`; and a file within the byte cap. The modes differ only in the page count (one, or the version's `page_count`), the container cap (100,000 or 1,000,000) and the byte cap (`renderMaxPageBytes` or `renderMaxDocumentBytes`). When every check holds, it writes `{n}.verified.pdf` with `pdf.save(..., linearize=False, object_stream_mode=pikepdf.ObjectStreamMode.disable, compress_streams=True)`, which serialises only the objects reachable from the trailer as one cross-reference table and no object stream, reopens that file with recovery off and runs every check on it once more. The parent uploads `{n}.verified.pdf`, opened without following links as a regular file of the verifier's UID with one link and within the page cap, and never the `render` child's bytes, so what readers receive is the serialisation of the object graph that was checked. Any failure (a refused page, the verifier's time or memory limit, a crash, a missing or invalid result) fails the item with `render_failed`, and nothing of the batch is uploaded.
9. **The whole-document rendition, from verified pages only.** While the running total of verified page bytes stays at most 104,857,600 bytes, the parent also writes each verified page, owned by root with mode 0644, into an assembly directory owned by root with mode 0700. After the last batch, once the `render` child has exited and its user is cleared, the directory is handed to the first parse user and an `assemble` child (300 seconds, the parse memory limit) opens each page from memory with `pikepdf.open(io.BytesIO(<bytes>), attempt_recovery=False, inherit_page_attributes=False)`, adds a blank page to one `pikepdf.Pdf.new()` and fills it with `copy_page` (decision 3), so the join adds only the page tree to what the verified pages hold and needs no link removed, and writes `document.pdf` with the same `pdf.save` options as decision 8, or, above 1,000,000 containers, writes no file and returns `documentPdf` `too_large`. The parent hands the bytes it read to a `verify-render` child in document mode under the second parse user (300 seconds): the same schema and the same invariants as decision 8, with the page count equal to the version's `page_count` and the document caps, and it writes `document.verified.pdf` from the object graph it checked; only that file is uploaded, to `renditions/{indexId}/{documentId}/{v}/document.pdf`. When the running total, `document.pdf` or `document.verified.pdf` exceeds the cap, or `assemble` returns `too_large`, the parent starts no further child for it, deletes any `document.pdf` at the version's path and records `too_large`; readers are then told that the document is too large to download as one file, and its pages still open. Any `assemble` or document-mode `verify-render` failure fails the item with `render_failed`. The whole-document rendition is never built from the version's PDF, so it carries nothing a page rendition doesn't.
10. **The rules version and stored renditions.** `RENDITION_RULES_VERSION`, an integer starting at 1, rises with every change to `pdf_schema.py`, which holds decisions 2, 3, 8 and 9 in code, and with every change of the pinned `pikepdf` or of the qpdf it bundles, whose parser, flattening and writer shape every rendition; a unit test holds `(SHA-256 of pdf_schema.py, pikepdf version, bundled qpdf version)` under each value, read as the module's hash, `importlib.metadata.version("pikepdf")` and `pikepdf.__libqpdf_version__` (the bundled qpdf has no documented accessor, so the test fails when that attribute is missing or isn't a string), and fails until a change raises the constant. `complete.json` and the column `chunk_sets.rendition_rules_version` (`INT NULL`, written only by `docchat_ingestion`) record it. Sweep duty 12 (`stale_renditions`) queues, in `maintenance` runs of priority 1, one item of the operation `rerender` per served chunk set recorded under a lower value or none, at most 10 outstanding and one per document, and not for a document with a queued or running item. The item's one activity, `rerender_pages` (stage `render`, 2,400 seconds), renders the stored PDF of the chunk set once more, overwrites the renditions, writes `complete.json` and the column, and skips with `renditions_current` or `document_deleted` when nothing is due. It doesn't touch `converted_sha256` before it writes pages, because the PDF and its `pdf_sha256` don't change, so every citation answers as before while it runs. On failure it deletes no page and the chunk set stays served; a chunk set whose item failed with `storage_unavailable`, `activity_timeout` or `processing_interrupted` is queued again after 24 hours, and one that failed with another code isn't queued again while the item's row exists. The event `ingestion_item_failed` carries the item's `operation`, and the alert `rerender-failed` (severity 3, runbook "Ingestion failures and stuck runs") fires on every `rerender` failure with `render_failed` or `render_too_large`, so a version that keeps renditions of the earlier rules is seen at once.

## Alternatives considered

- **Split pages without sanitising.** Rejected: every action, script, form field and embedded file of a page would reach an unsandboxed viewer, and a `URI` or `SubmitForm` action can send data out.
- **A denylist of dangerous subtypes and actions.** Rejected: any subtype or action the list misses, a future one included, would pass; an allowlist fails closed.
- **Copying the source page and stripping what the rules recognise.** Rejected: an allowlist of annotation subtypes and actions on a copied page still copies every key and object the rules don't visit, so an action under an unlisted page key, a file specification without its optional `/Type` or an object reached through an unknown resource key passes; building the page from a schema of what draws it writes none of them.
- **Rasterising each page into an image-only PDF.** Rejected by the product owner, who chose selectable text: no active content could survive, but the page would lose selectable text and sharp vector content, files would grow with resolution, and every page would cost a full render in the child.
- **Relying on the browser viewer's handling of scripts and forms.** Rejected: the viewer is the user's browser, with versions and settings this product doesn't control.
- **Keeping annotations, or same-page links, with rules for their subtypes and actions.** Rejected: every kept annotation brings its own dictionary, actions and appearance into the schema; flattening keeps what each annotation shows and leaves no annotation at all, so no link of any kind remains.
- **Dropping every annotation without flattening.** Rejected while a documented flattening exists (`Pdf.flatten_annotations`): readers would lose comments, highlights, stamps and filled form values that the page shows.
- **Two independent schema modules, one per child.** Rejected: two lists of the same ISO tables would drift apart and refuse each other's correct pages; one module keeps the copier and the checker equal, and the name and action net of decision 8 stays independent of it.
- **Re-rendering every stored version at the deploy that raises the rules version.** Rejected: a deploy would wait on hours of rendering; the sweep re-renders at most 10 at a time, after every interactive item, while readers keep the earlier verified renditions.
- **Writing every page to disk before uploading, with no total cap.** Rejected: the 2,000-page shared-image document would need about 10 GB of local disk and put as much into `renditions`.
- **Sanitising the version's PDF as a whole for the whole-document rendition.** Rejected: it would need a second set of rules for document-wide structures (outlines, name trees, forms, threads) and a second verifier; joining the verified pages reuses the page rules and checks, so the joined file carries nothing a page rendition doesn't.
- **Failing the item when the whole document is above its cap.** Rejected: every page still opens from its own rendition, so a large document stays searchable and citable, and only the single-file download is withheld.

## Consequences

- A rendition shows the page's content, images and the flattened appearances of its annotations (comments, highlights, shapes, stamps, ink, filled form fields); nothing in it can run a script, submit or import a form, open a URL or another file, take content or stream data from another file, or play media.
- No rendition holds a link of any kind, same-page jumps included; an annotation without a normal appearance, and a form field whose appearance qpdf finds out of date, leave no mark; content in a layer the source hides by default draws, because the catalogue holds no `/OCProperties`; a page that sets the device-dependent graphics state parameters can show slightly different colours; tags, metadata, thumbnails, transitions and article beads are left out.
- A page whose own resource or glyph names include a name of the net (a font resource named `/FS` or `/Annots`, for example), or whose content streams write one in an inline dictionary (a property list with `/AF`, an inline image with `/URL`), fails with `render_failed`; the property lists of tagged PDF (`/MCID`, `/ActualText`, `/Alt`, `/Lang`, `/E`) pass. A single content stream of about 200,000 or more marked-content and inline-image instructions exceeds `verify-render`'s 256 MB in page mode and fails with `render_failed`.
- A version whose pages share a large resource can fail with `render_too_large`: with a small PDF, about 100 pages sharing one 5 MB image reach the 500 MiB cap. Such a document is split into smaller files before upload; the caps are constants, so no setting raises them. A version whose verified pages total more than 104,857,600 bytes gets no whole-document rendition, and its `document_pdf_status` is `too_large`.
- Local disk per Render stays at about 280 MiB: at most 4 finished page files of at most 20 MiB each plus the page being written in the render directory, at most 4 pages in the verifier's directory, and at most 100 MiB of verified pages in the assembly directory; the parent's memory holds at most 4 pages, 80 MiB, or, while it reads the joined file, at most 100 MiB.
- Serving a construct outside the schema (an annotation, a link, an action, a URI, a file specification, an embedded file or a reference to another file included, in an object or in a dictionary written inline in a content stream) takes two successful exploits in two children under different UIDs: one in the `render` child's parser to make an unsafe page, and a second against qpdf or zlib in the `verify-render` child, through a page file the first compromised child must craft, to pass it (decision 8). A page that qpdf and a reader's PDF engine could read as different objects (an incremental update, a hybrid cross-reference, trailing data, a table qpdf would repair) is refused, and the uploaded file is qpdf's own serialisation of the checked objects, so no parse differential stands in for the second exploit. A flaw in the `render` child alone doesn't reach readers. The verifier writes each page once more, which adds one `pdf.save` per page inside its 120-second batch limit, and its directory holds at most 4 pages and their 4 verified files.
- Residual, a key the schema allows that a viewer acts on: the three children run one schema module, so a mistake in its lists is common to both children and passes both with no exploit at all, unless the net of decision 8 names it. For such a key the bound is the schema's correctness, not two exploits; its lists hold only keys of the ISO 32000-1 tables that draw a page, and a correction raises `RENDITION_RULES_VERSION`, which re-renders every served version (decision 10).
- Residual, the reader's PDF engine: a rendition keeps the data of the source's streams as the source encoded it (content streams, Type 3 glyph procedures, embedded font files, images and inline images, ICC profiles, CMaps, sampled and PostScript calculator functions, mesh shadings, `/Indexed` lookup streams and `/JBIG2Globals` streams), whose dictionaries alone the schema checks, so a stream of any of these kinds crafted to exploit the reader's PDF engine reaches the reader's viewer; the viewer and its sandbox bound it, and the design claims nothing about a particular viewer. Text that a page draws can read as an address that a viewer turns into a link, which needs the reader's click.
- Renditions stored under a lower rules version stay served until their `rerender` item replaces them, and stay when it fails with a code the same bytes would repeat (the alert `rerender-failed`; runbook R18).
- Each batch of 4 pages pays for a second open of its pages in a fresh child, a few seconds beside the build.
- The schema must list every key that draws a page in the documents users upload; a key it misses either is left out (the page draws without it) or fails the page with `render_failed`, never reaches readers; the rendition text test over the Office-saved controls and the base fixtures proves that the lists keep their text.
- Obligations (84-testing.md): a test on the fixture `active-content.pdf` (one of each action and annotation type above, plus a same-page and an other-page `Link`) and on the rendition schema fixtures (a `/PresSteps` whose `/NA` is a `/GoToR` without `/Type`, a `/GoToE` under an unlisted page key, a page `/AF` with an `/EF` file specification without `/Type`, an image with `/Alternates`, a form with `/Ref`, a stream with `/F`, a font with an unlisted key, an annotation with an appearance stream, an unknown dictionary under `/Resources`), in which every page file holds no `/Annots`, none of these constructs, only allowlisted page keys and a catalogue of `/Type` and `/Pages`, while the flattened appearances draw; no page file holds another page's content stream; `complete.json` is written last with `renditionRulesVersion`; a second run is skipped. The rendition text test (the Office-saved controls and the base fixtures keep their extracted text), the rendition schema limits test (the depth and container limits, with memory and time measured at each cap), the rendition rules version unit test (its entries carry the `pikepdf` and qpdf versions) and the re-render integration test (a marker left by a failed `rerender`, then a Render that fails part-way, leaves no marker, and the next `rerender` renders every page). A test on the fixture `shared-image-2000.pdf` (2,000 pages that share one 5 MB image), which fails with `render_too_large` after uploading at most 500 MiB, never holds more than 4 page files on local disk and leaves no page under the version's `pages/` prefix; a page file above 20 MiB fails the same way. The rendition verifier test, in which a stub `render` child writes a forged page with an `/OpenAction` (and, in further cases, each construct of the rendition schema fixtures, any `/Annots`, an unreached object, a `/JS` entry, a second page, an `/Outlines` entry whose item carries a `/URI` action, a catalogue `/Names` entry, a `/Type /Action` dictionary with `/S /SubmitForm`, a `Link` with a `/PA` URI action, an `/OpenAction` in an earlier revision reached through `/Prev`, a hybrid `/XRefStm`, bytes after the last `%%EOF`, a stream with `/F`, `/FFilter` or `/FDecodeParms`, a form XObject with `/Ref`, an XObject with `/OPI`, a `/URL` key and a URL file specification), each caught by `verify-render` with `render_failed` and nothing of its batch uploaded, while an object outside the cross-reference table is absent from the uploaded file, which is always the verifier's `{n}.verified.pdf`; a source page whose XObjects carry `/Ref`, `/OPI` and an external `/F` gives an uploaded page without them, which passes `verify-render`; the inline dictionary fixtures (a `BDC` property list with `/AF`, an inline image with `/URL`) fail `render` with `render_failed`, a stub page holding either in its page content, a form, a tiling pattern or a Type 3 glyph procedure, or a content stream qpdf can't parse, fails `verify-render`, and the tagged-PDF control passes both. A whole-document rendition test, in which two page files that number their font and image alike give a `document.pdf` whose every page has its own page file's text and image hashes, and in which the `document.pdf` of a PDF, a DOCX and a PPTX version holds every page in order and no annotation, no `/Dest` and no action dictionary, a forged joined file with a `Link` or a wrong page count fails `verify-render` in document mode with `render_failed`, and a version above the 104,857,600-byte cap records `too_large` with no `document.pdf` under its path. A `pikepdf` update passes these tests and raises `RENDITION_RULES_VERSION` before it merges. The alert query unit tests (`rerender-failed` fires on a `rerender` failure with `render_failed` or `render_too_large` only) and the claim integration test.
