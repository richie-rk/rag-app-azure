# ADR 0005: Ingestion on Elastic Premium with a custom container

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 14-ingestion.md, 83-infrastructure.md, 84-testing.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0003, 0010, 0047, 0049, 0053, 0101, 0103, 0109, 0123, 0124, 0152

## Context

The page-wise method runs `unstructured` with its high-resolution strategy and table-structure inference (ADR 0047). That needs operating-system packages (`poppler-utils`, `tesseract-ocr` with language packs, `libmagic1`, the OpenCV runtime libraries) beside the Microsoft ODBC Driver 18 that the SQL data layer uses, and models baked in at build time so nothing is fetched at run time. Ingestion is a Durable Functions app, one activity per unit of work, on the Azure Storage provider with identity-based connections; its host storage account has public access off, and the app accepts no inbound traffic. Parsing is CPU- and memory-heavy, about 2 GB per parsing process, and parallelism comes from processes and instances, never threads. This record compares the hosting options and states the one chosen.

The runtime must be one immutable image. Files written into a running instance outside the deployed artifact vanish on restart, platform maintenance, scale-out or redeploy: an OS package installed by hand would leave every PDF failing while DOCX and PPTX still succeed and runs still report success. Build tools must not ship either, because code that exploits a parser would find a compiler next to the run's credentials.

Vendor facts (checked 2026-10-14):

- Flex Consumption doesn't support containers; Python 3.12 is the last version on Linux Consumption.
- Functions on Container Apps autoscales Durable Functions only with the MSSQL or Durable Task Scheduler storage providers. Durable Task Scheduler is GA and works with any Functions SKU.
- Every Premium plan bills at least one instance, and scaling beyond the minimum is best effort; with VNet-secured storage, dynamic scale needs runtime scale monitoring; Linux Premium scales to 100 instances per plan in East US 2 and isn't offered in Australia Central 2, South India or USGov Texas.
- Microsoft's settings pages require an Azure Files content share for Elastic Premium, which takes a storage key, while Microsoft's template example for containers omits it.
- App settings containing a period aren't supported on Linux Elastic Premium; a Premium health check needs a function with an HTTP trigger; webhook continuous deployment isn't supported for custom containers on Elastic Premium.

## Decision

1. **Plan.** `asp-docchat-ingest-<env>`: `Microsoft.Web/serverfarms@2025-03-01`, `kind: 'elastic'`, `reserved: true`, `sku {name: EP1 | EP2, tier: 'ElasticPremium', family: 'EP', capacity: 1}`, `maximumElasticWorkerCount` = `ingestion.maxBurst`, `elasticScaleEnabled: true`, `zoneRedundant: false`. `dev` runs EP1 (always ready 1, burst 2); `prod` EP2 (always ready 1, burst 4); `load` EP2 (always ready 2, burst 4).
2. **Function app.** `func-docchat-ingest-<env>-<token>`, `kind: 'functionapp,linux,container'`, user-assigned identity `id-docchat-ingest-<env>` only; `httpsOnly: true`; `clientAffinityEnabled: false`; `publicNetworkAccess: 'Disabled'`; VNet integration into `snet-ingest-integration` (/24, delegated to `Microsoft.Web/serverFarms`) with `outboundVnetRouting {allTraffic: false, applicationTraffic: false, imagePullTraffic: true, contentShareTraffic: false, backupRestoreTraffic: false}`. `siteConfig`: `linuxFxVersion: 'DOCKER|<image digest reference>'`, `acrUseManagedIdentityCreds: true`, `acrUserManagedIdentityID` = the identity's client ID, `functionsRuntimeScaleMonitoringEnabled: true`, `minimumElasticInstanceCount` = `ingestion.alwaysReady`, `preWarmedInstanceCount: 1`, `functionAppScaleLimit` = `ingestion.maxBurst`, `minTlsVersion` and `scmMinTlsVersion` `'1.3'`, `ftpsState: 'Disabled'`, `remoteDebuggingEnabled: false`, `http20Enabled: false`, both IP-restriction default actions `'Deny'`, no `healthCheckPath`. App settings `WEBSITES_ENABLE_APP_SERVICE_STORAGE=false` and `WEBSITES_CONTAINER_START_TIME_LIMIT=900`.
3. **Durable on the Azure Storage provider.** The host account `stdocchathost<env><token>` (public network access disabled; Standard_LRS in `dev`, Standard_ZRS in `prod` and `load`) holds the host and the task hub only, reached through identity-based `AzureWebJobsStorage__*` settings with `__credential=managedidentity` and `__clientId`. The task hub is `docchat<env>`, set only by the app setting `AzureFunctionsJobHost__extensions__durableTask__hubName`. `azure-functions-durable` 1.7.0 (GA) on the Python v2 model. Per-SKU concurrency comes from app settings whose names contain no period: `FUNCTIONS_WORKER_PROCESS_COUNT` 1 (EP1), 2 (EP2), 4 (EP3); `AzureFunctionsJobHost__extensions__durableTask__maxConcurrentActivityFunctions` and `...maxConcurrentOrchestratorFunctions` 2, 4 and 8; one parse slot per worker process (ADR 0053).
4. **The image.** `docchat/ingestion`, built from `apps/ingestion/Dockerfile` in two stages, both `FROM mcr.microsoft.com/azure-functions/python:4.1055.300-3-python3.13` pinned by digest (ADR 0010; the pin moved from `4.1055.150-0` on 2026-11-07). Only the build stage installs build tools, installs dependencies from `uv export --locked` with hashes and downloads the models pinned in `apps/ingestion/models.lock.json`, using scripts under `apps/ingestion/image/`. The runtime stage adds only `libmagic1`, `poppler-utils`, `tesseract-ocr` with the `eng`, `fra`, `deu`, `spa`, `ita`, `nld` and `por` language packs, `libglib2.0-0`, `msodbcsql18`, `unixodbc`, `libgssapi-krb5-2`, `libseccomp2` and `procps`, and the Office converter of ADR 0152, LibreOffice 7.4.7 built without a graphical toolkit (`libreoffice-core-nogui`, `libreoffice-writer-nogui` and `libreoffice-impress-nogui` at `4:7.4.7-1+deb12u14`) with three metric-compatible font packages, about 300 MB, plus the pool of unprivileged parse users `docchat-parse-0` to `docchat-parse-15` and the root-owned scratch parent `/run/docchat-scratch` (mode 0711), with write access for others removed from every path but `/tmp` and `/var/tmp` (ADR 0049): no compilers, headers or pandoc. Models sit read-only in `/opt/docchat/models`; the image sets `HF_HUB_OFFLINE=1`, `DO_NOT_TRACK=true` and `SCARF_NO_ANALYTICS=true` and carries an extension bundle in `[4.39.1, 5.0.0)`. The last build step is the offline self-check, `RUN --network=none`, which converts the DOCX and PPTX fixtures to PDF, parses the PDF fixture and both converted PDFs and checks the ODBC driver.
5. **Sizing.** EP1 (1 vCPU, 3.5 GB) runs one parse at a time and EP2 (2 vCPU, 7 GB) two, at 2,048 MB per parsing child; global parallelism `p` needs `ceil(p / 2)` EP2 instances. The dispatcher's `ingestion.max_parallel_items` (ops config, default 1, range 1 to 16) is the real cap; the Durable settings are per-instance ceilings above it (ADR 0053).
6. **No content share unless the spike requires one.** The app has no Azure Files share, no `WEBSITE_CONTENTAZUREFILECONNECTIONSTRING` and no `WEBSITE_CONTENTSHARE`, and the host account keeps shared-key access off. The stage-0 content-share spike deploys the `dev` app exactly this way and checks seven criteria (ADR 0103): (1) provisioning succeeds with no content-share validation error; (2) the worker's first telemetry reaches Application Insights within 10 minutes of the deploy; (3) a queue message starts an orchestration within 2 minutes; (4) during a fan-out the app runs on 2 instances within 10 minutes and returns to 1 within 70 minutes of the last activity; (5) the orchestration completes; (6) 24 hours pass with no host error about Azure Files, the content share or `AzureWebJobsStorage`; (7) the image pull succeeds with the identity's client ID. If any of criteria (1) to (6) fails, fallback 1 of ADR 0103 applies.
7. **Delivery.** The image is built and scanned once per commit and deployed by digest through azd's `function` host with `imagePassthrough` and `--from-package <digest>` (ADR 0123, proven by the stage-0 container-deploy spike); changing the image restarts the app, and webhook deployment isn't used.

## Alternatives considered

- **Flex Consumption.** Lost: it runs no containers, so a code-only deployment can't add `poppler-utils`, `tesseract-ocr`, `libmagic1` or the ODBC driver, and the page-wise method can't run.
- **Linux Consumption.** Lost: Python 3.12 is the last version it supports, and the apps run on 3.13 (ADR 0010).
- **Functions on Container Apps.** Lost: it autoscales Durable Functions only with the MSSQL or Durable Task Scheduler providers, not with the Azure Storage provider this app runs on. It stays fallback 2 (with the MSSQL provider), taken only through a new ADR decided by the product owner if scale-out still fails under fallback 1 (ADR 0103).
- **Durable Task Scheduler as the storage provider.** Lost: the Azure Storage provider runs on the host storage account the Functions host needs anyway, behind private endpoints with identity-based roles already granted; the scheduler would add a resource with its own private endpoint, DNS zone and data-plane role assignment.
- **A Dedicated App Service plan running the function app container.** Lost: it scales only by a set instance count or autoscale rules on plan metrics, never on queued Durable work, while Elastic Premium's scale controller adds instances when messages and tasks wait.
- **Code deployment with OS packages installed into running instances.** Lost: anything outside the deployed image disappears when an instance restarts or a new one starts.
- **A one-stage image.** Lost: build tools would ship to every instance.

## Consequences

- OS packages, models and the extension bundle ship in one scanned image, identical on every instance and deployed by digest; nothing is fetched at run time, so the app keeps working when egress filtering arrives (ADR 0109).
- Elastic Premium bills its always-ready instances while idle: EP1 $145.93 a month in `dev`, EP2 $291.85 in `prod`, 2 × EP2 $583.70 in `load` while it exists (eastus2 list prices, checked 2026-10-15).
- Scale beyond always-ready is best effort, so `load` keeps 2 always-ready EP2 instances and the parallelism-4 test measures parallelism; an operator who raises prod's `ingestion.max_parallel_items` above 2 raises `ingestion.alwaysReady` to `ceil(p / 2)` in the same change (runbook, 86-operations.md).
- With no health check, liveness comes from telemetry: the `postdeploy` hook fails with `ingestion_start_failed` when no `ingestion_worker_started` event for the release arrives within 10 minutes, and the dispatcher heartbeat, ingestion-failure and queue-age alerts cover the running app.
- Obligations: the content-share spike and the container-deploy spike in stage 0 (and runbook R27 if fallback 1 is activated), the offline-models spike in stage 1; the preflight checks the Linux Elastic Premium column for the region (ADR 0101); the image self-check and the Trivy gate on every build (ADR 0124).
- Risks: the content share may turn out to be required (handled by ADR 0103); 2 GB per parse is a starting estimate that the ingestion tests and the load test measure; the large image lengthens cold starts, covered by the 900-second start limit and one prewarmed instance.
