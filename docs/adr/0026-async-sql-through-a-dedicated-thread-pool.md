# ADR 0026: Async SQL through a dedicated thread pool

- **Status:** Accepted
- **Date:** 2026-10-18; amended 2026-11-08 (the pool is warmed at start-up, the product owner's decision)
- **Decided by:** Product owner and architect
- **Specified in:** 01-repository.md, 11-api.md, 14-ingestion.md, 80-data-model.md, 81-config.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0006, 0009, 0014, 0025, 0027, 0034, 0036, 0105, 0113, 0129, 0132, 0150

## Context

Every I/O call in the Python apps is async and awaited, and nothing synchronous may run on the event loop; a library with no async client runs in a thread pool, and clients are created once per process. SQL holds configuration, access and the ingestion ledger, and the API checks access in SQL on every request, so the data-access path sits on every request path of the API and on every step of the ingestion ledger.

Three needs shape the path:

- Every statement uses bound parameters, because a value interpolated into SQL text is an injection path, and no driver or server message may reach a caller, because such messages can quote the values they reject.
- Both apps reach SQL through one path with one credential, so a credential change or a transient fault behaves the same everywhere and is retried in one place, and one failed write can't abort an ingestion run.
- The `dev` database runs General Purpose serverless with auto-pause on, because `dev` is idle most hours. It pauses only after zero sessions and zero user CPU for the whole auto-pause delay (at least 15 minutes), so neither app may keep idle connections open indefinitely, and both must ride out a resume. The ingestion dispatcher wakes every 60 seconds while work is outstanding and every 60 minutes when idle (ADR 0036).

Vendor facts that bound the choice (checked 2026-10-14):

- No GA async SQL Server driver exists. SQLAlchemy's `mssql+aioodbc` dialect is "a thread-wrapper around pyodbc"; aioodbc 0.5.0 is Development Status 3 (Alpha) with Python classifiers 3.10 to 3.12. SQLAlchemy's asyncio extension has no async event handlers, so a token fetch in `do_connect` would run on the event-loop thread. mssql-python 1.16.0 is GA but has no native async; Microsoft's guidance is to wrap it in `ThreadPoolExecutor` or `run_in_executor`.
- pyodbc 5.3.0 is Production/Stable with CPython 3.13 wheels; SQLAlchemy 2.1.4 supports Python 3.11 to 3.15.
- ODBC Driver 18 takes a Microsoft Entra access token in pre-connect attribute 1256 (`SQL_COPT_SS_ACCESS_TOKEN`): a 4-byte little-endian length, then the token in UTF-16-LE, no terminator, never combined with `UID`, `PWD`, `Authentication` or `Trusted_Connection`. The token pointer is part of the driver manager's pool key. `Encrypt=strict` (TDS 8.0, TLS 1.3) needs ODBC Driver 18.1.2.1 or later and refuses `TrustServerCertificate=true`.
- SQLAlchemy's `pool_recycle` defaults to -1 and `pool_pre_ping` tests liveness only at checkout; idle pooled connections keep their SQL sessions open.
- The first connection to a paused database fails with error 40613 and should be retried; databases generally resume in under a minute. Microsoft lists 926, 4060, 40197, 40501, 40613, 49918, 49919, 49920, 4221 and 615 as transient, with a first retry after 5 s, backoff up to 60 s and a connect timeout of at least 30 s.

## Decision

`docchat_core.sql.engine` is the only way any Python process reaches SQL. It runs SQLAlchemy 2.1 Core (2.1.4) over `pyodbc` 5.3 (5.3.0) and Microsoft ODBC Driver 18 for SQL Server (package `msodbcsql18` with `unixodbc` and `libgssapi-krb5-2`, installed in the API and ingestion images from Microsoft's Debian 12 repository with `ACCEPT_EULA=Y`) inside a thread pool that serves SQL only.

1. **Driver pooling off; one engine per process.** The module sets `pyodbc.pooling = False` when imported, before any connection. Each process creates one engine in the API lifespan (each Gunicorn worker, after the fork) or at the ingestion worker's first invocation, and disposes it at shutdown: `create_engine("mssql+pyodbc://", creator=<connect>, poolclass=QueuePool, pool_size=DOCCHAT_SQL_THREADS, max_overflow=0, pool_timeout=DOCCHAT_SQL_POOL_TIMEOUT_SECONDS, pool_pre_ping=True, pool_reset_on_return="rollback")`.
2. **Dedicated thread pool.** `concurrent.futures.ThreadPoolExecutor(max_workers=DOCCHAT_SQL_THREADS, thread_name_prefix="docchat-sql")`. Every SQL call runs there: never on the event loop and never on the loop's default executor. The connection pool holds exactly as many connections as the thread pool has threads.
3. **Connection string.** One helper builds it, `docchat_core.sql.engine.connection_string(service)`: `Driver={ODBC Driver 18 for SQL Server};Server=tcp:<DOCCHAT_SQL_SERVER>,1433;Database=<DOCCHAT_SQL_DATABASE>;Encrypt=strict;ConnectRetryCount=0;APP=docchat-<service>`, where `<service>` is `api`, `ingestion`, `migrations`, `grants` or `ops`, so `APP_NAME()`, `sys.dm_exec_sessions.program_name` and the SQL audit name the calling component (`APP` is the driver's application-name keyword; it has no `Application Name` keyword). Login timeout `DOCCHAT_SQL_CONNECT_TIMEOUT_SECONDS`; statement timeout `DOCCHAT_SQL_COMMAND_TIMEOUT_SECONDS` (pyodbc `Connection.timeout`). `ConnectRetryCount=0` leaves every reconnect to the layer's counted, traced retries. Local-emulator mode only (`DOCCHAT_LOCAL_EMULATORS=true`, refused on App Service): `Server=127.0.0.1,14330;UID=sa;PWD=<DOCCHAT_LOCAL_SQL_SA_PASSWORD>;Encrypt=yes;TrustServerCertificate=yes;APP=docchat-<service>`, because the SQL Server container has no Entra authentication and a self-signed certificate.
4. **Tokens fetched on the loop, used in the thread.** Before dispatching work, the async entry point awaits `ensure_token()`: it returns the cached token while that stays valid for more than 300 s; otherwise one coroutine, under an `asyncio.Lock`, awaits `ManagedIdentityCredential.get_token("https://database.windows.net/.default")` (the process's one credential from the client factory, ADR 0113) and the others wait for it. The connect function in the SQL thread passes the cached token as attribute 1256, `struct.pack(f"<I{len(b)}s", len(b), b)` with `b` the UTF-16-LE token. No identity call runs in a SQL thread. A credential failure raises `SqlUnavailable(reason="token")`.
5. **Units of work.** `async def run(work: Callable[[Connection], T], *, name: str, retry: Literal["transient", "none"]) -> T` runs `work` on one connection in one SQL thread inside `with connection.begin():`, committing on block exit; the connection returns to the pool with a rollback reset. `fetch_one`, `fetch_all` and `execute` wrap one statement, with `retry="transient"` for reads and an explicit choice for writes; `name` is a registered statement-set name (telemetry and the query-plan audit). If the awaiting coroutine is cancelled (a client disconnect), the work in the thread still runs to its commit or rollback and its result is discarded, so a unit of work is never half-applied.
6. **Whole-unit retry, outside the transaction.** A failed unit is rolled back and, when `retry="transient"`, run again as a whole on error numbers 1205 (deadlock), 40197, 40501, 40613, 49918, 49919, 49920, 4221, 10928, 10929, 10053, 10054, 10060, 233 and 64, and on SQLSTATE `08S01`. Attempt n waits `min(8 s, 0.25 s × 2^(n−1))` multiplied by a random factor from 0.8 to 1.2, awaited on the loop, for at most 6 attempts; before each attempt a token close to expiry is refreshed. Error 40613 has its own budget: at most 12 attempts, delays capped at 10 s, at most 90 s in total. A unit that writes may choose `"transient"` only when it is idempotent; every other write chooses `"none"`.
7. **Errors by number, never by text.** The SQLSTATE is `args[0]`; the native error number is group 1 of the last match of `\((\d+)\) \(SQL\w+\)` in the pyodbc message (no match gives 0). The layer raises `SqlError(number, sqlstate, constraint)` or its subclasses `SqlUniqueViolation` (2627, 2601; `constraint` parsed from the message), `SqlDeadlock` (1205), `SqlTimeout` (`HYT00`) and `SqlUnavailable` (retries exhausted, pool timeout, token or connection failure), and discards the server's message text, because a unique-violation message quotes the duplicate key value. The API maps `SqlUnavailable` and `SqlTimeout` to `503 dependency_unavailable` with `retryAfterSeconds` 5; in ingestion they are retryable activity results.
8. **Idle release.** Pool `checkout` and `checkin` events record the last activity time. A background task in the API lifespan and in each ingestion worker process checks every 60 s; when no connection is checked out and none was used for `DOCCHAT_SQL_IDLE_RELEASE_MINUTES` (default 10), it awaits `engine.dispose()` in the SQL thread pool, closing every idle connection, and increments `docchat.sql.idle_releases`. The next unit of work reconnects.
9. **Statements.** Only SQLAlchemy Core constructs over the `docchat_core.sql.tables` metadata with bound parameters; `sqlalchemy.text()` only as constants in `docchat_core.sql.statements` (Ruff S608 and the banned-API rule, ADR 0129). Repository functions on a request path carry `@request_path(example_params=…)`, a registration with no run-time effect that the query-plan audit reads.
10. **Telemetry.** One span `docchat.sql.<name>` per unit of work (kind `CLIENT`; `db.system.name = "microsoft.sql_server"`, `docchat.sql.attempts`, `docchat.sql.error_number`, `docchat.outcome` `ok` or `error`). Metrics: `docchat.sql.duration` (histogram, ms; `operation`, `outcome`), `docchat.sql.retries` (`error_number`), `docchat.sql.failures` (`error_number`, `reason`: `exhausted`, `not_retryable`, `pool_timeout`, `token`), `docchat.sql.pool.wait` (histogram, ms; `service`), `docchat.sql.pool.in_use` (observable gauge; `service`), `docchat.sql.idle_releases` (`service`). No statement text and no parameter value is ever recorded; pyodbc has no OpenTelemetry instrumentation, so none is added implicitly.
11. **Synchronous tools.** Alembic (`db/migrations/env.py`, `APP=docchat-migrations`) and the grants step (`scripts/deploy/sql_principals.py`, `APP=docchat-grants`) use the same connection-string and token-structure helpers synchronously, in processes that have no event loop; `docchat-ops` uses the async layer with `APP=docchat-ops`.
12. **Warm-up at start-up.** Added 2026-11-08 (the product owner's decision): each serving process opens its pool's `DOCCHAT_SQL_THREADS` connections before its first unit of work, the API lifespan right after the first ops-config snapshot loads and the ingestion worker process when it creates its engine at its first invocation. `warm()` takes the token on the loop, then each SQL thread checks one connection out through the pool's own connect function and events and holds it until every thread has one; it waits at most `DOCCHAT_SQL_CONNECT_TIMEOUT_SECONDS`, never retries and never stops the process, so a database that fails it is met by the units of work under decision 6, as before; it is recorded as the span `docchat.sql.warm_pool`, in `docchat.sql.duration` (`operation` `warm_pool`) and, when it ends early, in `docchat.sql.failures`. Context: the first units of work after a start each waited for a login, and with the pool cold T-522's 200 concurrent reads saw the loop miss a 10 ms tick by up to 0.2 s in about one run in four. Measured on the compose SQL Server under the loop guard, a warm pool alone made it worse: all eight threads then ran queued units back to back, holding the interpreter lock so often that the loop fell 0.33 to 0.41 s behind in every run. So the engine also hands at most `DOCCHAT_SQL_THREADS` pieces of work to the thread pool at once, the rest waiting on the loop for an `asyncio.Semaphore`; with both, the largest gap was 0.034 to 0.059 s in each of 27 runs. `docchat-ops`, the migrations, the grants tools and the ingestion start-up method check don't warm. `01-repository.md` section 6.2 item 11 holds the rules.

Settings, read once at start-up by `SqlSettings` in `docchat_core` (an invalid value stops the process). The first two come from Bicep outputs; the others are changed by a pull request to `infra/config/app-settings.json` (keys `api` and `ingestion`):

| Setting | Type | Default | Allowed | Purpose |
|---|---|---|---|---|
| `DOCCHAT_SQL_SERVER` | string | required in Azure | `<server>.database.windows.net` | SQL host |
| `DOCCHAT_SQL_DATABASE` | string | `docchat` | `docchat` | database name |
| `DOCCHAT_SQL_THREADS` | integer | 8 (API), 4 (ingestion) | 2 to 32 | thread-pool size, equal to the connection-pool size |
| `DOCCHAT_SQL_POOL_TIMEOUT_SECONDS` | integer | 10 | 1 to 60 | wait for a pooled connection |
| `DOCCHAT_SQL_CONNECT_TIMEOUT_SECONDS` | integer | 30 | 5 to 60 | ODBC login timeout |
| `DOCCHAT_SQL_COMMAND_TIMEOUT_SECONDS` | integer | 30 (API), 120 (ingestion) | 5 to 300 | per-statement timeout |
| `DOCCHAT_SQL_IDLE_RELEASE_MINUTES` | integer | 10 | 1 to 60 | idle-connection release, so the `dev` database can auto-pause |

## Alternatives considered

- **`mssql+aioodbc` with `create_async_engine`.** Rejected: aioodbc is Alpha with no Python 3.13 classifier, it is a thread wrapper anyway, and SQLAlchemy's synchronous event handlers would put the token fetch on the event loop.
- **mssql-python with SQLAlchemy's `mssql+mssqlpython` dialect.** The driver is GA and supports `Encrypt=strict`, but it has no native async either, so the same thread pool would still be needed; its SQLAlchemy dialect first shipped in the 2.1.0b2 pre-release, while the pyodbc dialect is the one whose access-token pattern both Microsoft's ODBC documentation and SQLAlchemy's documentation describe. Rejected: no gain for the event loop and a younger dialect.
- **The loop's default executor.** Rejected: it is shared with other blocking work, so SQL calls could queue behind unrelated tasks or starve them, and its size isn't tied to the connection pool.
- **`Authentication=ActiveDirectoryMsi` in the connection string.** Rejected: the driver would make its own identity call for every new physical connection, inside a SQL thread, outside the awaited token cache and the one credential factory, where unit tests can't replace it.
- **ODBC driver-manager pooling.** Rejected: a second pool that SQLAlchemy can neither see nor dispose, so the idle release couldn't empty it, and the token pointer is part of its pool key.
- **Retrying the failed statement inside the open transaction.** Rejected: a deadlock victim's transaction is already rolled back, so re-running one statement would apply part of a unit.
- **Microsoft's generic schedule alone (5 s first wait, backoff to 60 s).** Rejected for request paths: deadlocks and throttling clear in well under a second, and a 5-second first wait would hold a chat turn or an admin request; only a resuming database needs long waits, and error 40613's own 90-second budget covers it.
- **`pool_recycle`, or no pool (`NullPool`), for `dev` auto-pause.** Rejected: recycling acts only at checkout, so an idle pool keeps its sessions and the database never pauses; no pool adds a TCP, TLS 1.3 and login handshake to every unit of work, and each ingestion sweep runs many short transactions.
- **Auto-pause off in `dev`.** Rejected: `dev` would pay for its minimum compute around the clock while it sits idle most hours.

## Consequences

- One path holds credentials, retries, telemetry and the statement rules; no SQL password exists in Azure; errors are mapped by number, and no server message text leaves the layer. A transient fault on one write can't abort a run: idempotent units retry as a whole, and ingestion records outcomes per item (ADR 0034).
- Every repository function is `async` and awaits the layer; every unit that writes states its retry choice, and a non-idempotent write chooses `"none"`.
- Cancellation never interrupts a statement; the statement timeouts (30 s in the API, 120 s in ingestion) bound how long a thread stays busy after a client leaves.
- Concurrency per process is bounded by `DOCCHAT_SQL_THREADS`. Saturation shows in `docchat.sql.pool.wait` and `docchat.sql.pool.in_use`; a pool wait longer than 10 s ends as `503 dependency_unavailable`. Alert A31 (`sql-failures`: more than 5 failures per app role in 5 minutes, severity 2, runbook R07, incident response) watches `docchat.sql.failures`; the `capacity` workbook charts duration, retries, failures, pool use and idle releases.
- An idle `dev` database is billed for compute about 25 minutes of every idle hour (hourly dispatcher wake, 10-minute idle release, 15-minute auto-pause delay; ADR 0036). The first request after a pause waits for the resume inside error 40613's budget (at most 90 s); a longer resume surfaces as `SqlUnavailable`.
- Every image that reaches SQL proves its driver at build time: the last build step fails unless `/opt/microsoft/msodbcsql18/lib64/libmsodbcsql-18.*.so.*` exists and `pyodbc.drivers()` lists `ODBC Driver 18 for SQL Server`.
- The error-number parser depends on pyodbc's message format; tests pin it for a single-record message, the two-record Windows format and a message whose quoted key value itself contains `(1205) (SQLExecDirectW)`.
- Required tests: a deadlocked unit is re-run and succeeds on attempt 2, its work having run twice; error 40613 is retried under its own budget (at most 12 attempts, at most 90 s on a fake clock) and then raises `SqlUnavailable`; `retry="none"` never retries, and error 2627 raises `SqlUniqueViolation` with the constraint name and no message text; 50 concurrent units with an expired token cause exactly one `get_token` call, and a token valid for 200 s is refreshed before use; the token attribute has the exact structure above; two transactions forced into a deadlock both complete; after 10 minutes idle no session remains in `sys.dm_exec_sessions` and the next unit reconnects; the warm-up opens one session per SQL thread, each in its own thread, ends early without raising on a failed checkout, a failed token request or its bound, and the API lifespan and the ingestion worker process run it before their first unit of work; on a pool warmed that way, 200 concurrent `fetch_one` calls on 8 threads never block the loop for more than 100 ms; cancelling the caller mid-transaction still commits; no span, metric or log record holds statement text or a parameter value. The stage-1 acceptance check runs `dev` for 2 hours without work and requires `docchat.sql.idle_releases` to increment in both apps and `az sql db show … --query status` to return `Paused`.
- When a GA async SQL Server driver ships, a new ADR revisits the thread pool.
