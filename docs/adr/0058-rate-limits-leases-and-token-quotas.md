# ADR 0058: Rate limits, leases and token quotas

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 11-api.md, 12-chat-pipeline.md, 13-conversations-and-memory.md, 80-data-model.md, 81-config.md, 82-security.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0012, 0028, 0030, 0055, 0056, 0057, 0059, 0060, 0070, 0143, 0147, 0148

## Context

- Every chat turn spends Azure OpenAI capacity that the whole organisation shares, so the API enforces per-user limits before any model call, with the deployments' own limits as the backstop: a sliding-window limit on chat requests per minute; a cap on simultaneous streams, where a stream stops counting once its citations are sent, because the user can ask again from that point; and day and month token quotas counted from actual model usage on every call (the answer, the standalone-query call, the broadened-search passage, follow-ups, summaries and memory extraction). Values live in SQL ops config. Going over a limit returns `429` with a problem body carrying `retryAfterSeconds`, plus the `Retry-After` header for non-browser clients.
- Any instance serves any request, so a limiter in process memory would multiply with the instance count and reset on every restart; the counters live in the Cosmos DB `usage` container, partitioned by user object ID, and change atomically. A stream counter decremented at `citations` would leak a slot whenever an instance dies mid-stream and then refuse that user.
- Vendor facts (checked 2026-10-14). Cosmos DB: an item's `ttl` takes effect only when the container's default TTL is set, where `-1` means no default expiry and an item with `ttl` n expires n s after its last write, and expired items stop appearing in reads before background deletion; patch supports `incr` (creating a missing field), at most 10 operations per patch, conditional on an ETag; `if-match` fails with `412`; creating an existing `id` fails with `409`. Azure OpenAI: the token limiter estimates each request on arrival from its prompt plus `max_completion_tokens`, requests per minute are enforced over 1-second or 10-second windows, and excess requests get `429` with `retry-after-ms`.
- Cross-origin scripts can't read response headers, so the retry time must travel in the body.

## Decision

**Store.** Container `usage` in database `docchat`: partition key `/userId` (`Hash`), `defaultTtl: -1`, indexing policy `consistent` with every path excluded (the container sees only point reads, creates, patches, replaces and deletes), no unique keys. Every document is a Pydantic model with `extra="forbid"` and at most 1 KB; every partition key value is the validated token's `oid`. Items: `day:{YYYY-MM-DD}` (`ttl` 3,456,000 s, 40 days), `month:{YYYY-MM}` (`ttl` 34,560,000 s, 400 days), `rate:{epochMinute}` (`ttl` 180 s) and `lease:{slot}` (`ttl` = `chat.max_turn_seconds` + 30). The container also holds the citation-download windows and leases (ADR 0148) and the per-user write windows (ADR 0143), whose ID prefixes never collide with these.

**Order on `createChatTurn`.** The pre-body checks (token, role, first-sign-in provisioning; the route declares `route_options(body_limit=32768, burst_limited=False, write_limited=False)`, so the general burst and write limits don't apply to it), the body checks, then P3 request rate, P4 quota, P5 lease, P6 project access, P7 index resolution and P8 turn creation (ADR 0056). A lease acquired before a later pre-stream refusal is released before the error response is sent.

**Request rate (P3).** A two-bucket sliding window per user. At time `t` (UTC epoch seconds), `m = floor(t / 60)`, `f = (t − 60m) / 60`, `p` = the count in `rate:{m−1}` and `c` = the count in `rate:{m}` (a missing item counts 0): the request is allowed when `(c + 1) + p × (1 − f) ≤ L`, with `L` = `ratelimit.chat_requests_per_minute`. The API point-reads both items concurrently, decides, and only when it allows writes `rate:{m}`: a patch `incr /count 1` conditioned on the ETag it read (`MatchConditions.IfNotModified`), or a create with `count` 1 when the item didn't exist. A `412` or `409` restarts the check, at most 5 attempts; when attempts run out the answer is `429 rate_limited` with `retryAfterSeconds` 1. Refused requests aren't counted. Every request that passes token and body validation counts, replays and requests later refused with `404` or `409` included. For `rate_limited`, `retryAfterSeconds` is the smallest whole `s` from 1 to 120 for which the estimate at `t + s`, with no further requests, would allow one more request, found by stepping 1 s at a time.

**Concurrency leases (P5).** Each stream holds one item `lease:{slot}` (`turnId`, `sessionId`, `acquiredAt`, `expiresAt`), slot 1 to `ratelimit.max_concurrent_streams`. Acquisition tries slots in ascending order: `create_item`; on `409`, read the item and, when its `expiresAt` has passed, take it over with `replace_item` conditioned on that item's ETag; on `412`, a `404` on the read or a live lease, try the next slot. `ttl` and `expiresAt` = acquisition + `chat.max_turn_seconds` + 30 s (210 s by default), matching the turn's `deadlineAt` offset (ADR 0056). All slots live → `429 too_many_streams` with `retryAfterSeconds` 10. Release is `delete_item` conditioned on the ETag of the lease this request wrote; a `404`, a `412` or a timeout is ignored, because the TTL ends the lease. Release happens right after the `citations` event is written, or in the finaliser when the stream ends before citations (ADR 0057); a replay holds its lease until its own `citations` event.

**Token quotas (P4).** Per-user counters per UTC day and per UTC month hold, among other totals, `totalTokens` = prompt plus completion tokens (completion includes reasoning) over every Azure OpenAI call charged to the user. At turn start the API point-reads both concurrently; `day.totalTokens ≥ quota.tokens_per_day` or `month.totalTokens ≥ quota.tokens_per_month` → `429 token_quota_exceeded`, with `retryAfterSeconds` = the seconds until the next UTC midnight (day) or the first instant of the next UTC month (month), the larger when both are exceeded, rounded up. A turn that starts under quota finishes even if it crosses the quota, so the overshoot is bounded by one turn and its after-response calls. The background `summary` and `memory` calls check before each call through `docchat_api.usage.check_token_quota(oid) -> QuotaCheck {allowed, exceeded (day, month or null), retry_after_seconds}`, which reads the two counters only; when the reads time out twice it raises `UsageStoreUnavailable`, and the work defers with no model call and no attempt counted.

**Counter updates.** After every model call (ADR 0059), two concurrent writes to `day:{date}` and `month:{yyyy-mm}` of the call's end time (UTC): `patch_item` with `incr` on `promptTokens`, `completionTokens`, `reasoningTokens`, `cachedTokens`, `cacheWriteTokens`, `totalTokens` and `calls`, `incr` on `estimatedCostMicros` when the cost is known or on `unpricedCalls` when it isn't, `incr` on `estimatedCalls` when the record is estimated, and `set /updatedAt`: at most 10 operations. On `404` the API creates the item with those values; on `409` (created meanwhile) it patches again. Up to 3 attempts, 0.2 s then 0.4 s apart, on `408`, `429`, `449`, `503` and a client timeout. Persistent failure logs `usage_record_failed` (metadata only) and increments `docchat.usage.record_failures`; it never fails the turn. Each write runs as a shielded task that the turn's finaliser awaits.

**Timeouts and outages.** Every `usage` operation passes the async SDK's per-operation `timeout`: 2 s for point reads, 3 s for create, patch, replace and delete. Before the response starts, a timed-out operation is retried once, and a second timeout refuses the request with `503 dependency_unavailable` (`retryAfterSeconds` 5): the limits fail closed.

**`429` answers.** RFC 9457 problem details with `type` `urn:docchat:problem:<code>`, `title`, `status` 429, `detail`, `code` (`rate_limited`, `too_many_streams` or `token_quota_exceeded`), `correlationId` and `retryAfterSeconds`, an integer from 1 to 2,678,400 (a 31-day month in seconds); the `Retry-After` header carries the same integer.

**Settings and defaults** (typed ops_config rows in `RateLimitOps` and `QuotaOps`, changed only with `docchat-ops config set`, live on the first access after the API's 60-second snapshot): `ratelimit.chat_requests_per_minute` 3 (range 1 to 1,200); `ratelimit.max_concurrent_streams` 2 (1 to 200); `quota.tokens_per_day` 2,000,000 (10,000 to 1,000,000,000); `quota.tokens_per_month` 32,000,000 (from `quota.tokens_per_day` to 100,000,000,000). At 3 requests a minute and the 40,000-token context budget a user reserves at most 120,000 tokens per minute, 24% of the 500-unit chat deployment in `prod`; that capacity rule and its `docchat-ops chat capacity-check` are ADR 0147. Two streams let a user ask in a second session while an answer is still being written in the first. At an estimated 20,000 tokens per turn the quotas allow about 100 turns a day and 1,600 a month: a ceiling for heavy use, not a routine limit. Quotas are global; there is no per-user exception. Before a load test, and in the `load` environment only, operators set `ratelimit.max_concurrent_streams` 200, `ratelimit.chat_requests_per_minute` 1,200, `quota.tokens_per_day` 1,000,000,000 and `quota.tokens_per_month` 100,000,000,000 with `docchat-ops config set --env load`.

**Backstop.** Each Azure OpenAI deployment's tokens-per-minute limit is the service-level backstop (an excess call ends with `model_busy`), and the monthly budget `budget-docchat-<env>` with alerts at 50%, 80% and 100%, on by default, is the spend alert.

**Telemetry.** Counter `docchat.ratelimit.rejections` with `reason` `rate`, `concurrency`, `quota_day` or `quota_month`; alerts `quota-rejections` (more than 20 quota rejections in an hour), `rate-rejections-share` (rate and concurrency rejections above 10% of at least 50 chat requests in 30 minutes) and `usage-recording-failures` (any usage-recording failure).

## Alternatives considered

- **One counter per calendar minute.** A client can send 2 × L requests across a minute boundary within a second.
- **A sliding log, one item per request.** It needs a query over the user's items and an index the container otherwise doesn't need, and one write per request plus deletes.
- **A token bucket per user.** It needs the same ETag read-modify-write on every request, with a fractional balance and a refill-rate setting; the two-bucket window needs only an integer `incr` on minute items that expire by themselves.
- **In-process limiters.** Limits would multiply with the instance count and reset on restart.
- **Azure API Management policies or a Redis cache.** The platform has no API Management layer, and the counters sit in the Cosmos DB account that already holds conversations; Redis would add a resource, a private endpoint and a second store to operate.
- **A stream counter incremented and decremented.** It leaks a slot whenever an instance dies mid-stream.
- **Reserving a turn's worst-case tokens up front and settling afterwards.** It adds writes to every turn and a refund on every failure path, while the overshoot it removes is bounded at one turn.
- **Failing open when the store can't be read.** An outage would remove the cost controls exactly when nothing else watches them.

## Consequences

- Limits hold across instances and restarts with no sweeper job; a crashed instance strands a lease for at most `chat.max_turn_seconds` + 30 s (210 s by default, 250 s at the 220-second maximum), so "too many answers in progress" clears without an operator.
- Each chat request costs the `usage` container two point reads and one write for the rate, two point reads for the quota, a create (or a read and a replace) and a delete for the lease, plus two writes per model call; items stay under 1 KB and nothing is indexed.
- A `usage` outage refuses new turns with `503 dependency_unavailable` rather than running them unmetered. After the `200`, a counter write that keeps failing is logged and counted but never fails the turn, so the counters can under-count during an outage, which the `usage-recording-failures` alert reports.
- Every calendar minute holds at most L counted requests, but a 60-second span that crosses a minute boundary can hold up to 2 × L − 1 (5 at the default 3) when the earlier minute's requests came at its end; the deployments' token limits stay the backstop for that burst.
- A user can exceed a quota by at most one turn and its after-response calls.
- In `prod`, raising the request rate or the context budget first needs the capacity check of ADR 0147.
- Obligations: the four ops_config rows; runbook steps for "too many answers in progress", a user out of quota (no per-user exception), changing a limit and the load-test values; tests of the window decision and its `retryAfterSeconds` against fixture cases (an estimate exactly at the limit included), of quota retry times across month ends and 29 February, of `usage` timeouts (`503` after 2 × 2 s on a read and 2 × 3 s on a lease create, and a counter write that never returns leaving the turn to end with `done`), of 20 concurrent requests under a limit of 10 admitting exactly 10, of 10 concurrent lease acquisitions on 3 slots giving exactly 3 with takeover of an expired lease and no release of another holder's lease, of exact day and month totals after 50 concurrent counter updates, and of a quota refusal that makes no model call.
