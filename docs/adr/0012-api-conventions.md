# ADR 0012: API conventions

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 11-api.md, 80-data-model.md, 82-security.md, 10-web-client.md, 84-testing.md
- **Related ADRs:** 0004, 0007, 0013, 0014, 0015, 0017, 0020, 0021, 0022, 0023, 0055, 0056, 0058, 0069, 0094, 0143

## Context

The API serves 45 operations owned by four areas (identity and access, ingestion, chat, conversations and memory), and one web client calls all of them. Its errors must be RFC 9457 problem details with a correlation ID that a user can quote, and must never carry exception text, stack traces, SQL or upstream messages. Every input is a Pydantic model with explicit limits (a question is at most 4,000 characters), enums for closed sets and unknown fields rejected. API responses send `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; file responses also send `Content-Security-Policy: sandbox` and an RFC 6266 file name. A refused request over a rate limit or quota answers `429` with `retryAfterSeconds` in the body and `Retry-After` for non-browser clients. Every admin edit uses optimistic concurrency with a `rowVersion` in the body, `If-Match` on the write and `412` when stale. A resource the caller can't reach answers `404`, so existence never leaks, and `403` means only a missing role or a non-admin on an admin route. Failures before a chat stream starts are ordinary HTTP errors.

The browser calls the API across origins through App Service platform CORS, which can't expose response headers to scripts, so every value the client needs (the row version, the correlation ID, a retry hint) travels in the body. The client must be able to branch on a stable code and on typed fields, never on message text.

Standard and vendor facts (RFC 9457, checked 2026-10-18): the members are `type`, `title`, `status`, `detail` and `instance`; `title` "SHOULD NOT change from occurrence to occurrence of the problem, except for localization"; "clients consuming problem details MUST ignore any such extensions that they don't recognize"; "the type URI is allowed to be a non-resolvable URI"; the media type is `application/problem+json`; generators should not expose "implementation details such as a stack dump". FastAPI reads and parses a request body before it resolves the endpoint's dependencies, so authentication written as an ordinary dependency would let `413`, `415` or `422` answer before `401` and would parse the bodies of refused requests.

## Decision

1. **Problem details.** Every non-`2xx` response the app produces is `application/problem+json` with exactly: `type` (`urn:docchat:problem:<code>`), `title` (one per code, sentence case, at most 40 characters), `status`, `detail` (one safe text per code, written by the owning area), `code` (stable snake_case) and `correlationId` (the 32-character lower-case hex W3C trace ID of the request's server span). Extension members appear only here: `retryAfterSeconds` (integer 1 to 2,678,400, the 31-day monthly-quota wait) on every `429`, on every `503` that states a wait and on `409 turn_in_progress`, always with the same value in `Retry-After`; `errors` (1 to 50 items of `{ "path": string, "reason": string }`) on every `422`; `sessionId` and `turnId` (UUID text) on the four `409` problems raised when a chat turn starts (`turn_in_progress`, `turn_already_ended`, `client_turn_id_conflict` carry both; `session_turn_limit` carries `sessionId` only, because it refuses before any turn exists). `instance` is never used and no other member appears. A body never holds exception text, stack traces, SQL, upstream messages, input values, names or e-mail addresses. An unmapped exception becomes `500 internal_error`, logged once at the boundary as `request_failed` with `error.type` (the qualified type name) and `docchat.error_code`, never the message (ADR 0014). Models: `docchat_api.http.problems.Problem` and `FieldError`; the OpenAPI `Problem` schema declares `retryAfterSeconds` with `minimum: 1, maximum: 2678400` and the two extension members as optional UUID strings. No response header carries the correlation ID; it also appears in the stream's `meta` and `error` events (ADR 0055) and in `audit_events.correlation_id` for rows the request writes.
2. **The code catalogue.** `docchat_core.errors.CODES` is an open catalogue with one entry per code: status (`None` for a code that exists only as a stream `error` event or a stored turn code, the 13 stream-only chat codes and `turn_abandoned`; the problem handler never builds a response from such an entry), title, `detail`, retryable flag and owning area. The area that raises a code writes its one title and one `detail`; every other area cites them. A unit test fails when a code is registered twice, when a raised code isn't in the catalogue, or when an entry lacks a title or `detail`. Answers from platform authentication and platform CORS aren't the app's and carry no problem body; the web client classifies them by status, and a `403` without a problem body is an HTTP failure, never "not assigned".
3. **Status rules.** `403` only for `role_not_assigned` (any route) and `admin_required` (any `/v1/admin` route); every missing or unreachable resource is `404` with its resource's code (ADR 0020). Unknown path `404 route_not_found`; wrong method `405 method_not_allowed` with an `Allow` header. Optimistic-concurrency failures are `412` and `428` (item 7); limits are `429`; dependencies that don't answer are `503` (`dependency_unavailable` with `retryAfterSeconds` 5, `authentication_unavailable` with 30).
4. **Validation.** Bodies and query models are Pydantic models with `extra="forbid"`, so an unknown body field or query parameter is `422` with reason `unknown_field`. Every `422`, the generic `validation_failed` or an area's own `422` code, carries at least one `errors[]` entry. `errors[].path` is the location (`body`, `query`, `path`, `header`) followed by the dotted JSON path in camelCase names with zero-based list indices (`body.exampleQuestions.2`, `query.limit`, `path.projectId`, `header.If-Match`); it never carries the value. `errors[].reason` comes from the open catalogue `docchat_core.errors.REASONS`: the general reasons `required`, `unknown_field`, `invalid_type`, `invalid_json`, `invalid_uuid`, `invalid_format`, `invalid_cursor`, `invalid_characters`, `too_short`, `too_long`, `out_of_range`, `too_many_items`, `not_allowed`, `duplicate` and `not_found` (a referenced ID has no row); the memory and feedback reasons `category_requires_down`, `comments_disabled`, `empty`, `contains_link`, `contains_code`, `contains_instruction`, `contains_secret`, `duplicate_fact` and `memory_full`; any area may add more, and a unit test fails when a raised reason isn't in the catalogue. Pydantic error types map: `missing` → `required`; `extra_forbidden` → `unknown_field`; `json_invalid`, `json_type` → `invalid_json`; `uuid_parsing`, `uuid_type` and pattern failures on ID fields → `invalid_uuid`; `string_too_short` and a list's `too_short` → `too_short`; `string_too_long` → `too_long`; a list's `too_long` → `too_many_items`; `greater_than`, `greater_than_equal`, `less_than`, `less_than_equal` → `out_of_range`; `literal_error`, `enum` → `not_allowed`; every other `*_type` error → `invalid_type`; the text types and validators raise their own reasons (`invalid_characters`, `duplicate`, `invalid_cursor`); anything else → `invalid_format`. Invalid JSON or invalid UTF-8 is `{path: "body", reason: "invalid_json"}`. Identifiers in paths, queries and bodies must match `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$` and are lower-cased after validation; anything else is `invalid_uuid`, so a `404` always means "well-formed, and absent or unreachable" (ADR 0015). Text types in `docchat_api.http.text`: `SingleLineText(min, max)` applies Unicode NFC, trims, collapses every whitespace run to one space and rejects code points of category Cc, Cf, Cs, Co or Cn (`invalid_characters`); `MultiLineText(min, max)` applies NFC, turns CR LF and lone CR into LF, trims the whole text, allows LF and TAB and rejects every other Cc code point and every Cf, Cs, Co or Cn one; both measure length in code points after normalisation. Rejecting Cf (the bidirectional controls U+202A to U+202E and U+2066 to U+2069, the zero-width characters U+200B to U+200F and U+FEFF, and the rest of the category) keeps a text one admin enters from reordering or hiding characters on another person's screen. Every string, list and integer has explicit bounds shown in the OpenAPI document. Request fields are non-nullable unless an operation says otherwise; in a `PATCH`, an absent field means "unchanged". Responses include every field, `null` where empty, and give times as ISO 8601 UTC with milliseconds and `Z` (ADR 0015).
5. **Pre-body checks in one route class.** ASGI middleware, outermost first: OpenTelemetry instrumentation (continues the incoming `traceparent`), the security headers of item 8, then the request-size and content-type guard. Every `/v1` route is mounted on one router, `APIRouter(route_class=DocChatRoute)` (`docchat_api.http.routing.DocChatRoute`), whose handler runs, before FastAPI reads the body or resolves dependencies, and in this order: (i) token validation and the role check, building the `Principal` (ADR 0017); (ii) the per-user burst limit unless the route declares `burst_limited=False` (ADR 0143); (iii) `require_admin` on `/v1/admin/*`; (iv) the per-user write limit when the route declares `write_limited=True`; (v) first-sign-in provisioning (ADR 0021). The `Principal` is kept in `request.state.principal`; endpoints read it through the dependency `current_principal`, and no area declares an authentication dependency of its own. Each route declares `docchat_api.http.route_options(body_limit, content_types, burst_limited, write_limited)`, with defaults 65,536 bytes, `('application/json',)` (charset absent or `utf-8`), `True`, and `True` for `POST`, `PUT`, `PATCH` and `DELETE`. `createChatTurn` declares `body_limit=32768`, `burst_limited=False` and `write_limited=False`; `adminUploadContent` declares `content_types=('application/octet-stream',)` and `body_limit=None` and enforces `DOCCHAT_UPLOAD_MAX_BYTES` while it streams; the other three upload operations declare `write_limited=False`. At the first body read the guard refuses a `Content-Type` outside the route's list with `415 unsupported_media_type` (one shared text for every route), compares `Content-Length` with the limit, then counts bytes as they arrive; a breach is `413 request_too_large`. Because the first body read happens after the route class's checks, these refusals come after `401`, `403` and the limits. Exception handlers: `DocChatProblem` subclasses carry `code` and `status`; `RequestValidationError` becomes `422`; anything else `500 internal_error`.
6. **Lists.** Every list operation takes `limit` (each operation states its range, whose maximum is never above 100, and its default) and `cursor` (optional, 1 to 512 characters, `^[A-Za-z0-9_-]+$`), and answers `{ "items": [...], "nextCursor": string | null }` (two named exceptions: `getSession` answers `turns` with `earlierTurnsCursor`, and `adminGetIngestionRun` `items` with `nextItemsCursor`). Every list has a total order ending in a unique column; paging is keyset, never offset; the server reads `limit + 1` rows and returns `nextCursor` only when the extra row exists. A cursor is base64url without padding of compact UTF-8 JSON `{"v": 1, …}` holding the sort values of the last item returned and the filter values it was issued for, decoded through a Pydantic model with `extra="forbid"`; a cursor that fails to decode or validate, or whose filters differ from the request's, is `422 invalid_cursor`. Cursors aren't signed: they hold only positions inside the caller's own authorised view.
7. **Optimistic concurrency.** Every admin edit of an existing resource, and every memory write, requires `If-Match` with exactly one strong entity tag in double quotes: for SQL resources the `rowVersion`, the 8-byte `ROWVERSION` as standard base64 with padding (12 characters, `^[A-Za-z0-9+/]{11}=$`) present in every response body that carries the resource; for memory the `etag`, the Cosmos DB `_etag` verbatim. A missing header, `*`, a weak tag, a list or any other form is `428 precondition_required`; a well-formed tag that isn't the current value is `412 precondition_failed`. `adminUpdateProject` and the membership and mapping operations (`adminAddProjectMember`, `adminRemoveProjectMember`, `adminMapProjectIndex`, `adminUnmapProjectIndex`) all take the project's `rowVersion`; the four membership and mapping operations move it when they change a row and return it as `projectRowVersion`, and a call that changes nothing moves nothing and returns the current version (ADRs 0022, 0094). The check is part of a guarded `UPDATE … WHERE row_version = @rowVersion`; zero rows triggers one re-read that decides `404` (row gone) or `412` (version moved). Creates take no `If-Match`. No `ETag` response header is sent.
8. **Response headers.** Every response the app produces, problems, `204` and `/healthz` included, carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Strict-Transport-Security: max-age=31536000`. JSON and NDJSON responses add `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. File responses (`getCitationContent`, `getCitationDocument`, `adminGetDocumentPdf`) carry `Content-Security-Policy: sandbox` and a `Content-Disposition` built only by `docchat_api.http.content_disposition(name)`: always `attachment`, an RFC 8187 `filename*` of the name cut to 200 code points keeping its extension, and an ASCII `filename` derived from it (ADR 0069). No `Server` header and no access log: the worker class `docchat_api.http.worker.DocChatUvicornWorker` subclasses `uvicorn_worker.UvicornWorker` with `server_header=False` and `access_log=False`, because request lines would carry search text and identifiers into logs. No response compression. The app adds no CORS middleware; platform CORS answers preflights (ADR 0004).
9. **Evolution.** `/v1` is the only version, and every route except `GET /healthz` lives under it. Within `/v1`, responses may gain fields, requests may gain optional fields only, and error codes may be added; nothing is removed, renamed or retyped. A breaking change ships as `/v2` beside `/v1` until the web client has moved. Clients ignore unknown response fields (the web client's generated schemas strip them), and a new response enum value ships in the client first (ADR 0013).

## Alternatives considered

- **`detail` written per occurrence, with the specifics of the failure.** Lost: specifics are where input values, names and upstream text leak, and one text per code keeps every screen's message consistent. Specifics the client needs travel as declared members (`errors[]`, `retryAfterSeconds`, `sessionId`, `turnId`).
- **Status codes chosen by exception class, or the framework's default validation answer.** Lost: the status must follow the cause, and the client needs the field path and reason of every `422`.
- **Authentication and limits as FastAPI dependencies.** Lost: the body is read and parsed first, so an oversize or malformed request from an anonymous caller would get `413` or `422` and not `401`, and refused requests' bodies would be parsed. The route class runs the checks before any body read.
- **An `ETag` response header, or the correlation ID in a response header.** Lost: platform CORS can't expose response headers, so cross-origin scripts couldn't read either; both travel in the body.
- **Offset pagination.** Lost: inserts between pages skip or repeat rows, and the cost grows with the offset. Keyset paging over a unique tiebreak is stable and index-backed.
- **Signed or encrypted cursors.** Lost: a cursor holds only positions inside the caller's own view, so tampering can skip or repeat only items the caller may see anyway; a signing key would add a secret to manage.
- **`403` for resources the caller can't reach.** Lost: it confirms that the resource exists.
- **A version header or media-type versioning.** Lost: the path prefix is visible in every log line and route test, and `/v2` beside `/v1` keeps a deployed client working through a change.

## Consequences

- The web client has one problem parser and one message table keyed by `code`, shows every error with its correlation ID as the reference, waits `retryAfterSeconds` where the code says so, and never parses message text.
- Obligations: a new code ships with its catalogue entry, title and `detail` in the same pull request; a new list states its `limit` range, default, sort order and cursor members; a route that isn't a default JSON route declares its route options; a new write route is write-limited unless it declares otherwise.
- Tests: every problem renders exactly the members above; `retryAfterSeconds` 2,678,400 validates and 0 or 2,678,401 is refused; the code and reason catalogue tests; a sentinel string sent in every field never appears in a problem body; `If-Match` missing, `*`, `W/"…"`, a list or unquoted gives `428`; tampered cursors give `invalid_cursor`; upper-case UUIDs are accepted and lower-cased, while braces, URN and 32-hex forms give `invalid_uuid`; U+202E or U+200B in a project name gives `invalid_characters`; the headers of item 8 are on `200`, `204`, `4xx`, `5xx` and `/healthz` responses with no `Server` header; a call without a token and with an oversize body gets `401`, not `413`.
- Accepted costs: a text can't hold the joiners U+200C and U+200D, which some scripts and emoji sequences use; a membership or mapping change makes another admin's pending edit of the project's fields stale, which costs that admin one reload.
- Risk: the route class depends on FastAPI's route-handler hook. The `401`-before-`413` test and the check-order tests fail if a FastAPI upgrade changes when the body is read.
