# ADR 0052: Deleting a logical index

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 11-api.md, 14-ingestion.md, 80-data-model.md, 10-web-client.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0012, 0022, 0029, 0031, 0032, 0034, 0040, 0045, 0054, 0069

## Context

- A logical index (`search_indexes`) is served by one active physical index, plus at most one being built. Projects reach it through `project_indexes` (one default per project); a per-user override must name a mapping of its project (a composite foreign key to `project_indexes`); documents belong to the index. Only the ingestion app creates and deletes physical indexes, through the queue and the dispatcher; the API identity holds Search Index Data Reader only.
- Projects are archived and never deleted (ADR 0022), so a project's history survives. An index, by contrast, holds a search-service slot, a physical index of chunks, renditions and source files that cost money for as long as they exist. Admins need to remove an index that no project uses any more, so that unused indexes never fill the search tier's index quota and block the next index an admin creates.
- Vendor facts (checked 2026-10-14): Azure AI Search allows at most 15 indexes on Basic and 50 on S1, and a rebuild holds two physical indexes for one logical index; deleting an index needs `Microsoft.Search/searchServices/indexes/delete`, which the ingestion identity's custom role DocChat Search Index Manager (`e622b7ad-d5a9-48fb-8d1c-ae3d52a7cb9d`) holds with `indexes/read` and `indexes/write`.

## Decision

1. **Operation.** `adminDeleteIndex`, `DELETE /v1/admin/indexes/{indexId}`: `Admin` role, no body, `If-Match` with the index's `rowVersion`. Checks, in order, after authorisation: the index exists and isn't `deleted` (`404 index_not_found`); the `If-Match` value, compared with the row read under `UPDLOCK` (`428` when missing, `412` when stale, 11-api.md section 1.9); no `app.project_indexes` row references it (`409 index_mapped`, "Remove this index from every project before deleting it."); its status is `ready`, `reingest_required` or `failed` (`409 index_busy` for `provisioning`, `reingesting`, `rebuilding` and `deleting`). No override check is needed, because no override can exist without a mapping. Other answers: `401`, `403`, `429` (`too_many_requests`, `write_rate_limited`), `503 dependency_unavailable`.
2. **One transaction.** (a) The guarded `UPDATE app.search_indexes SET status = 'deleting' … WHERE id = @index AND row_version = @rowVersion`, row count checked (zero rows: `412`); the update holds the logical index row's lock, so it serialises with flips, repoints and re-ingest starts of that index. (b) Every live document of the index is deleted as a single document delete is, without per-document runs: `is_deleted = 1`, `deleted_at`, `deleted_by`, `current_version_id = NULL`; versions `pending`, `ingesting` and `ingested` become `superseded`, `uploading` ones `failed` with `document_deleted`; every `served_chunk_sets` row of those documents is deleted, which hides them from readers at once; their `building`, `ready` and `served` chunk sets become `retired`. (c) Every `queued` item of the index becomes `cancelled` with `index_deleted`. (d) One `index_delete` run, priority 1 (bulk), with one `delete_physical_index` item per physical index not yet `deleted` and one `purge_index_blobs` item. (e) Audit action `index.deleted` (actor type `user`, target `search_index`, metadata `runId`, `physicalIndexCount`, `documentCount`). After the commit the API sends one queue message `{runId, traceparent, tracestate}` and answers `202` `{index: IndexDetail, runId}` with status `deleting`.
3. **Physical indexes.** Each `delete_physical_index` item runs `delete_search_index` (deadline 300 s): `SearchIndexClient.delete_index(<name>)`, where `ResourceNotFoundError` counts as done; then one transaction deletes the physical index's `served_chunk_sets` rows, marks its chunk sets `retired` with `chunks_deleted_at`, and sets it `deleted` from `active`, `building` or `retiring`; event `physical_index_deleted`. The dispatcher's claim starts a `delete_physical_index` item only when no item of its physical index is running, so in-flight items end first; their Validate or Flip finds the document deleted and skips with `document_deleted`.
4. **Blobs.** The claim starts the `purge_index_blobs` item only when no item of the logical index is running (`r.search_index_id = i.search_index_id` in the claim's `NOT EXISTS`, ADR 0034), so a Render or `rerender` item that can still upload under either prefix ends before the purge lists it. The item lists `documents/{indexId}/` and `renditions/{indexId}/` (`ContainerClient.list_blobs(name_starts_with=…)`) and deletes in `delete_blobs` calls of at most 256 blobs. Each call works for at most `ingestion.activity_time_budget_seconds` (default 1,200) inside its 1,560-second deadline and returns `done: false` until both prefixes are empty; it then sets `storage_purged_at` on every version of the index. Errors are retryable `storage_unavailable`. Deleted blobs stay soft-deleted for 14 days (ADR 0031).
5. **Finalisation.** When the run has no `queued` or `running` item, the sweep finalises it and sets the logical index `deleted`. The row stays, as the target of run history and audit rows; `UX_search_indexes_display_name` is filtered to `status <> 'deleted'`, so the display name becomes free. Document, version and chunk-set rows stay too (ADR 0032).
6. **While `deleting` and after.** Uploads answer `409 index_not_accepting_uploads`; `adminUpdateIndex`, `adminStartReingest`, `adminDeleteDocument` and `adminReingestDocument` answer `409 index_busy`; `adminMapProjectIndex` answers `409 index_not_mappable`. Once `deleted`, every route answers `404 index_not_found`, and `adminListIndexes` omits the index unless asked for `status=deleted`. A stored citation that points into a deleted index answers `404 citation_not_found`, because no project maps the index (ADR 0069).
7. **Web client.** The Index page offers Delete index only when `mappedProjects` is empty and the status is `ready`, `reingest_required` or `failed`; a confirmation precedes `adminDeleteIndex` with `If-Match`; on `202` the Indexes list opens with a confirmation toast, and the run appears on Ingestion runs as Delete index.

## Alternatives considered

- **Unmap automatically on delete.** Each project using the index would lose its default silently and answer `409 project_index_unavailable` to every member. Requiring the admin to unmap first shows each affected project. Lost.
- **Archive indexes as projects are archived.** The physical index would keep its search-service slot (one of 15 on Basic) and its files would keep their cost. Lost.
- **Delete synchronously in the API.** The API identity can't manage indexes or write `renditions`, and a long purge must survive restarts; the ledger and dispatcher already give both. Lost.
- **Delete the SQL rows.** Run history, audit targets and document records would dangle; the row costs nothing, and the filtered unique index frees its name. Lost.
- **Allow deletion during a re-ingest or rebuild.** Build items would race the delete. `409 index_busy` keeps one index operation at a time, and an operator can abandon a stuck rebuild (ADR 0054). Lost.
- **One `cleanup_document` item per document, as a document delete does.** Thousands of key deletes into an index about to disappear; one `delete_index` removes every chunk at once. Lost.

## Consequences

- Admins free a search-service slot and storage without operator help, and deletion is two steps (unmap, then delete), so no project loses its index by accident.
- Readers stop seeing the documents at the commit; the physical indexes and blobs disappear over the run, at bulk priority behind interactive uploads. Blobs can be undeleted for 14 days, but the logical index can't be restored: an admin creates a new index and uploads again.
- The physical indexes keep counting against `DOCCHAT_SEARCH_MAX_INDEXES` until their items finish, and the display name stays taken until finalisation.
- Risk: a `delete_physical_index` item that still fails after its attempts (`index_delete_failed`) leaves that Azure AI Search index and its `physical_indexes` row in place, the run ends `completed_with_errors` or `failed`, and finalisation still sets the logical index `deleted`; the row keeps counting against `DOCCHAT_SEARCH_MAX_INDEXES`, so the capacity check stays correct, but no sweep duty retries it, because the sweep's due-deletion duty picks only `retiring` physical indexes.
- Obligations: the operation in the OpenAPI document with its codes; the `index.deleted` audit action and `index_deleted` item code; tests proving `428` and `412` on `adminDeleteIndex`; that a mapped index is refused and an unmapped one loses every physical index and blob and ends `deleted`; that mapping a `deleting` index gives `409 index_not_mappable` and a `deleted` one `404 index_not_found`; and that the web client shows Delete index only when it is allowed.
