# ADR 0122: Test-user credentials read from inside a network

- **Status:** Accepted
- **Date:** 2026-10-21; amended 2026-10-30 (standard GitHub-hosted runners with a transient runner rule by default, private networking optional); amended 2026-11-06 (no job holds the shared allowlist, so test-vault leftovers are swept only in runbook R26); amended 2026-11-07 (`nsg-docchat-ci-pe` denies outbound traffic to the network too, for PSRule's `Azure.NSG.LateralTraversal`, ADR 0106)
- **Decided by:** Product owner and architect
- **Specified in:** 83-infrastructure.md, 82-security.md, 81-config.md, 84-testing.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0019, 0098, 0104, 0114, 0119, 0120, 0126, 0141, 0142

## Context

The deployed smoke, full and load suites are part of the definition of done, and each needs tokens for real test users. Tokens come from ROPC (ADR 0019), so the test users' passwords are the first version's only stored secrets. The product owner placed them in a non-production Key Vault that only the CI test identity can read, rotated every 30 days by an operator script, with `prod`'s Key Vault empty.

That vault is a Key Vault, so the network rule for every Key Vault applies to it: selected networks with the operator allowlist and no trusted-service bypass (ADR 0098). A GitHub-hosted runner's address is never in that allowlist and can differ on every job, so a CI job reaches the vault in one of two ways: through a transient runner rule, added for the job's own address and removed inside the job, as ADR 0119 does for SQL and the `dev` registry; or through a private endpoint, from a runner joined to an Azure network. GitHub joins its hosted runners to an Azure network only for larger runners, which only the paid GitHub Team and GitHub Enterprise Cloud plans offer.

This ADR first made private networking the only path, which made a paid GitHub plan a prerequisite of the build and stopped the build without one. On 2026-10-30 the product owner decided that the build must not require a paid GitHub plan: standard GitHub-hosted runners reaching the vault through a transient runner rule are the default, the product owner's runner-address rule of ADR 0119 extends to the test vault for that purpose, and larger runners with private networking stay an optional path for organizations on GitHub Team or Enterprise Cloud. On 2026-11-06 the product owner decided that CI jobs don't receive the shared operator allowlist, so a runner rule a dead runner left on the vault is swept only through runbook R26.

Vendor facts (checked 2026-10-15 unless stated):

- Larger runners "are only available for organizations and enterprises using the GitHub Team or GitHub Enterprise Cloud plans"; "when larger runners are in use, they will always be billed at the per-minute rate", for public and private repositories alike; a 2-core Linux x64 larger runner costs $0.006 per minute.
- "Use of the standard GitHub-hosted runners is free and unlimited on public repositories"; for private repositories they "draw from your GitHub account's included compute usage, and are then charged at the per-minute rates", on every plan (checked 2026-10-30).
- Azure private networking for GitHub-hosted runners is "only available for larger runners (2-64 vCPU Ubuntu and Windows)". The subnet is delegated to `GitHub.Network/networkSettings`; the resource `GitHub.Network/networkSettings@2024-04-02` (GA; properties `businessId`, the organization's `databaseId`, and `subnetId`) returns the `GitHubId` tag that GitHub's network configuration takes; runners are created in the subnet's region and "use whatever outbound control your network is using". Supported regions on GitHub.com include EastUs2.
- GitHub REST creates the network configuration (`POST /orgs/{org}/settings/network-configurations`), the runner group (`POST /orgs/{org}/actions/runner-groups`, with `visibility`, `selected_repository_ids`, `allows_public_repositories`, `network_configuration_id`) and the hosted runner (`POST /orgs/{org}/actions/hosted-runners`, with `image`, `size`, `runner_group_id`, `maximum_runners`, `enable_static_ip`); "By default, only private repositories can access runners in a runner group, but you can override this".
- `jobs.<job_id>.runs-on` takes an expression, and the `vars` context is available there (GitHub's own example: `runs-on: ${{ vars.RUNNER }}`); a runner group is named as `runs-on: {group: <name>}` (checked 2026-10-30).
- A vault's `publicNetworkAccess: 'Disabled'` blocks "all traffic except private endpoint traffic and that that originates from trusted services", and "will override the set firewall rules, meaning that even if the firewall rules are present we will not honor the rules" (Key Vault template reference, API 2025-05-01, checked 2026-10-30). A runner rule therefore works only while public access is enabled with `defaultAction: 'Deny'`.
- `az keyvault network-rule add` and `az keyvault network-rule remove` take `--name` and `--ip-address` ("IPv4 address or CIDR range"); a vault's firewall holds at most 1,000 IP rules (checked 2026-10-30). The CLI reads the vault's `networkAcls`, changes the list and writes it back, so two jobs writing at the same moment can undo each other's change.
- No action of its own changes a vault's network rules: `Microsoft.KeyVault/vaults/write` "creates a new key vault or updates the properties of an existing key vault. Certain properties may require more permissions" (checked 2026-10-30). Microsoft's pages disagree on whether that action alone may change `enableRbacAuthorization` (the Key Vault access-control page says it may, the RBAC guide says unrestricted `Microsoft.Authorization/roleAssignments/write` is also needed); the deny assignment `docchat-deny-keyvault-access-policies` at `rg-docchat-shared` refuses a vault without the RBAC permission model whatever the caller holds (83-infrastructure.md section 12.1).
- A Key Vault read from an address the firewall doesn't admit answers `403` with the error code `ForbiddenByFirewall`.
- A concurrency group allows one running job (ADR 0119), and the jobs that hold test tokens run for up to 350 minutes and in parallel (84-testing.md sections 6.3 and 7.4).
- A Container Apps job used as a self-hosted runner registers on every start with a fine-grained personal access token holding repository Administration read and write; "Self-hosted runners are only recommended for *private* repositories".
- Subnets of new virtual networks default to `defaultOutboundAccess: false` from API versions released after 31 March 2026, while delegated subnets keep the outbound path the service manages.
- Key Vault Secrets User (`4633458b-17de-408a-b874-0445c86b69e6`) grants `getSecret` and `readMetadata` in the RBAC permission model (checked 2026-10-14).

## Decision

1. **One shared test vault.** `kv-docchat-tst-<sharedToken>` in `rg-docchat-shared`, declared in `infra/shared.bicep` and deployed by the bootstrap only, through AVM `avm/res/key-vault/vault` 0.14.2: `sku: 'standard'`, `enableRbacAuthorization: true`, soft delete 90 days, `enablePurgeProtection: true`, diagnostic setting `AuditEvent` and `AllMetrics` to `log-docchat-security`. It holds only the secrets `test-user-<alias>` (aliases `admin`, `member`, `outsider`, `norole`, `load-01` to `load-20`, `load-admin`; value the password; `contentType: 'text/plain'`; `exp` = write time + 30 days; tag `docchat-test-user=<alias>`, never a user principal name) and serves `dev` and every `load` run. Reader: `id-docchat-citest` only, through Key Vault Secrets User at the vault. Writers: `sg-docchat-operators` through DocChat Test Secret Writer (`setSecret` and `readMetadata`, never a value read). No app identity can read it, and every environment's own Key Vault, `prod`'s included, stays empty.
2. **Two CI paths, one switch.** The bootstrap configuration key `ciPrivateNetworking` (boolean, default `false`) chooses the path. It reaches `infra/shared.bicep` as the parameter `ciPrivateNetworking` (from `DOCCHAT_CI_PRIVATE_NETWORKING`, set by the bootstrap's `shared` step) and the workflows as the repository variable `DOCCHAT_CI_PRIVATE_NETWORKING` (`true` or `false`, written by the bootstrap's `github` step). Changing it is a reviewed pull request to the configuration followed by the bootstrap steps `shared`, `assignments`, `github` and `ci-runner`.
   - **Default (`false`): standard runners and a transient runner rule.** Test jobs run on standard GitHub-hosted `ubuntu-24.04` runners, on every GitHub plan, and reach the vault on its public endpoint through the transient runner rule of item 5. No CI network, private endpoint, runner group or GitHub network object exists.
   - **Optional (`true`): larger runners with private networking.** For an organization on GitHub Team or Enterprise Cloud that wants the vault closed to every public client: the CI network of item 4, larger runners in the runner group `docchat-ci-private`, and no runner rule on the vault.
3. **The vault's network rule.** With the shared allowlist `sharedOperatorIpAllowlist` (from `DOCCHAT_SHARED_OPERATOR_IP_ALLOWLIST`) holding an address: `publicNetworkAccess: 'Enabled'` with `networkAcls {defaultAction: 'Deny', bypass: 'None', ipRules: <the list>}`, in both paths. With it empty: by default `publicNetworkAccess: 'Enabled'`, `defaultAction: 'Deny'`, `bypass: 'None'` and no rule, so only a live runner rule of item 5 admits anyone, as for the shared registry (ADR 0119); under private networking `publicNetworkAccess: 'Disabled'` (and `defaultAction: 'Deny'` with no rule), reachable only through its private endpoint. Every redeploy of `infra/shared.bicep` writes `ipRules` from the shared allowlist, so it removes any live runner rule.
4. **The CI network (private networking only)**, declared by `infra/shared.bicep` only when `ciPrivateNetworking` is `true`, in region `ciNetworkLocation` (default `eastus2`, which must appear in `githubPrivateNetworkingRegions` of `infra/config/regions.json`): `vnet-docchat-ci` 10.60.0.0/24, overlapping no environment network and never peered; `snet-ci-runners` 10.60.0.0/26 (59 usable addresses: at most 10 runners plus GitHub's recommended 30% buffer), delegated to `GitHub.Network/networkSettings`, with `defaultOutboundAccess: true` set explicitly so the value can't move with an API version's default; `snet-ci-private-endpoints` 10.60.0.64/27, no delegation, `privateEndpointNetworkPolicies: 'Enabled'`, `defaultOutboundAccess: false`; 10.60.0.96 to 10.60.0.255 reserved. Network security groups:

   | Group (subnet) | Rules |
   |---|---|
   | `nsg-docchat-ci-runners` (`snet-ci-runners`) | outbound 100 `allow-vault-endpoint`: TCP 443 to `snet-ci-private-endpoints`; outbound 4000 `deny-vnet-outbound`; inbound 4000 `deny-vnet-inbound`; the platform's internet-outbound rule stays, so runners reach GitHub, Microsoft Entra ID, Azure Resource Manager, the environments' API host names and package indexes |
   | `nsg-docchat-ci-pe` (`snet-ci-private-endpoints`) | inbound 100 `allow-runners-https`: TCP 443 from `snet-ci-runners`; outbound 4000 `deny-vnet-outbound` (the endpoint originates nothing, so it changes no path); inbound 4000 `deny-vnet-inbound` |

   The vault's one private endpoint `pe-kv-docchat-tst-<sharedToken>-vault` (group `vault`) sits in `snet-ci-private-endpoints`, with a DNS zone group to the zone `privatelink.vaultcore.azure.net` in `rg-docchat-shared`, linked to `vnet-docchat-ci` only (`link-vnet-docchat-ci`). No environment network reaches the vault.

   The bootstrap's `ci-runner` step creates the runner group as an owner of the GitHub organization, only when `ciPrivateNetworking` is `true` (by default it reports `skipped` and changes nothing); each object is looked up by name first and created only when absent, and no pipeline identity can change any of them:
   - `ghns-docchat-ci`: `GitHub.Network/networkSettings@2024-04-02` with `properties {businessId: <the organization's databaseId>, subnetId: <snet-ci-runners ID>}`, deployed from `infra/bootstrap/ci-network-settings.bicep` only while it doesn't exist, so no redeploy overwrites the `GitHubId` tag the service sets; the step reads the tag back with `az resource show --ids <resource ID> --api-version 2024-04-02 --query tags.GitHubId -o tsv`. The `databaseId` comes from `gh api graphql -f query='query($login: String!) { organization(login: $login) { databaseId } }' -F login=<organization>`.
   - The hosted compute network configuration `docchat-ci` (`compute_service: 'actions'`, `network_settings_ids: [<GitHubId>]`).
   - The runner group `docchat-ci-private` (`visibility: 'selected'`, `selected_repository_ids: [<repository ID>]`, `allows_public_repositories` equal to whether the repository is public, `restricted_to_workflows: false`, `network_configuration_id` = `docchat-ci`'s ID).
   - The GitHub-hosted larger runner `docchat-ci-private` (`image {id: 'ubuntu-24.04', source: 'github'}`, `size: '2-core'`, `runner_group_id` = the group's ID, `maximum_runners: 10`, `enable_static_ip: false`).
   The step stops with `ci_region_unsupported` before creating anything when `ciNetworkLocation` isn't a listed region; with `ci_private_networking_unavailable` before creating anything when `GET /orgs/{org}/actions/hosted-runners/machine-sizes` lacks `2-core` or `GET …/hosted-runners/images/github-owned` lacks `ubuntu-24.04`, and when a create call answers `403` (the organization's plan offers no larger runners: the operator sets `ciPrivateNetworking` to `false` and re-runs the steps of item 2, and the build goes on on the default path); and with `ci_runner_mismatch` when a read-back value differs. The `providers` step registers `GitHub.Network` when `ciPrivateNetworking` is `true`.
5. **The transient runner rule on the vault (default path).** The vault joins the closed list of ADR 0119 item 1 as a third target:
   - **Jobs and identity.** Only jobs of the GitHub environments `dev-tests` and `load-tests`, as `id-docchat-citest`, through `scripts/deploy/firewall.py --target vault --env <dev|load>` (the environment the job tests; the vault is the one of `DOCCHAT_TEST_VAULT_URI` in both). The right is the custom role DocChat Test Vault Firewall Editor (`28936cba-1b39-4715-987a-4fc5adcdc5ab`; Actions `Microsoft.KeyVault/vaults/read` and `Microsoft.KeyVault/vaults/write`), assigned to `id-docchat-citest` at the test vault and nowhere else, by the bootstrap's `assignments` step only while `ciPrivateNetworking` is `false`. No other identity, the deploy identities included, holds a network right on the vault.
   - **Rule.** One IP rule `<runner address>/32`, the address resolved and checked as for every target (two echo services that must agree; a public IPv4 address only; `runner_ip_unresolved` and `runner_ip_mismatch`; ADR 0119 item 3). Addresses are compared without a trailing `/32`.
   - **The read window.** The rule exists only while the job reads the vault, not for the whole job: the passwords are read once, at the start, and tokens are then renewed from the in-memory passwords (84-testing.md section 6.4). The process that reads the vault (the token step's `docchat_testing.tokens.load_passwords`, used by the `pytest` session fixture, `docchat-load tokens` and the S4 driver) runs `firewall.py open --target vault` as a child process before its first vault read and `firewall.py close --target vault` in a `finally` right after its last; the nightly `test-credential-expiry` job runs `open` as the step before its `testusers check` step and `close` as the step after it. Every job that opens the rule also ends with `firewall.py close --target vault` under `if: always()` (the always-run cleanup step), which removes the rule when the reading process was killed before its own `close`. `open` keeps its state in `$RUNNER_TEMP/docchat-firewall-vault.json` (`{address, openedAt}`), so the cleanup step knows what to remove.
   - **No job-level concurrency group.** Test jobs run for hours and in parallel (`pytest` and `resume-start` start together; a load run's jobs overlap `dev`'s post-deploy and nightly tests), so the windows of several jobs can be live at once, and the vault takes no sweep at the start of a job. Instead every vault write is verified: `open` reads `ipRules` back after its write and writes again while its address is missing, at most 5 attempts with a random wait of 2 to 5 s; it then probes every 15 s for at most 300 s with `az keyvault secret list --vault-name <vault> --maxresults 1` as the job's identity (`403` with `ForbiddenByFirewall` means not yet; a probe whose read-back lacks the address writes it again), and a rule that never works is removed and `open` exits 3 with `rule_not_effective`. `close` removes only its own address and reads back until it is gone, at most 5 attempts, else exits 4 with `rule_close_failed`. A vault read answered `403 ForbiddenByFirewall` after `open` succeeded (another job's write undid the rule) runs `open` once more and repeats the read once.
   - **Leftovers.** A window lasts well under 30 minutes: each `open` gives up after its 5 writes and 300 s of probing, `load_passwords` bounds its reads at 120 s and repeats `open` at most once, and `close` gives up after 5 attempts. An address still listed long after its job therefore belongs to a runner that died inside its window, before its always-run cleanup step. No job removes it: no job holds the shared allowlist (83-infrastructure.md section 10.4), so a job can't tell it from an operator's address, and each job's `open` and `close` touch only its own address. `firewall.py sweep --target vault` removes every address outside the shared allowlist and is run only by the bootstrap operator in runbook R26, with the list exported in their shell, never by a job; with the list unset it removes nothing. The next run of the bootstrap's `shared` step also removes such an address (item 3).
   - **Audit.** Each window is two Administrative Activity Log events `Microsoft.KeyVault/vaults/write` under `id-docchat-citest`, copied by the subscription setting `activity-to-security` to `log-docchat-security` and kept 365 days where no pipeline identity can write (ADR 0115); the vault's `AuditEvent` log records every secret read with the caller's address.
6. **Who reads it, and from where.** Only jobs of the GitHub environments `dev-tests` and `load-tests`, whose subjects only `id-docchat-citest` trusts (ADR 0120), each with `runs-on: ${{ vars.DOCCHAT_CI_PRIVATE_NETWORKING == 'true' && fromJSON('{"group":"docchat-ci-private"}') || 'ubuntu-24.04' }}` and `permissions {contents: read, id-token: write}`. By default each such job gets a new standard GitHub-hosted Ubuntu 24.04 VM and reads the vault on its public host name inside its read window; under private networking it gets a new larger runner whose network interface GitHub attaches to `snet-ci-runners`, so `kv-docchat-tst-<sharedToken>.vault.azure.net` resolves to the private endpoint, it opens no rule, and an eleventh concurrent job waits in GitHub's queue. The token step (ADR 0019) awaits the job's GitHub OIDC assertion, builds `ClientAssertionCredential(tenant_id, client_id=DOCCHAT_CI_TEST_CLIENT_ID, func=lambda: assertion)`, reads the secrets with the async `SecretClient` into memory and closes both; a later read in the same job builds a new credential from a fresh assertion (and, by default, opens a new window). These jobs join no `docchat-env-*` concurrency group. A vault that can't be reached, an `open` that fails, or a read answered `403 ForbiddenByFirewall` twice fails the token step with `test_vault_unreachable` before any test runs; a job never falls back from one path to the other; a secret past its `exp` fails with `test_credentials_expired`.
7. **Operators write from the allowlist.** `docchat-ops --env dev testusers rotate` (ADR 0019, runbook R08) runs every 30 days from a machine whose address is in the shared allowlist; with an empty list the operator first adds their address through the bootstrap's `shared` step (R24 step 4) and removes it the same way afterwards, at a time when no test job is reading the vault (item 3).
8. **No paid GitHub plan is required.** The default path works on every GitHub plan, GitHub Free included. Private networking needs GitHub Team or Enterprise Cloud and is the owner's option, never a prerequisite; on another plan its refusal (`ci_private_networking_unavailable`) is fixed by returning to the default. No stop condition exists for the GitHub plan: SC-1 is withdrawn (ADR 0141).

## Alternatives considered

- **Larger runners with private networking as the only path** (this ADR's decision of 2026-10-21). Replaced as the default: it made GitHub Team or Enterprise Cloud a prerequisite of the build, and an organization on any other plan stopped at stage 0 (SC-1). It stays the optional path of items 2 and 4.
- **A static-address larger runner (`enable_static_ip: true`) with a standing vault rule for that address.** Rejected: a standing rule, and a paid plan.
- **One job-level concurrency group for the vault rule, with a sweep first in every job, as ADR 0119 does for SQL and the registry.** Rejected: token-holding jobs run for up to 350 minutes and in parallel, so one group would hold `dev`'s post-deploy tests, and with them every `prod` release, behind a load scenario for hours. Short windows with verified writes keep the jobs independent.
- **A rule open for the whole job.** Rejected: the passwords are read once at the start, so a rule after the read only widens the vault's exposure, for up to 350 minutes.
- **An ephemeral customer-operated runner** (a Container Apps job registering per start). Rejected: it needs a stored registration credential with repository Administration write, a second secret beside the test passwords and a broad repository-settings right, and Microsoft recommends self-hosted runners only for private repositories.
- **A persistent self-hosted runner in the network.** Rejected: whatever one job leaves on it reaches the next.
- **Passwords as GitHub Actions secrets.** Rejected: the repository holds no Actions secrets (ADR 0120), and any workflow change could read them.
- **A vault per environment or per load run.** Rejected: a `load` run lives for hours, so its passwords would be copied in for every run; one vault and one rotation serve both user sets.
- **Peering the CI network with the environment networks** (private networking). Rejected: the test jobs need only the vault; they reach the API on its public host name, and an unpeered network keeps the runners out of every environment.

## Consequences

- No GitHub plan blocks the build: by default the test jobs run on standard runners, free on a public repository and drawn from the plan's included minutes on a private one.
- By default the vault answers a runner only inside that job's read window, minutes long, and only `id-docchat-citest` holds a data right on it; it answers no other public client while the shared allowlist is empty. A runner rule is part of the operator allowlist in the sense of ADR 0119, and the Activity Log records each window's two writes.
- By default `id-docchat-citest` holds one management-plane right, `Microsoft.KeyVault/vaults/write` on the test vault only. A compromised test dependency could change that vault's network rules or other properties: purge protection can't be turned off once on, the deny assignments refuse a vault without the RBAC permission model or without purge protection (`docchat-deny-keyvault-access-policies`, `docchat-deny-keyvault-purge`), the vault holds only test passwords the same dependency can already read, and the next run of the bootstrap's `shared` step restores every declared setting. It still never reaches a deploy identity.
- A run of the bootstrap's `shared` step during a read window removes that window's rule; the job re-opens once (item 5), and operators run `shared` when no test job is reading.
- Under private networking the vault answers no public client while the shared allowlist is empty, and no network rule ever names a runner.
- Cost: by default nothing beyond standard runner minutes, and no Azure network resource. Under private networking GitHub bills every `dev-tests` and `load-tests` job's minutes at $0.006 per minute (2-core Linux larger runner), public repository included, and nothing while idle; at most 10 runners run at once; Azure adds the vault's private endpoint ($7.30 a month) and its DNS zone ($0.50 a month), and a typical load run adds at most about $5 of runner minutes.
- Operations: R08 (rotation from the shared allowlist), R24 (the shared allowlist), R26 (by default, addresses outside the shared allowlist on the test vault that no job's cleanup removed: `firewall.py sweep --target vault` while no test job runs, and the Activity Log for each write's caller; a caller other than `id-docchat-citest` or the bootstrap goes to R31), R34 (under private networking: a job waiting more than 15 minutes for a runner, or `test_vault_unreachable`: check the runner's status, the endpoint and the zone link, then re-run the bootstrap's `shared` and `ci-runner` steps).
- Tests (84-testing.md): the CI Bicep build of `infra/shared.bicep` gives the vault, by default, `publicNetworkAccess: 'Enabled'`, `defaultAction: 'Deny'`, `bypass: 'None'` and no `ipRules` with an empty shared allowlist, and no CI network or private endpoint; with two addresses, exactly those two `ipRules`; with `ciPrivateNetworking: true` and an empty list `publicNetworkAccess: 'Disabled'`, its private endpoint in `snet-ci-private-endpoints` and the zone linked only to `vnet-docchat-ci`. Unit tests prove `firewall.py`'s vault target (verified writes, repeated writes after a concurrent change, only its own address closed, no other address removed by any job, no sweep when a job starts, and a sweep that removes nothing while the shared allowlist is unset) and the `ci-runner` step's `skipped` by default, its create-when-absent behaviour and its three stop codes under private networking. Workflow checks prove that every job reading `DOCCHAT_CI_TEST_CLIENT_ID` runs in `dev-tests` or `load-tests` with the `runs-on` expression of item 6 and ends with the always-run `firewall.py close --target vault` step, that only those jobs use `--target vault`, and that no other job names `docchat-ci-private`. A deployed `dev` test proves, on the default path, that a `dev-tests` job on `ubuntu-24.04` is refused before `open`, reads one secret inside the window and is refused again after `close`, that the Activity Log holds the window's two `Microsoft.KeyVault/vaults/write` events under `id-docchat-citest` and no vault write by any other pipeline identity, and that no address outside the shared allowlist remains; under private networking, that a `dev-tests` job resolves the vault to an address in `snet-ci-private-endpoints` and reads one secret, that the same read from a plain `ubuntu-24.04` runner is refused, and that the Activity Log holds no `Microsoft.KeyVault/vaults/write` on the vault by any pipeline identity. Stage-0 acceptance A0-9 (90-build-order.md) requires the deployed test of the configured path.
