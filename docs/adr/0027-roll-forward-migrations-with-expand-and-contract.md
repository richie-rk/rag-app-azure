# ADR 0027: Roll-forward migrations with expand and contract

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 01-repository.md, 80-data-model.md, 81-config.md, 83-infrastructure.md, 84-testing.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0025, 0026, 0028, 0029, 0044, 0045, 0046, 0071, 0104, 0108, 0119, 0125, 0127, 0147

## Context

The SQL schema of both apps changes through Alembic migrations kept in `db/migrations/`, one history for every app, run by the pipeline's deploy identity as one step with the SQL user grants, after provisioning and before any app deploys. The app identities read and write data but can't change the schema. Every migration stays compatible with the running app: expand, deploy, then contract in a later release.

Forces:

- **Two releases share one schema.** The migrations step runs while the previous release still serves traffic, and App Service and the Functions host replace instances one at a time, so the previous release and the new one both run against the new schema during every deployment. A rollback redeploys earlier images by digest and runs no migration (ADR 0127), so the previous release must keep working on the newer schema afterwards too.
- **Every environment must say which schema it runs.** A schema change needs one repeatable, reviewed path that every environment follows in the same order, and search indexes need the same for their schemas (ADRs 0044, 0045).
- **The schema carries data rules.** Ops-config rows (ADR 0028), method-catalogue rows (ADR 0046), the audit action catalogue in `CHECK` constraints (ADR 0029) and the database roles and grants (ADR 0025) all change through revisions.
- **The rule spans releases.** Expand and contract is a discipline across several releases, so only a mechanical check in CI can keep a destructive change out of the release that still needs the old shape.

Vendor facts that bound the choice:

- Alembic 1.20.0 (released 2026-09-11) is Production/Stable and requires Python 3.10 or later (checked 2026-10-14).
- `alembic check` (since 1.9.0) runs autogenerate's comparison without writing a revision and exits with an error when new operations would be rendered. Autogenerate detects table and column additions and removals, nullability changes, basic changes in indexes, explicitly named unique constraints and foreign keys, and column types (on by default); it compares named `CHECK` constraint additions and removals and server defaults only when enabled (both off by default); it sees a table or column rename as a drop and an add (checked 2026-10-18).
- GitHub's REST API lists an environment's deployments with `GET /repos/{owner}/{repo}/deployments?environment=<name>&per_page=<n>`, and a deployment's statuses (`error`, `failure`, `inactive`, `in_progress`, `queued`, `pending`, `success`) with `GET /repos/{owner}/{repo}/deployments/{deployment_id}/statuses` (checked 2026-10-18).

## Decision

1. **One linear history in one place.** The workspace member `db` (distribution `docchat-db`, virtual with `[tool.uv] package = false`, depending on `docchat-core`) holds `db/alembic.ini`, `db/migrations/env.py`, `db/migrations/script.py.mako` and the revisions `db/migrations/versions/NNNN_<snake_slug>.py`, each with `revision = "NNNN"` (4 digits, sequential from `0001`) and `down_revision` the previous number. The target metadata is the SQLAlchemy Core metadata in `docchat_core.sql.tables`, which each table's owning section defines. The first revision, `0001_initial_schema` (build stage 0), creates every table in schema `app`, the five database roles and their table grants (ADR 0025). Every later schema change of every app is a revision here; no app creates or alters a table, and no code calls `metadata.create_all` against an Azure database.
2. **Run by the deploy identity before the apps deploy.** The azd `postprovision` hook, under the deploy identity (a standing member of `sg-docchat-<env>-sql-admins`), after every provision: (1) `firewall.py sweep`, then `open --target sql` (the job's transient runner rule, ADR 0119); (2) waits for a TDS login (`Encrypt=strict`, the deploy identity's Entra token for `https://database.windows.net/.default`), retrying errors 40613 and 40615 every 5 s, then backing off to 30 s, for at most 5 minutes; (3) `uv run --frozen --package docchat-db alembic -c db/alembic.ini upgrade head` with `DOCCHAT_SQL_SERVER` and `DOCCHAT_SQL_DATABASE` from the azd environment (`env.py` connects synchronously through `connection_string("migrations")`, so the session carries `APP=docchat-migrations`; ADR 0026); (4) the grants step `scripts/deploy/sql_principals.py --env <env>` (contained users and role memberships, `APP=docchat-grants`; ADR 0125); (5) in `dev` and `prod`, `docchat-ops chat capacity-check` (ADR 0147); (6) in `finally`, `firewall.py close --target sql`. A failure fails `azd provision`, and the workflow stops before any app deploys. An operator's `azd provision` from an allowlisted machine runs the same hook.
3. **No downgrade.** Every revision's `downgrade()` raises `NotImplementedError("roll forward")`. A rollback is `deploy.yaml` dispatched with `rollback: true` and the earlier release's `image_commit`, which runs `images-only`: no provision and no migration (ADR 0127). Runbook R02 (rollback) step 2 refuses to roll back across a contract revision: when `git log --oneline <good commit>..<current commit> -- db/migrations/versions` lists a revision whose docstring starts `Contract:`, the fix goes forward.
4. **Expand, deploy, contract.** Every revision keeps the release serving `prod` working. A revision is an expand revision unless the first line of its docstring is `Contract: completes NNNN`, naming the expand revision whose change it finishes. Only a contract revision may contain a destructive operation: `op.drop_table`, `op.drop_column`, `op.drop_constraint`, `op.drop_index` of an index created before the revision's parent, `op.alter_column` that changes `type_` or sets `nullable=False`, a table or column rename, or an `op.execute` whose SQL contains `DROP`, `TRUNCATE` or a `DELETE` without `WHERE`. A contract revision merges only when its expand revision is in the commit of the latest successful `prod` deployment, and it removes only what the release serving `prod` doesn't read or write: the check proves the first condition, and the pull request's review proves the second.
5. **Checks in CI.** The `migrations` job (15 minutes; checkout with `fetch-depth: 0`; the SQL Server container; workflow permission `deployments: read`) asserts exactly one head, runs `upgrade head` on an empty database, runs `alembic check` (no difference between the `docchat_core.sql` metadata and the migrated schema) and runs `scripts/ci/check_migrations.py`. That script parses each new revision, fails on a destructive operation outside a contract revision, finds the newest `prod` deployment with a `success` status through `GET /repos/{owner}/{repo}/deployments?environment=prod&per_page=10` and its statuses, and fails unless `git cat-file -e <sha>:db/migrations/versions/<NNNN>_<slug>.py` finds the named expand revision in that deployment's commit.
6. **Data that revisions own.** Ops-config keys: the revision that ships a key inserts its row with `value_json` = `default_json` = `{"value": <default>}`; a revision that changes a default updates `default_json`, and `value_json` only where it still equals the old default; a contract revision deletes a retired key (ADR 0028). Method catalogue: one `ingestion_methods` row per shipped key and version (ADR 0046). Audit catalogue: a new action or target type re-creates `CK_audit_events_action` and `CK_audit_events_target_type` with the wider lists in an expand revision (ADR 0029). Each table's owning section grants its roles' rights on its tables in its own revision.
7. **The same rule outside SQL.** Every Cosmos DB document in `conversations` and `memories` carries `schemaVersion: 1`, and a `usage` counter document carries none: its shape never changes in place, and a changed shape takes a new `type` and `id` prefix; stored-document models ignore unknown fields when reading and forbid them when building a write, so the previous release reads what the next one writes, and a change an older reader can't handle takes a new `schemaVersion` and two releases (ADR 0071). A search index schema never changes in place: a new schema version builds a new physical index (ADRs 0044, 0045).

## Alternatives considered

- **Downgrade scripts and rollback by downgrading.** A downgrade that drops what an upgrade added destroys every value written since, it is the least exercised code in the repository, and it would run under pressure during an incident. Rejected: rollback redeploys images onto a schema that expand and contract keep compatible, which loses nothing and needs no SQL access.
- **Expand and contract in one release.** Rejected: the previous release runs against the new schema during the rolling deployment and after a rollback, so a column dropped in the same release breaks it.
- **Branching history with merge revisions.** Alembic supports several heads, but expand and contract depend on order, and a linear four-digit sequence makes the order visible and the one-head check simple; two pull requests that pick the same number collide in CI and one renumbers.
- **Migrating at app start-up (`alembic upgrade` or `metadata.create_all` in the lifespan).** Rejected: the app identities hold no schema right; several instances would race; a failed migration would crash-loop the app rather than stop the pipeline before deployment.
- **A state-based schema tool (a desired-state model that the tool diffs and applies).** Rejected: the diff decides at deployment time what to drop or rebuild, so a destructive change becomes implicit rather than a reviewed contract revision, and Alembic keeps every revision in the same Python toolchain as the metadata it is checked against.
- **Contract allowed once the expand revision is in `dev`, or after a waiting period.** Rejected: `prod` is the environment whose running release matters, and the deployments API answers the exact question.
- **Running migrations from a deployment script inside the network.** Recorded as the alternative for organisations that forbid any public SQL endpoint (ADR 0104); not built.

## Consequences

- Every environment's schema is the head of one history, recorded in Alembic's version table, and every change is reviewed as a revision.
- Removing or reshaping anything takes at least two releases: the expand revision with code that works on both shapes, then, after a release that doesn't use the old shape serves `prod`, the contract revision. Until the first `prod` deployment exists, no contract revision can merge.
- Rollback is an image redeploy that loses no data and needs no SQL access; a release that carries a contract revision can only be followed by a correcting release (runbook R02).
- A migration failure stops `azd provision` before any app deploys, so no release runs against a schema it doesn't expect; the previous release keeps serving on the partly expanded schema, which every expand revision keeps compatible.
- Migration statements run as the deploy identity through the SQL Entra admin group, so the privileged SQL audit records them in `log-docchat-security` (ADR 0108).
- Risks: the destructive-operation check is syntactic, so destructive SQL built at run time, or a `DELETE` with a `WHERE` (the ops-config key retirement of item 6), passes it and rests on review. `alembic check` compares neither `CHECK` constraint bodies nor server defaults and reads renames as drop-and-add pairs; the owning sections' integration tests cover constraint bodies (the audit-catalogue test inserts every catalogue value and one value a character away from each).
- Obligations: the `migrations` CI job; `scripts/ci/check_migrations.py` and its unit test (fails on `op.drop_column` without the contract docstring, fails when the named expand revision is absent from the latest successful `prod` deployment's commit, passes otherwise, against a recorded deployments API response and a temporary git repository); the test fixture that migrates one database per test session to head and re-inserts the ops-config seed rows exactly as the revisions wrote them; runbooks R01 (deploy) and R02 (rollback).
