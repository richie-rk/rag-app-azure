# ADR 0004: Browser calls the API directly

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 10-web-client.md, 11-api.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 90-build-order.md
- **Related ADRs:** 0003, 0012, 0017, 0018, 0083, 0084, 0085, 0086, 0087, 0110

## Context

The web client is static files on Azure Static Web Apps (ADR 0082). Static Web Apps' linked-backend proxy can't carry this API. Microsoft Learn limits each proxied API request to 45 seconds, doesn't support network-isolated backends, requires the `/api` route prefix and offers bring-your-own backends only on the Standard plan; linking an App Service app gives it an identity provider, "Azure Static Web Apps (Linked)", that admits only proxied traffic. This product needs more than that: a chat turn streams for up to `chat.max_turn_seconds` (default 180 s, at most 220 s), a citation download may take 300 s, uploads reach 50 MB while the Static Web Apps quotas list a 30 MB request size, `dev` runs the Free plan, the routes are `/v1/...` and `/healthz`, and the API authenticates with its own Microsoft Entra provider plus in-app token validation (ADR 0017). So the browser calls the API's own origin with a bearer token, across origins.

That has a cost the design accepts openly: the access and refresh tokens live in the browser's session storage, so any script injected into the app could read them, and the defences against cross-site scripting become security-critical. Two other rules shape the decision. On a shared machine, a token cache that outlives the browser would sign the next person in as the last one, so the cache must end with the tab. And a cross-origin API must never accept an ambient credential, or any site a user visits could call it as that user.

Vendor facts: MSAL's `sessionStorage` cache lasts until the tab closes and isn't shared across tabs, and MSAL treats browser storage as safe "as long as your application does not have cross-site scripting"; single-page-app refresh tokens last 24 hours and never slide; App Service platform CORS allows every method and header for an allowed origin and takes precedence over CORS code in the app; its Bicep `siteConfig.cors` has only `allowedOrigins` and `supportCredentials`, so no response header can be exposed and no max-age set, and browsers then cache a preflight for 5 seconds; no Microsoft page states whether platform authentication lets an `OPTIONS` preflight through, so a deployed test settles it.

## Decision

1. **Static files only.** The Static Web Apps resource has no linked backend, no managed functions, no app settings, no Static Web Apps authentication and `stagingEnvironmentPolicy: 'Disabled'`.
2. **The browser calls the API's own origin.** `config.json` `apiBaseUrl` is `https://app-docchat-api-<env>-<token>.azurewebsites.net`, the API's default host. Every call goes through `src/api/http.ts` with `mode: 'cors'`, `credentials: 'omit'`, `cache: 'no-store'` and `redirect: 'error'`, and sends only `Authorization: Bearer <token>`, `Accept`, `Content-Type` (with a body), `traceparent` and, where required, `If-Match`. No cookie is set or sent.
3. **Platform CORS and nothing else.** The API's `siteConfig.cors.allowedOrigins` is `https://<Static Web Apps default host name>` plus `https://<host>` for each `webCustomDomains` entry, as exact origins (no wildcard, no trailing slash, no localhost in any environment), with `supportCredentials: false`. The app runs no CORS code anywhere; locally the Vite dev server proxies `/v1` and `/healthz` to `DOCCHAT_DEV_API_TARGET` (default `http://127.0.0.1:8000`), so local calls are same-origin.
4. **Values travel in bodies.** The client reads only CORS-safelisted response headers (`Content-Type`, `Content-Length`). `rowVersion`, `etag`, `correlationId`, `retryAfterSeconds` and a citation's `fileName` are body fields; `Retry-After` is also sent for non-browser clients. Responses from platform authentication and platform CORS carry no problem body: the client handles a bare `401` with its token retry and a bare `403` as an `http` failure that shows the request's trace ID, never as "not assigned".
5. **Tokens in session storage, renewed without iframes.** MSAL uses `cache.cacheLocation: 'sessionStorage'` and requests only the `access_as_user` scope. Renewal is `acquireTokenSilent` with `CacheLookupPolicy.AccessTokenAndRefreshToken`, then `acquireTokenRedirect` on `InteractionRequiredAuthError` or a second `401` (ADR 0018). Local storage holds only `docchat.theme` and `docchat.nav.open`. Sign-out clears every open tab through the `docchat-auth` broadcast channel.
6. **The defences that make session storage acceptable.** The CSP of ADR 0083 (`script-src 'self'` with no `unsafe-inline` or `unsafe-eval`; `connect-src 'self'`, the API origin and `https://login.microsoftonline.com`; `frame-src blob:`; `form-action 'none'`; `frame-ancestors 'none'`); the rendering of ADR 0084 (raw HTML as text, images as alt text, links only from the turn's `allowedLinks`, DOMPurify, one insertion point); runtime validation of every stream event (ADR 0085); ESLint rules that confine `fetch` and `XMLHttpRequest` to `src/api/http.ts` and `localStorage`, `sessionStorage` and `indexedDB` to `src/platform/storage.ts`; and `scripts/check-dist.mjs`, which fails a build holding an inline script, a `style=` attribute or a source map.
7. **The preflight test and the stop.** Right after the first `dev` deployment of the API-platform stage, and in every deployed `smoke` run, `tests/deployed/test_cors_preflight.py` runs five cases: (1) `OPTIONS /v1/me` from the web origin, no token, requesting `authorization,traceparent` → `200` or `204` with `Access-Control-Allow-Origin` equal to that origin; (2) `OPTIONS /v1/admin/projects/<random UUID>` for `PATCH` with `authorization,content-type,if-match,traceparent` → the same; (3) `GET /v1/me` from that origin without a token → `401`; (4) a preflight from `https://not-allowed.example.invalid` → no `Access-Control-Allow-Origin`; (5) `GET /v1/me` with a token → `200` with the header. When case (1) or (2) fails, the stage stops and the product owner chooses: (a) platform authentication passes anonymous requests through (`requireAuthentication: false`, `unauthenticatedClientAction: 'AllowAnonymous'`, the Entra provider kept, in-app validation the only gate for calls without a token); or (b) one Azure Front Door Standard profile per environment routes `/v1/*` and `/healthz` to the API and everything else to Static Web Apps, the API admits only the `AzureFrontDoor.Backend` service tag with the profile's `X-Azure-FDID`, `apiBaseUrl` becomes the web origin and preflights disappear. The choice is recorded in a new ADR and the test runs again.

## Alternatives considered

- **Static Web Apps' linked backend.** Lost: the 45-second request limit cuts chat streams and downloads, the 30 MB request size cuts uploads, the `/api` prefix and the Standard-only rule conflict with the routes and with `dev`'s Free plan, the API could never be network-isolated behind it, and linking puts a provider that admits only proxied traffic in place of the API's own Entra provider.
- **A session cookie on the API (platform authentication sessions or an app cookie), so no token reaches the browser.** Lost: the cookie belongs to the API's host, a different site from the Static Web Apps host, so browsers that block third-party cookies don't send it; it would need `supportCredentials: true` plus CSRF defences; server-directed sign-in needs a client secret for the hybrid flow, and the design holds no secrets; a same-site cookie needs one origin, which is option (b).
- **MSAL `memoryStorage`.** Lost: every reload and every new tab loses the cache and costs a full-page redirect to Entra ID, and injected script could still call MSAL inside the page, so it doesn't remove the exposure that item 6 addresses.
- **`localStorage`.** Lost: it survives closing the browser and is shared by every tab, so on a shared machine the next person would be signed in as the last one.
- **Azure Front Door as the single origin from the start.** Lost for the first version: a Standard profile per environment and another public resource to harden, while platform CORS costs nothing; it stays option (b).
- **CORS middleware in the app.** Lost: platform CORS takes precedence over app CORS code, which then has no effect.

## Consequences

- No ambient credential exists, so another site can't make a browser call the API as its user; CORS only decides which origins may read responses.
- Script injected into the app would expose the user's access token and the 24-hour refresh token, so item 6's defences are security-critical: a change that weakens the CSP, the renderer or the storage rules needs a new ADR.
- Every cross-origin call may pay a preflight: with no max-age, a call more than 5 seconds after the last preflight to the same URL costs one extra round trip; accepted.
- Obligations: the five CORS cases in every deployed `smoke` run and in the API-platform stage's acceptance; the stream and upload buffering checks through platform authentication (a 49 MB upload completes; a chat stream's `meta` line arrives within 3 s); browser tests that local storage holds only the two preference keys and that clearing session storage sends the page to sign-in; browser tests fail on any CSP violation.
- Risk: platform authentication answers preflights with `401` or buffers streams; the tests above find either one and stop the build for the product owner.
