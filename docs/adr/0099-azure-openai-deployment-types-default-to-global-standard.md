# ADR 0099: Azure OpenAI deployment types default to Global Standard

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Product owner
- **Specified in:** 83-infrastructure.md, 81-config.md, 82-security.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0045, 0066, 0067, 0068, 0095, 0096, 0100, 0101, 0112, 0140, 0147

## Context

Each environment with an Azure OpenAI account (`dev` and `prod`; `load` calls a model stub, ADR 0112) has five deployments: `chat` (answers), `chat-small` (question rewrites, search passages, follow-ups, summaries and memory extraction), `ingest-summary` (ingestion's table summaries) and, per embedding model, `embed-query-<key>` (query vectors) and `embed-ingest-<key>` (chunk vectors). Ingestion has its own deployments so a bulk upload can never starve chat. Deployment names, models and versions are Bicep parameters, never constants in code; ADR 0100 records the models, versions and capacities.

A deployment's type decides where its prompts and completions are processed, which model versions a region offers it and which quota pool its capacity comes from. The product has no data-residency requirement: processing prompts and completions in any Azure region is acceptable. It does need current GA models, a small one included, in a new subscription and with the largest standard quota, and an organisation that has a residency boundary must be able to set one per deployment without a code change.

Vendor facts (Microsoft Learn, checked 2026-10-14):

- Deployment types are SKU names. `GlobalStandard` processes requests in any Azure region; `DataZoneStandard` within the US, EU or APAC data zone, to which Microsoft can add regions without notice; `Standard` within the resource's Azure geography. Data at rest stays in the designated geography with every type. Microsoft advises starting with Global Standard: geography-based types "arrive last, have no guaranteed availability date, and depend on capacity that frees up as older models retire".
- New versions roll out to Global Standard first, then Global Provisioned, then Data Zone, and to Standard and Provisioned last. No gpt-5.4, gpt-5.5, gpt-5.6 or GPT-6 model is offered as Standard (table dated 2026-09-03); gpt-5.1, the newest chat model offered as Standard, launched on 2025-11-13. A GA version is deprecated 12 months after launch, after which a subscription that never deployed it can't create deployments of it. Global Standard offers `gpt-5.6-sol`, `gpt-5.6-terra` and `text-embedding-3-large` 1 in every listed Americas and Europe region, except that `northeurope` lacks the gpt-5.6 models. The APAC data zone offers only gpt-5.4, gpt-5.4-mini, gpt-5.6-sol and gpt-6.1-sol.
- Since 2026-05-07, Global Standard deployments of one model and version share one quota pool per subscription across all regions, and Data Zone Standard deployments one pool per data zone. Tier-1 defaults: the gpt-5.6 models get 1,000,000 tokens per minute (TPM) on Global Standard and 333,000 on Data Zone Standard; `text-embedding-3-large` gets 1,000,000 on both.
- `Microsoft.CognitiveServices/accounts/deployments` (GA API 2026-07-01) takes the type as `sku.name` with `sku.capacity`, the model as `properties.model {format, name, version}`, and `versionUpgradeOption`.

## Decision

1. **A type on every deployment object.** The Bicep user-defined type `openAiDeployment` has the field `type`: `'GlobalStandard'` (default) | `'DataZoneStandard'` | `'Standard'`, written to the deployment's `sku.name`. `openAi.deployments` holds three such objects, `chat`, `chatSmall` and `tableSummary`, each with its own `type`. Each entry of the array `openAi.embeddingModels` carries two type fields: `queryType` for `embed-query-<key>` and `ingestionType` for `embed-ingest-<key>`, each `'GlobalStandard'` (default) | `'DataZoneStandard'` | `'Standard'`. No deployment inherits another's type, and Bicep derives no type.
2. **Defaults.** `infra/env/dev.json` and `infra/env/prod.json` set all five types to `GlobalStandard`: `chat`, `chat-small`, `ingest-summary`, `embed-query-te3-large-v1` and `embed-ingest-te3-large-v1`. `load` declares no Azure OpenAI account (ADR 0112).
3. **Processing location.** With the defaults, the text sent to the deployments (questions, retrieved chunk text, memory facts, conversation summaries, table content and chunk text for embedding) may be processed in any Azure region, while the account and its deployments live in the environment's region. Conversation content is kept only in the product's own Cosmos DB store, because the apps call Chat Completions and Embeddings, never the Responses API (ADR 0068); the type governs where text is processed, not where it is kept. `82-security.md` states: "every Azure OpenAI deployment's type is set in `infra/env/<env>.json`; with `GlobalStandard`, the default, prompts and completions may be processed in any Azure region".
4. **Pinned values stay per deployment.** A type never selects a model or a version: each deployment keeps its pinned `model` and `version`, and embedding deployments keep `versionUpgradeOption: 'NoAutoUpgrade'` under any type (ADR 0100). The apps address deployments by name only (the `DOCCHAT_OPENAI_*_DEPLOYMENT` app settings and the embedding catalogue `DOCCHAT_OPENAI_EMBEDDING_MODELS`), so a type change needs no code or app-setting change.
5. **Checked against the region.** Before every provision, the preflight checks each deployment's pinned version against that deployment's own type in the region (offered, not retired, not deprecated for the subscription, not retiring within 183 days) and its capacity against that type's quota (ADR 0101); the nightly model watch repeats the version checks (ADR 0140).
6. **Changing a type.** A pull request edits one field in `infra/env/<env>.json` (`openAi.deployments.<role>.type`, `queryType` or `ingestionType`); the pull-request job runs the preflight against `dev` and what-if shows the SKU change; `prod` takes it through the approved release. An embedding deployment's type change keeps its model and version, so the physical indexes that name the deployment stay valid (ADR 0045).

## Alternatives considered

- **Data Zone Standard for `chat`, `chat-small` and `ingest-summary`, and Standard (regional) for the embedding deployments.** Rejected: the product needs no residency boundary, and this one would cost quota and availability. Data Zone Standard gives the gpt-5.6 models a third of the Tier-1 quota (333,000 against 1,000,000 TPM), the APAC data zone offers neither `gpt-5.6-terra` nor the embedding model, new versions reach data zones after Global Standard, and a zone can gain regions without notice, so the boundary itself can move.
- **Standard (regional) for every deployment.** Rejected: no model of the gpt-5.4 generation or later is offered as Standard, the small chat models that are offered are deprecated for subscriptions that never deployed them, and new versions reach Standard last with no guaranteed date, so a new environment would fail the preflight or run models months from retirement.
- **One type for all deployments.** Rejected: the preflight can check versions and quota only per deployment and type, and an organisation that needs a boundary for one deployment would have to impose it on all five, including deployments whose model its region doesn't offer under that type.
- **One type per embedding model, shared by its query and ingestion deployments.** Rejected: they are separate quota consumers, and a separate type lets an operator move bulk ingestion to another type's pool without touching the deployment that serves chat queries.
- **Provisioned or batch types** (`GlobalProvisionedManaged`, `DataZoneProvisionedManaged`, `ProvisionedManaged`, `GlobalBatch`, `DataZoneBatch`). Not allowed values: batch deployments don't serve interactive requests, and provisioned deployments are sized in provisioned throughput units, not in the 1,000-tokens-per-minute capacity units that every capacity parameter, the quota check and the per-user limit check (ADR 0147) use.

## Consequences

- Easier: the default models are available under the default type in every listed Americas and Europe region except `northeurope` for gpt-5.6, with the largest Tier-1 quota, and replacement versions reach Global Standard first, which keeps the model upgrade runbook supplied.
- Data handling: prompts and completions may be processed outside the environment's region. An organisation with a residency requirement sets the five type fields to `DataZoneStandard` or `Standard` in its environment files; the preflight then reports per deployment whether the region offers the pinned version and enough quota under that type (`model_sku_not_offered`, `quota_insufficient`), and it may have to pin other models (ADR 0100).
- Quota: `dev` and `prod` share one subscription (ADR 0095), so their Global Standard deployments of one model and version draw on one pool; ADR 0100 sizes the capacities to fit Tier 1, and the preflight sums capacities by model, version and type.
- Obligations: `81-config.md` lists the five type fields with their allowed values and defaults; `83-infrastructure.md` lists each deployment's type and where each type processes data; `82-security.md` carries the processing-location statement; `86-operations.md`'s procedure for changing a model version, deployment type or capacity changes these fields only by pull request, and the model version upgrade runbook keeps `GlobalStandard` unless the product owner chooses another type.
- Tests (`84-testing.md`): the preflight unit test where `queryType` `GlobalStandard` is offered and `ingestionType` `Standard` isn't fails `model_sku_not_offered` for `embed-ingest-<key>` only; a per-environment parameter file with a mistyped `type` value fails `bicep build-params`; the CI preflight passes for the shipped `dev` and `prod` files.
- Risk: Microsoft may change what a type covers or where a model is offered; the nightly model watch fails when a pinned version stops being offered for its deployment's type, and the references below record the deployment-types page with its check date.
