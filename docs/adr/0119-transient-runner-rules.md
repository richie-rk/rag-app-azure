# ADR 0119: Transient runner rules

- **Status:** Accepted
- **Date:** 2026-10-21; amended 2026-10-30 (the test-credential vault as a third target, ADR 0122); amended 2026-11-06 (no job holds the shared allowlist, so leftover registry and test-vault rules are swept only in runbook R26)
- **Decided by:** Product owner and architect
- **Specified in:** 83-infrastructure.md, 82-security.md, 84-testing.md, 86-operations.md
- **Related ADRs:** 0024, 0027, 0097, 0098, 0104, 0115, 0118, 0122, 0124, 0125, 0142

## Context

The product owner requires SQL and Cosmos DB to be reachable only from the environment's virtual network and a named operator IP allowlist, and every other resource that holds or processes the documents follows the same rule (ADR 0098). Two pipeline steps still need a public path, because they run on GitHub-hosted runners outside any network: migrations and SQL grants after every provision (ADR 0027), and image pushes and lookups on the shared registry (ADR 0124). SQL and the registry therefore stay on "selected networks" with no standing rule, so a job can open them for its own runner. The product owner decided that a transient rule of this kind, added and removed by the job's identity inside one job and recorded in the Activity Log, counts as part of the operator allowlist, for SQL and, for `dev` only, the registry. On 2026-10-30 the product owner extended the list to the shared test-credential vault, so that the test jobs reach it from standard GitHub-hosted runners and no paid GitHub plan is required (ADR 0122). That makes a closed list: every other resource keeps the allowlist rule unchanged. On 2026-11-06 the product owner decided that CI jobs don't receive the shared operator allowlist, so leftover runner rules on the registry and the test vault are swept only through runbook R26.

SQL accepts only Microsoft Entra authentication (ADR 0125), the registry accepts only Entra tokens with its admin user and anonymous pull off (ADR 0097), and the test vault accepts only Entra tokens under the RBAC permission model with `id-docchat-citest` its only reader (ADR 0122), so a runner rule widens the network layer for minutes while authentication applies in full.

Vendor facts (checked 2026-10-14 unless stated):

- "There might be up to a five-minute delay for changes to the Azure SQL Database firewall configuration to take effect" (checked 2026-10-15). A firewall rule is the child resource `Microsoft.Sql/servers/firewallRules`, which Contributor's `*` action covers.
- The registry's `networkRuleSet` holds `defaultAction` and `ipRules`; changing it needs `Microsoft.ContainerRegistry/registries/write` ("Creates or updates a container registry"), and no separate network-rule action exists.
- A Key Vault's `networkAcls` likewise changes only through `Microsoft.KeyVault/vaults/write`; with `publicNetworkAccess: 'Disabled'` the vault honours no IP rule, and `az keyvault network-rule add` and `remove` rewrite the whole rule list (checked 2026-10-30; ADR 0122).
- A concurrency group allows one running job; with the default `queue: single` a newly queued run cancels the pending one, while `queue: max` keeps up to 100 pending runs in order and can't be combined with `cancel-in-progress: true`.
- GitHub-hosted runners take their public address from ranges that every GitHub customer shares, and the address can differ on every job.

## Decision

1. **A closed list of runner rules.** Only these jobs add a runner rule, each under its own identity and on one target:

   | Target | Jobs | Identity and right | Rule | Never overlapping because |
   |---|---|---|---|---|
   | The environment's SQL server `sql-docchat-<env>-<token>` | the `deploy` job of `deploy-environment.yaml` for `dev`, `prod` and `load` (its azd `postprovision` hook: migrations, grants and, in `dev` and `prod`, the chat capacity check; in `dev` also its `grants-check` step, the deployed grants test); in `dev` also `deployed-tests.yaml`'s `infra-checks` (the deployed infrastructure suite); in `load` also `load-test.yaml`'s `seed-config`, `stream-reset`, `s4-set1-config`, `s4-set2-config` and `s4-reset` (each runs `docchat-ops --env load config set`) | that environment's deploy identity, Contributor (`Microsoft.Sql/servers/firewallRules/write` and `delete`) | firewall rule `ci-runner-<GITHUB_RUN_ID>-<GITHUB_RUN_ATTEMPT>`, start = end = the runner's address | concurrency group `docchat-env-<env>`; in `load` also the workflow group `docchat-load-test` (one run at a time) and the run's job order |
   | The shared registry `crdocchat<sharedToken>` | `deploy.yaml`'s `publish` and `resolve`, and `nightly.yaml`'s `trivy-rescan` | the `dev` deploy identity, DocChat Registry Firewall Editor (`Microsoft.ContainerRegistry/registries/read` and `write`) | one IP rule `{action: Allow, value: <runner address>}` | concurrency group `docchat-registry` |
| The shared test-credential vault `kv-docchat-tst-<sharedToken>`, only while `ciPrivateNetworking` is `false` (the default, ADR 0122) | every job of the GitHub environments `dev-tests` and `load-tests` that reads the vault: `deployed-tests.yaml`'s `pytest` and `resume-start`, `load-test.yaml`'s `seed`, scenario and S4 jobs, and `nightly.yaml`'s `test-credential-expiry` | `id-docchat-citest`, DocChat Test Vault Firewall Editor (`Microsoft.KeyVault/vaults/read` and `write`) at the vault only | one IP rule `<runner address>/32`, only for the job's read window | overlap is expected and harmless: each window holds only its own address, every write is read back and repeated when a concurrent write undid it, and no job sweeps another's live rule (item 3) |

2. **No other resource takes a runner rule.** Cosmos DB, both storage accounts, AI Search, Azure OpenAI, Content Safety, Document Intelligence and every environment Key Vault answer only their private endpoints and the operator allowlist, and nothing when the allowlist is empty (ADR 0098). Under the private-networking option of ADR 0122 (`ciPrivateNetworking: true`) the test vault takes no runner rule either: jobs that hold test tokens or read it run inside the CI network and open no rule. `prod` and `load` jobs never contact the registry, because they deploy verified digests that the apps pull through their private endpoints (ADR 0118). `firewall.py` accepts only `--target sql`, `--target registry` and `--target vault`; any other target exits 2 with a usage error.
3. **Mechanics.** `scripts/deploy/firewall.py` (Python standard library and `az`), subcommands `sweep`, `open` and `close`, each `--target sql|registry|vault --env <env>`:
   - `sweep --target sql` runs first in every job that uses SQL and removes every rule named `ci-runner-*`; the concurrency groups of item 1 guarantee that no other job's live rule exists at that moment, so the sweep clears only rules a crashed runner left behind. No job sweeps the registry or the vault: their rules are bare addresses, and no job holds the shared allowlist (`DOCCHAT_SHARED_OPERATOR_IP_ALLOWLIST` lives only in the bootstrap operator's shell), so a job can't tell a crashed runner's address from an operator's. `sweep --target registry` and `sweep --target vault` remove every address outside that list and belong to runbook R26 alone; with the variable unset they remove nothing, print a warning naming R26 and exit 0, because an unset list read as empty would remove every operator's standing address.
   - `open` reads the runner's public address from `https://api.ipify.org?format=text` and cross-checks it with `https://ifconfig.me/ip` (HTTPS, 5-second timeouts). A failed call, two different answers or an address that isn't a public IPv4 address (private, CGNAT, loopback or link-local) exits 2 with `runner_ip_unresolved` or `runner_ip_mismatch` and adds nothing. It then adds the rule (`az sql server firewall-rule create`, `az acr network-rule add`, `az keyvault network-rule add --name <vault> --ip-address <address>/32`) and probes every 15 seconds for at most 300 seconds until the rule works: for SQL a TDS login with `Encrypt=strict` (error 40615 means not yet), for the registry an anonymous `GET https://<registry>.azurecr.io/v2/` (`401` means reachable, `403` not yet), for the vault `az keyvault secret list --vault-name <vault> --maxresults 1` as the job's identity (`403` with `ForbiddenByFirewall` means not yet). For the vault, `open` reads `ipRules` back after its write and writes again while its address is missing, at most 5 attempts 2 to 5 seconds apart, and a probe whose read-back lacks the address writes it again; it records `{address, openedAt}` in `$RUNNER_TEMP/docchat-firewall-vault.json`. A rule that never works is removed and `open` exits 3 with `rule_not_effective`.
   - `close` removes exactly the rule `open` added, in a step with `if: always()` (in the `postprovision` hook and in each test of the deployed infrastructure suite that opens a rule, a `finally` block); a failure exits 4 with `rule_close_failed` and fails the job; on SQL the next job's `sweep` removes the rule, on the registry and the vault runbook R26 does. The `deploy` job also runs `firewall.py sweep --target sql` with `if: always()` after `azd provision`.
   - For the vault the rule covers only the job's read window, not the job (ADR 0122 item 5): the reading process runs `open` before its first vault read and `close` in a `finally` right after its last, and the job's last step runs `close --target vault` with `if: always()` again. `close` removes only its own address and reads back until it is gone, at most 5 attempts; it never removes another address. An address a runner left when it died inside its window, before its always-run `close`, stays until R26 or the next run of the bootstrap's `shared` step, which rewrites the vault's rules.
   - Outside GitHub Actions (`GITHUB_ACTIONS` unset) `open` adds nothing: it resolves the caller's address and exits 2 with `not_in_allowlist` unless the address is already in the allowlist, because operators work from allowlisted machines.
4. **Lifetime.** A rule exists from `open` to `close` inside one job and never longer than that job's `timeout-minutes` (`deploy` 90, `infra-checks` 60, `publish` and `resolve` 30, `seed-config` 20, `stream-reset` and the S4 configuration jobs 15); a vault rule exists only for its read window, minutes long, and at most until the job's always-run `close`. No rule is kept between jobs, and none is standing.
5. **Audit.** Each rule's create and delete is an Administrative Activity Log event under the job's identity (`Microsoft.Sql/servers/firewallRules/write` and `delete`, `Microsoft.ContainerRegistry/registries/write`, `Microsoft.KeyVault/vaults/write`), copied by the subscription setting `activity-to-security` to `log-docchat-security` and kept 365 days where no pipeline identity can write (ADR 0115). Every registry write also raises `docchat-alert-registry-writes` (severity 2) to the security action group, one notification per 30-minute window.
6. **Repair.** Runbook R26 (the bootstrap operator, from an allowlisted machine, with `DOCCHAT_SHARED_OPERATOR_IP_ALLOWLIST` exported), the only sweep of the registry and the vault: list stray `ci-runner-*` SQL rules and registry and test-vault addresses outside the shared allowlist, run `firewall.py sweep --target <sql|registry|vault> --env <env>` (while no job holding a rule on that target runs), and read the Activity Log for each rule's caller; a caller other than a pipeline identity goes to R31.

## Alternatives considered

- **Run migrations, grants and image pushes inside a network.** Not adopted: the product owner chose the transient runner rule. Operators reach SQL from the allowlist anyway, and an in-network runner per environment adds a subnet, GitHub network objects and billed runner minutes to every deploy; ADR 0104 records this form for organisations that forbid any public SQL endpoint.
- **Standing rules for GitHub's published runner ranges.** Rejected: the ranges are shared by every GitHub customer, so the rules would admit all of them permanently.
- **Runner rules on further resources** (Cosmos DB or storage for seeding). Rejected: the product owner's rule covers SQL, the `dev` registry and the test vault only, and seeding goes through the API.
- **Reading the test vault only from inside a network** (ADR 0122's decision of 2026-10-21). Kept as an option, not the default: it needs larger runners, which only paid GitHub plans offer.
- **One echo service for the runner address.** Rejected: a wrong answer would open a rule to some other address; two independent answers must agree before any rule exists.
- **Removing rules only by a scheduled cleanup.** Rejected: a rule would outlive its job by hours; `close` with `if: always()` bounds it to one job, and on SQL the next job's `sweep` removes a crashed runner's rule.
- **The shared allowlist in every job** (as a GitHub variable), so registry jobs could sweep and the vault's always-run `close` could remove another runner's leftover. Not adopted (product owner, 2026-11-06): the shared allowlist stays in the bootstrap operator's shell only. A leftover needs a runner that died before its always-run `close`, admits one former runner address that still needs an Entra token, and R26 or the next `shared` step removes it.
- **Registry rules for `prod` jobs.** Rejected: only `dev` edits the registry firewall (ADR 0118); `prod` deploys digests that `dev`'s `publish` or `resolve` verified, and its apps pull privately.

## Consequences

- Outside the jobs of item 1, SQL, the registry and the test vault answer only their private endpoints (the vault has one only under private networking) and the allowlist, and inside one of them one runner address for minutes. Every connection still needs an Entra token for a principal with a role.
- Two third-party echo services sit in the deploy path. A wrong answer can only open a rule to an address that still needs Entra credentials, and disagreement fails the job before any rule exists.
- A crashed runner's SQL rule lives until the next job on that server sweeps it or R26 runs; an address a crashed runner left on the registry or the vault lives until R26 runs or the bootstrap's `shared` step rewrites that resource's rules. Such an address admits one former runner address for which every request still needs an Entra token.
- Every `dev` publish, resolve and nightly re-scan raises a severity 2 registry-write notification; R20 maps it as expected when such a job ran at that time, and one with no matching run goes to R31.
- Any new job that needs SQL or the registry joins the list of item 1: it uses `firewall.py` with `open` and an `if: always()` `close` (and, for SQL, `sweep` first), under its own environment's identity and concurrency group; a new job that reads the test vault runs in `dev-tests` or `load-tests` and ends with the always-run `close --target vault`. Workflow checks in CI fail on any `firewall.py` target other than `sql`, `registry` or `vault`, and on `--target vault` outside `dev-tests` and `load-tests`.
- Tests (84-testing.md): unit tests prove that `firewall.py` accepts only the three targets, that `sweep` removes only `ci-runner-*` SQL rules and registry or vault addresses outside the shared allowlist, and no registry or vault address while that list is unset, that `close` removes only the rule `open` added, that `open` refuses private, CGNAT, loopback and link-local addresses and disagreeing echo answers, probes every 15 seconds and gives up after 300, and, for the vault, that a write undone by a concurrent change is repeated and that `close` never removes another address; deployed `dev` tests prove that SQL, the registry and (by default) the test vault refuse the runner until `open` adds its rule, and that after a deploy job the Activity Log holds the rule's create and delete under the deploy identity and no `ci-runner-*` rule remains.
