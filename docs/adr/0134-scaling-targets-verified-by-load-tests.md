# ADR 0134: Scaling targets verified by load tests

- **Status:** Accepted
- **Date:** 2026-10-21
- **Decided by:** Product owner and architect
- **Specified in:** 84-testing.md, 83-infrastructure.md, 81-config.md, 86-operations.md, 90-build-order.md
- **Related ADRs:** 0006, 0007, 0053, 0058, 0112, 0126, 0131, 0135, 0138, 0141, 0151

## Context

The product's scaling targets are numbers: 100 concurrent chat streams on one API instance of the smallest production size with zero errors while a cheap authenticated endpoint keeps p95 latency at or under 200 ms; any instance serves any request, and stopping one instance mid-test fails only the streams it held; autoscale adds an instance when average CPU stays above 70% for 5 minutes, with the cheap endpoint's p95 still at or under 200 ms; a 200-document ingestion run at parallelism 1 finishes with no throttling failures and at parallelism 4 takes at most half as long; every chat-path Cosmos DB query is single-partition and every request-path SQL query is index-backed. A load test with a stubbed model, run in a short-lived environment with production SKUs, proves them.

The API's process model (Gunicorn workers per vCPU, async I/O, no thread held per stream, ADR 0007) is a claim until something measures how many streams an instance carries. A target is only proven when its criterion is code that passes or fails, measured where the number is defined: client-side latency from a generator close to the API, server-side concurrency, CPU and scale events from Azure Monitor and the Activity Log.

Vendor facts: k6's `constant-arrival-rate` and `ramping-arrival-rate` executors implement an open model, whose arrival rate doesn't fall when the system slows, while a closed model's rate drops with longer iterations (coordinated omission); k6 exits with code 99 when a threshold fails. Autoscale evaluates a rule's metric over its time window and waits out the cooldown after each action.

## Decision

1. **Where it runs.** In `load` (ADR 0126): prod SKUs (API on P1v3 with 2 Gunicorn workers per instance) and the prod autoscale rules on a profile of minimum 1, default 1, maximum 6 (out when `CpuPercentage` averages more than 70 over 5 minutes, +1, cooldown 5 minutes; in below 35 over 10 minutes, −1, cooldown 10 minutes); real AI Search, Cosmos DB, SQL, storage and Content Safety; the model stub as both apps' model endpoint (ADR 0112); ingestion with 2 always-ready instances. `load-test.yaml` tests only a release that a successful `deploy.yaml` run on `main` built, scanned and attested (`check_deploy_run.py` fails otherwise with `deploy_run_invalid`).
2. **Ops config and stub values in `load`.** `ratelimit.max_concurrent_streams` 200, `ratelimit.chat_requests_per_minute` 1,200, `quota.tokens_per_day` 1,000,000,000, `quota.tokens_per_month` 100,000,000,000, everything else at its default (follow-ups, summaries and memory on, so after-response work loads the system as in production). Stub: `DOCCHAT_STUB_WORKERS=2`, `DOCCHAT_STUB_RECORD=false`, `DOCCHAT_STUB_FIRST_TOKEN_DELAY_MS=800`, `DOCCHAT_STUB_TOKEN_DELAY_MS=25`, `DOCCHAT_STUB_TOKENS_PER_CHUNK=2`, `DOCCHAT_STUB_ANSWER_TOKENS=400`, `DOCCHAT_STUB_TEXT_TOKENS=120`, `DOCCHAT_STUB_JSON_DELAY_MS=300`, `DOCCHAT_STUB_EMBEDDING_DELAY_MS=40`, `DOCCHAT_STUB_THROTTLE_EVERY_N=20`, `DOCCHAT_STUB_THROTTLE_DEPLOYMENTS=<ingestion embedding deployment>,<table-summary deployment>`, `DOCCHAT_STUB_RETRY_AFTER_MS=500`.
3. **Common rules.** Every request carries a client-generated `traceparent` whose trace ID the generator records; the 20 load users are assigned to virtual users round-robin; a chat virtual user runs sessions of five turns with questions from `tests/fixtures/questions/load.json`; every `cheap` scenario sends `getCurrentUser` round-robin over the 20 load users, so no user sends more than 1 request a second. A stream fails when its status isn't `200`, a line isn't valid JSON or has an unknown `type`, the first event isn't `meta`, `citations` doesn't precede `done`, it holds an `error` event, or it doesn't end with exactly one `done`. Time to first token is measured server-side (`docchat.chat.time_to_first_token`). Every S1 to S3 verdict also applies `C-db` and every verdict `C-cap` (ADR 0151).
4. **S1, event loop.** Autoscale at minimum = maximum = default = 1. `streams`: `ramping-vus` 0 to 100 over 60 s, hold 9 minutes, graceful ramp-down 30 s (each stream about 11 s: 800 ms to the first token, 400 tokens at 25 ms, plus pipeline time). `cheap`: `constant-arrival-rate` 20 requests per second from minute 1 to minute 10, 20 to 60 VUs. Pass: S1-a `http_req_failed{scenario:streams}` rate 0; S1-b `checks{scenario:streams}` rate 1; S1-c `http_req_duration{scenario:cheap}` p(95) ≤ 200 ms; S1-d `http_req_failed{scenario:cheap}` rate 0; S1-e the per-minute maximum of concurrent `POST /v1/chat/turns` requests in `AppRequests` is at least 95 in every minute from minute 2 to minute 9; S1-f zero `5xx` in `AppRequests`; S1-g exactly one `AppRoleInstance` served the run; S1-h each Cosmos DB container's charge per completed turn is at most 400 RU and its peak 1-minute consumption fits its `prod` autoscale maximum.
5. **S2, statelessness.** Autoscale at 3. `streams`: `ramping-vus` 0 to 60 over 60 s, hold 8 minutes; `cheap`: 10 requests per second. At 240 s the workflow sets autoscale to 2; T_r is the first 5-second poll of `az webapp list-instances` showing 2 instances, and the removed instance is the `AppRoleInstance` with `AppRequests` rows in [T_r − 120 s, T_r] and none in [T_r + 60 s, end]. Pass: S2-a every failed request has its `AppRequests` row on the removed instance, or has no row and started before T_r + 5 s; S2-b no request with a row on a surviving instance failed, client-side or server-side; S2-c no request that started at or after T_r + 60 s failed; S2-d at least 30% of sessions with two or more turns had turns served by two or more instances, and every turn of those sessions succeeded.
6. **S3, scale-out.** Autoscale at the `load` profile, so the main phase starts on one instance. A 4-minute calibration at a constant 5 turns per second plus 10 cheap requests per second measures C5 (the mean 1-minute plan `CpuPercentage`) and sets the main rate R = min(R_cpu, R_ps, R_db, 60) turns per second with R_cpu = ceil(5 × 85 ÷ C5); the dependency bounds R_ps and R_db, and the answer length L (`[[stub:tokens=<L>]]`, default 80, allowed 80 to 4,000), are ADR 0151's. Main: `constant-arrival-rate` R turns per second (2R to 6R VUs) plus 20 cheap requests per second for 15 minutes. Pass: S3-a the first successful `Microsoft.Insights/AutoscaleSettings/Scaleup/Action` in the resource group's Activity Log falls between main minutes 5 and 12; S3-b the mean of the five 1-minute plan `CpuPercentage` averages before it is above 70; S3-c the instance count at the end is at least the count at main start + 1; S3-d cheap p(95) ≤ 200 ms over the main phase; S3-e `http_req_failed` rate 0 in both scenarios. A run that fails only S3-a or S3-b with every 1-minute average below 70 is `inconclusive`: cause `calibration_miss` when R = R_cpu (re-run with `rate` = ceil(1.25 × R)), cause `dependency_bound` when R < R_cpu (re-run with four times the answer length, at most 4,000; a `dependency_bound` verdict at 4,000 goes to the product owner with its measurements).
7. **S4, ingestion.** Runs on the GitHub-hosted runner as a Python driver (ADR 0135). Set 1: `ingestion.max_parallel_items` = 1, corpus variant `a` (200 byte-unique copies of the four fixture documents) into index `load-ingest-a`; set 2: parallelism 4, variant `b` into `load-ingest-b`. Each set preflights in batches of 50, reserves and uploads with 8 requests in flight, then submits two `adminSubmitUploads` calls of 100 versions within 5 s; duration = latest `completedAt` − earliest `createdAt` of its two runs. The stub throttles every 20th ingestion model request. Pass: S4-a both runs of each set end `completed` with `counts.succeeded` 100 and `counts.failed` 0; S4-b duration(set 2) ≤ 0.5 × duration(set 1); S4-c `docchat.ingestion.throttled` summed over each set is above 0, so throttling happened and was retried.
8. **S5, data access.** Not a load profile: the chat-path Cosmos DB audit and the request-path SQL plan test pass on the release commit.
9. **Verdicts.** `docchat-load verdict` reads k6's result and runs every server-side criterion through the Log Analytics query API, platform metrics and the Activity Log, writes `load-results/<scenario>/verdict.json` and the criteria table to the job summary, and exits 1 on any failed criterion. The workflow's `verdict` job fails when any selected scenario or the alert probe failed or came out `inconclusive`.
10. **When it runs.** All five at stage-6 acceptance (every verdict `passed`, artifacts attached). S1 to S4 again before any prod deploy that changes the API or ingestion plan SKU, the Gunicorn worker settings, the Durable concurrency settings, the AI Search tier or replica count, or adds a model call to the chat path; the verdicts are attached to that deploy's approval (runbook R11).

## Alternatives considered

- **Load testing in `dev`.** Rejected: B1 and EP1 say nothing about the P1v3 and EP2 sizing that serves users.
- **Load testing against `prod`.** Rejected: real users would share the instances under test, and the model costs and quota would be real.
- **Real Azure OpenAI in `load`.** Rejected: model latency varies by minute and region, so the API's own capacity wouldn't be what is measured, and every run would spend pooled quota; the stub's constant timings isolate the API.
- **Constant-VU (closed-model) load for the cheap endpoint.** Rejected: when the API slows, a closed model sends fewer requests and hides the latency the 200 ms criterion is about.
- **Client-side time to first token.** Rejected: k6 buffers response bodies, and the server-side histogram is the source the dashboard and alerts use.
- **Accepting scale-out from the instance count alone.** Rejected: an instance added for another reason would pass; S3-a and S3-b tie the scale-up event to five minutes of CPU above 70%.
- **Stopping an instance by restarting the site.** Rejected: a restart recycles every instance; lowering autoscale capacity removes exactly one, which the telemetry identifies.
- **Pass criteria judged by a person reading dashboards.** Rejected: the targets are numbers, so each becomes a threshold or a query with a stated pass rule.

## Consequences

- Each run creates a prod-SKU environment that lives at most 24 hours; S4's two sets can each take up to 350 minutes, and S3 can need re-runs before it is conclusive.
- A change to sizing, worker settings, Durable concurrency, the search tier or the chat path's model calls can't reach prod without fresh verdicts, which keeps the targets true after the first release.
- The stub doesn't reproduce model-side variance; the targets measure the platform's capacity, and model-side latency is watched in production by the latency alerts (ADR 0138).
- Obligations: runbook R11 (start, access gate, verdict reading, S3 re-runs, teardown checks); the fixtures `tests/fixtures/questions/load.json` and the load corpus; the `load` ops-config and stub values in `infra/config/app-settings.json` and the `seed-config` job.
- Tests (84-testing.md): the S1 to S4 verdicts; S5 on the release commit; `s3-rate` choosing each bound and the `inconclusive` causes on recorded responses; `C-db`, `C-cap` and S1-h on recorded responses.
