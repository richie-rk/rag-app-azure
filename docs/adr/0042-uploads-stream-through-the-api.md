# ADR 0042: Uploads stream through the API

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 11-api.md, 14-ingestion.md, 10-web-client.md, 80-data-model.md, 81-config.md, 82-security.md, 83-infrastructure.md, 84-testing.md, 85-observability.md
- **Related ADRs:** 0004, 0012, 0031, 0034, 0038, 0039, 0043, 0083, 0093, 0098, 0113, 0116, 0141, 0143

## Context

The product owner requires that only the backend holds credentials, through managed identities, and that the browser makes no direct call to any Azure data or AI service; nothing authenticates with shared keys. A storage key, SAS token or storage URL in the browser would let anyone who loads the page read, overwrite or delete every stored file, so a cited page could be swapped for forged content. Admins upload PDF, DOCX and PPTX files of up to 50 MB each by default; the size limit must hold while the file streams, never after buffering it, and a file of the wrong type, size or content must be refused before it is stored. Ingestion must always read exactly the bytes that were checked, at a path the product generated.

Vendor facts that bound the design:

- Put Block takes a block ID of at most 64 bytes before Base64 encoding, of the same length for every block of a blob (`400` otherwise); a block holds up to 4,000 MiB, a blob up to 50,000 committed and 100,000 uncommitted blocks. Put Block supports no conditional headers. Uncommitted blocks are garbage collected when no Put Block or Put Block List succeeds on the blob within a week after the last successful Put Block, and Put Block List discards every uncommitted block it doesn't name.
- Put Block List supports conditional headers. `If-None-Match: *` performs a write only if the blob doesn't exist; an unmet condition on a write answers `412 Precondition Failed`. In `azure-storage-blob`, `match_condition=MatchConditions.IfMissing` sends `If-None-Match: *`.
- Defender for Storage on-upload scanning starts on BlobCreated, which a Put Block List commit raises; Put Block alone starts no scan. Updating a blob's metadata soon after its upload can make the scan fail.
- With `allowSharedKeyAccess: false` the account refuses service and account SAS. A user delegation SAS needs Get User Delegation Key, whose action `Microsoft.Storage/storageAccounts/blobServices/generateUserDelegationKey/action` must be assigned at storage-account scope or above; a container-scoped data role doesn't grant it.
- App Service disconnects a request idle for 230 seconds (its troubleshooting page gives about 240 seconds on Linux; this design uses 230) and documents no request-body size setting for Linux containers. Microsoft doesn't document whether platform authentication buffers large request bodies, so a deployed test settles it.

## Decision

1. **One path for bytes.** The browser sends each file's bytes to `PUT /v1/admin/indexes/{indexId}/uploads/{versionId}/content` (`adminUploadContent`) as `application/octet-stream` with `Content-Length`, and the API writes them to `documents/{indexId}/{documentId}/{versionNumber}/source` with its managed identity. The browser never receives a storage URL, account name, key or SAS, and the web client's CSP `connect-src` admits only the site, the API origin and Microsoft Entra ID (ADR 0083).
2. **The flow around it.** `adminPreflightUploads` (read-only statuses per file, ADR 0043), `adminReserveUpload` (a version in state `uploading` with the reserved size, SHA-256 and media type, recording the project the upload came through, which must be an active project mapped to the index: `422 project_not_mapped` otherwise), `adminUploadContent`, then `adminSubmitUploads`. The browser computes each SHA-256 with `crypto.subtle.digest`, one file at a time, and uploads one file at a time with `XMLHttpRequest` for progress (ADR 0093). All four operations require `Admin`, pass the per-user burst limit (`429 too_many_requests`), skip the per-user write limit (`write_limited=False`, because their own bounds cap them), answer `503 malware_scanning_not_ready` with `retryAfterSeconds` 3,600 while scanning is enabled and no scanner canary was clean within 48 hours (ADR 0039), and refuse an index in status `failed` or `deleting` with `409 index_not_accepting_uploads`; uploads to a `provisioning` index are accepted and wait for its physical index.
3. **Route options.** `adminUploadContent` declares `route_options(content_types=('application/octet-stream',), body_limit=None, write_limited=False)`: any other content type gets `415 unsupported_media_type`, and the request-size middleware applies no JSON limit because the route enforces `DOCCHAT_UPLOAD_MAX_BYTES` itself. The handler reads `request.stream()` with no body model, so FastAPI never buffers the file.
4. **Checks before the first byte is read**, in order: the version belongs to the path's index (`404 version_not_found`); its state is `uploading` (`409 version_not_uploading`, except that a `pending` version with the reserved hash answers `200` with its summary, so a retried request is harmless); `Content-Length` is present (`411 content_length_required`), at most `DOCCHAT_UPLOAD_MAX_BYTES` (`413 file_too_large`) and equal to the reserved size (`422 size_mismatch`, `errors` `[{path: "header.Content-Length", reason: "out_of_range"}]`); a free stream slot in this worker process (`429 upload_busy`, `retryAfterSeconds` 5).
5. **Staged 4 MiB blocks.** The body is cut into blocks of 4,194,304 bytes (the last one shorter) and staged in order with `await blob.stage_block(block_id, data)`. Each block first updates a running `hashlib.sha256()` and byte count; the first block's signature is checked against the reserved type before anything is staged (ADR 0043, `422 file_signature_mismatch`); a count above `Content-Length` stops the stream (`422 size_mismatch`). Each request draws a nonce of 32 hexadecimal characters (`secrets.token_hex(16)`), and `block_id` is the Base64 of `<nonce>-<block index as 8 zero-padded digits>`: 41 characters before encoding, the same length for every block and under the 64-byte limit, so two concurrent streams for one version (two browser tabs, or a retry served by another instance) stage disjoint blocks and each commits only its own. A stream holds at most one 4 MiB block of file data in memory.
6. **Verify, then commit once.** At the end of the stream a count different from the declared size is `422 size_mismatch` and a SHA-256 different from the reserved one is `422 hash_mismatch`; neither commits anything. Otherwise `await blob.commit_block_list(block_ids, content_settings=ContentSettings(content_type=<the version's media type>), match_condition=MatchConditions.IfMissing)` sends `If-None-Match: *`, so a version's path is written once. `ResourceModifiedError` with `error_code == "ConditionNotMet"` means an earlier attempt or a concurrent stream already committed these exact bytes (only bytes that hashed to the reserved SHA-256 ever reach a commit), so the API reads `get_blob_properties()` and continues with its `last_modified`.
7. **Record the commit.** `UPDATE app.document_versions SET state = 'pending', committed_at = SYSUTCDATETIME(), blob_last_modified = @lastModified WHERE id = @version AND state = 'uploading'`; the scan fields stay as the reservation's insert set them from `DOCCHAT_STORAGE_MALWARE_SCANNING_ENABLED` (ADR 0038), because the API's `UPDATE` grant on `document_versions` excludes them (ADR 0025 rule 4a). Zero rows with the version already `pending` under this hash answers `200`. A violation of `UX_document_versions_document_sha` or `UX_document_versions_index_sha` deletes the blob, marks the version `failed` with `content_unchanged` or `duplicate_content`, and answers `409` with that code. Audit `document.upload_committed` (IDs, version number, size and media type only); answer `200 {version: VersionSummary}`.
8. **Submit and queue.** `adminSubmitUploads` takes 1 to `DOCCHAT_UPLOAD_MAX_FILES_PER_BATCH` version IDs and, in one transaction, creates one `upload` run (priority 0) with one `ingest` item per `pending` version not already queued, targeting the active physical index (or, with none, the building one), stores the request's `traceparent` and `tracestate` on the run and writes `ingestion.run_submitted`. After commit it sends one `IngestionQueueMessage`; a send failure after the client's 3 retries is logged (`ingestion_queue_send_failed`) and the request still succeeds, because the dispatcher's next wake finds the queued items. `202` when at least one item was created, otherwise `200` with `runId: null`.
9. **No blob metadata or tags.** The API writes neither: the media type travels in the commit, and index tags come only from Defender's scanner.
10. **Failures.** Staging and commit errors are retried by the Blob client of `docchat_core.clients` (`ExponentialRetry(initial_backoff=1, increment_base=2, retry_total=3, random_jitter_range=1)`, waits of about 1, 3 and 5 seconds; `connection_timeout=10`, `read_timeout=60` seconds), then answer `503 storage_unavailable` (retryable). A client disconnect (`ClientDisconnect`) stops the stream: nothing is committed, the version stays `uploading` for a retry, the service discards the staged blocks a week later, and the dispatcher's sweep deletes versions still `uploading` after `ingestion.stale_upload_hours` (default 24) with any blob at their path. The stream slot is released in a `finally` block.
11. **Limits.** `DOCCHAT_UPLOAD_MAX_BYTES` 52,428,800 bytes by default (shown as 50 MB), allowed 1,048,576 to 209,715,200; `DOCCHAT_UPLOAD_CONCURRENT_STREAMS_PER_WORKER` 4, allowed 1 to 16; `DOCCHAT_UPLOAD_MAX_FILES_PER_BATCH` 100, allowed 1 to 100 (preflight and submit). Each upload request, transfer and commit included, must finish within App Service's 230-second limit, which a 50 MB file meets at about 1.8 Mbit/s or more.
12. **No identity can hand out storage access.** The API identity holds Storage Blob Data Contributor (`ba92f5b4-2d11-453d-a403-e96b0029c9fe`) on container `documents` and Storage Blob Data Reader (`2a2b9908-6ea1-4ae2-8e65-a410df84e7d1`) on container `renditions`, both container-scoped, so it can't request a user delegation key; the data account sets `allowSharedKeyAccess: false`, so no service or account SAS is accepted, and an Azure Policy Deny keeps key authentication off (ADR 0116). Every Blob client comes from `docchat_core.clients` with the process's `ManagedIdentityCredential` (ADR 0113); no client accepts a key, connection string or SAS.

## Alternatives considered

- **Direct browser upload with a short-lived user delegation SAS per version.** Rejected: the browser would call Azure Storage directly, which the product owner rules out; the data account's blob endpoint would need to accept browsers from any network, with CORS, against its private posture (ADR 0098); the bytes would land before anything checked size, signature or hash; and the API identity would need an account-scope role to obtain delegation keys.
- **Buffer the whole body, then one Put Blob.** Rejected: up to 50 MB per stream in memory, 200 MB per worker at 4 streams, and the size limit must hold while the file streams.
- **Stream straight into one Put Blob.** Rejected: the blob would exist, start a scan and be readable before its hash was known, and a mismatch would need a delete afterwards. Staged blocks become a blob only when verified bytes are committed.
- **Stage into a separate container, verify, then copy server-side to the version path.** Rejected: two writes and a copy per file, and one more container with its own lifecycle and scan rules, for the guarantee one conditional commit already gives.
- **Other block sizes.** 1 MiB blocks need 50 Put Block calls for a 50 MB file; 16 MiB blocks quadruple memory per stream (64 MiB of file data per worker at 4 streams). 4 MiB needs 13 calls for a 50 MB file and 50 at the 209,715,200-byte maximum, far below the 50,000-block limit.
- **An unconditional commit.** Rejected: a stale or concurrent attempt could replace a committed, scanned version's bytes; `If-None-Match: *` makes every version path write-once.

## Consequences

- One place enforces size, type and hash before any byte becomes a blob, every committed blob matches its reserved SHA-256, and ingestion always reads the bytes that were checked. No storage credential, URL or SAS exists for a browser to leak, and the data account stays closed to every network except its private endpoints, the operator allowlist and Defender's scanner (ADR 0098).
- The API carries all upload traffic and the hashing CPU. The 230-second limit ties file size to the admin's bandwidth: the 209,715,200-byte maximum needs about 7.3 Mbit/s, so `DOCCHAT_UPLOAD_MAX_BYTES` is raised only together with that check.
- Platform authentication must not buffer request bodies, which Microsoft doesn't document: the build-order spike on stream and upload buffering (ADR 0141) uploads a 49 MB file through it in `dev` and stops the build for the product owner when the upload doesn't complete, and the deployed test below measures memory and time.
- Abandoned attempts leave staged blocks, billed as storage, until the service discards them a week later; each attempt is bounded by the reserved size.
- Telemetry: span `docchat.ingestion.upload` (IDs, `docchat.ingestion.upload_bytes`, `docchat.outcome`, `docchat.error_code`); metrics `docchat.uploads.completed` (`outcome`, `error_code`) and `docchat.uploads.size` (`content_type`); never file names.
- Tests (84-testing.md): a wrong signature stops before any block is staged, size and hash mismatches commit nothing, and peak memory per stream stays under 10 MiB for a 50 MB file; a 50 MB upload through platform authentication raises API memory by less than 32 MB and finishes within the front-end limit (deployed, `dev`); a retried commit after a committed attempt gets `412 ConditionNotMet` and still ends `pending` with the blob's `last_modified`, and two concurrent streams for one version commit once with the reserved SHA-256 (Azurite); identical bytes uploaded again and two concurrent uploads of one document create no duplicate; the scan gate open, closed and disabled; the Blob and Queue client options; the upload routes' options.
