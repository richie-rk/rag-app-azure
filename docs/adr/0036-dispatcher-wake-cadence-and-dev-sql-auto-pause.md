# ADR 0036: Dispatcher wake cadence and dev SQL auto-pause

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 14-ingestion.md, 81-config.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, 86-operations.md, 90-build-order.md, CONTEXT.md
- **Related ADRs:** 0023, 0026, 0028, 0034, 0035, 0053, 0138, 0144

## Context

Ingestion runs as a singleton Durable Functions dispatcher over a SQL ledger (ADR 0034). The dispatcher wakes on a `run_queued` event, on a finished sub-orchestration or on a durable timer, and every wake reads the `ingestion` ops-config area and runs the sweep in SQL. Because a lost queue message or event only delays work until the next wake, the timer sets the longest delay a run can see.

The `dev` environment runs Azure SQL Database General Purpose serverless with auto-pause on, so that an environment idle most hours bills only storage while paused; `prod` and `load` run provisioned databases with no auto-pause. Microsoft documents that auto-pause starts only when the database has zero sessions and zero user CPU for the whole delay (General Purpose: 15 minutes minimum, 60 by default, `-1` disables it), that open sessions are the most common reason a database doesn't pause, that a resume generally takes under a minute, and that the first connection to a paused database fails with error 40613 and must be retried. A sweep every 60 seconds, or pooled connections left open while idle (SQLAlchemy keeps up to `pool_size` connections, 5 by default, and `pool_recycle` replaces a connection only at its next checkout), would keep the database online around the clock.

The dispatcher also needs a watchdog that restarts it when it stops making progress, and that watchdog must not read SQL either: a query every few minutes keeps a serverless database awake as surely as a frequent sweep. Durable Functions stores an orchestration's custom status (`set_custom_status`) with the instance in task-hub storage, and the Python client's `get_status(instance_id, show_history=False, show_input=False)` returns it with `runtime_status` and `last_updated_time`. A Python durable timer can last up to 6 days.

## Decision

1. **Wake cadence.** The dispatcher's timer is `ingestion.active_wake_seconds` (`ops_config`, integer, default 60, range 15 to 300) when the wake's sweep reports outstanding work (`hasOutstandingWork`: an item `queued` or `running`, a version awaiting a scan, or a physical index `building` or `retiring`) or a sub-orchestration is running, and `ingestion.idle_wake_minutes` (integer, default 60, range 5 to 60) otherwise. A wake without a valid settings snapshot, or whose sweep failed, waits 60 seconds. A `run_queued` event or a finished sub-orchestration wakes the dispatcher at once. A run whose queue message was lost, and every run an operator creates (operators hold no queue-send right), is claimed at the next wake: within 60 seconds while work is outstanding, within 60 minutes when idle.
2. **Custom status.** Every wake ends with `context.set_custom_status({generation, lastSweepAt, outstanding, queued: {interactive, bulk}, running, oldestQueuedAgeSeconds, configValid})`, built only from recorded activity outputs so that a replay produces the same value: `lastSweepAt` is the sweep's `sweptAt` (the heartbeat's `SYSUTCDATETIME()`); `outstanding` is the sweep's `hasOutstandingWork` or any running sub-orchestration; `queued` is the queued count per priority less the items this wake claimed; `running` is the sweep's running count plus the items claimed; `oldestQueuedAgeSeconds` is null when nothing is queued; `configValid` says whether the wake had a valid `ingestion` snapshot (ADR 0028). Without a successful sweep in the wake, `queued` and `oldestQueuedAgeSeconds` are null and `outstanding` is true.
3. **Keep-alive and watchdog, without SQL.** `ingestion_keepalive` (`@app.timer_trigger(schedule="0 */5 * * * *", arg_name="timer", run_on_startup=False)` with a durable client, inside the failure boundary of ADR 0144) calls `ensure_dispatcher`, then `get_status("docchat-ingestion-dispatcher", show_history=False, show_input=False)`. From the custom status it emits the gauges `docchat.ingestion.dispatcher.heartbeat_age` (seconds, now minus `lastSweepAt`), `docchat.ingestion.items.queued` (`priority` `interactive` and `bulk`), `docchat.ingestion.items.running` and `docchat.ingestion.queue.oldest_age` (seconds), skipping null values. When the runtime status is `Running`, `configValid` isn't false, and `lastSweepAt` is older than 10 minutes while `outstanding` is true or older than 75 minutes otherwise (the longest idle wake plus 15 minutes), it calls `terminate(instance, "watchdog")`, polls `get_status` every 2 seconds for at most 60 seconds until `Terminated`, starts a new instance and emits `ingestion_dispatcher_restarted` (`oldGeneration`, `reason` `heartbeat_stale`). An absent custom status or a null `lastSweepAt` counts as outstanding, with `last_updated_time` in place of `lastSweepAt`. A failed tick is logged and retried at the next tick. The keep-alive never opens a SQL connection. Every sweep still writes the heartbeat row of `app.ingestion_dispatcher_state`, which only the sweep and `docchat-ops ingestion status` read.
4. **Idle SQL connections and resume.** Both apps reach SQL only through the data-access layer of ADR 0026. Pool `checkout` and `checkin` events record the last activity time; a background task in the API lifespan and in each ingestion worker process checks every 60 seconds and, when no connection is checked out and none was used for `DOCCHAT_SQL_IDLE_RELEASE_MINUTES` (app setting, integer, default 10, range 1 to 60), runs `engine.dispose()` in the SQL thread pool, closing every pooled connection, and increments `docchat.sql.idle_releases` (dimension `service`). Error 40613 is retried under its own budget: at most 12 attempts, each delay capped at 10 seconds, 90 seconds in all, after which the unit of work raises `SqlUnavailable`. The API runs no periodic SQL query: its ops-config snapshot refreshes on the first access after it is 60 seconds old, never on a timer (ADR 0028), and `GET /healthz` reads no data (ADR 0023), so App Service's health check never reaches SQL.
5. **The `dev` database.** `GP_S_Gen5_2` (General Purpose serverless, at most 2 vCores, `minCapacity` 0.5) with `autoPauseDelay` 15 minutes, from the environment-file field `sql.autoPauseDelayMinutes` (`-1` or 15 to 10,080; `dev` 15; `prod` and `load` -1, where the database is the provisioned `GP_Gen5_2`). Fifteen minutes is the service minimum and the only delay that pauses between hourly wakes: the connections close 10 to 11 minutes after a wake's last statement and the pause starts 15 minutes after that, so an idle `dev` database is online about 25 minutes of each hour. Its only scheduled SQL traffic is the dispatcher's wakes and the daily 02:40 UTC `ingestion_maintenance`.

## Alternatives considered

- **Auto-pause off in `dev`.** `autoPauseDelay: -1`, with `dev`'s cost stated at minimum vCores: no resume latency and no cadence rule to protect. Rejected by the product owner, because `dev` is idle most hours and a paused database bills only storage.
- **A 60-second timer at all times.** The database sees a session and CPU every minute and never pauses, so auto-pause would have no effect.
- **A watchdog that reads a SQL heartbeat row.** One query every 5 minutes keeps `dev` awake; the custom status carries the same facts without SQL.
- **No idle timer, relying on queue messages and the keep-alive.** A lost message or an operator's run would wait indefinitely, the sweep's duties (expired leases, stale uploads, orphaned versions, run finalisation, the poison gauge, scanner canaries) would stop while nothing is queued, and the watchdog would have no heartbeat to judge.
- **A longer idle wake, such as 6 hours.** Durable timers allow it, but a lost message could then wait hours; 60 minutes bounds that delay and still leaves the database paused about 35 minutes of each idle hour.
- **The service's default pause delay of 60 minutes.** It is never reached between hourly wakes.
- **Pool settings in place of an idle release.** `pool_recycle` acts only at checkout, so an idle pool keeps its sessions open. A pool that holds no idle connection would pay a TDS 8.0 login and a token for every unit of work, and each sweep runs many short transactions. One idle release serves both apps and keeps pooling under load.

## Consequences

- `dev` compute is billed for about 25 minutes of each idle hour. The first statement after a pause waits for the resume, usually under a minute; a resume beyond the 90-second budget surfaces as `SqlUnavailable` (`503 dependency_unavailable` on an API request, a retryable activity result in ingestion).
- The delays are bounded and documented: a lost message's run, or an operator's run, starts within 60 minutes when the system is idle and within 60 seconds while it is busy. Versions awaiting a scan count as outstanding work, so scan results are polled every 60 seconds.
- `ingestion.idle_wake_minutes` may be lowered to 5 in `prod` and `load`, which never pause. In `dev` the database pauses only while the idle wake exceeds the idle release plus 16 minutes (26 minutes with the defaults), so `dev` keeps 60; a `DOCCHAT_SQL_IDLE_RELEASE_MINUTES` above 2,640 (44 minutes) stops the pause at a 60-minute wake.
- The watchdog's 10-minute limit assumes a sweep ends well inside its 300-second deadline; raising `ingestion.active_wake_seconds` towards 300 narrows that margin. A terminated dispatcher's running sub-orchestrations finish on their own (termination doesn't propagate), and the next instance's claim counts them from SQL, so the slot limit holds.
- Idle wakes add orchestration history; continue-as-new after 60 wakes (ADR 0035) makes an idle generation last about 60 hours.
- Obligation: neither app may add a periodic SQL query (a timer, a background refresher, a health check that reads SQL); code review and the stage-1 acceptance check it. Monitoring reads the keep-alive's gauges: alert A18 `ingestion-dispatcher-stale` (heartbeat age above 900 seconds while items are queued) and A17 `ingestion-queue-age` (oldest queued item above 1,800 seconds), both with runbook R18.
- Tests: a dispatcher replay harness proves a 60-second timer while busy and a 60-minute timer when idle; 7 simulated days keep every generation's history under 1,000 events; a dispatcher crash with a running item ends with a restarted dispatcher and the slot limit intact; the keep-alive restarts an instance whose `lastSweepAt` is 11 minutes old with work outstanding or 76 minutes old without, leaves one with `configValid` false running, and makes no data-access call; every custom status field is checked, identical on replay; an invalid ops-config area keeps the last valid snapshot; error 40613 is retried within its 12-attempt, 90-second budget. The stage-1 acceptance leaves `dev` idle for 2 hours and requires at most one wake an hour, no SQL from the keep-alive, `docchat.sql.idle_releases` rising in both apps, and `az sql db show --resource-group rg-docchat-dev --server <server> --name docchat --query status -o tsv` returning `Paused`.
