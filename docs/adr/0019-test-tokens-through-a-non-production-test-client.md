# ADR 0019: Test tokens through a non-production test client

- **Status:** Accepted
- **Date:** 2026-10-18; amended 2026-10-30 (the test vault read from standard GitHub-hosted runners through a transient runner rule by default, private networking optional, ADR 0122)
- **Decided by:** Product owner and architect
- **Specified in:** 84-testing.md, 82-security.md, 81-config.md, 83-infrastructure.md, 86-operations.md
- **Related ADRs:** 0016, 0017, 0092, 0119, 0120, 0122, 0126, 0131, 0134, 0139

## Context

DocChat's deployed smoke, full and load suites gate every release, and each needs to call the API as real users with real roles, issued by the real Entra ID tenant, with no person at the keyboard. The load test runs in a short-lived `load` environment with production SKUs, and registrations never cross environments, so every non-production environment (`dev` and each `load` run) needs its own test client. Production must refuse that client in every layer, so no password-only path into production data can exist.

ROPC is the only non-interactive way Microsoft documents for automated tests to sign in as a user. It needs each test user's password and fails for users who must do MFA, so the test users need an MFA exclusion, and their passwords become the product's only stored secrets. The product owner chose cloud-only test users in the main tenant, with a Conditional Access MFA exclusion scoped to those users and the test client, over a separate test tenant, so non-production environments run against the same tenant, consent rules and policies as production. The passwords must live in a non-production Key Vault readable only by the CI test identity, rotate every 30 days through an operator script, and never exist in any environment's own vault.

Vendor facts that bound the choice (Microsoft Learn and the MSAL for Python source, confirmed 2026-10-14):

- ROPC: `POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` with `grant_type=password`, `client_id`, `scope`, `username`, `password`; the tenant can't be `common` or `consumers`; public clients must not send `client_secret`; a refresh token comes only with `offline_access`, an ID token only with `openid`. It fails for MFA-required, federated, passwordless and personal accounts and for passwords with leading or trailing whitespace. Microsoft recommends against ROPC, and rigs that rely on it will be locked out as MFA spreads.
- Microsoft's integration-test guidance: a separate test tenant; test user names and passwords as Key Vault secrets; a dedicated test app registration with public client flows on; pre-consented permissions; test users and the test app excluded from MFA Conditional Access. Avoid the production tenant for automated sign-in tests when its policies require interaction.
- msal 1.39.0: `PublicClientApplication.acquire_token_by_username_password` raises a DeprecationWarning ("deprecated for public client flows and will be removed in a future release").
- Security defaults require MFA for all users and allow no exclusions; Conditional Access, needed for a scoped MFA exclusion, requires Entra ID P1, as does group-based app assignment, which ignores nested groups.
- `tid` and `oid` need the `profile` scope; access tokens live a random 60 to 90 minutes. Error codes: `AADSTS50126` (bad user name or password), `AADSTS50076` and `AADSTS50079` (MFA required or registration required), `AADSTS53003` (blocked by Conditional Access), `AADSTS50105` (not assigned), `AADSTS65001` and `AADSTS90094` (consent missing).
- Key Vault Secrets User (`4633458b-17de-408a-b874-0445c86b69e6`) grants `getSecret` and `readMetadata`, in the RBAC permission model only.

## Decision

1. **Where the test client exists and is accepted.** In `dev` and in every `load` run, never in `prod`; its registration (ADR 0016 item 7) has public client flows on, no redirect URI, Microsoft Graph `openid` and `profile` only, pre-authorization on the API for `access_as_user`, a tenant-wide grant for `openid profile`, and assignment required. Three gates accept it only there: (a) the pipeline sets `DOCCHAT_AUTH_TEST_CLIENT_ID` to its `appId` only in `dev` and `load`, empty in `prod`; (b) platform authentication lists it in `allowedApplications` only in `dev` and `load`; (c) in-app validation adds it to the allowed `azp` set only when that setting is not empty and `DOCCHAT_CORE_ENVIRONMENT` is `dev`, `load` or `local` (ADR 0017). Settings validation stops the API before it serves when `DOCCHAT_CORE_ENVIRONMENT` is `prod` and `DOCCHAT_AUTH_TEST_CLIENT_ID` is not empty, when the API, web and test client IDs aren't distinct, and when `local` runs with `WEBSITE_SITE_NAME` or `WEBSITE_INSTANCE_ID` set.
2. **Token method: ROPC over `httpx`.** `POST https://login.microsoftonline.com/<tenantId>/oauth2/v2.0/token` with form fields `grant_type=password`, `client_id=<test client appId>`, `scope=<API scope string> openid profile`, `username=<name>@<initial domain>` and `password`; no client secret and no `offline_access`, so no refresh token is issued; timeout 15 s, 2 retries on connection errors and `5xx`, none on `4xx`. The helper is `httpx`, never MSAL for Python. Each token is cached in memory for the test session and re-acquired with the in-memory password within 5 minutes of `exp`. Before any test runs, each token's claims are decoded without signature checking and compared with its alias's expectations (`aud` = the API client ID, `scp` contains `access_as_user`, `roles` as assigned); a mismatch fails the run. Every token is masked with `::add-mask::` before any other output, and `docchat-load tokens` writes only tokens, never passwords, to its output file. Errors map to the runbook that resolves them:

   | Entra answer | The token step reports |
   |---|---|
   | `AADSTS50126` | password mismatch: run R08 |
   | `AADSTS50076` or `AADSTS50079` | MFA demanded: the Conditional Access exclusion is missing (R13) |
   | `AADSTS53003` | blocked by Conditional Access: the run's API or test client is missing from the block policy's exclusions (R11) |
   | `AADSTS50105` | user not assigned to the application (R13) |
   | `AADSTS65001` or `AADSTS90094` | admin consent missing for the test client (R13) |

3. **Test users and groups.** Cloud-only users in the main tenant, user principal names `<name>@<initial domain>` (the domain in the variable `DOCCHAT_TEST_USER_DOMAIN` of the GitHub environments `dev-tests` and `load-tests`), all in the administrative unit `DocChat test users`, which holds nothing else; a tenant administrator creates them once per tenant (runbook R13 part (a)):

   | Set | Users | Group | API assignment |
   |---|---|---|---|
   | `dev` | `docchat-test-admin` | `sg-docchat-dev-test-admins` | `Admin` |
   | `dev` | `docchat-test-member`, `docchat-test-outsider` | `sg-docchat-dev-test-users` | `User` |
   | `dev` | `docchat-test-norole` | `sg-docchat-dev-test-norole` | default access, no app role, so its tokens carry no `roles` |
   | `load` | `docchat-load-01` to `docchat-load-20` | `sg-docchat-load-test-users` | `User` |
   | `load` | `docchat-load-admin` | `sg-docchat-load-test-admins` | `Admin` |

   Aliases: `admin`, `member`, `outsider`, `norole`; `load-01` to `load-20`, `load-admin`. The post-provision script (ADR 0016 item 9) assigns the groups, and every test group also to its environment's web client and test client with default access, because assignment is required on all three registrations: the `dev` groups once (R13 part (b)), the `load` groups to each run's new registrations at its access gate. It requires the three `dev` test-group flags in `dev` and the two `load` ones in `load`, and refuses every test flag in `prod`. When Graph refuses the no-role group's default-access assignment on the API (HTTP 400, because the API declares app roles), the script exits 2 after every other step; a repository administrator sets the `dev-tests` variable `DOCCHAT_TEST_NOROLE_SKIP_REASON` to `graph_default_access_refused`, the deployed `norole` check reports skipped with that reason, and the unit and integration tests of `403 role_not_assigned` remain its proof.
4. **Conditional Access (Entra ID P1).** Once per tenant, after `dev`'s first post-provision step (R13 part (c)): every policy that requires MFA for all users excludes the five test groups (`conditions.users.excludeGroups`), and the policy `DocChat test users: non-production APIs only` (`state: enabled`) includes the five groups with `includeApplications: ["All"]`, `excludeApplications` = the `dev` API and `dev` test-client application IDs, `clientAppTypes: ["all"]` and the grant control `block`. Each `load` run's API and test client join `excludeApplications` at the run's access gate (R11 step 5) and leave it after teardown (R11 step 11). The MFA waiver therefore yields tokens only for non-production APIs, and no test user can sign in to a web client; browser tests use a stub identity provider (ADR 0092).
5. **Passwords and the vault.** Each password is 32 characters from `secrets.choice` over letters, digits and `!#%+-.:=?@_~`, so it never has the whitespace ROPC refuses. The passwords live only in the shared non-production test vault `kv-docchat-tst-<sharedToken>` in `rg-docchat-shared` (RBAC mode, purge protection, selected networks with the shared operator allowlist and no trusted-service bypass; while that allowlist is empty, by default no standing rule, and under the private-networking option public network access disabled; ADR 0122), as `test-user-<alias>` with `contentType` `text/plain`, `exp` = write time + 30 days and the tag `docchat-test-user=<alias>`, never a user principal name in metadata. Reader: only `id-docchat-citest` (Key Vault Secrets User), whose federated credentials trust only `dev-tests` and `load-tests`: by default from standard GitHub-hosted runners, each only inside its job's read window, a transient runner rule for its own address that the identity adds and removes through DocChat Test Vault Firewall Editor (ADR 0119); under the private-networking option only from jobs on the runner group `docchat-ci-private`, through the vault's private endpoint (ADR 0122). Writers: `sg-docchat-operators` through DocChat Test Secret Writer, which sets values and reads metadata but never reads a value. Every environment's own Key Vault, `prod`'s included, holds no test credential. The token step fails with `test_vault_unreachable` when the vault can't be reached, when its `open` fails, or when a read is answered `403 ForbiddenByFirewall` twice, and with `test_credentials_expired` after a secret's `exp`; a job never falls back from one path to the other.
6. **Rotation every 30 days.** Every 30 days, and at once after a suspected exposure, an operator in `sg-docchat-operators` who holds Password Administrator scoped to the administrative unit runs, from a machine in the shared operator allowlist, `uv run docchat-ops --env dev testusers rotate --set all --ticket <id> --reason "30-day test password rotation"` (runbook R08). For each alias it sets a new password through Graph (`PATCH https://graph.microsoft.com/v1.0/users/{upn}` with `passwordProfile {password, forceChangePasswordNextSignIn: false}`), writes the secret with a new `exp`, and proves an ROPC sign-in for each `dev` user; a failure stops the run and names the user, leaving the others on their previous passwords. It exits 2 with `load_run_in_progress` and changes nothing while `rg-docchat-load` carries a `docchat-load-run` tag. `nightly.yaml`'s `test-credential-expiry` job runs `testusers check --set all` as `id-docchat-citest` on the test runner of item 7 (by default inside a read window) and raises a warning annotation when a secret expires within 7 days.
7. **One identity per job.** Every job that reads the vault or holds test tokens runs in `dev-tests` or `load-tests` as `id-docchat-citest`, with `runs-on: ${{ vars.DOCCHAT_CI_PRIVATE_NETWORKING == 'true' && fromJSON('{"group":"docchat-ci-private"}') || 'ubuntu-24.04' }}` (a standard GitHub-hosted runner by default, the runner group `docchat-ci-private` under the private-networking option; ADR 0122) and `permissions {contents: read, id-token: write}`, and signs in as no other identity; every step that needs a deploy identity runs in its own `dev` or `load` job and passes on only non-secret outputs (base URLs, client IDs, the API scope, resource names, run IDs, timestamps). No job holding `id-token: write` runs `npm ci`. `prod_smoke` runs with no GitHub environment and no `id-token`, because `prod` has no test client and its checks need no token.
8. **Load runs.** The `load` set's 20 `User` accounts and one admin, with the run's ops-config values `ratelimit.max_concurrent_streams` 200, `ratelimit.chat_requests_per_minute` 1,200, `quota.tokens_per_day` 1,000,000,000 and `quota.tokens_per_month` 100,000,000,000, keep per-user limits from throttling the 100-stream scenario. Before approving the `load-access` gate (required reviewers `docchat-tenant-admins`), the reviewer runs the post-provision script for the run, adds the run's applications to the block policy's exclusions and runs `testusers check --set load --min-hours 24`; when a password stays valid for less than 24 hours, the reviewer rejects the gate, the run tears down, the `load` set is rotated (R08 with `--set load`) and a new run starts. Teardown permanently deletes the run's registrations (ADRs 0016, 0126).
9. **Tests of this decision.** Unit: the test client's `azp` passes in `dev` and `load` (and `local`) when its setting is present and fails with `bad_client` when it is empty; settings validation fails in `prod` with the setting present and when two client IDs are equal. Workflow unit test: every job that reads `DOCCHAT_CI_TEST_CLIENT_ID` runs in `dev-tests` or `load-tests` with the `runs-on` expression of item 7 and ends with the always-run `firewall.py close --target vault` step, every job that signs in names one GitHub environment and one client-ID variable, and the `prod-smoke` and `web-deployed` jobs have no environment and no `id-token`. Rotation unit test: `testusers rotate` exits 3 and writes nothing on a Graph `403`, exits 5 naming the alias when a `dev` user's ROPC still fails after 3 attempts, and exits 2 with `load_run_in_progress`. Deployed smoke: `outsider` gets `404 project_not_found` on the test project, `norole` `403 role_not_assigned`, `member` `403 admin_required` on an admin route and `admin` `isAdmin: true`; `prod` answers an anonymous call with `401` and its `authsettingsV2` allows exactly the web client. Stage-0 acceptance, on the configured path: by default a `dev-tests` job on a standard runner reads one secret only inside its read window and is refused before and after it; under the private-networking option a `dev-tests` job on `docchat-ci-private` reads one secret through the private endpoint, and the same read from a runner outside the group fails with `test_vault_unreachable`.

## Alternatives considered

- **A separate test tenant, as Microsoft recommends for ROPC.** Non-production environments would run against another tenant than `prod`, so the registrations, assignment, consent and Conditional Access that `prod` depends on would be exercised differently, and a second tenant needs its own administration.
- **A test client in `dev` only.** The load test runs in its own short-lived environment and registrations never cross environments, so it couldn't get a token.
- **App-only tokens (client credentials) for tests.** They carry no `scp`, no user `oid` and no user roles; the API accepts only delegated tokens for `access_as_user` (ADR 0017), and an app-only path in production code would be a second way in.
- **Tokens minted with a test key that deployed APIs trust.** A deployed API would accept a signer other than Entra ID; minted tokens stay in in-process tests, where a static `SigningKeyProvider` serves the test key.
- **Device code or interactive sign-in.** Both need a person at every run, and security defaults block device code flow.
- **MSAL for Python's username-password method.** Deprecated for public clients in msal 1.39.0; the token request is one documented POST.
- **Passwords as GitHub Actions secrets.** The repository holds no Actions secrets (ADR 0120), and any workflow job could read them; a vault with one reader identity, which only the test jobs can sign in as, keeps them to those jobs.
- **A confidential test client with a secret or certificate.** It adds a credential to a registration, which ADR 0016 never does, and ROPC with a confidential client still needs each user's password.
- **A test client in `prod`.** It would open a password-only path into production data, and `prod`'s checks need no token.
- **Reading the vault only from inside a network** (this ADR's rule until 2026-10-30). Kept as the private-networking option of ADR 0122, not the default: it needs larger runners, which only paid GitHub plans offer, so by default a per-job runner rule opens the vault for one read window.

## Consequences

- The 25 test passwords are the product's only stored secrets, in one non-production vault; `prod` has no test client, no test users and no secret.
- A compromised test job reaches the test passwords and the `load` resource group's operator rights, never a deploy identity; a leaked password yields tokens only for non-production APIs, and the incident runbook (R07) rotates it at once through R08.
- ROPC is a protocol Microsoft recommends against. A tenant change that demands MFA from the test groups, adds a blocking policy or turns on security defaults stops the deployed and load suites with a mapped error (`AADSTS50076`, `AADSTS53003`) before any test runs. The tenant must hold Entra ID P1 and keep security defaults off.
- Every load run waits for a tenant administrator to assign the run's registrations, edit the block policy and check password validity (R11 steps 3 to 7).
- Tokens live 60 to 90 minutes and no refresh token exists, so a long run re-acquires tokens with the in-memory password.
- Obligations: rotation every 30 days (R08) and the nightly expiry warning; runbooks R11 and R13; the workflow, rotation and settings unit tests; the deployed smoke checks; the stage-0 acceptance check of the vault path.
