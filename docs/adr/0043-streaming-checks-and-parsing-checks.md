# ADR 0043: Streaming checks and parsing checks

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Architect
- **Specified in:** 11-api.md, 14-ingestion.md, 81-config.md, 82-security.md, 84-testing.md
- **Related ADRs:** 0038, 0042, 0047, 0048, 0049, 0093, 0145, 0152

## Context

Admins upload PDF, DOCX and PPTX files only. A file of any other type, or one whose bytes don't match its extension, must be refused before it is stored, and the per-file size limit must hold while the file streams. DOCX and PPTX files are ZIP containers, so their entry count and uncompressed size must be capped before anything expands them, encrypted files must be refused, and a file must be the type its name says, so that the converter of ADR 0152 only ever opens a Word document or a PowerPoint presentation. Documents are written by other people and parsed by large libraries, so parsing runs only in the ingestion app, inside a process with its own time and memory limits, never in the API, whose identity reaches conversations, memory and every search index. Every refusal must reach the admin as a named reason: an upper-case extension such as `Q3.PDF` from a scanner must be accepted like `q3.pdf`, and a file that can't be processed must show why, so no upload silently goes unindexed.

What the API can check without parsing is what passes through it in order: the declared length, the running byte count, the first bytes and a running hash. Everything structural needs the whole file. Vendor facts:

- A ZIP archive holds its local file headers and file data first and its central directory, with every entry's sizes and flags, at the end; the local file header signature is `0x04034b50`, the bytes `50 4B 03 04`; general-purpose bit 0 marks an encrypted entry.
- An encrypted Office Open XML document is stored as a single stream inside an OLE compound file, so it doesn't begin with a ZIP local file header.
- Document Intelligence's layout model refuses password-locked PDFs and analyses at most 2,000 pages.
- Defender for Storage scans every file type, ZIP archives included.

## Decision

1. **Two places, nothing in between.** The API checks names, sizes, the signature and the SHA-256 before any byte becomes a blob, and never runs a document parser. The ingestion app checks structure inside the parsing child process (command `inspect`, at the start of Extract, for every method) before any parse. Malware scanning, when enabled, sits between the two (ADR 0038).
2. **Names and types, at preflight and reserve.** `normalize_document_name` applies Unicode NFC, trims, collapses whitespace runs and casefolds; the name must be 1 to 255 characters after trimming, end in `.pdf`, `.docx` or `.pptx` matched case-insensitively, and contain no `/` or `\` and no code point of Unicode category Cc, Cf, Co, Cs or Cn as Python 3.13's `unicodedata` reports it. A failing name is `422 invalid_file_name` (reasons `invalid_characters`, `too_short`, `too_long`; preflight `rejected` with `invalid_name`); a wrong extension is `422 unsupported_type` (reason `invalid_format`; preflight `rejected` with `unsupported_type`). The version's media type comes from the extension, `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document` or `application/vnd.openxmlformats-officedocument.presentationml.presentation`, and a `CHECK` constraint on `document_versions.content_type` admits only those three.
3. **Sizes.** Zero bytes is `422 empty_file` (preflight `empty_file`); a reservation above `DOCCHAT_UPLOAD_MAX_BYTES` (default 52,428,800) is `422 validation_failed` at `body.sizeBytes` with reason `out_of_range` (preflight `too_large`). At upload, `Content-Length` must be present (`411 content_length_required`), at most the limit (`413 file_too_large`) and equal to the reserved size (`422 size_mismatch`); the running count stops the stream when it passes the declared length, and a final count that differs is `422 size_mismatch` (ADR 0042).
4. **Signature, on the first block, before anything is staged.** PDF: the bytes `%PDF-` within the first 1,024 bytes. DOCX and PPTX: the bytes `50 4B 03 04` at offset 0, which also refuses encrypted Office files (OLE compound files) and binary Word and PowerPoint files renamed to `.docx` or `.pptx`. A mismatch is `422 file_signature_mismatch` with `errors` `[{path: "body", reason: "invalid_format"}]`.
5. **Integrity.** The SHA-256 recomputed over every byte must equal the reserved hash (`422 hash_mismatch`). A file failing any API check is never committed as a blob (ADR 0042).
6. **Preflight shows refusals before upload.** Each file gets, in this order of precedence, `rejected` (reason `unsupported_type`, `too_large`, `empty_file`, `invalid_name`, or `duplicate_in_batch` when an earlier file of the same request has the same normalised name or SHA-256), `unchanged`, `duplicate`, `update` or `new`. Preflight is advisory and read-only; reserve and commit enforce the same rules atomically.
7. **Parser checks, in the child process.** Extract first checks the downloaded source's SHA-256 against the version's (`source_changed`). The `inspect` child runs as one of the unprivileged parse users (`docchat-parse-0` to `docchat-parse-15`, UIDs 10002 to 10017, never shared with a concurrent child) with no capabilities and a system-call filter that refuses sockets, under a resident-memory limit of `DOCCHAT_INGESTION_PARSE_MEMORY_LIMIT_MB` (default 2,048) summed over every process of its UID and a 120-second wall clock (ADR 0049), and checks in order, comparing part names and content types case-insensitively. For a DOCX or PPTX these checks guard the converter: they refuse a file that isn't the type its name says, that would exhaust the child before the conversion starts, or that the converter would be asked to decrypt, and leave every other construct to the converter's sandbox and settings, because no reader ever receives the Office file (ADR 0152):
   - the signature again (`file_signature_mismatch`);
   - DOCX and PPTX, from the central directory read with `zipfile`, never extracting to disk: more than 10,000 entries is `zip_entry_limit_exceeded`; declared uncompressed sizes summing to more than 536,870,912 bytes (512 MiB), or any entry above 10 MiB uncompressed that declares a compression ratio above 200 to 1, is `zip_size_limit_exceeded`; any entry with general-purpose bit 0 set is `encrypted_document`; an unreadable archive or XML part, or two entries whose names are equal case-insensitively, is `corrupt_document`; a content type in `[Content_Types].xml` that contains `macroEnabled` or equals `application/vnd.ms-office.vbaProject`, or an entry name ending in `vbaProject.bin`, is `macro_content_declared`, so a file whose content types declare macros is refused whatever the converter's settings;
   - the Office type: the package's main part, the target of the `_rels/.rels` relationship whose `Type` ends in `/officeDocument`, missing, or with a content type other than the main content type of the version's media type, is `file_signature_mismatch`, so a template, a slide show or a file of the other type under a `.docx` or `.pptx` name is refused;
   - XML parts are read as streams with `lxml.etree.iterparse(..., resolve_entities=False, no_network=True, huge_tree=False)`, inside the ZIP caps and the child's limits, so no entity is expanded and nothing is fetched;
   - PDF, for a PDF source and for every converted PDF: `pikepdf.open()` with no password; a required password is `encrypted_document`; a PDF with only an owner password (permission flags, empty user password) opens and is accepted; any other open failure is `corrupt_document`;
   - a page count of the PDF, the converted PDF of a DOCX or PPTX included, above `ingestion.max_pages_per_document` (default 2,000) is `page_limit_exceeded`.
8. **Outcome of a parser refusal.** Every code above is non-retryable: the item fails with that code and the catalogue's safe message, a new version becomes `failed` with `failure_code`, the run continues (one failed document never fails its run) and ends `completed_with_errors` or `failed`, and the Documents and Ingestion runs screens show the message. Declared ZIP sizes can lie, so the child's memory and time limits (`parse_memory_exceeded`, `parse_timeout`) are the backstop.

## Alternatives considered

- **Inspect the ZIP structure, macros and PDF password in the API before commit.** Rejected: parsing stays out of the API, whose identity reaches conversations, memory and every search index; and the central directory sits at the end of the archive, so the API would have to buffer the file or read it back from storage.
- **Extension only.** Rejected: a renamed file of another type would be stored and handed to the parsers.
- **Full type detection with libmagic in the API.** Rejected: libmagic parses many formats from untrusted bytes inside the API. The two signature tests answer the one question the API needs before storage, whether the bytes look like the declared type, and the child process answers the rest.
- **Every check in ingestion only.** Rejected: wrong-type bytes would reach storage, the scanner and the ledger before failing, and the admin would learn of it only from the run.
- **Refuse PDFs that carry an owner password.** Rejected: they open without a password, and both Document Intelligence and the page-wise parser read them; refusing them would refuse common documents for no gain.
- **Other ZIP caps.** 10,000 entries keeps a 2,000-slide deck accepted; 512 MiB is about ten times the largest upload expanded; the ratio rule above 10 MiB catches single-entry bombs that stay inside the total. Tighter caps would refuse real decks; looser ones lean harder on the memory limit.

## Consequences

- Wrong-type, oversize and altered files never become blobs, every refusal before storage has a code the upload panel shows per file, and the API never runs a document parser.
- Structural refusals (ZIP caps, encryption, an Office main part of another type, a PDF password, the page count, a failed conversion) arrive only after upload and scan, as item failures on the Documents and Ingestion runs screens, not at preflight.
- The `%PDF-` window accepts a file that carries bytes before its header; whether such a file is a usable PDF is decided by `pikepdf` and the parser in the child process.
- Defender scans the stored file, ZIP members included, so a DOCX or PPTX archive is scanned whole even though the API reads only its first bytes.
- Obligations: each API check and each parser check is a testable statement in 82-security.md. Tests (84-testing.md): the name rules, including every Cc, Cf, Co, Cs and Cn case; upper-case extensions (`Q3.PDF`, `Notes.DocX`) accepted with the media types of `.pdf` and `.docx`; `many-entries.pptx`, `bomb.docx`, an encrypted entry and `encrypted.pdf` failing with their codes and `macro.docm-as.docx` with `file_signature_mismatch`, while `owner-only.pdf`, a hyperlink-only DOCX and the DOCX and PPTX fixtures with a remote template, a DDE field, a linked image or an embedded package pass `inspect` and meet the converter; preflight statuses in order; a wrong signature stopping before any block is staged, and size and hash mismatches committing nothing.
