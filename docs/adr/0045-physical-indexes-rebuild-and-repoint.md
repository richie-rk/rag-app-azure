# ADR 0045: Physical indexes, rebuild and repoint

- **Status:** Accepted
- **Date:** 2026-10-18
- **Decided by:** Product owner and architect
- **Specified in:** 14-ingestion.md, 80-data-model.md, 11-api.md, 12-chat-pipeline.md, 81-config.md, 83-infrastructure.md, 84-testing.md, 85-observability.md, 86-operations.md
- **Related ADRs:** 0020, 0022, 0034, 0041, 0044, 0046, 0052, 0054, 0061, 0100, 0113

## Context

The product owner decided that the ingestion method belongs to the index, comes from a growing catalogue and can be swapped, and that the product supports the re-ingest a swap needs. A logical index (what projects map and admins edit) is therefore served by physical indexes (the Azure AI Search indexes behind it). Each physical index records its generated name, schema version, embedding model, dimensions and its own query and ingestion embedding deployments, in state `building`, `active`, `retiring` or `deleted`; a logical index has one active physical index plus at most one being built, and repointing changes only which one is active.

A method or parameter change marks the index `reingest_required` and shows admins a banner; the re-ingest an admin then starts queues every current version at bulk priority. With the same embedding model, dimensions and schema it builds new chunk sets in the same physical index. Anything else needs every chunk built again in a new physical index while the active one keeps serving, because chat must never lose its index mid-change. The repoint, a single SQL update of the active pointer, runs only when every live document's current version is served in the building index, and the old physical index is deleted no sooner than 10 minutes after the repoint, so readers holding a cached index record (cached in process for at most 60 seconds) and in-flight queries finish safely. Names must never come from admin text: two names that normalise alike would make two projects share one index and read each other's documents, and a character the service refuses would fail every upload. The ingestion app owns index lifecycle, creating physical indexes and deleting retired ones through its queue and dispatcher.

Vendor facts:

- An index name has 2 to 128 characters of lowercase letters, digits, `-` and `_`, starts with a letter or digit and has no consecutive dashes or underscores. Basic holds at most 15 indexes and S1 50; index creation and deletion are each throttled at 12 per minute per search unit.
- A field's analyzer can be assigned only when the field is created, and changing a field's name, type or attributes needs a rebuild; a new embedding model or dimension count needs every vector computed again in any case.
- Index aliases are GA in data-plane API 2026-04-01; an alias update can take up to 10 seconds to propagate, and an index that an alias maps can't be deleted.

## Decision

1. **Generated names.** `physical_index_name(search_index_id, generation)` = `docchat-` + the logical index ID's 32 lowercase hexadecimal digits (hyphens removed) + `-g` + the generation in decimal, so generation 2 of index `3f2c0d9e-8b7a-41c6-a5d4-e3f2c1b0a998` is `docchat-3f2c0d9e8b7a41c6a5d4e3f2c1b0a998-g2`. Generation starts at 1 per logical index and increases by 1 for each new physical index (`UX_physical_indexes_generation` unique on (`search_index_id`, `generation`); `UX_physical_indexes_name` unique on `name`). Before any call the name is checked against `^docchat-[0-9a-f]{32}-g[1-9][0-9]{0,4}$` and the service rules (at most 47 characters here); a mismatch fails the activity as a programming error. No admin text ever enters a name, and the API never returns it: `PhysicalIndexSummary` carries `generation`, `schemaVersion`, `embeddingModel`, `embeddingDimensions`, `languageAnalyzer`, `state`, `createdAt` and `activatedAt`.
2. **The record.** One `app.physical_indexes` row per Azure index, with `schema_version`, `embedding_model`, `embedding_model_version`, `embedding_dimensions` (256, 1,024 or 3,072), `embedding_encoding` (`cl100k_base`), `embedding_max_input_tokens` (8,192), `language_analyzer`, `query_embedding_deployment`, `ingestion_embedding_deployment`, `state` (`building`, `active`, `retiring`, `deleted`), `build_run_id` (the `index_create` or `index_rebuild` run filling it, cleared when it leaves `building`), `provisioned_at`, `activated_at`, `retiring_at`, `delete_after` and `deleted_at`. The model, version, dimensions, encoding, input limit and both deployment names are copied from the embedding catalogue `DOCCHAT_OPENAI_EMBEDDING_MODELS` when the row is created, so a later setting change never alters an existing index. Filtered unique indexes `UX_physical_indexes_one_active` and `UX_physical_indexes_one_building` on (`search_index_id`) allow one `active` and one `building` physical index per logical index.
3. **Create.** `adminCreateIndex` inserts, in one transaction, the logical index (`provisioning`), physical index generation 1 (`building`, `build_run_id` set) and an `index_create` run (priority 0) with one `create_physical_index` item, after the capacity check: the non-deleted physical indexes on the service plus 1 must not exceed `DOCCHAT_SEARCH_MAX_INDEXES` − 1 (default 15 on Basic and 50 on S1, from the SKU; allowed 2 to 200), keeping one slot free for a rebuild, else `409 search_index_capacity`. The item's activity `create_search_index` (deadline 300 seconds) calls `build_chunk_index` (ADR 0044) and `SearchIndexClient.create_index()`; on `ResourceExistsError` it reads the index with `get_index(name)` and compares field names, types, dimensions and analyzers with the built definition (equal: continue; different: non-retryable `index_schema_conflict`). Then one transaction sets `provisioned_at` and, holding the logical index row's update lock, when `active_physical_index_id` is null, sets the pointer, the status `ready` and the physical index `active` with `activated_at`. `429` or `503` is retryable `search_unavailable`; `400` is `index_create_failed`; an index-count quota error is `search_index_capacity`; a failed generation 1 leaves the logical index `failed`.
4. **Same index or a new one.** `adminStartReingest` (`If-Match` with the index's `rowVersion`; status `ready`, `reingest_required` or `failed`, else `409 index_busy`) builds into a new physical index when the logical index has no active physical index, or when the active one's embedding model, dimensions, language analyzer or schema version differs from the logical index's settings and `CHUNK_INDEX_SCHEMA_VERSION`; otherwise it creates an `index_reingest` run (priority 1) with one `ingest` item per live document's current version into the active physical index, and the status becomes `reingesting`. The analyzer is the fourth trigger because a field's analyzer is set for its lifetime at creation.
5. **Rebuild.** One transaction holding the logical index row's update lock: the capacity check (room for one more physical index on the service, non-deleted physical indexes plus 1 at most `DOCCHAT_SEARCH_MAX_INDEXES`, the slot rule 3 keeps free; `409 search_index_capacity` otherwise); a new physical index (`building`, generation + 1, the deployments of its model from the catalogue); an `index_rebuild` run (priority 1) with its `create_physical_index` item first and one `ingest` item per live document's current version; status `rebuilding`; audit `index.reingest_started` (`runId`, `mode`, `itemCount`). For a `failed` index, its never-provisioned leftover physical index first becomes `retiring` with `delete_after` = now and its queued items move to the new one. The answer is `202 {index, runId, mode: "same_index" | "new_physical_index", itemCount}`. New versions reach the building index through the active-index Flip (ADR 0041).
6. **Repoint condition.** No live document (not deleted, `current_version_id` not null) lacks a `served_chunk_sets` row in the building index for its current version. The dispatcher's sweep counts it for each logical index in `rebuilding` whose building physical index is provisioned.
7. **Repoint.** One transaction under the logical index row's update lock, counting the condition again: the single `UPDATE app.search_indexes SET active_physical_index_id = @new ... WHERE id = @index AND active_physical_index_id = @old`; the new physical index becomes `active` with `activated_at`; the old one becomes `retiring` with `delete_after` = now + 10 minutes; `queued` `ingest` items targeting the old index are re-targeted to the new one, or cancelled when a duplicate exists; a `delete_physical_index` item with `not_before` = `delete_after` is added to the rebuild run, and only then is the new index's `build_run_id` cleared. Event `index_repointed` (`indexId`, `oldPhysicalIndexId`, `newPhysicalIndexId`, `generation`).
8. **Retire and delete.** The delete item's activity `delete_search_index` (deadline 300 seconds) runs no sooner than 10 minutes after the repoint: `SearchIndexClient.delete_index(name)` (`ResourceNotFoundError` counts as done), then one transaction deletes the old index's `served_chunk_sets` rows, which stay until now so readers holding a cached record still filter correctly, marks its chunk sets `retired` with `chunks_deleted_at`, and the physical index `deleted`; event `physical_index_deleted`. The sweep gives any `retiring` physical index 15 minutes past `delete_after` with no delete item one in a `maintenance` run. The rebuild run finalises once that item is done, and its finalisation sets the status from `compute_index_status`.
9. **Readers.** Chat resolves the active physical index through the authorisation module's index-record cache: at most 256 entries for at most 60 seconds, holding only records that have an active physical index, read again on every request for a logical index without one. The record carries the physical index's `id`, `name`, `schema_version`, `embedding_model`, `embedding_dimensions` and `query_embedding_deployment`. A logical index in `reingest_required`, `reingesting` or `rebuilding` serves from its active physical index, and `listMyProjects` reports `hasDefaultIndex: true` only while the default mapping's logical index has one. The 10-minute delay exceeds the 60-second cache ten times over.
10. **Statuses.** `search_indexes.status` is `provisioning`, `ready`, `reingest_required`, `reingesting`, `rebuilding`, `failed`, `deleting` or `deleted`. `compute_index_status` returns `reingest_required` when the active physical index's embedding model, dimensions, analyzer or schema version differs from the logical index's settings, or any live document's served chunk set in the active index has another method key, method version or parameter hash; otherwise `ready`. Mappable statuses (`adminMapProjectIndex`): `provisioning`, `ready`, `reingest_required`, `reingesting`, `rebuilding`; `failed` and `deleting` get `409 index_not_mappable`, and a `deleted` index `404 index_not_found`.
11. **Abandon.** Only an operator abandons a building index: `docchat-ops ingestion abandon-rebuild --index-id <uuid>` (just-in-time `config` level) moves it to `retiring` with `delete_after` = now, cancels its queued items, adds a delete item in a `maintenance` run, recomputes the status and writes `ingestion.rebuild_abandoned`. A failed create of a rebuild's physical index leaves the logical index `rebuilding`, with the failure on the run, until an operator abandons it.
12. **Deployments.** A physical index keeps the deployment names it was built with. Embedding deployments use `versionUpgradeOption: NoAutoUpgrade`, so a model change happens only through a new physical index; a deployment is never renamed or deleted while a physical index uses it; `docchat-ops ingestion set-deployments --physical-index-id <uuid> --query <name> --ingestion <name>` moves an index to new deployments of the same model and version (refused with exit 2 otherwise; audit `ingestion.deployments_changed`), and a different model or version goes through a rebuild.
13. **Rights.** Only the ingestion identity manages indexes, with the custom role "DocChat Search Index Manager" (actions `Microsoft.Search/searchServices/indexes/read`, `write` and `delete`) and Search Index Data Contributor (`8ebe5a00-799e-43f5-93ac-243d3dce84a7`), both at the search service, because names are generated; the API identity holds only Search Index Data Reader (`1407120a-92aa-4202-b7e9-c0e197c71c8f`).

## Alternatives considered

- **Change the live index in place.** Rejected: the service refuses changes to a field's analyzer, type or attributes, and a new model or dimension count needs every vector computed again; readers would see missing or mixed results throughout.
- **A search index alias as the active pointer.** Rejected: readers need the physical index's record anyway (schema version, dimensions, query embedding deployment) to embed the query and build the request, and an alias moves outside the SQL transaction, taking up to 10 seconds to propagate, so a reader could embed a query for one index and send it to another; the served-chunk-set filter is keyed by physical index ID; and an aliased index can't be deleted until the alias moves. The SQL pointer is one update in the same transaction that checks the repoint condition.
- **Delete and recreate under the same name.** Rejected: chat would fail from the delete until every document was ingested again.
- **Names derived from display names.** Rejected: names that normalise alike collide, characters the service refuses fail index creation, and a rename would mean a new index.
- **Random names without a generation.** Rejected: a name that carries the logical index ID and generation lets an operator match a service index to its SQL rows from the portal alone, and the generation gives each logical index's builds a strict order.
- **Delete the old index at the repoint.** Rejected: readers holding a cached record (up to 60 seconds) and in-flight queries would hit a deleted index.
- **Keep the old index for rollback.** Rejected: it doubles the index count against Basic's 15, and a rebuild can always be repeated.

## Consequences

- A rebuild holds two physical indexes for its logical index until the delete item runs, so the create check keeps one slot free and operators check capacity first (Basic 15, S1 50); `dev` on Basic fits about 7 logical indexes at one active and one building physical index each.
- A rebuild re-processes every live document at bulk priority, so it takes hours on a large index and bills Document Intelligence pages and summary and embedding tokens again; an operator may raise `ingestion.max_parallel_items` for it after checking the ingestion deployments' quota (re-index runbook, 86-operations.md).
- Readers never see a gap: the active index serves until the repoint and the new one after it, and nothing they may hold names a deleted index.
- A failed rebuild item holds the repoint back until an admin re-ingests the document or an operator abandons the rebuild (ADR 0041; stuck-run runbook, 86-operations.md); `adminGetIndex` shows `activePhysicalIndex`, `buildingPhysicalIndex` and `rebuildProgress` (`servedCurrent`, `liveDocuments`).
- Index creation and deletion are throttled at 12 per minute per search unit; throttling is retried as `search_unavailable`.
- Tests (84-testing.md): the name pattern, the 47-character bound and refusal of generation 0; the repoint as one pointer update, queued items re-targeted or cancelled, a delete item 10 minutes later and the old index's served rows kept until it runs; `compute_index_status` after a method change and after every served set matches; an update during a rebuild; `If-Match` on `adminStartReingest`; the capacity check; `hasDefaultIndex` turning true in the transaction that makes the first physical index active.
- Runbooks (86-operations.md): re-index an index, stuck rebuilds and abandon-rebuild, embedding deployment names, and search capacity.
